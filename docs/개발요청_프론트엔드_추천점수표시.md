## 한 줄 요약

**부품 카드의 "점수"는 지금 예산 비중이다. 추천 적합도(100점)를 따로 보여 주고, 정상 추천이 아닌 구성과 조합 여유를 화면에 드러낸다.** 값은 모두 서버가 계산해 보낸다. 화면이 다시 계산하거나 반올림하지 않는다.

## 1. 부품 카드에 추천 적합도 표시

**지금:** [`itemFromWire()`](../web/src/api/http/mapping.ts:177)의 `score`는 `예산의 N%`(`budget_share × 100`)다. 추천 적합도가 아니다. 사용자는 이 문구를 점수로 읽기 쉽다.

**요청:**
- `budget_share`는 지금 문구 그대로 두고, 추천 적합도를 **별도 항목**으로 추가한다. 예: `추천 적합도 66.5점`.
- 값은 `items[].fit.score`(0~100, 소수 첫째 자리)를 그대로 쓴다. 100을 다시 곱하거나 다시 반올림하지 않는다.
- `items[].fit`의 모양:

```json
{"status": "scored", "score": 66.5,
 "axes": [{"axis": "가격", "points": 80.0, "weight": 0.45, "weighted_points": 36.0}],
 "method_version": "pc-fit-v2", "reason": null}
```

| `fit.status` | 뜻 | 화면 |
|---|---|---|
| `scored` | 점수가 있다 | `score`점 표시 |
| `legacy_method` | 옛 방식으로 만든 추천이다(`score` 없음) | "이전 방식으로 만든 추천이라 적합도 점수는 제공하지 않아요". 100점으로 바꿔 보여 주지 않는다 |
| `unavailable` | 새 방식인데 점수 근거가 없다(`reason` 코드 참고) | "적합도 점수를 표시할 수 없어요". 사용자가 교체한 부품이 추천 당시 후보 풀에 없을 때(`candidate_not_in_snapshot`)도 여기에 해당 |

`reason` 코드: `snapshot_missing`, `candidate_not_in_snapshot`, `invalid_snapshot`, `snapshot_identity_mismatch`. 화면에는 위 문구 하나면 충분하고, 코드는 로그·문의용이다.

**알아 둘 것:** 사용자가 교체한 부품도 추천 당시 후보 풀에 있으면 `scored`로 온다(교체 후에도 같은 기준으로 비교된다).

## 2. 축별 점수·기여분·가중치

- `fit.axes[]`는 가격·성능·리뷰 순서다. 각 항목: `points`(그 축의 100점 점수), `weight`(가중치 0~1), `weighted_points`(`100 × 가중치 × 축 점수`, 이 축이 추천 점수에 더한 점수).
- 예: 가격 `points 80.0`, `weight 0.45`, `weighted_points 36.0`. 세 축의 `weighted_points` 합이 `fit.score`이다(표시 반올림으로 0.1~0.2 차이가 날 수 있다).
- **`explanation.contribution`과 다른 값이다.** `contribution`은 구성 전체에서 각 축이 차지하는 비율(합 100%, 정수)이고, `weighted_points`는 부품 하나의 점수 기여분이다. 같은 이름·같은 자리에 섞어 표시하지 않는다. 두 값 모두 그대로 제공되며 `contribution`은 바뀌지 않았다.
- 가중치는 사용자의 우선순위(성능·가성비·저소음)에 따라 요청마다 다르다. 화면에 고정 문구로 적지 않는다.

## 3. 견적 평균 적합도

- `totals.avg_fit_score`(0~100, 점수가 있는 선택 부품의 평균), `totals.avg_fit_score_count`(점수가 있는 부품 수), `totals.avg_fit_score_of`(선택된 부품 수).
- `avg_fit_score`가 `null`이면(옛 방식 run 또는 점수 근거 없음) 평균 칸을 숨긴다.
- `count < of`이면 "N개 부품 기준"처럼 평균의 기준 개수를 함께 보여 준다.
- 부품별 표시 점수를 화면에서 다시 평균하지 않는다(서버가 원본 값으로 평균한다. 표시 점수의 평균과 0.1 다를 수 있다).

## 4. 부적격(확인용 구성)과 후보 부족 화면

### 4-1. `eligibility`

결과에 `eligibility`가 추가됐다(없는 옛 추천은 `null`).

```json
{"status": "not_recommendable",
 "detail": "정상 추천 조건을 만족하는 구성을 찾지 못해 확인용 구성을 보여 드려요: ...",
 "reasons": [{"code": "required_info_missing", "axes": ["gpu_len"], "text": "호환 확인에 꼭 필요한 정보가 없어요 — ...",
              "missing": [{"slot": "케이스", "key": "max_gpu_length_mm", "side": "purchase", "name": "..."}]}],
 "enrichment": {"...": "보완 시도 기록"}}
```

- `status`: `recommendable`(정상) / `not_recommendable`(확인용 구성).
- **`not_recommendable`이면 정상 추천처럼 보이지 않게 한다.** 결과 위에 "정상 추천 조건을 만족하지 못한 확인용 구성"임을 알리는 영역을 둔다. 사유는 `reasons[].text`를 그대로 쓴다(서버가 만든 문장).
- `reasons[].code`: `compat_violation`(서로 맞지 않는 부품), `required_info_missing`(호환 확인에 꼭 필요한 정보 없음), `requirement_unmet`(요청 조건 미충족), `budget_exceeded`, `no_compatible_set`, `verification_inputs_missing`.
- `required_info_missing`의 `missing[]`: 어느 부품(`slot`, 구매 `side: purchase` / 쓰고 계신 부품 `side: owned`)의 어떤 정보(`key`)가 없는지다. `side: owned`가 있으면 "쓰고 계신 ○○의 모델명을 정확히 알려 주시면 확인할 수 있어요"와 같이 **유지 부품 정보를 보완하라는 안내**와 입력 경로를 보여 준다.
- `enrichment`는 서버가 빠진 정보를 채워 보려 한 기록이다. 사용자에게 필수로 보일 필요는 없고, "보완을 시도했지만 근거를 찾지 못했어요"처럼 요약해도 된다.
- **현재 상태의 기준은 `eligibility`다.** 부품을 교체·수량 변경하면 서버가 다시 판정해 `eligibility`를 갱신한다. 반면 `explanation.text`(추천 요약)의 앞 문장("확인용 구성을 보여 드려요")은 엔진이 처음 고른 구성 기준으로 저장되며, 교체로 정상 구성이 되어도 다시 쓰지 않는다. 요약과 `eligibility`가 다르면 `eligibility`를 우선한다.
- 요약 생성이 끝나기 전(`explanation.status: pending`)에도 `eligibility`는 와 있다.

### 4-2. 상태 API `candidates_insufficient`

후보가 부족하면 추천이 `failed`로 끝난다. `GET /session/{id}/result/status`와 `GET /session/{id}/result`의 `error`는 다음 모양이다(`slots`는 이번에 응답 스키마에 정식으로 포함됐다).

```json
{"status": "failed", "error": {"code": "candidates_insufficient", "message": "추천할 수 있는 후보가 부족해요...",
                              "slots": {"GPU": {"...": "슬롯별 사유·보완 시도"}}}}
```

- `error.code == "candidates_insufficient"`이면 일반 실패("오류가 발생했어요") 문구를 쓰지 않는다. `message`와 슬롯별 사유를 보여 주고, "조건(예산·브랜드·부품 지정)을 바꾸거나, 쓰고 계신 부품 모델명을 알려 주신 뒤 다시 시도해 주세요"로 **보완 후 재시도**를 안내한다.
- `recommend_failed`는 지금처럼 일반 실패 화면이다.

## 5. 조합 여유(`margins`)

결과에 `margins`가 추가됐다(없는 옛 추천은 `null`).

```json
{"version": 1, "detail": "...",
 "power": {"compat_check": {...}, "requirement_sizing": {...}, "total": {...}},
 "size": {"gpu_length": {...}, "cooler_height": {...}, "psu_length": {...}, "gpu_slots": {...}, "radiator": {...}, "not_evaluated": [...]},
 "cooling": {...}}
```

- 항목마다 `status`(`available` / `unavailable` / `not_applicable`), `unit`(`W`, `mm` 등), `value`, `formula`(계산식), `inputs[]`(입력 부품·값·출처·확인일), `missing[]`, `reason`, `note`가 있다.
- `available`: `value`와 `unit`을 보여 주고, 계산식(`formula`)과 입력 출처(`inputs[].source`)를 펼쳐 볼 수 있게 한다. 음수 값도 그대로 보여 준다(진단용 구성).
- `unavailable`: 값 대신 부족한 자료(`missing[]`의 슬롯·키)와 `reason`을 보여 준다. **적격성 사유와 섞지 않는다** — 여유 자료 부족은 추천 부적격이 아니다.
- `not_applicable`: 이번 견적에서 해당하지 않는 항목(예: 바꾸지 않는 부품끼리, 수랭에서의 쿨러 높이)이다. `reason`/`note`를 짧게 보여 주거나 숨긴다.
- 냉각(`cooling`): 자료가 없으면 "확인 불가"와 사유를 보여 준다. 수치가 오면 그대로 쓴다.
- **문구:** 여유는 점수나 통과 보장이 아니라 "계산에 쓴 값으로 본 여유"다. "여유가 있어요"처럼 단정하거나 점수·등급을 만들지 않는다. 예: "입력한 값 기준 약 ○○W 여유 (제조사 정격·카탈로그 값으로 계산, 실사용 부하와 다를 수 있어요)".
- 값은 서버가 저장한 기록 그대로다. 화면에서 다시 계산하지 않는다.

## 6. RAM 가격·수량 (3단계 변경 안내)

- `GET /alternatives` 응답에 `qty`가 생겼다. RAM의 `price`는 **이미 2개 구성 전체 가격**이다(키트 1개 또는 단품 2개를 산 총액). 화면에서 `price × qty`로 다시 곱하면 안 된다. `price_delta`도 같은 기준이다.
- 결과 `items[].price`는 **상품 단가**이고, 합계는 지금처럼 `price × qty`로 계산한다(이 부분은 바뀌지 않았다).
- RAM이 단품 2개이면 `qty`가 2다. 카드에 "×2"를 보여 주는지 확인한다.

## 7. 광고 표시

이번 범위가 아니다. 광고 가산점은 구현하지 않았고 관련 필드도 없다. 6단계 구현 때 별도 요청한다.

## 확인 방법

- 결과 응답에서 `items[].fit`, `totals.avg_fit_score*`, `eligibility`, `margins`를 확인한다. 이 필드가 없는 응답(옛 추천)에서도 화면이 깨지지 않아야 한다(`fit.status: legacy_method`, `eligibility: null`, `margins: null`).
- 부품 교체 후 `fit`이 교체한 부품 기준으로 바뀌는지, `eligibility`가 다시 판정된 값으로 바뀌는지 확인한다.
