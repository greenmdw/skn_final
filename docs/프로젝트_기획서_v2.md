## 1. 한 문장 정의

> **영업사원의 화면 우측 하단에 상주하면서, 회사 CRM을 대신 읽고 공급사 에이전트와 대신 협상해 "지금 이 고객에게 무엇을 약속해도 되는지"를 근거와 함께 알려주는 AI 동료.**

### 엘리베이터 피치

영업사원이 고객 앞에서 가장 자주 막히는 질문은 하나다. **"그거 몇 대까지, 언제까지 되나요?"**

지금은 이 질문에 답하려면 구매팀에 물어보고, 구매팀은 벤더에 견적을 요청하고, 벤더 회신을 기다린다. 며칠이 걸린다. 그 사이 고객은 경쟁사 견적을 받는다.

우리 시스템은 CRM 화면 우측 하단에 캐릭터로 상주한다. 영업사원이 견적을 만드는 순간 캐릭터가 **먼저** 말을 건다 — "이 건 5대인데, 지금 약속 가능한 건 3대입니다." 클릭하면 채팅창이 열리고, 부족한 2대의 조달 가능 여부를 물어볼 수 있다.

그러면 화면이 갈라지면서 옆에 **우리 대시보드 구역**이 열린다. 바이어 에이전트가 **공급사들의 셀러 에이전트와 실제로 협상하는 라운드**가 거기서 흐르고, 단가·납기 후보안이 순위표로 쌓인다. 영업사원은 왼쪽 CRM을 계속 보면서 오른쪽에서 확정 버튼을 누른다. 수일이 수십 초가 된다.

확정은 언제나 사람이 한다. 에이전트는 안(案)과 근거만 만든다.

### 왜 지금, 왜 에이전트인가

가격·수량·납기 매칭만이라면 규칙 엔진으로 충분하다. 에이전트가 필요한 이유는 **판단이 아니라 판단의 재료**에 있다.

1. **내부 상황을 스스로 파악해야 한다** — "약속 가능 수량"은 현재고 숫자가 아니다. 타 주문 예약분을 빼고 입고 예정을 더한 날짜별 계산이며, 지금은 담당자 개인의 경험에 의존한다.
2. **회사 경계를 넘어야 한다** — 상대 회사의 최저수용가는 우리가 볼 수 없다. 볼 수 없는 값을 두고 조건을 좁혀 나가는 일은 규칙 테이블로 표현되지 않는다.
3. **사람이 자연어로 물어본다** — 영업사원은 SQL을 쓰지 않는다. "작년에 이 회사한테 평균 몇 % 깎아줬지?"라고 묻는다.

## 2. 제품 컨셉 — 데스크톱 오버레이 영업 코파일럿

### 2.1 왜 오버레이인가

**기존 CRM을 교체하지 않는다. 그 위에 얹는다.**

B2B 영업 조직은 이미 CRM을 쓰고 있고, 그걸 바꾸는 일은 몇 달짜리 프로젝트다. 반면 우리가 주는 가치는 "기존 CRM의 데이터를 읽어서 더 나은 판단 재료를 만드는 것"이므로, CRM 자체를 대체할 이유가 없다.

**참고 레퍼런스 — [Mecus](https://maple-focus.web.app/).** Mecus는 화면 캡처 도구도, 창 정렬 도구도 아니다. **입력을 창별로 갈라주는 오버레이**다. 주 작업 창(게임)에 키보드 포커스를 유지한 채 옆 패널을 마우스로 다룰 수 있어서, alt-tab 없이 두 화면을 동시에 쓴다. 별도로 화면을 구역으로 나눠 보여주는 공유 존도 제공한다.

**우리가 가져오는 것은 이 구조다.** 주 작업 창은 고객사 CRM이고, 옆 구역은 우리 대시보드다. 영업사원은 CRM에서 손을 떼지 않은 채 옆 구역에서 영업 현황·재고·협상 진행을 본다.

**그래서 우리 제품은 화면에 두 개의 층으로 존재한다.**

| 층 | 무엇 | 언제 쓰나 |
|---|---|---|
| **① 상주 챗봇** (우측 하단) | 캐릭터 + 알림 + 채팅 | 짧게 묻고 짧게 답받을 때. "이거 몇 대까지 되지?" |
| **② 구역 대시보드** (측면 분할) | 영업 현황 · 재고 현황 · 협상 진행 · 영업 결과 보고서 · 액션 | 표와 숫자를 눈으로 훑고 결정을 내릴 때 |

**둘이 분리되어야 하는 이유.** 채팅은 한 번에 한 가지만 말한다. 후보 3안의 가격·납기·사양 유사도를 비교하거나, 이번 분기 영업 현황을 훑거나, 지난 협상 리포트를 다시 읽는 일은 **표와 화면**이 필요하다. 챗봇 말풍선에 표를 욱여넣으면 둘 다 못 쓰게 된다. 그래서 **대화는 챗봇이, 열람과 결정은 대시보드가** 맡는다.

이 선택이 만드는 네 가지 결과:

| | 효과 |
|---|---|
| **도입 비용** | CRM 마이그레이션 불필요. API 자격증명 발급만으로 시작 |
| **컨텍스트 스위칭 제거** | 영업사원이 CRM 화면을 떠나지 않는다. 지금은 CRM → 사내 메신저 → 구매팀 → 메일 → 다시 CRM |
| **동시 시야** | 우리 대시보드에서 확정한 결과가 **같은 화면 안의** CRM에 반영되는 것을 눈으로 확인한다. 두 시스템을 오가며 대조할 필요가 없다 |
| **확장성** | CRM 연동을 어댑터로 분리하면 Odoo 외 다른 CRM으로 갈아끼울 수 있다 (§5.4) |

### 2.2 상주 캐릭터 — 알림에서 채팅으로

화면 우측 하단에 **캐릭터가 항상 떠 있다**. 참고 레퍼런스는 Codex pets 계열의 데스크톱 상주 캐릭터다.

캐릭터는 단순 장식이 아니라 **에이전트의 상태 표시기**다.

- 평상시 — 조용히 대기
- 백그라운드 작업 중 — 움직임으로 "지금 뭔가 하고 있음"을 표시 (예: 협상 라운드 진행 중)
- 알릴 것이 생김 — 말풍선 토스트를 띄우고 시선을 끈다
- 클릭 — 채팅 패널이 위로 확장되어 대화 시작

**핵심은 캐릭터가 먼저 말을 건다는 것이다.** 사용자가 물어봐야만 답하는 챗봇이 아니다. 영업 현황에 변화가 생기면(견적 수량이 약속 가능 수량을 넘었다, 협상이 끝났다, 원가가 바뀌어 마진이 위험해졌다) 캐릭터 쪽에서 먼저 알린다. 이것이 "AI 동료"와 "검색창"의 차이다.

### 2.3 네 개의 표면

**평상시 — CRM 전체 화면 + 캐릭터만**

```
┌───────────────────────────────────────────────────┐
│  고객사 CRM (Odoo) — 우리가 한 줄도 수정하지 않음    │
│                                                   │
│                                                   │
│                          ┌──────────────────┐     │
│                          │ ② 토스트 알림     │     │
│                          └──────────────────┘     │
│                                          ┌───┐    │
│                                          │ ① │    │
│                                          └───┘    │
└───────────────────────────────────────────────────┘
```

**대시보드 호출 시 — 구역 분할**

```
┌───────────────────────────────┬───────────────────┐
│  고객사 CRM (Odoo)             │ ④ 구역 대시보드    │

│                               │  영업 현황         │
│  확정 결과가 여기 반영되는 것을 │  재고 · ATP        │
│  같은 화면에서 확인한다         │  협상 진행 (라운드) │
│                               │  후보 순위 · 확정   │
│                               │  영업 결과 보고서   │
```

| 표면 | 상태 | 담는 것 |
|---|---|---|
| **① 캐릭터** | 항상 표시 | 에이전트 상태(대기 / 작업중 / 알림있음). 클릭 시 ③ 열림 |
| **② 토스트 알림** | 이벤트 발생 시 | 한 줄 요약 + 배지. 클릭 시 맥락에 맞는 ③ 또는 ④가 열림 |
| **③ 채팅 패널** | 클릭 시 확장 | 자연어 질의응답, 계산 근거, 짧은 조회·조작. 표가 필요해지면 ④를 연다 |
| **④ 구역 대시보드** | 호출 시 화면 분할 | 표·차트·목록으로 보는 열람 화면과 실제 액션 (아래 §2.4) |

### 2.4 구역 대시보드의 뷰 구성

챗봇이 "말"이라면 대시보드는 "장부"다. 뷰는 다섯 가지다.

| 뷰 | 담는 것 | Phase |
|---|---|---|
| **협상 진행** | 라운드 실시간 스트림, 감사자 차단 표시, 후보 다속성 순위표, **확정 버튼** | **A** |
| **재고 · ATP 현황** | 품목별 현재고 / 예약 / 입고예정 / 약속 가능 수량, 계산 근거 전개 | **A** |
| **영업 현황** | 진행 중 기회·견적·수주 목록, 마진 상태, 납기 위험 표시 | B |
| **영업 결과 보고서** | 거래별 리포트 6섹션 열람 (§10.4), 기간별 집계 | B |
| **알림 센터** | 단가 이상(S6) · 마진 변동(S9) · 문서 불일치(S7) 등 처리 대기 목록 | B |

**액션은 대시보드에서 일어난다.** 협상 결과 확정, 승인 요청, 재견적 여부 결정 같은 "사람의 결정"은 전부 이 구역에서 클릭으로 이뤄진다. 챗봇은 결정을 대신 실행하지 않고 대시보드의 해당 뷰를 열어줄 뿐이다.

**CRM은 계속 살아 있다.** 대시보드가 열려 있는 동안에도 왼쪽 CRM은 조작 가능하다. Mecus의 입력 분리 아이디어가 여기에 해당한다 — 확정 버튼을 누른 직후 왼쪽 CRM에서 반영 결과를 확인하는 흐름이 **한 화면 안에서** 끝난다.

### 2.5 상호작용 원칙 — 에이전트는 안(案), 결정은 사람

이 원칙은 UI 문구가 아니라 **구조적 제약**이다.

1. **에이전트는 실행 권한이 아니라 제안 권한만 갖는다.** 외부 발송·지급·계약 확정에 해당하는 tool은 에이전트의 tool 목록에 **아예 넣지 않는다.** 오작동해도 대외 행위가 발생할 수 없다.
2. **모든 답변에 근거 레코드를 함께 표시한다.** "3대입니다"가 아니라 "현재고 8 − 타주문 예약 5 + 입고예정 0 = 3대"이며, 각 숫자는 클릭하면 원본 레코드로 간다.
3. **산출할 수 없는 질문에는 추정하지 않는다.** 데이터가 없으면 없다고 답한다.
4. **확정 시 확정자·확정 시각·제시된 근거를 함께 기록한다.** 사후 추적과 책임 소재 확인이 가능해야 한다.
5. **자동화의 목표는 승인 절차의 제거가 아니라 검토 시간의 단축이다.**

## 3. 문제 정의

### 3.1 배경

**① 조달 측면** — B2B 조달 현장에서 담당자가 매번 반복적으로 견적을 요청·비교·협상하는 데 상당한 시간을 쓴다.

**② 영업 측면** — 영업사원이 견적 단계에서 "이 물량을 실제로 조달할 수 있는가"를 확인하려면 구매팀을 경유해야 하고, 벤더 회신까지 수일이 걸린다. 그 사이 고객은 경쟁사 견적을 받는다.

**③ 재고 측면** — 대부분의 시스템이 현재고 숫자만 제공한다. 타 주문 예약분과 입고 예정을 반영한 **약속 가능 수량(ATP, Available-To-Promise)** 판단은 담당자 개인의 경험에 의존한다.

**④ 컨텍스트 스위칭 측면** — 위 ②③을 확인하는 과정에서 영업사원은 CRM을 떠나 다른 도구를 여러 번 오간다. 화면을 떠나는 순간 고객과의 대화 흐름도 끊긴다. *(v2에서 추가된 관점 — 오버레이 컨셉의 직접적 근거)*

**⑤ "왜 AI 에이전트인가"에 대한 답의 부재** — 기존 "AI 에이전트 마켓플레이스" 단독 컨셉은 이 질문에 답하기 어려웠다. 가격·수량·납기 조건 매칭은 단순 규칙/분류 문제로도 해결 가능하다는 내부 검토 결과가 있다.

### 3.2 재정의된 문제의식

- **판매와 조달의 분리가 근본 원인이다.** 영업이 만든 수요(수주)가 조달 소요로 이어지고 조달 결과(원가)가 다시 판매 마진으로 돌아오는데, 실무에서는 두 흐름이 서로 다른 부서·다른 시스템에 나뉘어 있다.
- **에이전트가 필요한 이유는 "협상 자체"가 아니라 "내부 상황을 스스로 파악해 무엇이 언제 필요한지 알아내는 것"에 있다.**
- **모든 거래에 매번 협상이 필요하지는 않다.** 표준 조건 범위 내 거래는 자동으로 안을 만들고, 대량주문·급납기 등 예외적 상황에서만 실제 협상이 발동한다.
- **자동화의 대상은 "판단의 재료를 모으고 정리하는 과정"이지 "판단 자체"가 아니다.** 계약·지급의 책임 소재를 명확히 유지하기 위해 확정 권한은 사람에게 남긴다.

### 3.3 핵심 컨셉 세 문장

> - "평소엔 자동, 예외적인 경우에만 진짜 협상이 필요해진다."

### 4.7 핵심 발견과 포지셔닝

1. **ERP·CRM 내장 AI는 모두 한 회사 내부의 데이터 범위에서 동작한다.** 회사 경계를 넘어 상대 기업의 에이전트와 협상하는 구조를 제품화한 사례는 확인되지 않았다.
2. **에이전트 간 거래 프로토콜은 형성되었으나 협상 로직은 비어 있다.** 규격 위에 올라가는 **판단 계층**이 본 프로젝트의 자리다.
3. **양측 자동화 사례가 없다.** Pactum은 구매측만, Arkestro는 예측만 담당한다. 셀러 측 에이전트가 자사 정책으로 대응하는 구조는 확인되지 않았다 — **본 프로젝트의 차별점.**

> **포지셔닝 한 문장**
> 본 프로젝트는 CRM/ERP를 대체하지 않는다. 내장 AI가 넘지 못하는 **회사 경계**에 협상 계층을 두고, 그 결과를 **영업사원이 보고 있는 화면**으로 되돌린다.

### 5.2 4노드 분산 구성

**왜 한 프로세스가 아니라 4대로 나누는가.** 이것이 이 프로젝트에서 가장 중요한 아키텍처 결정이다.

셀러의 최저수용가(`floor_price`)를 중앙 서버가 알고 있으면, 협상은 계산 한 번으로 끝난다. 양측 유보가격을 모두 아는 주체가 있으면 다회 라운드 협상은 **계산상 불필요**해진다. 즉 "에이전트 협상"이 연출이 되어버린다.

그래서 정보 비대칭을 **배포 구조로 강제**한다.

| 노드 | 포트 | 역할 | 아는 것 | 모르는 것 |
|---|---|---|---|---|
| **Buyer** (EC2 #1) | 8000 | 오버레이 백엔드, 어시스턴트 에이전트, Odoo 연동 | 자사 상한가·재고·고객 이력 | 셀러 최저수용가 |
| **Seller ×2** (EC2 #2·#3) | 8000 | 셀러 에이전트, 셀러측 감사자 | 자사 최저수용가·재고·정책 | 바이어 상한가, 타 셀러 조건 |
| **Broker** (EC2 #4) | 9000 | 라운드 오케스트레이션, 중앙 감사자 | 공개 정보 + 제출된 제안 | **양측 유보가격 모두** |

각 노드는 독립 컨테이너로 뜬다. 보안그룹 `SG-nego`가 VPC 내부의 8000·8069·9000만 상호 허용하고, PostgreSQL 5432는 열지 않는다. 배포·검증 절차는 [RUNBOOK.md](RUNBOOK.md)에 있다.

### 5.3 정보 경계 원칙

1. **셀러의 최저수용가·할인 정책·양보 규칙은 셀러 노드에만 보관한다.** 중앙 서버와 Odoo DB에 저장하지 않는다.
2. **중앙에는 공개 정보(정가·재고·사양·납기·MOQ)와 셀러가 제출한 제안 내용만 존재한다.**
3. **브로커는 `floor_price`를 애초에 수신하지 않는다.** 따라서 브로커 로그에 그 값이 남을 수 없다.
4. **바이어의 상한가(`cap_price`)는 셀러에게 전달되지 않는다.**

이 경계는 **주장이 아니라 검증 가능한 사실**이다. RUNBOOK §6-4에 검증 절차가 있다 — 브로커 로그를 `grep -i floor` 했을 때 **0건**이어야 통과하고, 같은 명령을 셀러 노드에서 실행하면 **나오는 것이 정상**이다. 발표에서 이 대조를 그대로 보여준다.

### 5.4 고객사 CRM 연동 계층

**Odoo는 고객사가 쓰던 시스템이다. 우리는 여기에 손대지 않는다.**

- **연동 방식** — Odoo 19의 **JSON-2 API**를 통한 조회 중심. 엔드포인트는 `POST {base}/json/2/{model}/{method}`, 인증은 `Authorization: bearer <API 키>`, DB 라우팅은 `X-Odoo-Database` 헤더 ([client.py](../app/integrations/odoo/client.py))
- **커스텀 모듈 없음** — Odoo 애드온을 설치하지 않고, Odoo 소스·화면을 수정하지 않는다
- **쓰기 최소화** — Phase A는 확정 이력 기록 1건만. 발주서 송부·대금 지급 같은 외부 행위는 시스템이 자동 실행하지 않는다 (§10.3)
- **어댑터 인터페이스** — 연동부를 `app/integrations/` 아래 어댑터로 격리한다. `get_partner` / `get_product` / `get_stock` / `get_sale_orders` 같은 인터페이스만 지키면 Salesforce·더존 등 다른 CRM 어댑터로 교체 가능하다. **"Odoo 전용"이 아니라 "Odoo가 첫 번째 어댑터"라는 것이 확장 서사의 핵심이다.**

Odoo 사용 앱은 CRM · 판매 · 재고관리 · 매입 4종이다(회계는 의존성으로 설치되나 사용하지 않음). 제조(MRP) 모듈은 쓰지 않고, 수주로부터 부품 소요를 산출하는 BOM 전개는 룰 테이블로 자체 구현한다.

## 6. 기술 스택

> 이 장은 v1(docx)에 없던 부분이다. AWS 해커톤 심사기준 *Technological Implementation*에 직결된다.

### 6.1 에이전트 런타임 — Strands Agents SDK

**무엇인가.** AWS가 사내 시스템에서 뽑아 오픈소스로 공개한 에이전트 프레임워크다. Python/TypeScript를 지원하며, `pip install strands-agents`로 설치한다.

**핵심 개념 세 가지.**

| 개념 | 내용 |
|---|---|
| **모델 주도 agent loop** | "어떤 tool을 언제 부를지"를 개발자가 분기문으로 짜지 않는다. 모델이 판단하고 SDK가 루프를 돌린다 |
| **`@tool` 데코레이터** | 파이썬 함수에 데코레이터만 붙이면 타입힌트에서 JSON 스키마가 자동 생성되어 tool이 된다 |
| **모델 추상화** | Bedrock을 포함해 여러 공급자를 같은 인터페이스로 다룬다 |

추가로 **Agent-as-Tool**(에이전트를 다른 에이전트의 tool로 노출), **Swarm**(다중 에이전트 협업) 패턴과 **MCP 클라이언트**를 내장하며, 모든 결정에 대한 트레이싱이 기본 제공된다.

**왜 채택하는가.**

1. **해커톤 필수 요건이다.** *Agents for Humans*는 Strands Agents SDK 사용을 1순위 요건으로 명시한다.
2. **우리 구조와 정확히 맞는다.** 우리는 "협상 엔진"을 이미 함수로 갖고 있다. 이것을 어시스턴트의 `@tool`로 노출하는 것이 Agent-as-Tool 패턴 그 자체다.
3. **권한 통제가 코드 구조로 표현된다.** §2.5의 "외부 행위 tool을 부여하지 않는다"는 원칙이 tool 목록에서 눈으로 확인 가능해진다.

**우리가 정의할 tool (Phase A).**

```python
from strands import Agent, tool

@tool
def get_available_to_promise(product_code: str, promise_date: str) -> dict:
    """현재고 − 타주문 예약분 + 입고예정으로 약속 가능 수량을 산출한다."""
    ...

@tool
def negotiate_procurement(item: str, qty: int, cap_price: int,
                          max_lead_time_days: int) -> dict:
    """부족 물량에 대해 셀러 에이전트들과 협상하고 후보안을 순위로 반환한다."""
    ...
```

### 6.2 모델 — Amazon Bedrock

**호출 경로.** Strands Agents SDK → Amazon Bedrock. Bedrock의 Claude 모델 ID는 `anthropic.` 접두사를 갖는다 (예: `anthropic.claude-opus-5`).

**모델 배치안.**

| 용도 | 모델 | 이유 |
|---|---|---|
| 영업 어시스턴트 (대화·tool 선택·근거 서술) | `anthropic.claude-opus-5` | 사람과 직접 대화하는 유일한 에이전트. 잘못된 tool 선택이 곧 오답 |
| 협상 발화·제안 근거 생성 | `anthropic.claude-sonnet-5` | 가격은 알고리즘이 정하고 모델은 서술만 담당 (§7.3) |
| 사양 태그 추출 · 분류 | `anthropic.claude-haiku-4-5` | 짧은 구조화 출력. 캐시로 반복 호출 제거 |

**비용 관리.** 해커톤 AWS 크레딧은 $50다. 세 가지로 제어한다.

1. **거래 1건당 LLM 호출 수 상한** — 협상 라운드 상한(`MAX_ROUNDS=3`)이 그대로 호출 상한이 된다
2. **사양 태그 추출 캐시** — 텍스트 해시 기준 캐시로 동일 입력의 반복 호출을 제거한다 ([spec_match.py](../app/spec_match.py)에 이미 구현)
3. **effort 조절** — 단순 분류 경로는 낮은 effort로 내린다

> 참고: 아래는 Anthropic 1st-party 기준 단가이며 **Bedrock은 별도 요금표**를 따른다 ([Bedrock pricing](https://aws.amazon.com/bedrock/pricing/)). 비율 감각용으로만 사용한다.
> Opus 5 $5 / $25 · Sonnet 5 $2 / $10 · Haiku 4.5 $1 / $5 (입력/출력, 1M 토큰당 USD)

**현재 상태 (정직한 표기).** 지금 코드는 **OpenAI 전용**이다([llm_agents.py](../app/llm_agents.py)). Strands·Bedrock 전환은 **Phase A의 1순위 필수 작업**이며 아직 착수 전이다. 다행히 [negotiate.py](../app/negotiate.py)가 `SellerAgentPort` / `BuyerAgentPort` 인터페이스로 구현체를 갈아끼우게 되어 있어, 전환 범위가 에이전트 구현체 파일로 한정된다.

### 6.3 AWS 인프라

| 구성 | 내용 |
|---|---|
| **컴퓨트** | EC2 4대 (Buyer / Seller1 / Seller2 / Broker). Broker는 Odoo가 없어 t2.micro로 충분 |
| **네트워크** | 단일 VPC. 보안그룹 `SG-nego`가 내부 8000·8069·9000 상호 허용. 5432(DB)는 미개방 |
| **OS** | 리눅스 통일 (환경 불일치 비용 제거) |
| **모델 접근** | Bedrock 모델 액세스 활성화 + EC2 인스턴스 역할에 `bedrock:InvokeModel` 부여 |
| **배포** | 각 EC2에서 `docker compose up -d`. 절차는 [RUNBOOK.md](RUNBOOK.md) |
| **Bedrock AgentCore** | **스트레치 목표.** 해커톤 규정상 필수는 아니나 기술 점수에 유리. 어시스턴트 에이전트 1종만 AgentCore Runtime에 올리는 것을 시간이 남을 때 시도 |

VPC 3개·게이트웨이 분리 구성은 도식용으로만 두고 구현하지 않는다. 구현분과 계획분은 발표 자료에서 색으로 구분한다.

### 6.4 백엔드 — Python 3.11 / FastAPI / Pydantic v2

**Python 3.11** (`requires-python = ">=3.11, <3.12"`) — Strands SDK·boto3 호환 범위 안에서 상한을 고정했다.

**FastAPI** — 선택 이유 세 가지:
- Pydantic 모델을 그대로 요청·응답 스키마로 쓴다. 검증 코드를 따로 쓰지 않는다
- OpenAPI 문서가 자동 생성되어 4개 노드 간 계약을 사람이 읽을 수 있다
- SSE(Server-Sent Events)로 협상 라운드를 오버레이에 실시간 스트리밍할 수 있다 (Phase A 데모의 2:00 구간)

**Pydantic v2** — 단순한 검증 도구가 아니라 **프로토콜 강제 장치**로 쓴다.

```python
class Envelope(BaseModel):
    """모든 노드 간 메시지는 반드시 이 형태로만 오간다. 확장은 payload 안에서만."""
    frm: str = Field(alias="from")
    to: str
    type: MsgType          # REQUEST · OFFER · ACCEPT · REJECT · SETTLED
    txid: str
    ts: str
    payload: dict[str, Any]
```

4개 노드가 프로세스를 넘어 통신하는데 메시지 형태가 제각각이면 로그를 하나로 합칠 수 없다. Envelope을 고정했기 때문에 **어느 노드에서 나온 메시지든 같은 리포트 파이프라인으로 들어간다.** ([schemas.py](../app/schemas.py))

### 6.5 영속 계층 — SQLAlchemy / SQLite → PostgreSQL

**이중 저장 구조.**

| 대상 | 저장소 | 이유 |
|---|---|---|
| 카탈로그·거래 상태 | SQLAlchemy ORM | 조회·집계가 필요한 구조화 데이터 |
| 협상 원문 로그 | 거래별 JSONL 파일 (`data/logs/{txid}.jsonl`) | append-only. 리포트는 **로그에서만 파생**되며 에이전트가 리포트를 직접 쓰지 않는다 |

두 번째가 감사 가능성의 핵심이다. 리포트를 에이전트가 쓰면 "에이전트가 자기 행동을 자기가 요약한 것"이 되어 신뢰할 수 없다. [report.py](../app/report.py)는 항상 append된 로그만 읽어서 요약을 만든다.

**DB 엔진 로드맵.**

- **Phase A (~9/14)** — **SQLite**. 노드별 독립 파일이라 배포가 단순하고, 데모 규모에서 성능 문제가 없다
- **Phase B (9/15~10/26)** — **PostgreSQL 전환**. 동시 쓰기, 다중 노드 공유 조회, Odoo와 동일 엔진 사용에 따른 운영 단순화가 이유다. Odoo 컨테이너가 이미 PostgreSQL 16을 쓰고 있어 인프라 추가 부담이 없다

**전환이 쉬운 이유.** `store.py`의 메서드 시그니처(`register_seller`, `sellers_for`, `append`, `get_log`, `set_deal`, `get_deal`)가 고정되어 있어, 저장 방식이 바뀌어도 이 파일 바깥은 건드리지 않는다.

> ⚠️ **개발 중 함정** — 스키마 필드를 추가하면 `create_all()`이 기존 테이블에 컬럼을 추가해주지 않는다. 현 단계에서는 `data/` 폴더를 삭제 후 재기동하는 것이 가장 간단한 대응이다. Phase B의 PostgreSQL 전환 시점에 마이그레이션 도구 도입을 함께 검토한다.

### 6.6 컨테이너 — Docker · docker-compose

**Dockerfile** — `python:3.11-slim` 기반. 의존성은 `pyproject.toml`의 느슨한 핀과 동일한 목록을 명시 설치한다(`requirements.txt`는 `uv export` 결과라 사설 인덱스 핀이 포함되어 공용 PyPI에서 재현되지 않기 때문).

**compose 2종** — 노드 역할이 다르므로 파일을 나눴다.

| 파일 | 대상 | 서비스 |
|---|---|---|
| `docker-compose.yml` | EC2 #1~#3 (Buyer/Seller) | `app` + `odoo`(19) + `db`(PostgreSQL 16) |
| `docker-compose.broker.yml` | EC2 #4 (Broker) | `broker` 단독. Odoo·DB 없음 |

**한 이미지, 여러 역할.** 같은 이미지를 `APP_MODULE` 환경변수로 다른 서비스로 띄운다.

```yaml
command: uvicorn ${APP_MODULE:-app.main:app} --host 0.0.0.0 --port 8000
#   Buyer  EC2 → APP_MODULE=app.buyer_service:app
#   Seller EC2 → APP_MODULE=app.seller_service:app
```

빌드 대상이 하나라서 4대에 배포해도 이미지 버전이 갈라지지 않는다.

> ⚠️ `.env` 값을 바꾼 뒤에는 재시작이 아니라 **컨테이너 재생성**이 필요하다 (`docker compose up -d --force-recreate app`).

### 6.7 오버레이 클라이언트

**Phase A 구현 방식 — 리버스 프록시 주입.**

Odoo는 `X-Frame-Options: SAMEORIGIN`을 보내므로 다른 오리진에서 iframe으로 감쌀 수 없다. 그래서 **nginx 리버스 프록시가 Odoo를 서빙하면서 오버레이 스크립트를 주입**한다.

```
브라우저 → nginx(단일 오리진) ─┬→ /            → Odoo 19 (HTML에 <script> 1줄 주입)
                              └→ /api/, /events → Buyer 노드 FastAPI
```

- 동일 오리진이라 CORS·프레임 정책 문제가 없다
- **"고객사 CRM 화면에 스크립트 한 줄로 얹힌다"**는 제품 서사가 구현과 일치한다
- Electron 없이 9일 안에 들어간다

**구역 분할을 어떻게 만드는가.** 주입된 스크립트가 Odoo의 `<body>`를 래퍼로 감싸고, 그 옆에 우리 대시보드 패널을 형제 요소로 붙인 뒤 CSS Grid로 좌우를 나눈다.

```
document
└─ #skn-split            (display: grid; grid-template-columns: 1fr 480px)
   ├─ #skn-crm-pane      ← Odoo가 원래 그리던 DOM 전체를 그대로 이동
   └─ #skn-dashboard     ← 우리 대시보드 (드래그로 폭 조절, 접기 가능)
```

Odoo의 DOM·JS·CSS는 손대지 않고 **위치만 옮긴다.** Odoo가 자기 컨테이너 폭에 맞춰 반응형으로 다시 그리므로 레이아웃이 깨지지 않는다.

> **Mecus는 입력 라우팅이 필요했지만 우리는 필요 없다.** Mecus는 OS 레벨에서 서로 다른 창(게임 / 브라우저)을 다루기 때문에 키보드·마우스를 갈라 보내야 했다. 우리 Phase A는 **두 구역이 같은 문서 안에 있으므로** 브라우저가 알아서 각 구역에 포커스를 준다. 왼쪽에서 타이핑하다 오른쪽을 클릭해도 alt-tab이 없다. 같은 사용자 경험을 훨씬 싸게 얻는다.

**기술 구성** — 의존성 없는 바닐라 JS + CSS. 캐릭터는 CSS 애니메이션(또는 경량 스프라이트), 서버 푸시는 **SSE**(`EventSource`)로 받는다. WebSocket이 아닌 이유는 단방향 푸시면 충분하고 FastAPI에서 구현·디버깅이 훨씬 간단하기 때문이다.

**폴백** — 프록시 주입이 막히면 우리 페이지가 좌우를 나누고 왼쪽에 CRM 화면(정적 캡처 또는 별창)을 두는 형태로 대체한다. 데모 영상은 촬영 가능하다.

**Phase B — Electron 승격.** 여기서부터 Mecus 구조가 그대로 필요해진다. CRM이 브라우저가 아니거나(설치형 ERP), 사용자가 CRM을 다른 모니터에 두고 싶을 때를 위해 **OS 레벨 구역 분할 + 입력 라우팅**을 구현한다. 대시보드 뷰 코드는 Phase A 것을 그대로 재사용하고, 껍데기만 바뀐다.

**기존 3화면 목업의 처지** — [static/index.html](../static/index.html)의 셀러등록/구매요청/승인 3화면은 **백오피스**로 남긴다. 셀러 카탈로그 등록에 계속 쓰이고, 승인·로그 열람 부분은 Phase B에서 대시보드의 「영업 결과 보고서」 뷰로 흡수한다. 영업사원의 주 동선에서는 빠진다.

### 7.3 LLM 사용 지점 — 6곳으로 한정

1. 비정형 텍스트(카탈로그·견적서·요청서) → 구조화 필드 파싱
2. 의미 기반 사양 매칭 — 표현이 다른 텍스트 간 실질적 동일성 판단
3. 매입 문서 3자 대조 — 서로 다른 양식에서 동일 항목 식별·불일치 설명 *(Phase B)*
4. 제안 근거 문장 생성 — 왜 이 조합이 상대에게 유리한지 자연어 설명
5. 영업 어시스턴트의 자연어 질의 해석 및 tool 호출
6. 협상 결과·검토 근거의 자연어 요약·리포트 생성

**가격 결정 원칙 — LLM에게 가격을 맡기지 않는다.**

가격은 검증 가능한 알고리즘(수식)이 전담한다. 이는 한계가 아니라 설계 결정이다. 감사자를 통해 **"최저수용가 위반이 구조적으로 불가능"**하게 만들기 위함이다. 산출된 가격 또한 확정이 아니라 담당자에게 제시되는 후보안이다.

### 7.4 협상 알고리즘

**기반** — Boulware/Conceder(1998) 시간 기반 양보 곡선. 단 **"시간 경과"를 "협상 라운드 비율"로 재해석**한다. 에이전트 간 협상은 응답 시간이 사실상 0에 가까워 심리적 시간 개념이 그대로 적용되지 않기 때문이다.

**재고 기반 E값(양보 속도 파라미터)** — 판매자의 영업 정책을 수치화한다.

| 재고 상황 | E값 | 행동 |
|---|---|---|
| 재고 적음(급함) | 빠른 양보 | 초반부터 크게 내림 |
| 재고 많음(여유) | 완만한 양보 | 후반까지 버팀 |

E값 입력은 Odoo 실재고와 회전율에서 산출한다.

**상대별 조정** — 거래처 이력(거래 횟수·누적 금액·결제 이력)에 따라 동일 조건에서도 제시안이 달라진다. 재고만 반영하면 재고 처분 로직에 그치고 영업 판단이 되지 못한다.

**다속성 제안** — 가격 단일 축이 아니라 가격·수량·납기·사양 조합으로 복수 안을 제시하고, 바이어가 사전 선택한 가중치(`priority`: `price_min` / `spec_max`)로 점수화하여 순위를 산출한다.

**산출물은 순위가 매겨진 후보안이며, 낙찰 확정은 사람이 수행한다.**

*고도화 방향(Phase C)* — 2025년 연구(MiCRO)의 "상대 반응에 적응하는 최소 양보" 개념 반영 검토.

### 7.5 감사자 — 2계층

| 계층 | 시점 | 검증 항목 | 위치 이유 |
|---|---|---|---|
| **셀러 측 감사자** | 발신 **전** | ① 재고·납기·MOQ·사양 위반 → `available: false` 로 **차단**<br>② 제안가가 자사 최저수용가 미만 → 최저수용가로 **보정** 후 발신 | 최저수용가가 셀러 노드에만 존재하므로 이 검증도 셀러 노드에서만 가능 |
| **중앙 감사자** | 수신 **후** | 공개 정보만으로 판정 가능한 항목 — 등록 재고 초과 수량 약속, 카탈로그에 없는 사양 주장, 스키마 위반 | 브로커는 유보가격을 모르므로 공개 정보 판정만 가능 |

**할루시네이션 대응이 여기서 나온다.** "재고 10대인데 100대 가능하다"는 응답은 LLM 안전장치가 아니라 **룰**로 걸린다. 재고·납기 초과 주장을 코드로 제외하는 것으로 충분하며, 데모에서 가장 잘 보이는 장면이기도 하다(§9 S8).

**감사 사실은 응답에 담지 않는다.** ②의 보정 여부는 셀러 노드의 로컬 로그(`audit_note`)에만 남고
`OfferResponse` 스키마에는 들어가지 않는다. "이 제안은 보정되었다"는 곧 "이 가격이 곧 최저수용가"라는
뜻이므로, 플래그 하나가 §5.3 정보 경계를 그대로 무너뜨리기 때문이다.

따라서 **바이어 화면에는 감사 보정이 표시되지 않는 것이 정상이다.** 데모에서는 셀러 로그와 브로커 로그를
나란히 놓는 **데모 전용 관측 창**으로 보여준다 — 우리가 양쪽 노드를 다 운영하기 때문에 가능한 것이며,
실제 고객 환경에서 바이어는 셀러 쪽 로그에 접근할 수 없다.

기성 가드레일 프레임워크(Guardrails AI / NeMo Guardrails / Llama Guard 3 / OpenAI Moderation) 중 1종을 중앙 감사자에 적용하는 것을 검토한다 *(Phase B)*.

**범위 밖 명시** — 거래 적법성 감시(담합·제재 대상 거래 등)는 이상탐지·KYC/AML 영역이므로 본 프로젝트 범위 밖이다. 거래 로그 보존과 사업자 인증 자리만 확보한다.

### 7.6 안전장치

| 장치 | 구현 |
|---|---|
| 무한 루프 방지 | 최대 라운드 수 제한 (`MAX_ROUNDS = 3`). 초과 시 `NO_DEAL`로 결렬 |
| 라운드별 재검증 | 매 라운드 감사자가 규칙 위반 여부를 다시 본다 |
| 비용 상한 | 거래 1건당 LLM 호출 수 상한 → 비용을 예측 가능한 범위로 관리 |
| 대외 행위 차단 | 외부 발송·지급 tool을 에이전트 목록에서 제외 (§7.2) |
| 실패 사유 분리 | `NO_MATCH`(조건 맞는 셀러 없음) vs `NO_DEAL`(협상 결렬) — 사람이 고쳐야 할 것이 다르므로 |

## 10. 의사결정 권한 · 승인 · 감사 기록

### 10.1 부서별 확정 권한

| 대상 | 확정자 |
|---|---|
| 견적 · 수주 | 영업 담당자 |
| 발주 · 매입 단가 | 구매 담당자 |
| 재고 조정 | 재고 담당자 |
| 금액·조건 한도 초과 건 | 승인권자 |

### 10.2 승인 2단계

| 단계 | 조건 | 절차 |
|---|---|---|
| **1단계 (간소 확인)** | 기준단가 대비 **+5% 이내**(인하 제한 없음) **AND** 요청 납기 대비 **+3일 이내** **AND** 발주 총액 **500만원 이하** | 담당자가 근거 요약을 확인하고 한 번의 조작으로 확정 |
| **2단계 (정식 승인)** | 위 조건을 하나라도 벗어남 | 초과 항목과 초과 폭을 함께 제시. 담당자 검토 후 승인권자 승인 |

**어느 단계에서도 사람의 확정 없이는 발주가 성립하지 않는다.**

**업무 절감 지표** — 전체 거래 중 1단계로 처리되는 비율과 건당 검토 소요 시간을 측정하여 정량화한다. *(수치는 도메인 확정 후 재조정)*

### 10.3 외부 행위 제한

시스템은 다음을 **자동 실행하지 않는다.**

- 발주서 송부
- 견적서 송부
- 대금 지급 · 결제

에이전트 간 협상 결과 역시 **합의안일 뿐**이며, 사람의 확정 이전에는 계약으로 성립하지 않는다.

### 10.4 감사 기록

모든 확정 건에 **확정자 · 확정 시각 · 제시된 근거**를 함께 기록한다. 리포트는 append-only 로그에서만 파생되며(§6.5), 에이전트가 리포트를 직접 작성하지 않는다.

리포트 6섹션: ① 거래 개요 ② 요청 조건 ③ 소집·응답 내역 ④ 비교·낙찰(선택 사유) ⑤ 승인 이력 ⑥ 타임라인

> 비식별화 — 리포트에 상대 업체명을 노출하지 않고 `벤더 A` 형식으로 표기한다.

## 11. 비즈니스 모델

### 11.1 과금 구조

- **구독형 기본 요금 + 거래 성사 수수료 병행** — 신규 매칭 2~3%, 재거래 0.5~1%
- **건당 수수료 상한선** — 대형 거래의 플랫폼 이탈(직접 컨택 우회) 유인을 구조적으로 완화
- **카탈로그·요청 등록은 무료** — 실제 거래 성사 시에만 과금

### 11.2 도입 소구점

**바이어(플랫폼 도입 기업)** — 별도 전문 인력 없이 **기존 CRM 화면 안에서** 동작한다. 중소기업의 최대 도입 장벽인 전문성 부족(OECD 33.3%, §4.6)을 정면으로 완화한다.

**셀러** — 표준 범위 거래는 영업 접촉 없이 반복 수주로 유입되고, 예외 거래에서는 자사 정책이 반영된 제안이 자동 생성된다.

### 11.3 대상 기업 정의

| 구분 | 정의 |
|---|---|
| **플랫폼 도입 기업(바이어)** | GPU 서버·워크스테이션 조립/SI 업체. GPU는 이들에게 자본재가 아니라 **원자재**이므로 반복 구매가 발생하고 표준 발주 경로가 성립한다 |
| **거래 상대(셀러)** | GPU 유통사·제조사. 자사 카탈로그와 협상 정책을 보유 |
| **바이어의 고객** | 데이터센터·연구기관·AI 스타트업 등. CRM에 기록되며, 조달 상대와는 서로 다른 집단 |

### 11.4 표준 호환 로드맵

향후 A2A·AP2 등 에이전트 간 거래 규격과의 호환을 확보하여 특정 플랫폼 종속을 피한다 (§4.4). 우리가 채우는 것은 그 규격 위의 **판단 계층**이다.

| **AgentCore** | Amazon Bedrock의 에이전트 실행 런타임. 스케일링·세션 관리를 대신 처리 |
