# 미사용 테이블 8개 — 삭제 전 팀 확인용 정리

- 목적: DB 정리 작업 중 발견한, 코드에서 전혀 쓰이지 않는 테이블 8개의 원래 의도와 현재 상태를 정리한다.
- 결론: 삭제 자체는(스키마 관점) 안전해 보이지만, 실제 삭제(새 마이그레이션)는 팀 확인 후 진행한다 — `db/setup_all.py` 베이스라인이 바뀌고 `tests/test_schema_reduction.py`의 `EXPECTED_TABLES`도 같이 고쳐야 한다.
- 확인 방법: 코드 전체(`src/`)에서 각 테이블명을 검색해 실제 쿼리하는 곳이 있는지 확인(0건), `history/db/table_spec.md`(팀이 이전에 작성한 전체 테이블 설계 문서)에서 원래 의도 확인.

## 그룹 1 — `community.pc_build` / `pc_build_version` / `pc_build_component` (3개)

### 원래 의도: "전체 PC 리뷰" 기능

부품 하나씩이 아니라 **사용자가 조립한 PC 전체를 하나의 지속적인 객체로 추적**하려던 설계.

| 테이블 | 역할 |
|---|---|
| `pc_build` | "이 사용자의 PC"라는 영속적 식별자 — 여러 번 부품을 교체해도 같은 PC로 추적(`owner_user_id`, `current_version_id`) |
| `pc_build_version` | 부품을 바꿀 때마다 새 버전 번호. "전체 PC 리뷰"를 게시(`published`)하면 그 시점 구성은 이후 불변 |
| `pc_build_component` | 리뷰 게시 시점에 장착돼 있던 부품들의 스냅샷(`component_snapshot`에 당시 브랜드·모델·규격 보존) — 나중에 부품을 또 바꿔도 리뷰 당시 구성은 안 바뀜 |

### 현재 상태: 팀이 이미 폐기를 결정했음(실행만 안 됨)

`src/repo/review_repo.py:3-4`에 이런 주석이 남아있다:

> "P0 v3: review/review_revision, pc_build/pc_build_version은 community.review 하나로 병합됐고(record_type 'review'|'build'), pc_build_component는 community.review_component로 이름이 바뀌었다."

확인해보니 이 병합은 **주석에만 있고 실제 스키마엔 반영되지 않았다** — `community.review`에 `record_type` 컬럼이 없고, `community.review_component` 테이블 자체가 존재하지 않는다(`db/migrations/*.sql` 전체 검색 결과 0건). 코드에서 `pc_build`류 테이블을 실제로 쿼리하는 곳도 없다.

**→ 팀이 예전에 "이 3개를 없애고 review 테이블에 통합한다"고 이미 결정했던 사안이라, 승인은 형식적일 가능성이 높다.**

## 그룹 2 — `catalog.product_fact` + `assets.file_object` / `product_material` / `material_revision` / `material_applicability` (5개)

### 원래 의도: "제조사 문서 근거 기반 검증" 파이프라인 (RAG-01 / ENG-06)

호환성 검사 결과에 "이 판단의 근거가 된 제조사 설명서 문구"를 인용해 붙이려던 설계. 하나의 파이프라인을 이룬다:

```
assets.file_object (원본 파일, S3 등 객체저장소 — DB엔 메타데이터만)
  ↓
assets.product_material (설명서·사양표라는 논리적 자료)
  ↓
assets.material_revision (그 자료의 버전 — 원본이 갱신돼도 과거 인용을 재현 가능하게)
  ↓
assets.material_applicability (이 문서가 어느 모델/옵션에 적용되는지)
  ↓
catalog.product_fact (문서에서 근거를 인용해 뽑아낸 호환성 스펙 값)
```

`product_fact`는 지금 실제로 쓰는 `product.attributes`/`variant.attributes`(단순 "표시용 캐시")보다 상위의, **검증에 실제로 쓰는 "근거 있는" 스펙 기준**으로 설계됐다(`history/db/table_spec.md` §20: "호환성·안전 검사에 쓰는 규격의 기준은 product_fact다").

### 현재 상태: 설계만 되고 실경로엔 끝내 연결 안 됨, 참조 대상도 이미 삭제됨

- 이 기능은 지난번 벡터DB 논의에서 확인했던 **바로 그 "검사 근거"(RAG-01/ENG-06) 기능**이다 — 호환성 검사 실경로(`stage3c_verify.verify_build`)에는 문서 RAG가 끝내 연결되지 않았고, 데모 경로(`verify_set`)에만 인메모리 코퍼스가 연결돼 있다.
- `assets.material_revision.active_ingestion_id`는 `rag.ingestion_job.id`를 참조하는데, **`rag` 스키마 자체가 나중에 통째로 삭제**됐다(`tests/test_schema_reduction.py`의 `REMOVED_SCHEMAS = ["rag", "dataset", "shared"]`). 즉 이 5개 테이블은 이미 존재하지 않는 상위 파이프라인을 참조하는, 구조적으로 고아가 된 상태다.
- 코드에서 이 5개 테이블을 실제로 쿼리하는 곳은 없다.
