- [ ] §1~§5를 읽는다 (30분). 특히 §3 원칙은 코드 리뷰 기준이다.
- [ ] 환경을 준비한다 (§14.1). Git에 없는 데이터 파일은 팀에서 받는다.
- [ ] 데모를 돌리고 로그를 §9의 해설과 나란히 읽는다.
  `MOCK_MODE=1 CATALOG_SOURCE=mock UV_CACHE_DIR=/tmp/uv-cache uv run python main.py computer_research`
- [ ] §15.2의 재현 스크립트로 **실경로와 같은 검증 함수**를 돌려 본다. 조건 값을 바꿔 가며 결과가 어떻게 달라지는지 본다.
- [ ] 빠른 테스트와 전체 테스트를 돌린다 (§14.3). 둘 다 통과하는 것을 확인한다.
- [ ] 연습 과제: 별도 작업 사본에서 `config/computer_verification_rules.yaml`의 `ranking.priority_weights.value`를 가격 0.50→0.45, 성능 0.15→0.20으로 바꾼다. 합은 1로 유지하며 점수·결과 차이와 테스트를 확인하고 연습 변경만 되돌린다. 실제 정책 변경은 §16.1을 따른다.
- [ ] §17 함정 모음과 §18 협업 규칙을 읽는다.
- [ ] §21의 7분 발표를 소리 내어 해 보고, “신뢰도 80은 무엇인가”, “전체 상품 중 최적인가”, “RAG는 어디에 쓰는가”에 문서를 보지 않고 답한다.

## 1. 30초 요약

Truefit 추천 엔진은 **대화로 모은 조건을 바탕으로 PC 부품 구성을 고르고, 선택 이유와 확인할 사항을 함께 제공하는 프로그램**이다. 새로 조립할 때는 8종을 하나씩, 업그레이드할 때는 교체할 종류만 고른다.

```
조건(용도·예산·우선순위…) ─[2]→ 슬롯별 요구사양 ─[3-A]→ 슬롯별 통과 후보
   ─[3-B]→ 슬롯별 점수·순위 ─[4]→ 후보 범위 안에서 세트 탐색 ─[3-C]→ 신뢰도·쟁점
   ─(신뢰도<80이면 후보 하나 빼고 [4]부터 다시, 최대 3라운드)─[5]→ 설명 문장
```

- **추천 본체의 선택·판정·점수는 규칙(코드)이 계산한다.** LLM(대규모 언어 모델)은 [3-C] 쟁점 문장과 [5] 설명 문장을 돕는다. 기본 API 경로의 [1] 조건 추출도 규칙 기반이다. 별도 선택 기능인 조건 대화 에이전트와 데모 경로는 §5.3에서 구분한다.
- 규칙의 숫자(요구 등급, 가중치, 호환 규칙 키)는 대부분 **YAML 설정**에 있다. 코드를 고치기 전에 설정을 먼저 본다.
- 요청 경로는 두 개다. **데모 경로**(`main.py` → `src/pipeline.py`, 시나리오 파일로 돈다)와 **실경로**(HTTP API → `src/services/recommendation_service.py`, DB 카탈로그로 돈다). 두 경로는 같은 단계 함수와 같은 재탐색 루프를 공유한다.
- 주변기기(모니터·키보드·마우스·스피커)는 **PC 세트와 분리된 부속 결과**로 따로 계산한다. 아직 API 응답에는 나가지 않는다(§12).

### 1.1 어떤 문제를 푸는가

사용자는 “150만원으로 QHD 게임용 PC를 맞추고 싶다”라고 말한다. 하지만 상품 목록만 보여 주면 다음 일을 사용자가 직접 해야 한다.

1. QHD 게임에 필요한 CPU·GPU·메모리 수준을 정한다.
2. 그 수준을 만족하는 상품들을 찾고 가격·우선순위로 비교한다.
3. 부품을 함께 골랐을 때 소켓·크기·전원이 맞는지, 총액이 예산 안인지 확인한다.
4. 데이터가 없어 확인하지 못한 부분과 구매 전 확인할 사항을 찾는다.

엔진은 이 과정을 단계로 나누어 수행한다. 예를 들어 가장 점수가 높은 GPU가 케이스보다 길면, GPU 또는 케이스를 바꾼 조합을 비교해야 한다. 따라서 핵심은 **좋은 상품의 나열이 아니라, 함께 사용할 부품의 조합을 찾는 것**이다.

현재 추천은 구매 이력으로 취향을 학습하는 협업 필터링이나 학습된 추천 모델이 아니다. 사용자가 이번 요청에 명시한 조건과 YAML 정책을 사용하는 **규칙 기반 추천 + 조합 탐색 + 문장 생성** 방식이다. 가중치도 코드·설정으로 정하며, 사용자 피드백을 받아 자동 학습하는 단계는 아직 없다.

### 1.2 처음에 구분할 여섯 단어

| 말 | 이 문서에서의 뜻 | 예 |
|---|---|---|
| 조건 | 사용자가 원하는 것 | QHD 게임, 150만원, 가성비 우선 |
| 요구사양 | 조건을 비교 가능한 기준으로 옮긴 것 | GPU 등급 7 이상, VRAM 12GB 이상 |
| 후보 | 선택할 수 있는 상품 하나 | 이름·가격·스펙이 붙은 GPU A |
| 점수 | 같은 종류의 후보를 비교하는 선호도 값 | A 0.458, B 0.418 |
| 세트 | 여러 종류에서 하나씩 뽑은 전체 구성 | CPU + GPU + RAM + … |
| 쟁점 | 조합에서 발견한 문제나 미확인 항목 | GPU가 케이스보다 큼 / GPU 길이 데이터 없음 |

**점수, 신뢰도, 기여도는 서로 다른 수치다.** 점수는 상품 순위용, 신뢰도는 쟁점 감점 합계로 만든 내부 재탐색 기준, 기여도는 일부 점수 축을 100%로 나눈 설명용 비율이다. 어느 것도 “이 PC가 잘 작동할 확률”이 아니다(§8.7, §8.9).

## 2. 도메인 배경: PC 부품 8종과 호환

엔진에서 중요한 부분은 "부품끼리 맞는가"를 따지는 일이다. 하드웨어를 처음 접한다면 아래 역할·규격부터 익힌다.

### 2.1 슬롯 8종

코드에서는 부품 종류를 **슬롯(slot)**이라 부르고, 이름은 한국어 문자열 그대로 쓴다: `CPU`, `GPU`, `RAM`, `메인보드`, `저장장치`, `파워`, `케이스`, `쿨러`.

| 슬롯 | 하는 일 | 엔진이 보는 주요 스펙 |
|---|---|---|
| CPU | 연산 장치 | 성능 등급(`perf_tier`), 소켓(`socket`, 예: LGA1851·AM5), 소비전력(`tdp_w`, 최대 `max_power_w`), 세대·계열 |
| GPU (그래픽카드) | 화면·게임 연산 | 성능 등급, VRAM(`vram_gb`), 길이(`length_mm`), 두께(`slot_thickness`), 소비전력(`power_w`), 보조전원 커넥터 |
| RAM (메모리) | 작업 메모리 | 규격(`mem_type`: DDR4/DDR5), 용량, 속도, 모듈 구성(예: 2x16) |
| 메인보드 | 모든 부품을 연결하는 기판 | 소켓, 메모리 규격, 크기(`form_factor`: ATX/mATX/ITX), 메모리 슬롯 수, M.2 슬롯 수, 지원 CPU 계열 |
| 저장장치 (SSD) | 저장 | 프로토콜(NVMe/SATA), 폼팩터(M.2 등), 용량 |
| 파워 (PSU) | 전원 공급 | 용량(`wattage_w`), 효율 등급(80+ Bronze<Gold<…), 크기(ATX/SFX), 길이, 제공 커넥터 |
| 케이스 | 본체 외함 | 지원 보드 크기, 허용 GPU 길이·쿨러 높이·파워 길이, 확장 슬롯 수, 라디에이터 장착 크기 |
| 쿨러 | CPU 냉각 | 높이, 지원 소켓, 유형(공랭/수랭), 라디에이터 크기 |

### 2.2 호환이란

부품 하나하나가 좋아도 **서로 맞지 않으면 조립할 수 없다.** 대표적인 예:

- CPU 소켓 ≠ 메인보드 소켓 → CPU가 꽂히지 않는다.
- RAM이 DDR5인데 메인보드가 DDR4 전용 → 꽂히지 않는다.
- GPU 길이 > 케이스 허용 길이 → 케이스에 들어가지 않는다.
- (CPU 전력 + GPU 전력) > 파워 용량 → 켜지지 않거나 불안정하다.

그래서 이 문제는 "슬롯별로 가장 좋은 것을 하나씩 고르면" 끝나지 않는다. 한 슬롯의 선택이 다른 슬롯의 선택지를 바꾸는 **조합 최적화 문제**이고, 이것을 [4]가 푼다.

### 2.3 성능 등급(tier)

CPU·GPU의 성능은 **1~10 눈금의 tier**로 표현한다. 벤치마크 실측이 아직 없어서, 제조사 등급(예: GPU "Mid-Range" → 7)을 표로 옮긴 **거친 대용값**이다. 요구사양("QHD 게임이면 GPU tier 7 이상")도 같은 눈금으로 적는다.

등급 8이 등급 4보다 두 배 빠르다는 뜻은 아니다. `QHD_165`의 `QHD`는 2560×1440 해상도, `165`는 목표 모니터 주사율(초당 화면 갱신 횟수, Hz)을 가리킨다. 이것을 조건으로 받는다고 게임에서 **165 FPS(초당 렌더링 프레임 수)를 보장하는 것은 아니다.** 현재는 게임 설정·실측 FPS를 입력받아 성능을 예측하는 모델이 없다. FHD는 1920×1080, 여기서 4K/UHD는 3840×2160이다.

## 3. 반드시 지켜야 할 원칙

새 코드를 작성하거나 기존 결과를 설명할 때 확인할 기준이다. 현재 구현의 예외도 같은 표에 적었다.

| # | 원칙 | 구체적으로 |
|---|---|---|
| 1 | **판정·수치는 코드, LLM은 서술만** | 후보 선택·호환 판정·감점은 코드가 소유한다. [3-C] 쟁점 문장에는 판정어 검사, [5]에는 별도의 금지어·슬롯 검사가 있다. 모든 LLM 출력의 사실성을 완벽히 검증한다는 뜻은 아니다(§8.9) |
| 2 | **모르는 것은 Pending** | 스펙 값이 없거나 파싱에 실패하면 **Fail이 아니라 Pending(판정 보류)**이다. 호환 검사에서도 값이 없으면 "ok (근사)"로 두고 "확인 필요" 쟁점으로 알린다 |
| 3 | **근사·잠정값을 구분한다** | 탐색 절단(`capped`)·재탐색 라운드·잠정값(`provisional`)·합성 데이터·참고가를 해당 내부 결과나 안내에 남긴다. 현재 내부 DTO의 모든 정보가 API에 노출되는 것은 아니다(§10.3) |
| 4 | **조건을 조용히 완화하지 않는다 — 목표 원칙** | 주변기기는 후보 0건이면 "없음"과 이유를 낸다. 다만 PC [3-A]는 Pass·Pending이 모두 없으면 Fail 후보를 다시 남긴다. 이 예외는 **실경로에도 적용**되므로 원칙이 완전히 구현됐다고 발표하면 안 된다(§8.4) |
| 5 | **결정 기록 준수** | [0001](decisions/0001-정제-후-평점을-판정기-없이-내지-않는다.md) 리뷰 진위를 판정하거나 점수화하지 않는다 · [0003](decisions/0003-데모-화면에서-세트-신뢰도·회색축·표시용-리뷰-수를-뺀다.md) 사용자에게 보이는 문장에 **신뢰도 숫자를 넣지 않는다** · [0004](decisions/0004-목업_표시_근거_원칙.md) 목업 데이터 표시 근거 |
| 6 | **기존 결과 회귀 확인** | 새 조건을 처리하는 기능을 추가할 때, 그 조건이 없는 요청의 결과를 불필요하게 바꾸지 않는다. 골든 테스트는 고정된 입력·데이터의 기대 결과를 확인한다. 정책 변경 자체가 목적이면 전후 차이를 검토한다 |
| 7 | **설정 버전 규율** | YAML의 정책값을 바꾸면 `rule_set_version`을 올린다. 구조를 바꾸면 `schema_version`을 올리고 로더에 검증을 추가한다. 로더는 잘못된 설정을 **로드 시점에 즉시 오류로** 낸다 |
| 8 | **API 계약은 엔진 밖** | `src/schemas.py`(응답 모델)와 `src/routers/*`는 프론트와의 계약이다. 새 응답 필드는 프론트 합의 후에만 넣는다. 엔진은 "계약 모양 dict를 만드는 순수 함수"까지만 만든다 |

**설계 이유** — 추천 이유를 추적하려면 사용자의 조건, 코드의 계산, 데이터의 출처를 연결할 수 있어야 한다. 위 표는 설계 원칙과 현재 구현의 예외를 함께 적은 것이다. 원칙을 서비스가 이미 완전히 보장하는 기능으로 읽지 않는다.

## 4. 제품 안에서 엔진의 위치

### 4.1 사용자 여정

```
브라우저 ─ 조건 대화(칩 선택·자유 입력) ─▶ 추천 실행 ─▶ 결과 화면(부품표·요약·구매 전 확인)
                                                        └ 대안 보기·교체·수량 변경 ─▶ 확정 ─▶ 리포트
```

- **조건 대화**는 대화 계층(`session_service`, 선택적으로 Strands 조건 에이전트)이 담당한다. 엔진은 모인 조건을 **읽기만** 한다.
- **추천 실행**이 엔진의 몫이다. 백그라운드에서 돌고 결과를 DB에 저장한다.
- **결과 화면**은 저장된 결과를 읽어 조립한다. 교체 뒤에는 엔진의 호환 검사만 다시 돈다.

### 4.2 식별자 관계 (헷갈리기 쉽다)

| 이름 | 실체 | 설명 |
|---|---|---|
| `list_id` | `planning.plan.id` | API URL에 쓰는 ID. "견적 목록" 하나 |
| `revision_id` | `planning.plan_revision.id` | 목록의 버전. 조건(`plan_condition`)이 여기에 붙는다. 엔진은 revision 단위로 돈다 |
| `run_id` | `engine.recommendation_run.id` | 추천 실행 1회. revision 하나에 여러 번 돌 수 있고 최신 run이 결과가 된다 |
| `product_key` | DB PC 후보는 `"{종류}:{브랜드}:{모델}"`을 소문자로, 공백은 `-`로 | 엔진 내부 식별자(`catalog_repo.pc_catalog_key`). 합성 후보는 이름 기반 키를 쓰며, 기존 리뷰 키와는 `data/review_catalog_map.csv` 매핑이 필요할 수 있다 |
| `variant_id` | `catalog.product_variant.id` | 상품의 판매 단위(기본 variant) |
| `offer_observation_id` | 가격 관측 행 | 이 가격을 언제 어디서 관측했는가. PC 후보는 **반드시** 있어야 저장된다 |

### 4.3 DB 스키마

PostgreSQL 16, 스키마 9개. 엔진이 주로 닿는 곳:

| 스키마 | 엔진과의 관계 |
|---|---|
| `catalog` | **읽기만.** 상품·스펙(`*_spec`)·가격(`offer`, `offer_observation`, 주변기기는 `peripheral_price_snapshot`) |
| `planning` | 조건을 읽는다(`plan_condition`), 슬롯 요구사항 행을 만든다(`plan_node`, `requirement`) |
| `engine` | 결과를 쓴다(`recommendation_run`, `recommendation_candidate`, `validation_result`, `feedback_event`) |
| 그 외 | `identity`(계정), `evidence`, `community`, `notification`, `config`, `assets` — 엔진은 거의 안 쓴다 |

DB 스키마 변경(`db/migrations/`)은 **엔진 작업 범위 밖**이다. 기준 마이그레이션은 정확히 4개 파일이다([AGENTS.md](../AGENTS.md)).

## 5. 전체 흐름

### 5.1 단계 번호

기획서의 단계 번호를 코드 전체에서 쓴다. 로그에도 `[3-B]`처럼 찍힌다.

| 단계 | 이름 | 모듈 | LLM |
|---|---|---|---|
| [1] | 조건 수집 (의도 분해·슬롯 채우기) | `slot_rules.py`(실경로), `stage1_intent.py`(데모), `slots.py` | 기본 API는 안 씀. 데모 호출 주의는 §5.3 |
| [2] | 요구사양 빌드 | `stage2_requirement.py` | 안 씀 |
| [3-0] | 후보 수집 | `stage3_0_candidates.py`, `repo/catalog_repo.py` | 안 씀 |
| [3-A] | 하드 필터 (Pass/Fail/Pending) | `stage3a_hardfilter.py` | 안 씀 |
| [3-B] | 적합도 점수·순위 | `stage3b_rank.py` | 안 씀 |
| [4] | 세트 최적화 (분기한정 탐색) | `stage4_optimize.py` | 안 씀 |
| [3-C] | 세트 검증 (신뢰도·쟁점) | `stage3c_verify.py` | 쟁점 **문장**만 |
| (루프) | [3-C]→[4] 재탐색 | `research_loop.py` | 안 씀 |
| [5] | 설명 생성 | `stage5_explain.py` | 설명 **문장**만 |
| [6] | 피드백 반영 배치 | `stage6_feedback.py` | 자동 반영 **미구현**(스텁: 함수 형태만 있는 자리) |

[4]가 [3-C]보다 먼저 돈다. 번호는 기획서 순서이고, PC는 "세트를 먼저 만들고 세트를 검증"하므로 실행 순서가 [4]→[3-C]다.

### 5.2 두 실행 경로

```
                 ┌──────────── 데모 경로 ─────────────┐   ┌──────────────── 실경로 ─────────────────┐
입력              data/scenarios/*.json                    POST /session/{id}/message, /answer
                 (mock_slot_fill 에 정답 조건)             → session_service + slot_rules (규칙 추출)
                                                          → DB에 조건 저장
[1]              stage1_intent.run                        slots.slots_from_conditions
[2]              stage2_requirement.run  ◀──────── 같은 함수 ────────▶
[3-0]            stage3_0_candidates                       catalog_repo.load_candidates_by_slot_from_db
                 (DB 시도 → 실패 시 합성 카탈로그)
[3-A] [3-B]      stage3a / stage3b       ◀──────── 같은 함수 ────────▶
[4]+[3-C]+루프   research_loop.run_set_with_research  ◀─ 같은 함수, 주입만 다름 ─▶
                   verify = verify_set (시나리오 정답값 주입)   verify = verify_build (실제 규칙)
                   choose_exclusion = 시나리오 problem_slot   choose_exclusion = rule_based_exclusion
주변기기          _run_peripherals (조건에 peripherals 있을 때만)  (아직 연결 안 됨 — R-7 대기)
[5]              stage5_explain.run      ◀──────── 같은 함수 ────────▶
출력              PipelineResult (콘솔 표)                  DB 저장 → GET /session/{id}/result 가 조립
```

**데모 경로의 [3-C]는 계산된 검증 결과가 아니다.** 시나리오 파일의 `verify.rounds[i]`에 적힌 신뢰도·쟁점을 그대로 주입한다. 데모의 [4]에서도 실제 호환 규칙은 실행하지만, 뒤의 [3-C] 신뢰도는 그 결과에서 계산하지 않는다. 전체 규칙 검증 흐름을 확인하려면 `verify_build`를 쓰는 §15.2의 재현 스크립트를 실행한다.

### 5.3 실행 경로, 데이터, 외부 호출은 따로 고른다

`MOCK_MODE=1` 하나로 모든 데이터가 가짜가 되거나 DB 사용이 꺼지는 것은 아니다.

| 선택 | 무엇이 달라지는가 | 달라지지 않는 것 |
|---|---|---|
| `main.py` 데모 / API 실경로 | 조건의 출처와 [3-C] 검증 함수 | [2]·[3-A]·[3-B]·[4]의 주요 계산 함수 |
| `CATALOG_SOURCE=mock` | 데모·재현 도구에서 합성 카탈로그 선택 | API는 DB 카탈로그를 직접 읽음 |
| `MOCK_MODE=1` | 이 추천 흐름의 LLM 호출·사용 가이드 임베딩을 모의 처리 | DB 조회와 규칙 계산은 실행 가능 |
| `CONDITIONS_AGENT=1` | 실호출 조건을 갖추면 선택적인 LLM 조건 대화 경로 사용 | 기본값은 0, 추천 본체의 판정은 규칙 |

데모 [1]은 정답 조건을 시나리오에서 읽지만 내부에서 `call_llm`도 호출한다. **데모 명령에는 `MOCK_MODE=1`을 명시한다.** `MOCK_MODE=0`으로 바꿔도 데모 [3-C]는 여전히 정답 주입이며 실제 검증으로 바뀌지 않는다. 별도 RAG 도구의 외부 호출 설정까지 이 표가 설명하는 것은 아니다.

### 5.4 학습 데이터와 요청 시 데이터의 차이

현재 추천 요청 한 건을 처리할 때는 모델을 학습하거나 인터넷에서 상품을 새로 수집하지 않는다.

```text
사전에 준비: 수집 파일 → DB 시드 → 상품·스펙·가격 관측
             리뷰 분석 산출물 → 상품별 관측 신호
             YAML 정책 → 요구 등급·가중치·호환 검사 키
요청 시 사용: 사용자 조건 + 위 데이터 → 필터·점수·세트 탐색 → 결과 저장
```

따라서 “DB에서 읽었다”와 “지금 판매 가능한 최신 가격이다”는 다르다. 가격 갱신 주기·재고·정확한 판매 옵션은 별도 데이터 문제이며, 추천 결과는 사용한 가격 관측을 연결해 보존한다.

### 6.3 코드 관례

- **단계 함수는 순수 함수에 가깝다.** 입력 DTO를 바꾸지 않고 `model_copy(update=...)`로 새 객체를 만든다. 예: [3-A]는 `cand.model_copy(update={"verdict": ..., "reasons": ...})`.
- **로그는 콜백으로.** 모든 단계가 `log: LogFn`을 받는다. `print`를 직접 쓰지 않는다(실경로에서 stdout이 오염된다).
- **설정 로더는 캐시된다.** `load_computer_rules()`는 `lru_cache`로 한 번만 읽는다.
- **주석은 한국어, WHY만.** 기존 파일의 docstring 스타일(무엇을 왜 이렇게 했는지, 어떤 사고가 있었는지)을 따른다.
- **재현 조건을 함께 기록한다.** [4] 최대 점수 탐색의 동점 규칙은 점수 합 → 가격 합 → `product_key`다. [3-B]는 점수만 정렬하므로 동점이면 입력 후보 순서를 유지한다. 같은 사용자 조건만으로 모든 환경에서 같은 결과가 보장되지는 않는다. 카탈로그·리뷰 파일·정책·후보 순서가 같아야 비교가 의미 있으며 LLM 문장은 달라질 수 있다.

## 7. 데이터 모델(DTO) 흐름

DTO(Data Transfer Object)는 단계 사이에 주고받는 **이름 붙은 데이터 상자**다. 이 저장소는 Pydantic 모델로 필드와 기본값을 정의한다. DTO는 DB 테이블도, API 응답 그 자체도 아니다. 예를 들어 `Candidate`에는 계산에 쓸 스펙이 있지만 `BuildItem`에는 선택 결과 중심의 필드만 있다.

모든 단계는 "이전 DTO + 컨텍스트 → 다음 DTO"다. 여기서 컨텍스트는 사용자 조건, 정책 설정, 후보 카탈로그처럼 계산에 함께 필요한 정보다.

```
Slots ──[2]──▶ RequirementSpec ──[3-A]──▶ HardFilterResult ──[3-B]──▶ RankResult
                                                                        │
          ┌─────────────────────────────────────────────────────────────┘
          ▼
   [4] BuildResult ──[3-C]──▶ VerificationResult ──[5]──▶ Explanation
          ▲                         │
          └── 재탐색(exclude 추가) ◀─┘   (research_loop 가 RoundRecord 로 라운드별 보관)
```

| DTO | 핵심 필드 | 만드는 곳 |
|---|---|---|
| `Slots` | `values`(조건 dict), `assumed_keys`(기본값으로 채운 키), `mode`(build/upgrade) | [1] |
| `RequirementSpec` | `targets[slot]`(슬롯별 조건), `budget{total, alloc}`, `flags`, `owned`(업그레이드 유지 부품), `games`, `unresolved` | [2] |
| `Candidate` | `product_key`, `slot`, `price`, `specs`(판정용 스펙), `provenance`(출처 — **specs와 분리**), `verdict`, `reasons`, `score`, `breakdown`(축별 점수), `rank`, `flags`, `price_source` | [3-0]에서 생성, [3-A]/[3-B]가 갱신 |
| `HardFilterResult` | `slots[slot] = [Candidate]`, `stats[slot]`(pool/pass/fail/pending) | [3-A] |
| `RankResult` | `slots[slot] = {ideal_tier, ranked(top-N), pool(전체), bottleneck_hint}`, `weights_used`, `weight_adjustments` | [3-B] |
| `BuildResult` | `items[BuildItem]`, `totals`, `budget{max, used, used_pct}`, `link_check{axis: state}`, `alternatives`(탐색 통계), `round` | [4] |
| `VerificationResult` | `mode`("set"/"per_item"), `targets[VerificationTarget{confidence, passed, issues, gray_axes, rounds, transcript}]` | [3-C] |
| `Issue` | `axis`, `text`(중립 문장), `tool_result`(관측값), `judge`("위반"/"확인 필요"/…), `penalty`, `evidence` | [3-C] |
| `Explanation` | `headline`, `summary`, `items[slot, reason, evidence]`, `contribution{가격,성능,호환성}`, `caveats`, `review_line_by_slot` | [5] |
| `PipelineResult` | 위 전부 + `peripherals` + `logs` (데모 경로 최종 출력) | pipeline |

> `RankResult.slots[...]["ranked"]`와 `["pool"]`은 **dict 목록**(`model_dump()` 결과)이다. 다시 쓰려면 `Candidate.model_validate(...)`로 되살린다. `BuildItem`에는 `specs`가 없으므로 뽑힌 부품의 스펙이 필요하면 `research_loop.resolve_chosen(rank, build)`를 쓴다.

다음은 같은 요구가 이름을 바꾸며 이동하는 모습이다. `GPU A`는 설명용 가상 상품이다.

```text
Slots.values             resolution="QHD_165", budget_max=1500000
RequirementSpec.targets  GPU: perf_tier_min=7, vram_gb_min=12
Candidate.specs          GPU A: perf_tier=7, vram_gb=12, length_mm=330
Candidate.verdict        Pass (GPU 자체 요구 충족)
Candidate.score          다른 GPU와 비교할 점수
BuildResult.items        함께 쓸 케이스·총액까지 비교해 최종 GPU 선택
VerificationResult       선택 세트의 GPU 길이 등 쟁점을 집계
Explanation              왜 이 구성을 골랐는지 문장으로 설명
```

`Pass`는 GPU 자체 요구를 통과했다는 뜻이다. 이 시점에는 어떤 케이스와 조합될지 모르므로, 최종 조립 가능 판정과 구분해야 한다.

## 8. 단계별 알고리즘

숫자 예시는 §9에 모아 두었다. 이 절은 규칙을 설명하고, §9에서 같은 규칙을 실제 값으로 확인한다.

### 8.1 [1] 조건 수집

**실경로** — 대화 계층(`session_service`)이 조건을 모은다.

- 질문 칩을 누르면 `computer.yaml`의 `question_sets[].maps_to` 필드에 값이 바로 들어간다.
- 자유 텍스트는 기본 경로에서 `slot_rules.py`가 **정규식 규칙으로** 뽑는다(예: "150만원", "삼백만원" → 정수 원). 기본 계약은 규칙 추출이며 선택적 조건 에이전트 경로는 §5.3과 구분한다.
- 공통 필수 조건은 `required_inputs: [mode, purpose, budget_max, priority]`이고, `mode=upgrade`면 `upgrade_parts`가 추가된다. 업그레이드는 교체 부품과 현재 사양에 따라 `owned_platform`·`owned_ram_type`·`owned_psu_w`도 **조건부 필수**가 된다(§11의 표). `session_service.compute_missing`이 현재 필요한 키를 계산하며, 해당 키가 없거나 값이 `None`이면 추천 요청(`POST /recommend`)이 `conditions_incomplete`로 거절된다. 조건부 질문에 `"unknown"`으로 답하는 것과 답을 생략하는 것은 다르다.

추천 실행 시 `slots.slots_from_conditions`가 조건 dict를 `Slots`로 바꾼다. 생략한 키는 `computer.yaml`의 `defaults`(해상도 FHD_144, 조립 대행, 소음 민감 아님, 브랜드 무관)로 채우고 `assumed_keys`에 기록한다. 이 기록은 요구사양의 `resolution_assumed` 같은 플래그에 쓰인다. 다만 현재 병합은 입력 dict가 우선이므로 **명시적인 `None`·빈 문자열이 기본값을 다시 덮을 수 있다.** 생략과 빈 값 입력이 항상 같다고 가정하지 않는다. 기본값 사용 안내가 모든 화면에 자동 노출되는 것도 아니다.

**데모 경로** — 시나리오의 `mock_slot_fill`(confirmed/assumed/missing)을 그대로 쓴다. `tests/test_slots_equivalence.py`는 준비된 대응 사례에서 두 경로의 조건·후속 결과를 비교한다. 임의의 자유 문장까지 같은 의미로 해석한다는 보장은 아니다.

### 8.2 [2] 요구사양 빌드

`stage2_requirement._computer_build` — 조건을 **슬롯별 요구사양 `targets`**로 번역한다. 전부 `config/computer_verification_rules.yaml`의 `requirements` 절을 읽는다.

1. **요구 등급(tier) 결정**
   - 용도가 `office/study/other/creation`이면 `purpose_profiles[용도].tier`를 쓴다. 이 프로필은 RAM 규격·저장 용량·파워 효율·소켓 목록·예산 배분 같은 다른 기본값도 덮어쓴다.
   - 그 외(게임·미지정)는 해상도로 `game_tiers`를 고른다. 예: `QHD_165 → {gpu: 7, cpu: 5, ram_gb: 16, vram_gb: 12}`.
   - 게임 제목(`games`)이 있으면 `game_titles` 표에서 찾아 **요소별로 큰 값**을 취한다(가벼운 게임은 아무것도 바꾸지 않고, 무거운 게임만 올린다). 표에 없는 게임은 `unresolved`로 남긴다. 현재 제목별 값은 기본 상태가 `provisional`(잠정값)이며, 하나라도 잠정이면 `games_provisional` 플래그를 남긴다. 실경로 서비스가 이 정보를 읽어 [5]의 안내 문장·범위 설명으로 전달한다. 플래그만으로 모든 호출 경로에 안내가 자동 추가되는 것은 아니다.
2. **소켓** — `brand_pref`로 `sockets_by_brand`를 고른다(게임 기본: intel→LGA1851, amd→AM5, 무관→둘 다).
3. **파워 최소 용량** — `(추정 CPU + 추정 GPU + 기타) × 1.5` 이상인 첫 표준 용량. 게임 기본값이면 `(125+300+75)×1.5 = 750 → 750W`.
4. **예산 배분** — `budget_allocation`(게임: GPU 40%, CPU 18% …). [3-B]의 가격 점수 기준이다. GPU 배분액이 60만원이어도 65만원 GPU를 바로 탈락시키지는 않는다. [4]가 검사하는 예산 제약은 **전체 합계**다.
5. **링크 규칙** — `link_rules` 문자열 목록을 기록한다(로그·계약용이며 실제 판정은 [4]의 코드가 한다).

결과 `targets` 예 (게임·QHD):

```python
{"CPU": {"perf_tier_min": 5, "socket_in": ["LGA1851", "AM5"], "tdp_budget_w": 125},
 "GPU": {"perf_tier_min": 7, "vram_gb_min": 12, "tgp_budget_w": 300},
 "RAM": {"type": "DDR5", "capacity_gb_min": 16},
 "메인보드": {"socket_in": [...], "form_in": ["ATX", "mATX"], "mem_type": "DDR5"},
 "저장장치": {"interface": "NVMe", "capacity_gb_min": 1000},
 "파워": {"wattage_min": 750, "plus_rating_min": "Gold"},
 "케이스": {"form": "ATX_mid"}, "쿨러": {"tdp_capacity_w_min": 125}}
```

업그레이드 모드는 `upgrade_parts`에 적은 슬롯만 `targets`에 남기고 예산 배분을 그 슬롯들 안에서 다시 정규화한다(§11).

“최소 등급”과 “이상 등급”도 다르다. QHD GPU의 `perf_tier_min=7`은 [3-A]의 탈락 기준이고, `ideal_tier=7.5`는 [3-B]가 적당한 성능 균형을 선호하는 기준이다. 전자는 통과 여부, 후자는 통과한 후보 사이의 점수에 쓰인다.

### 8.3 [3-0] 후보 수집

`catalog_repo.load_candidates_by_slot_from_db`가 `catalog.product` + 종류별 `*_spec` + 기본 variant + 활성 offer의 최신 유효 가격 관측을 조인한다. 즉, 판매 단위와 사용할 수 있는 가격 기록이 있는 상품을 엔진의 공통 `Candidate` 모양으로 바꾼다.

- **가격이 없는 상품은 후보에서 뺀다.** 가격 없이 추천하지 않는다.
- `perf_tier`는 **CPU·GPU에만** 있다(`lineup_perf_tier` 표). 표에 없는 등급은 비워 두어 Pending이 된다.
- `provenance`에 `spec_url`, `checked_at`, 키별 출처 URL(`by_key`)을 담는다. `specs`는 판정값, `provenance`는 그 값의 출처로 역할을 나눈다. 현재 결손 감점은 설정에 나열된 키만 검사하므로 URL을 넣는 즉시 감점이 바뀐다는 설명은 정확하지 않다.

데모 경로(`stage3_0_candidates.load_pc_catalog`)는 DB를 먼저 시도하고, 접속 실패나 빈 카탈로그면 `data/parts_list.csv` 기반 **합성 카탈로그**로 대체한다. `CATALOG_SOURCE=mock`이면 처음부터 합성 카탈로그를 쓴다. 가격·tier는 이름의 해시(같은 문자열을 항상 같은 수로 바꾸는 계산)로 만들고, `data/demo_part_overrides.csv`에 값이 있으면 우선 적용한다. 모든 슬롯에 tier가 생기고 호환 스펙은 대부분 비어 있으므로 실제 성능 비교에 쓰면 안 된다. **API 경로에는 이 합성 대체 동작이 없다.**

### 8.4 [3-A] 하드 필터

`stage3a_hardfilter._judge_computer` — 후보마다 **그 슬롯 혼자서** 판정할 수 있는 조건(단방향)만 본다. 부품 사이의 조합 조건(소켓 일치 등)은 여기서 보지 않고 [4]로 넘긴다.

| 검사 | 비교 |
|---|---|
| 성능 등급 | `perf_tier ≥ perf_tier_min` |
| 소켓 | `socket ∈ socket_in` |
| VRAM | `vram_gb ≥ vram_gb_min` |
| 메모리 규격 | `mem_type == type` |
| 용량 | `capacity_gb ≥ capacity_gb_min` |
| 폼팩터 | `form_factor ∈ form_in` |
| 저장장치 프로토콜 | `"NVMe" in protocol` |
| 파워 용량·효율 | `wattage_w ≥ wattage_min`, 효율 등급 순위 ≥ `plus_rating_min` |

- 값이 없으면 그 검사는 **Pending**. 여러 검사 중 가장 나쁜 것(Fail > Pending > Pass)이 후보의 `verdict`가 된다. 이유는 `FAIL_PERF_BELOW:6<7`, `PENDING_SPEC_MISSING:socket` 같은 코드 문자열로 `reasons`에 남는다.
- **Pending 승격 규칙**: 슬롯의 Pass가 `TOP_N_DEFAULT`(3)개 이상이면 Pass만 남긴다. 3개 미만이면 Pending도 함께 남긴다(대신 [3-B]에서 0.20 감점).
- 케이스 `form`, 쿨러 `tdp_capacity_w_min`은 대응하는 실측 컬럼이 없어 **판정하지 않는다.**

예를 들어 GPU 요구가 등급 7·VRAM 12GB라면, `(등급 8, VRAM 12)`는 Pass, `(등급 6, VRAM 12)`는 Fail, `(등급 8, VRAM 없음)`은 Pending이다. VRAM이 없어도 등급이 6이면 이미 알려진 실패가 있으므로 Fail이다. Pending을 살려 두는 이유는 “데이터 없음”과 “성능 미달”을 구별하기 위해서다.

**현재 예외:** Pass도 Pending도 없는 슬롯은 `keep = judged`로 Fail 후보까지 다시 남긴다. 로그에는 “데모는 목 후보로 진행”이라고 나오지만 모드 검사 없이 실행되므로 **API에도 적용된다.** 이후 [3-B]에는 Fail 전용 감점도 없고 [3-C]가 원래의 모든 요구사양을 다시 검사하지도 않는다. 따라서 현재 엔진을 “최소 요구를 반드시 만족하는 추천기”라고 설명하면 안 된다. 이 문서는 동작을 정확히 기록하며 해당 정책을 코드에서 변경하지 않는다.

### 8.5 [3-B] 적합도 점수·순위

`stage3b_rank` — 슬롯별로 후보를 점수화하고 top-N을 남긴다.

**축별 점수 (대부분 0~1, 밸런스는 예외)**

| 축 | 계산 | 비고 |
|---|---|---|
| 가격 | `max(0, 1 − 가격 / 슬롯예산)`, 슬롯예산 = 총예산 × `alloc[slot]` | 쌀수록 높다. 슬롯예산 이상이면 0 |
| 성능 | `min(1, perf_tier / 10)` | tier가 없으면 5로 간주 → 0.5 |
| 밸런스 | `1 − abs(tier − ideal_tier) / 4` | `abs`는 차이의 절댓값. 이상 등급에 가까울수록 높다. 0으로 제한하지 않아 음수 가능. `ideal_tier`가 없으면 0.5 |
| 리뷰 | 관측 없음 0.5 / 비교 지표 중 기준 이상 없음 0.75 / 하나라도 대조군 중앙값의 2배 이상이면 0.25 | 상품별 관측 신호로 순위만 조정. 진위 확률이 아님 |
| 호환여유 | CPU/GPU: 전력 예산 대비 여유, 파워: 요구 대비 초과 용량(1.0 상한), 그 외 0.5 | 값 없으면 0.5 |
| 소음 | CPU/GPU 소비전력·쿨러 유형으로 만든 휴리스틱 | **가중치가 0보다 클 때만** 계산 |

> DB 카탈로그에서는 CPU·GPU 외 슬롯에 tier가 없고 `ideal_tier`도 없으므로 **성능·밸런스 축이 상수(0.5)**다. 즉 메인보드·RAM·케이스 등은 사실상 **가격·리뷰·호환여유·결손 감점**으로 순위가 정해진다.

**가중치** — `ranking.weights`(기본: 가격 .35, 성능 .25, 밸런스 .15, 리뷰 .20, 호환여유 .05, 소음 0). `priority`가 있으면 `priority_weights`의 세트로 바꾼다(성능 우선이면 성능 .55, 가성비면 가격 .50). `noise_sensitive=true`면 소음 가중치를 최소 0.15로 올리고 나머지를 비율대로 줄인다. 어떤 가중치를 썼는지는 `RankResult.weights_used`에 남는다.

**최종 점수**

```
score = Σ(가중치 × 축 점수)
        − 0.20                              (verdict가 Pending이면)
        − min(빈 검사용 스펙 수 × 0.10, 0.20)   (데이터 결손 감점)
```

`Σ`는 각 축의 값을 더한다는 기호다. `0.20` 감점은 **점수에서 0.20을 빼는 것**이며 “점수의 20%를 빼기”가 아니다. 최종 점수는 소수 셋째 자리까지 반올림하고, 0~1로 다시 제한하지 않아 음수도 가능하다. 예: 가중합 0.53에서 Pending 감점 0.20과 결손 감점 0.10을 빼면 0.23이다.

리뷰축은 리뷰 별점 평균이 아니다. 예를 들어 특정 기간에 리뷰가 몰리는 정도 등 상품 단위 지표를 비교 집단(대조군)의 중앙값과 비교한다. 중앙값은 값을 정렬했을 때 가운데 값이다. 이상 신호가 있다고 개별 리뷰를 가짜로 판정하거나 삭제하지 않는다. 관련 산출물·상품 키 매핑이 없으면 “관측 없음”으로 둔다. `review_focus.py`는 리뷰 문장 표시 순서용이며 이 점수를 계산하는 함수가 아니다.

- **데이터 결손 감점**은 `ranking.data_gap.specs`에 적힌 "호환 검사에 필요한 스펙"이 빈 후보를 깎는다. "정보 없음은 통과" 원칙 때문에 데이터가 빈 싼 부품이 검사를 피해 계속 뽑히던 문제를 막는다. **그 슬롯에서 아무 후보도 값을 갖지 않는 키는 제외**한다(데이터가 아예 없는 카탈로그의 점수는 바뀌지 않게).
- **게임 요구 반영**: `games_applied` 플래그가 있고 [2]의 `perf_tier_min`이 `ideal_tier`보다 높으면 `ideal_tier`를 그 값까지 올린다. 없으면 무거운 게임을 골라도 밸런스 축이 하한 바로 위 등급을 선호하는 문제가 생긴다.
- **top-N**: `impact_slots`(GPU·CPU)는 5개, 나머지는 3개. 자르기 전 전체 순위도 `pool`에 보관한다([4]가 필요하면 넓혀 쓴다).
- 1위 후보의 등급이 `ideal_tier − 0.5`보다 낮으면 `bottleneck_hint`를 남긴다.

> 리뷰 산출물 파일(`data/amazon23/pcparts_product_risk.json`, Git 미추적)을 사용할 수 없으면 리뷰축이 전부 0.5로 고정돼 **추천 구성이 달라질 수 있다.** [3-B]의 `⚠ 리뷰축 비활성` 로그로 어느 상태인지 확인한다. 같은 점수의 후보는 입력 순서가 유지되므로, top-N 경계의 동점은 카탈로그 순서에도 영향을 받는다.

### 8.6 [4] 세트 최적화 — 분기한정 탐색

`stage4_optimize.build_computer` → `_search_pc_build`. 이 단계가 엔진에서 가장 복잡하다.

**문제 정의** — 슬롯마다 후보 하나씩 골라, **확인된 비호환이 없고 예산 안에 드는** 조합 중 **점수 합이 최대**인 세트를 찾는다. 동점이면 더 싼 것, 그다음 `product_key` 사전순으로 결정한다. “확인된 비호환 없음”에는 스펙을 몰라 검사하지 못한 조합도 포함된다.

분기한정(branch-and-bound)은 부품을 하나씩 고르며 경우를 나누되, 더 살펴봐도 답이 될 수 없는 부분 조합은 일찍 멈추는 방법이다. 예를 들어 현재 선택액이 100만원이고 남은 부품의 최저가 합이 60만원이라면 150만원 예산을 맞출 수 없다. 이미 찾은 점수 합이 4.0인데 현재 점수 2.0에 남은 슬롯 최고 점수를 전부 더해도 3.7이면 그 가지도 더 볼 필요가 없다. 뒤의 값은 실제 달성 가능 여부와 무관하게 계산한 **낙관적 상한**이다.

**탐색 순서** — `메인보드 → 케이스 → CPU → RAM → GPU → 쿨러 → 파워 → 저장장치`. 호환 제약을 많이 거는 슬롯을 앞에 둬야 가지치기가 일찍 일어난다.

**핵심 코드** (`_max_score_search`의 축약형; 방문 횟수 집계·노드 상한 처리는 생략)

```python
from src.engine.stage4_optimize import _pc_known_failures

def search(pools, order, slots, budget, spec, rules):
    # 슬롯 i부터 끝까지: 최저가 합과 최고 점수 합. 끝에서는 둘 다 0이다.
    min_price = [0] * (len(order) + 1)
    max_score = [0.0] * (len(order) + 1)
    for i in range(len(order) - 1, -1, -1):
        pool = pools[order[i]]
        min_price[i] = min_price[i + 1] + min(c.price for c in pool)
        max_score[i] = max_score[i + 1] + max(c.score for c in pool)
    chosen, best, best_key = {}, {}, None

    def visit(i, price, score):
        nonlocal best, best_key
        if budget and price + min_price[i] > budget:       # ① 예산 가지치기
            return
        if best_key is not None and score + max_score[i] < -best_key[0] - 1e-9:
            return                                        # ② 점수 상한 가지치기
        if i == len(order):
            key = (-score, price, tuple(chosen[s].product_key for s in slots))
            if best_key is None or key < best_key:
                best, best_key = chosen.copy(), key
            return
        slot = order[i]
        for cand in pools[slot]:                           # 점수 높은 순
            chosen[slot] = cand
            if not _pc_known_failures(chosen, spec, rules): # ③ 비호환이면 재귀 생략
                visit(i + 1, price + cand.price, score + cand.score)
            del chosen[slot]                              # 성공·가지치기 모두 선택 취소

    visit(0, 0, 0.0)
    return best
```

`pools`는 슬롯별 후보 목록, `order`는 탐색 순서, `slots`는 동점 비교에 쓸 고정 슬롯 순서다. 슬롯마다 후보가 한 개 이상 있다는 전제이며, 실제 호출부는 빈 슬롯을 먼저 처리한다. 비교 키의 `-score`는 점수가 높을수록 작은 값이 되게 해 **점수 내림차순 → 가격 오름차순 → 상품 키 순**을 한 번에 비교한다. `1e-9`는 부동소수점 계산 오차를 위한 작은 여유다.

**선택 취소가 중요한 이유:** `chosen`은 여러 재귀 호출이 함께 쓰는 dict다. 한 가지를 다 봤거나 비호환으로 멈췄으면 `del chosen[slot]`으로 그 선택을 반드시 되돌려야 한다. 그래야 다음 메인보드를 검사할 때 이전 가지의 CPU가 남아 엉뚱한 비호환 판정을 만들지 않는다. 최선의 조합은 이후 변경에 영향받지 않도록 `chosen.copy()`로 보관한다.

**단계적 후퇴** — 한 단계에서 답을 못 찾으면 다음 단계로 넘어간다.

```
① top-N 풀에서 정확 탐색 ─── 찾음 ──▶ 채택
      │ 없음
② 전체 풀(pool)로 넓혀 다시 탐색 (노드 상한 WIDEN_NODE_CAP = 150,000)
      │   top-N은 호환을 모른 채 잘랐으므로 호환 조합이 전부 잘렸을 수 있다
      │ 없음
③ 예산을 무시하고 가장 싼 호환 세트 탐색 (확장 풀 탐색에는 노드 상한)
      │ 찾으면 채택, 실제 총액이 예산 초과면 link_check["budget"]="fail"
      │ 못 찾음
④ top-N 전 조합 중 비호환 개수가 가장 적은 세트
      ├ 비호환이 남거나 필수 슬롯 누락 → link_check["set"]="fail"
      └ 호환되지만 예산 초과 → link_check["budget"]="fail" (set 실패와 구분)
```

④에서도 비호환 0개인 조합이 있으면 그중 예산 안 조합을 우선하고, 가장 싼 것을 고른다. `set=fail`은 실제로 비호환이 남거나 필요한 슬롯을 모두 고르지 못한 경우다. 확장할 풀 자체가 없으면 ②·③을 건너뛰고 ④에서 최소 가격의 호환 조합을 찾을 수 있다. 후보가 빈 슬롯이 있으면 빈 구성과 실패 상태를 반환한다.

**최적이라는 말의 범위:** ①은 **top-N 조합 안에서만 정확한 최적해**다. 여기서 답을 찾으면 전체 `pool`로 넓히지 않으므로 전체 카탈로그에서 가장 좋은 조합이라고 보장할 수 없다. ②·③은 최대 150,000 노드에서 멈출 수 있으므로 그 범위에서도 최적 또는 “해가 없음”을 증명하지 못할 수 있다. 최대 라운드 제한과 노드 상한은 계산량을 제어하는 장치이며 품질 보장은 아니다.

탐색 통계는 `BuildResult.alternatives`에 남는다. `considered`는 top-N의 이론상 전체 조합 수, `visited`는 최초 탐색에서 방문한 부분 조합 수, `valid`는 그 탐색에서 실제 도달한 적합한 완성 조합 수다. `valid`를 전체 가능한 적합 조합 수로 해석하지 않는다. 확장 시 `widened`·`widened_visited`, 상한에 걸린 일부 경로에서는 `capped=1`이 기록된다. 현재 확장 탐색이 **해를 못 찾고 상한에 도달한 기록은 후속 탐색 결과에 따라 누락될 수 있어**, `capped`가 없다는 것만으로 전체 탐색 완료를 보장하지 않는다. 이 통계는 API 공개 필드가 아니다.

**확정 비호환 판정** (`_pc_known_failures`) — 양쪽 값을 모두 알 때만 실패로 본다. 한쪽이라도 모르면 실패가 아니다.

| 축 | 규칙 |
|---|---|
| `socket` | CPU 소켓 == 메인보드 소켓 |
| `memory` | RAM 규격 == 메인보드 메모리 규격 |
| `motherboard_case` | 보드 크기 ≤ 케이스 지원 최대 크기 (ITX<mATX<ATX<EATX 위계) |
| `gpu_len` | GPU 길이 ≤ 케이스 허용 길이 |
| `cooler_height` | 쿨러 높이 ≤ 케이스 허용 높이 |
| `cooler_socket` | CPU 소켓 ∈ 쿨러 지원 소켓(약어 목록을 풀어서 비교) |
| `bios` | CPU 세대·계열이 보드 지원 계열 목록에 있음 (소켓이 이미 틀리면 중복으로 세지 않음) |
| `psu_form` | 파워 폼팩터가 케이스에 들어감 |
| `power` | 파워 용량 ≥ (CPU 전력 + GPU 전력) / 0.9. CPU는 최대전력 우선, 없으면 TDP. 두 전력값을 알 수 없으면 [2]의 `wattage_min` 사용 |
| `gpu_connector` | 파워가 GPU 보조전원 커넥터 종류·개수를 제공 |
| `psu_length`, `gpu_slots`, `radiator`, `ram_slots`, `m2` | 확장 열이 채워진 만큼만 판정 |

**`pc_compat_details` / `pc_link_check`** — 같은 규칙을 축별 상세로 낸다. 각 행은 `{axis, label, state: ok|unknown|fail|skipped, detail, missing_slots, inputs}`이다.

- `missing_slots`: 값이 없어 근사가 된 쪽 슬롯 → 재탐색 루프가 "무엇을 뺄지" 고를 때 쓴다.
- `inputs`: 비교에 쓴 `(slot, key, value)` → [3-C]가 출처 근거를 만들 때 쓴다.
- `pc_link_check`는 이를 `{"socket": "ok", "gpu_len": "ok (근사)", ...}` 모양으로 줄인 것이다. `BuildResult.link_check`에 들어가 [3-C]의 입력이 된다. 확장 축(`psu_length` 등)은 데이터가 없으면 아예 싣지 않는다(`_QUIET_WHEN_DATA_MISSING`).

전력 계산이 두 번 나오는 이유도 다르다. [2]의 `×1.5`는 후보를 모으기 전 용도별 **추정 전력으로 최소 파워 용량**을 정한다. [4]의 `/0.9`는 **선택한 CPU·GPU의 전력값으로 파워와 비교**한다. 정밀한 전체 시스템 소비전력 시뮬레이션이 아니며, CPU의 TDP와 최대전력도 같은 값이 아니다.

`unknown → "ok (근사)"`는 통과처럼 보이는 내부 표기지만 뜻은 “확인 못 함”이다. 또한 어댑터가 필요하거나 RAM·SSD가 낮은 속도로 동작하는 경우도 미확인 쟁점이 될 수 있다. 값이 없는 모든 확장 축이 감점에 들어가는 것은 아니므로, 신뢰도 100이라도 모든 물리 조건을 검사했다는 뜻은 아니다.

### 8.7 [3-C] 세트 검증

`stage3c_verify.verify_build`(실경로) — `link_check`를 **신뢰도 점수와 쟁점 목록**으로 바꾼다.

```
신뢰도 = max(0, 100 − Σ감점)        통과 = 신뢰도 ≥ CONFIDENCE_THRESHOLD(80)
```

| 상태 | 판정(judge) | 감점 | 문장 |
|---|---|---|---|
| `fail` (확정 비호환) | 위반 | 20 (`_FAIL_ISSUE_PENALTY`) | LLM 중립 문장. 판정어가 섞이면 1회 재생성, 그래도 섞이면 규칙 템플릿 |
| `ok (근사)` (값을 몰라 정밀 검사 못 함) | 확인 필요 | 6 | 코드가 쓰는 고정 문장("부품 스펙 데이터가 부족해 정확히 확인하지 못했습니다…") |
| 예산 `fail` | 위반 | 20 | |
| 사용률 > 110% | 초과 | 15 | 두 원인이 겹치면 한 건(축 `budget`, 35)으로 합친다 |

- **근거(evidence)**: `chosen`/`spec`/`rules`를 넘기면 `pc_compat_details`의 `inputs` × 후보 `provenance`로 "케이스 X — GPU 최대 길이 365mm (제조사 사양, 2026-08-14 확인)" 같은 **카탈로그 출처 근거**를 붙인다. 출처 URL이 없는 값은 근거를 만들지 않는다.
- **회색축(gray_axes)**: 근거가 0건인 쟁점 축 + "설명서·규격(RAG 미연결)" 등. 결정 0003에 따라 **사용자 문장에는 내보내지 않고** 내부 DTO·콘솔 로그에 남긴다. 전체 목록이 DB에 저장되는 것은 아니다.
- **LLM 문장 실패는 신뢰도에 영향을 주지 않는다.** 문장만 템플릿으로 바뀐다.
- 쟁점은 `engine.validation_result`에 저장될 때 감점 15 이상이면 `severity="warning"`, 아니면 `"info"`가 된다.

**신뢰도는 통계적 확률이 아니다.** 80이라는 문턱과 20·6이라는 감점은 현재 정책값이다. 실제 고장률·조립 성공률·추천 정확도로 검증된 수치가 아니다. `passed=True`도 “내부 재탐색 문턱 이상”이라는 뜻이며, 알려진 문제 0건 또는 구매 승인이라는 뜻은 아니다.

| 예 (다른 쟁점은 없다고 가정) | 내부 신뢰도 | `passed` | 읽는 법 |
|---|---:|---|---|
| 확인 필요 3건 | 100 − 18 = 82 | True | 미확인 항목이 남아도 루프 종료 |
| 확인 필요 4건 | 100 − 24 = 76 | False | 제외 가능한 후보가 있으면 재탐색 |
| 예산 105% 사용, `budget=fail` | 100 − 20 = 80 | True | 예산 위반은 남아 있으며 확정 API는 별도로 거절 |
| 예산 115% 사용, `budget=fail` | 100 − 35 = 65 | False | 예산만 문제라면 후보 제외 방식의 재탐색은 하지 않음 |

`judge`는 사람이 이해할 판정 종류, `penalty`는 집계할 숫자, `text`는 이를 설명할 문장이다. 이 셋을 나눈 덕분에 문장을 다시 생성해도 점수와 선택 결과는 바뀌지 않는다. [4]의 상태를 집계하므로 [3-C]를 **독립된 모델의 교차 검증**이라고 발표하지 않는다.

`verify_set`(데모)은 앞서 말했듯 시나리오 정답값을 주입한다.

### 8.8 재탐색 루프 (E1)

`research_loop.run_set_with_research(rank, spec, log, *, verify, choose_exclusion, base_exclude, max_rounds)`

```
exclude = base_exclude
for 라운드 in 1..3:
    build = [4](rank, exclude)
    verification = verify(build)
    기록 보관
    통과면 종료(stop_reason="passed")
    3라운드면 종료("max_rounds_exhausted")
    choice = choose_exclusion(build, verification)
    없으면 종료("no_researchable_exclusion" — 재탐색으로 개선 불가)
    exclude += choice
채택 = 신뢰도가 가장 높은 라운드 (동점이면 앞 라운드)
```

**왜 이렇게 설계했나** — [4]가 이미 예산·확정 비호환을 고려하므로, 재탐색은 스펙이 더 잘 알려진 대안으로 **“확인 필요”를 줄이는 시도**에 집중한다. 단순히 후보를 제거해도 예산을 늘리거나 새 상품을 추가할 수는 없다. 단, 탐색에 상한이 있으므로 남은 `fail`을 “전체 카탈로그에 호환 세트가 절대 없음”의 증명으로 해석하면 안 된다.

**실경로의 제외 대상 선택** (`rule_based_exclusion`)

1. `set`/`budget`/`예산` 축과 `위반` 판정은 대상이 아니다.
2. "확인 필요" 쟁점을 감점 큰 순으로 보고, `pc_compat_details`의 `missing_slots`에서 뺄 슬롯을 고른다. 그 슬롯에서 **이번에 뽑힌 후보**를 뺀다.
3. 업그레이드 유지 부품(`spec.owned`)과 이미 가진 부품(`base_exclude`)은 뺄 수 없다.
4. **CPU·GPU(`impact_slots`)는 빼지 않는다.** 데이터가 없다는 이유만으로 빼면 성능이 눈에 띄게 낮은 구성이 "확인 필요 건수가 줄었다"는 이유로 채택될 수 있다.

**채택 규칙이 보장하는 것**: 시도한 라운드 중 **내부 신뢰도가 가장 높은 것**을 고르고, 동점이면 앞 라운드를 유지한다. 따라서 채택 신뢰도는 첫 라운드보다 낮아지지 않는다. 가격·성능·후보 점수 합이 나빠지지 않는다는 보장은 없다. CPU·GPU도 직접 제외하지 않을 뿐, 다른 부품이 바뀌면서 조합 탐색 결과로 함께 바뀔 수 있다.

최대 3라운드는 **첫 구성 1회 + 재구성 최대 2회**다. 매번 [2]·[3-A]·[3-B]를 다시 돌리거나 외부 상품을 더 수집하지 않는다. 같은 순위 풀에서 제외 목록을 누적해 [4]부터 다시 실행한다. 제외 전략을 주지 않은 호출은 `no_exclusion_strategy`로 종료한다.

**출력**: 채택 라운드의 `VerificationTarget.rounds`, 라운드별 `transcript`(`{round, excluded, issue_count, issues, stop_reason}`). 2라운드 이상 돌았으면 `research_trace_detail`이 "확인 필요 4건 → 쿨러 'A'(…)를 빼고 다시 구성 → 확인 필요 1건 구성 채택" 같은 문장을 만들어 `reasoning_log`에 넣는다. **신뢰도 숫자는 넣지 않는다.**

교체·수량 변경 뒤의 재검증(`reverify_set`)에는 루프를 **붙이지 않는다.** 사용자가 직접 고른 구성을 엔진이 바꾸면 안 된다.

### 8.9 [5] 설명 생성

`stage5_explain.run(build, verification, log, rank=..., conditions=..., extra_caveats=...)`

1. **기여도** (`_contribution`, 계산) — 뽑힌 부품의 `breakdown` × `rank.weights_used`를 가격/성능/호환성 3축(`밸런스`·`호환여유` → 호환성)으로 모아 100으로 정규화한다. 음수 축 값은 0으로 본다. 소수 부분이 큰 축부터 1씩 더하는 최대 나머지법으로 합을 100에 맞춘다. 리뷰·소음·감점은 이 3축 비율에 넣지 않는다. `rank`가 없으면 **빈 dict**를 낸다.
2. **문장** (`_llm_draft`, 최대 2회 시도) — 조건·부품명·가격·순위·쟁점을 코드가 입력으로 주고, LLM은 `headline`·`summary`·`items[].reason`만 쓴다. 신뢰도 숫자와 회색축은 입력에서 제외한다. 금지어(`_BANNED_IN_DRAFT`: “강력”, “최고”, “완벽”, “안정성”…)가 headline·summary에 있으면 초안 전체를 버리고 재시도한다. 특정 슬롯 reason에만 있으면(또는 다른 슬롯 부품명이 섞이면) **그 슬롯만** 규칙 템플릿으로 바꾼다. 호출이 실패하면 전체를 규칙 템플릿으로 대체한다.
3. **리뷰 관측 줄** (`_review_line`) — [3-B]가 후보에 남긴 `REVIEW_OBS:` 플래그를 슬롯별 한 줄과 근거로 바꾼다. 관측값이 정책 문턱을 초과했다는 플래그가 있으면 "검토 권장"과 "상품 단위 신호이며 개별 리뷰의 진위가 아닙니다" 주의 문구를 붙인다. 관측 플래그가 없으면 "관측 없음", 관측은 있지만 문턱 초과가 없으면 "특이 없음"으로 표시하며, 이 두 경우에는 해당 리뷰 주의 문구를 붙이지 않는다.
4. **caveats는 코드가 소유한다** — 잠정 게임 기준, 업그레이드 미확인 안내, 리뷰 주의 등은 코드가 만든 문장이다. LLM이 같은 내용을 다시 쓰게 하지 않는다.

> `rank=`를 빼고 호출하면 리뷰 관측이 전 슬롯 "없음"이 되는데, 기본값이 `None`이라 **조용히** 그렇게 된다. 항상 넘길 것.

**확장 탐색의 현재 한계:** 리뷰 플래그를 찾는 `_ranked_flags`는 `rank.slots[slot]["ranked"]`(top-N)만 조회한다. 따라서 `rank`를 넘겼더라도 [4]가 top-N 밖의 `pool` 후보를 선택하면, 그 후보에 리뷰 플래그가 있어도 [5]는 "관측 없음"으로 표시하고 리뷰 근거·주의 문구도 빠진다. 기여도 계산은 `pool`까지 조회하므로 두 기능의 조회 범위가 다르다. "관측 없음"을 원본 리뷰 데이터가 없다는 뜻으로 단정하지 말고 선택 상품의 `product_key`가 어느 목록에 있는지 확인한다.

기여도에서 “성능 57%”는 실측 성능 향상률도, 모든 선택 원인의 57%라는 인과 설명도 아니다. 선택된 부품의 **일부 가중 점수를 묶어 보여 준 비율**이다. `BuildResult.alternatives`는 대체 상품 목록이 아니라 탐색 통계라는 점도 함께 구분한다.

문장 검사는 잘못된 출력 일부를 막는 장치다. 모든 수치·주장을 원천 데이터와 대조하는 완전한 사실 검증기는 아니다. 규칙 템플릿조차 현재는 “조건 충족”이라는 정형 문구를 쓰므로, §8.4의 Fail 후보 복구 상황에서는 문장만 믿지 말고 판정값을 확인해야 한다.

### 8.10 근거 검색(RAG)은 어디까지 연결되어 있나

RAG(Retrieval-Augmented Generation)는 관련 문서를 찾아 그 내용을 답변에 활용하는 방식이다. **문장을 검색했다는 사실만으로 상품의 호환성이 검증되는 것은 아니다.** 현재 코드에는 목적이 다른 세 경로가 있다.

| 경로 | 실제 하는 일 | 추천 선택·판정에 미치는 영향 |
|---|---|---|
| 데모 `evidence_search` | 시나리오의 `corpus`를 분야·축 이름으로 필터링 | 쟁점 문장에 예시 근거를 붙임. 신뢰도는 시나리오 주입값이며 인터넷 검색이 아님 |
| 실경로 `verify_build` | 비교에 사용한 스펙값과 `provenance`를 연결 | 쟁점에 카탈로그 출처를 붙임. 매뉴얼을 검색해 새로운 호환 사실을 판정하지 않음 |
| 실경로 `search_care_guide` | `data/pc_care_guides.json`에서 부품 종류에 맞는 사용 안내 검색 | 선택 후 “구매 전 확인”을 보충. 점수·호환 판정은 바꾸지 않음 |

사용 안내 검색은 먼저 슬롯에 맞는 문서로 범위를 제한하고, 질문과 문서를 벡터(숫자 배열)로 바꿔 코사인 유사도(방향이 비슷한 정도) 순으로 고른다. 문서가 작아 별도 벡터 DB 대신 메모리에서 계산한다. 실호출 조건에서는 임베딩 API를 사용하고, `MOCK_MODE=1` 또는 키가 없으면 단어 해시 기반 모의 벡터를 사용한다. 모의 검색 결과를 의미 검색 품질의 증거로 제시하지 않는다.

카탈로그 출처 근거를 공개 응답으로 바꾸는 `verification_issue_payload`는 구현되어 있지만 조회 API에 아직 연결되지 않았다. 현재는 저장된 근거와 화면에서 보이는 근거의 범위도 다르다(§10.3).

## 9. 한 요청을 숫자로 따라가기

### 9.1 처음부터 끝까지: 150만원 QHD 게임용 PC

이 절의 GPU A·B와 케이스 C·D는 **계산을 설명하기 위한 가상 상품**이다. 실제 판매가·벤치마크·실측 결과가 아니다. 규칙과 숫자의 연결을 이해한 뒤 §9.2의 데모 또는 §15.2의 실제 검증 함수를 실행한다.

**① 조건 → 요구사양**

사용자가 신규 조립, 게임, QHD, 150만원, 가성비를 지정했다면 조건은 다음처럼 전달된다.

```python
values = {
    "category": "computer", "mode": "build", "purpose": "game",
    "resolution": "QHD_165", "budget_max": 1_500_000, "priority": "value",
}
```

게임 제목은 이 예제에 없다. [2]는 GPU 등급 7 이상·VRAM 12GB 이상, CPU 등급 5 이상, RAM 16GB 이상 등을 만든다. GPU 가격 점수의 기준액은 150만원 × 0.40 = **60만원**이다. 가성비 가중치는 가격 0.50, 성능 0.15, 밸런스 0.10, 리뷰 0.20, 호환여유 0.05다.

**② 후보 → 하드 필터**

| GPU 후보 | 가격 | 등급 | VRAM | 전력 | 길이 | [3-A] 판정 |
|---|---:|---:|---:|---:|---:|---|
| A | 420,000원 | 7 | 12GB | 210W | 330mm | Pass |
| B | 480,000원 | 8 | 12GB | 237W | 250mm | Pass |
| E | 300,000원 | 6 | 12GB | 150W | 250mm | Fail: 등급 미달 |

케이스에 들어가는지는 아직 판단하지 않는다. GPU 자체의 최소 요구만 검사한 결과다. VRAM이 비어 있는 후보가 더 있다면 Pending이며, Pass가 2개라서 함께 순위 계산에 남는다.

**③ 필터 통과 후보 → 점수**

A·B에는 리뷰 관측이 없어 리뷰축은 0.5라고 가정한다. 두 후보 모두 필요한 길이 정보가 있고, 두께 정보는 전 후보에 없어 결손 감점 대상에서 빠진다고 가정한다. 다른 Pending·결손 감점은 없다.

| 축 | A | B |
|---|---:|---:|
| 가격 | 1 − 420,000/600,000 = 0.30 | 1 − 480,000/600,000 = 0.20 |
| 성능 | 7/10 = 0.70 | 8/10 = 0.80 |
| 밸런스 (이상 등급 7.5) | 1 − 0.5/4 = 0.875 | 1 − 0.5/4 = 0.875 |
| 리뷰 | 0.50 | 0.50 |
| 호환여유 (전력 기준 300W) | 1 − 210/300 = 0.30 | 1 − 237/300 = 0.21 |
| 가중합 | 0.4575 → **0.458** | 0.418 → **0.418** |

A의 계산을 풀면 `0.50×0.30 + 0.15×0.70 + 0.10×0.875 + 0.20×0.50 + 0.05×0.30`이다. B가 등급은 높지만, 이 요청은 가성비 우선이어서 저렴하고 전력을 덜 쓰는 A가 1위다. 우선순위를 성능으로 바꾸면 가중치가 달라져 순위도 바뀔 수 있다.

**④ 슬롯 1위 → 세트 선택**

나머지 6종은 동일한 부품으로 고정했고 합계가 950,000원이라고 가정한다. 케이스 C는 60,000원·GPU 길이 한도 300mm·점수 0.600, D는 120,000원·350mm·점수 0.400인 예시 후보다. 케이스 점수는 조합 비교를 위한 가정값이며 여기서 실제 카탈로그로 계산한 값은 아니다. GPU 길이 외 호환 제약은 모두 충족한다고 가정한다.

| 조합 | 전체 금액 | GPU 길이 | GPU + 케이스 점수 합 | [4] 선택 가능 여부 |
|---|---:|---|---:|---|
| A + C | 1,430,000원 | 330 > 300mm | 1.058 | 길이 비호환으로 제외 |
| A + D | 1,490,000원 | 330 ≤ 350mm | 0.858 | 가능 |
| B + C | 1,490,000원 | 250 ≤ 300mm | **1.018** | **가능한 조합 중 최고점** |
| B + D | 1,550,000원 | 250 ≤ 350mm | 0.818 | 예산 초과로 제외 |

나머지 6종의 점수는 모든 조합에 똑같이 더해지므로 비교에서 생략했다. 결과는 **GPU 2위 B + 케이스 1위 C**다. 이것이 슬롯별 1위만 고르는 방식과 세트 탐색의 차이다. A를 좋아한다는 사용자 선호도와 A가 C에 들어가지 않는다는 물리 조건은 별개다.

**⑤ 세트 → 검증 → 설명**

다른 기본 검사 4개에서 스펙이 부족하다고 가정하면 신뢰도는 `100 − 6×4 = 76`이다. 실경로 루프는 그중 교체 가능한 비핵심 슬롯의 현재 후보를 제외하고 다시 세트를 찾는다. 대안 세트가 확인 필요 2건이면 88로 통과한다. 반대로 2·3라운드가 모두 76 이하라면 처음 구성을 유지한다. 이는 채택 규칙을 설명하기 위한 별도 가정이며 위 네 조합에서 자동으로 도출되는 수치는 아니다.

마지막 [5]는 선택된 부품·가격·쟁점을 입력받아 설명한다. 발표자는 “GPU 단품 1위보다, 예산과 케이스 길이를 함께 만족하는 조합의 점수 합이 높아 B를 골랐다”고 설명할 수 있어야 한다. 실제 생성 문장이 이 상세 비교를 항상 그대로 말해 준다는 뜻은 아니다.

### 9.2 데모로 재탐색 동작 확인하기

저장소 루트에서 다음을 실행한다. §14.1의 의존성 설치가 필요하다.

```bash
MOCK_MODE=1 CATALOG_SOURCE=mock UV_CACHE_DIR=/tmp/uv-cache \
  uv run python main.py computer_research
```

이 시나리오에는 `priority`가 없어서 §9.1의 가성비 가중치가 아니라 **기본 가중치**가 적용된다. 합성 카탈로그·보정 CSV·리뷰 산출물 유무에 따라 부품·가격·방문 노드 수는 달라질 수 있다. 다음은 시나리오에 고정된 핵심 흐름이다.

```text
[1] 시나리오의 조건 주입: 게임, QHD, 150만원, 롤·오버워치
[2] 해상도·게임 표로 요구사양 계산
[3-A] 후보별 Pass / Fail / Pending
[3-B] 점수 계산과 top-N
[4] 라운드 1 세트 탐색
[3-C] 시나리오 신뢰도 72 → 기준 미달
      시나리오가 지정한 GPU 후보 제외
[4] 라운드 2 세트 탐색
[3-C] 시나리오 신뢰도 86 → 통과, 라운드 2 채택
[5] 설명 생성 (MOCK_MODE에서는 규칙 템플릿)
```

72·86은 `data/scenarios/computer_research.json`의 정답값이다. **2라운드 쟁점 감점은 4인데 신뢰도는 86이다.** `100−4=96`으로 계산하지 않고 별도 필드를 그대로 읽기 때문이다. 이 데모는 “재탐색 배선이 연결되어 있다”는 시연이며, 실제 신뢰도 계산이나 추천 품질 개선을 입증하는 실험이 아니다. 시나리오의 `example.com` 근거 URL도 외부 검증 자료가 아니다.

### 9.3 실제 규칙 검증 결과 읽기

§15.2는 같은 엔진의 `verify_build`·`rule_based_exclusion`을 사용한다. 여기서는 신뢰도가 실제 `100−감점`으로 계산된다.

- 합성 후보는 스펙 결손이 많아 확인 필요 쟁점과 재탐색이 발생하기 쉽다. 몇 라운드를 시도했는지와 어느 라운드를 채택했는지를 따로 본다.
- DB 후보는 데이터 충실도·리뷰 관측·가격에 따라 결과가 달라진다. 특정 예산에서 항상 80점 또는 항상 1라운드 통과라고 기대하지 않는다.
- “신뢰도 80, 예산 위반 1건”이라면 내부 문턱을 통과한 것이며, 예산을 지켰다는 뜻은 아니다.
- 보고할 값은 조건, 데이터 출처, 정책 버전, 선택 부품·금액, 호환 상태, 쟁점, 시도/채택 라운드다. 품질 개선을 주장하려면 비교 조건과 실제 결과를 함께 남긴다.

## 10. 실서비스 경로: API → 백그라운드 실행 → 저장 → 조회

### 10.1 요청 수명

```
POST /session/{id}/recommend
  └ start_recommendation     필수 조건 확인, 실행 중 중복 방지, run 행 생성 → 202 {run_id, status: running}
  └ BackgroundTasks: execute_recommendation(revision_id, run_id)
       ┌ 트랜잭션 1 ──────────────────────────────────────────────┐
       │ 조건 로드 → Slots → [2] → 카탈로그 로드 → [3-A] → [3-B]   │
       │ → run_set_with_research(verify_build, rule_based_exclusion)│
       │ → 후보 저장(add_candidate, reason=None → pending)          │
       │ → 검증 저장(_store_validations) → run 완료                 │
       └──────────────────────────── 커밋: 부품표가 먼저 보인다 ──┘
       ┌ 트랜잭션 2 ──────────────────────────────────────────────┐
       │ [5] 설명(LLM) → 부품별 reason 저장                         │
       │ → 부품별 "구매 전 확인" 가이드 검색·저장                   │
       │ → reasoning_log(trace) + 설명 문장 저장                    │
       └── 실패해도 부품표는 done 그대로, 문장 상태만 failed ─────┘
GET /session/{id}/result   (폴링)
  └ get_stored_result        저장된 결과로 응답 조립 + 현재 구성의 compat_checks 계산 (추천 탐색 재실행 없음)
```

**트랜잭션을 둘로 나눈 이유** — 트랜잭션은 여러 DB 변경을 한 번에 반영하거나 취소하는 단위이며, 커밋은 그 변경을 확정하는 일이다. `get_conn()`은 `with` 블록 전체를 한 트랜잭션으로 묶는다. [5]의 문장 생성을 같은 블록에 두면 부품표가 [5]가 끝날 때까지 조회되지 않는다. 현재는 **부품표·검증 저장을 먼저 커밋**해서 설명이 `pending`이어도 부품을 먼저 보여 준다. 단, [3-C]의 쟁점 문장화 LLM은 첫 트랜잭션에 있으므로 모든 LLM 대기가 제거된 구조는 아니다.

HTTP 202는 “접수됨”이지 “추천 완료”가 아니다. 브라우저는 GET을 반복 호출하는 **폴링**으로 상태를 확인한다. DB의 `completed`는 응답에서 `done`으로 바뀐다. `done`은 계산 결과 저장 완료이며, 예산·호환성에 문제가 없다는 뜻은 아니다. `BackgroundTasks`는 API 프로세스 안에서 실행되므로 독립 작업 큐처럼 프로세스 종료 후 자동 재시작을 보장하지 않는다.

**실패 처리** — 트랜잭션 1이 실패하면 별도 커넥션으로 run을 `failed`로 바꾼다(`running`으로 영원히 남지 않게). 트랜잭션 2가 실패하면 문장 필드만 `failed`로 둔다. 문장 필드는 `{"status": "pending"|"ready"|"failed", "text": ...}` 모양이다.

### 10.2 저장 위치 (`engine` 스키마)

| 테이블 | 내용 |
|---|---|
| `engine.recommendation_run` | 실행 1건. `status`(queued/running/completed/failed/stale), 입력 스냅샷·해시, `reasoning_log`(jsonb), `explanation_*` |
| `engine.recommendation_candidate` | 슬롯별 선택 후보. `variant_id`, `offer_observation_id`(PC는 **필수** — 없으면 예외), `score`, `reason`/`reason_status`, `checks`/`checks_status`, `selected`, `qty`, `timing` |
| `engine.validation_result` | 쟁점 1건 = 1행. `rule_key`(축), `severity`, `message`, `measured_values`(jsonb: penalty, confidence, round, evidence) |

`measured_values`는 jsonb라 새 값(라운드, 근거 등)을 마이그레이션 없이 넣을 수 있다.

### 10.3 조회 조립과 공개 필드

`get_stored_result`가 만드는 응답 중 엔진이 채우는 곳:

- `items[].checks` — "구매 전 확인". 가이드 문장 + 그 슬롯에 걸린 쟁점(`AXIS_SLOTS`로 축→슬롯 매핑) + 교체 여부.
- `verification.issues[].text` — 쟁점 문장.
- `reasoning_log` — `list[dict]`로 이미 공개돼 있어, 단계(예: "세트 재검토")를 추가해도 스키마가 바뀌지 않는다.

`RecommendResultOut`(pydantic)은 **모르는 키를 조용히 버린다.** 엔진이 새 dict를 결과에 얹어도 `schemas.py`에 필드가 없으면 응답에 나가지 않는다.

내부 결과를 설명할 때 “저장되어 있다”와 “현재 화면에서 볼 수 있다”를 구분한다.

| 정보 | 내부 계산 | DB/API의 현재 범위 |
|---|---|---|
| 선택 부품·가격·점수 | `BuildResult.items` | DB 저장. 부품·가격은 API 응답, 내부 순위 점수는 별도 공개 필드 없음 |
| 검증 쟁점·감점·출처 근거 | `VerificationResult` | 쟁점별 DB 저장. API는 축·심각도·문장만 내며 근거 목록 노출은 미연결 |
| 신뢰도 | `VerificationTarget.confidence` | DB 쟁점의 `measured_values`에 저장. 조회 응답의 `verification.confidence`도 유지하지만 사용자 설명 문장에는 넣지 않음 |
| 회색축·전체 라운드 기록 | 내부 DTO·로그 | 전체가 DB/API에 저장·공개되는 구조는 아님. 채택 라운드와 재탐색 요약 일부만 저장 |
| 탐색 통계·축별 기여도 | `BuildResult.alternatives`, `Explanation.contribution` | 내부 DTO·데모 로그용, 현재 조회 응답에 별도 필드 없음 |
| `reasoning_log` | 서비스가 만든 단계별 요약 | DB 저장·API 공개. LLM의 내부 사고 과정이 아니라 규칙·선택 사실 요약 |

GET은 추천 탐색이나 설명 생성을 다시 하지 않는다. 다만 `compat_checks` 상세를 조립할 때 현재 카탈로그와 선택 구성을 읽어 호환 검사를 다시 계산한다. “저장된 결과 JSON만 그대로 돌려준다”는 설명도 정확하지 않다.

### 10.4 교체 후 재검증

`PATCH /items/{id}`(선택 해제·수량), `POST /items/{id}/swap`(교체) 뒤에는 `reverify_set`이 **지금 선택된 부품으로** `pc_link_check` → `verify_build`를 다시 돌려 검증 행을 교체한다. 순위·설명은 다시 만들지 않고, 재탐색 루프도 돌리지 않는다.

### 10.5 API로 직접 돌려 보기

§14.1에서 시드까지 준비한 뒤 서버를 띄운다. 아래는 **수동 개발 시연**이며 개발 DB `truefit`에 세션·추천 기록을 저장한다. 자동 테스트는 §14.3의 일회용 테스트 DB를 사용한다.

```bash
DATABASE_URL=postgresql://truefit:truefit@localhost:5432/truefit \
  MOCK_MODE=1 CONDITIONS_AGENT=0 RESULT_AGENT=0 UV_CACHE_DIR=/tmp/uv-cache \
  uv run uvicorn src.api:app --port 8000
```

다른 Bash 터미널에서 신규 조립 한 건을 요청한다. 게스트 쿠키(`truefit_guest`)로 소유자를 확인하므로 **쿠키 저장소(`-c`/`-b`)를 꼭 쓴다.** 아래 `/slot` 호출은 개발 시연용 직접 입력이다.

```bash
truefit_base=http://localhost:8000
truefit_cookie_file=$(mktemp /tmp/truefit-guide-cookie.XXXXXX)
truefit_curl=(curl --silent --show-error --fail-with-body
  -c "$truefit_cookie_file" -b "$truefit_cookie_file" -H 'Content-Type: application/json')
truefit_list_id=$("${truefit_curl[@]}" -X POST "$truefit_base/session" |
  python3 -c 'import sys,json; print(json.load(sys.stdin)["list_id"])')
truefit_session="$truefit_base/session/$truefit_list_id"
"${truefit_curl[@]}" -X POST "$truefit_session/category" -d '{"category":"computer","mode":"build"}'
"${truefit_curl[@]}" -X PATCH "$truefit_session/slot" -d '{"field":"purpose","value":"game"}'
"${truefit_curl[@]}" -X PATCH "$truefit_session/slot" -d '{"field":"budget_max","value":1500000}'
"${truefit_curl[@]}" -X PATCH "$truefit_session/slot" -d '{"field":"priority","value":"value"}'
"${truefit_curl[@]}" -X PATCH "$truefit_session/slot" -d '{"field":"resolution","value":"QHD_165"}'
"${truefit_curl[@]}" "$truefit_session" | python3 -m json.tool  # can_recommend: true 확인
"${truefit_curl[@]}" -X POST "$truefit_session/recommend" -d '{}'  # run_id, running 응답
"${truefit_curl[@]}" "$truefit_session/result" | python3 -m json.tool
```

마지막 GET을 잠시 간격을 두고 반복해 `status: done` 또는 `failed`를 확인한다. `done`이어도 `explanation.status`가 `pending`일 수 있으므로 설명 상태도 별도로 본다. `failed`면 반복을 멈추고 오류·서버 로그를 확인한다. 부품 금액은 `totals.selected_price`, 예산 초과는 `totals.over_budget`, 호환은 `compat_checks`와 `verification.issues`를 본다.

자유 텍스트 입력은 `POST /session/{list_id}/message`에 `{"text":"150만원으로 게임용"}`, 칩 답변은 `POST /session/{list_id}/answer`에 `{"question_id":"q_priority","selected":["value"]}`를 보낸다.

전체 여정(신규 조립·업그레이드·경계 상황)을 자동 점검하려면 DB 서버를 켜고 다음 테스트를 실행한다.

```bash
PYTHONPATH=. UV_CACHE_DIR=/tmp/uv-cache TRUEFIT_REQUIRE_TEST_DB=1 \
  uv run pytest -q tests/test_pipeline_http_smoke.py
```

위 테스트는 자동으로 일회용 DB를 준비한다(§14.3). `scripts/e2e_smoke.py`를 직접 실행할 때는 자동 DB 생성이 없으므로, 이름에 `test`가 들어가는 별도 DB에 마이그레이션·시드를 먼저 적용하고 `TEST_DATABASE_URL`을 지정해야 한다.

## 11. 업그레이드 모드

`mode=upgrade`면 사용자가 고른 부품(`upgrade_parts`)만 견적을 내고, 나머지는 **이미 가진 부품**으로 호환 검사에만 쓴다.

- `owned_parts.owned_for_conditions` — 사용자가 적은 현재 사양 글("i5-13600K", "DDR4 16GB")을 카탈로그와 매칭해 `spec.owned[slot] = {name, specs}`를 만든다. **카탈로그 이름의 의미 있는 토큰이 전부 사용자 글 안에 있어야** 대응으로 본다("5600"은 "5600X"가 아니다). 모호하면 후보들이 모두 같은 값만 남기고, 근거가 없으면 비운다.
- `owned_platform`/`owned_ram_type`/`owned_psu_w` 칩 답변도 스펙으로 쓴다. 필요한 질문에는 답해야 하며, "모르겠어요"(`"unknown"`)도 답으로 인정한다. 그 경우 추천은 진행하지만 "확인 못 함"으로 안내한다. **답을 생략하면 추천이 막히는 것과 구분한다.**
- 지금 쓰는 CPU·GPU보다 낮은 등급은 업그레이드가 아니므로 그 등급을 `perf_tier_min` 하한으로 건다. 같은 제품은 `base_exclude`로 다시 추천하지 않는다.
- [4]의 호환 판정(`_pc_known_failures`)은 견적에 없는 슬롯의 값을 `spec.owned`에서 읽는다. GPU와 파워 중 하나만 견적에 들어가면 GPU 제조사 권장 파워를 유지 파워 용량과 비교한다.

### 추천 전에 추가로 필요한 답변

`computer.yaml`의 `question_sets[].ask_when`과 `session_service._required_keys`가 다음 조건을 적용한다. `mode=build`에는 이 질문들이 필수가 아니다.

| `upgrade_parts`에 하나라도 포함되면 | 조건부 필수 필드 / 질문 ID | 질문을 생략하는 현재 사양 입력 |
|---|---|---|
| CPU·메인보드·쿨러 | `owned_platform` / `q_owned_platform` | `current_specs`에 CPU 또는 메인보드 값이 있음 |
| RAM·메인보드 | `owned_ram_type` / `q_owned_ram` | `current_specs`에 RAM 값이 있음 |
| GPU | `owned_psu_w` / `q_owned_psu` | `current_specs`에 파워 값이 있음 |

여러 행이 해당하면 모두 충족해야 한다. 예를 들어 메인보드 교체는 플랫폼과 RAM 종류를 둘 다 묻는다. 저장장치·파워·케이스만 교체하면 이 세 질문은 추가되지 않는다. 현재 사양은 `{"파워": "650W"}`처럼 슬롯 이름을 키로 하는 dict이며, 질문 생략은 해당 값의 존재 여부로 판단한다. **사양 글이 있다는 것과 엔진이 그 글에서 정확한 스펙을 추론했다는 것은 다르다.**

공통 필수값과 `upgrade_parts=["GPU"]`를 채웠다고 가정하면:

- 현재 파워 사양이 없을 때, `owned_psu_w`를 생략하거나 `None`으로 두면 `compute_missing`에 `owned_psu_w`가 남고, 추천 요청은 `conditions_incomplete`가 된다.
- `owned_psu_w="unknown"`이면 답변 완료로 인정해 추천을 진행하되, 파워 정보는 미확인으로 남긴다. 칩 API 예시는 `POST /session/{list_id}/answer`에 `{"question_id":"q_owned_psu","selected":["unknown"]}`이다.
- `current_specs={"파워":"650W"}`가 있으면 파워 질문을 생략한다. 직접 용량 칩을 답할 때 값은 `"450"`·`"500"`·`"700"`·`"900"`처럼 **문자열 구간 하한**이다(§13.2의 조건 계약).

관련 테스트: `test_upgrade_*.py`, `test_owned_inference.py`, `test_owned_parts_preview.py`.

예를 들어 “GPU만 80만원 안에서 교체, 나머지 부품 유지”라면 `targets`에는 GPU만 남고, GPU의 배분 비율은 1.0이 된다. 유지 파워·케이스는 `owned`에 들어가 호환 검사에만 쓰며 구매 총액에는 넣지 않는다. 유지 파워 용량이 없으면 확인 필요로 남긴다. 견적에서 빠진 유지 부품끼리의 모든 상태를 새로 진단하는 기능은 아니다.

현재 등급을 알면 하한을 지키려 하지만, 같은 등급의 다른 상품도 후보가 될 수 있어 실측 성능 향상이 보장되지는 않는다. [3-A]의 Fail 후보 복구 예외도 있으므로 업그레이드 결과는 `perf_tier_min`과 최종 선택을 함께 확인한다.

## 12. 주변기기 하위 엔진

모니터·키보드·마우스·스피커는 **컴퓨터 요청의 부속 결과**다. 독립 카테고리가 아니다(`Category`는 `computer` 하나).

### 12.1 현재 상태 (중요)

| 항목 | 상태 |
|---|---|
| 엔진 계산 | **구현됨** — `peripheral_select.run_peripherals`. 아래 데이터·연결 한계는 남아 있음 |
| 데모 경로 | 조건에 `peripherals`가 있을 때만 PC 분기 뒤에 돈다. 현재 데모 시나리오 중 이 조건을 가진 것은 없다 |
| 실경로(`execute_recommendation`) | **미연결** — 저장 위치 결정(R-7) 뒤에 연결한다. 저장할 곳 없이 연결하면 계산 결과가 버려진다 |
| API 응답 | **미노출** — 응답 필드(R-6)와 대화 조건 입력(R-8) 합의 전 |
| 결과 가공 | `peripheral_payload.peripheral_payload(result)`가 공개 계약 모양 dict를 만든다(순수 함수) |

### 12.2 왜 PC 세트에 넣지 않았나

- 그래픽카드 출력 단자 데이터가 없어(R-1) 세트 제약을 걸면 전부 Pending이 된다.
- 9번째 슬롯으로 넣으면 프론트의 8슬롯 고정 화면과 `offer_observation_id` 필수 저장 경로에 막힌다. 주변기기 가격은 출처·관측일을 모르는 **참고가**(`peripheral_price_snapshot`)뿐이다.
- 그래서 **분리 블록 + 모니터↔PC 교차 검사**로 간다. 주변기기 가격은 PC 총액에 **합산하지 않는다.**

### 12.3 흐름

```
values.peripherals = ["monitor", "mouse", ...]
 [2]  build_requirements        종류별 hard(모니터만)·soft 선호 (config/peripherals.yaml requirements)
 [3-A] filter_candidates        hard 조건 Fail만 제외. 0건이면 status="empty" + 이유 (조건 완화 없음)
 [3-B] rank_candidates          가격(종류 중앙값 대비) · 선호적합 · 데이터충실 · 리뷰(가중치 항상 0)
 조합  choose                   예산 없으면 종류별 1위. peripheral_budget_max 있으면 top-5 곱 전수 탐색
 교차  peripheral_cross         모니터 ↔ PC: 해상도 등급 / GPU 단자·대역폭 / USB-C 전용 입력
 [3-C] verify_per_item          품목마다 신뢰도(같은 감점식). PC 세트 신뢰도에는 영향 없음
 가공  peripheral_payload       items[{product, price, price_note, requirement, checks, reason, alternatives, guide}]
```

**모니터 하드 조건** — PC 목표 해상도와 **등급 일치**(이상이 아님). GPU 등급이 그 해상도를 목표로 잡혔기 때문이다. `FHD_144 → FHD·144Hz 이상`, `QHD_165 → QHD·165Hz 이상`, `4K → UHD·60Hz 이상`(게임이면 120Hz 이상). 주어진 카탈로그에서 통과 후보가 0건이면 “맞는 모니터 없음”을 반환한다. 0건인지 여부는 데이터 버전에 따라 달라지므로 고정된 제품 특성처럼 발표하지 않는다.

**교차 검사 결과** — 현재 PC DB 로더는 그래픽카드 출력 단자 데이터를 제공하지 않으므로, 선택된 모니터를 해당 GPU와 비교하면 `monitor_gpu_port`가 “확인 필요”가 된다. 후보 `specs`에 `hdmi_version`/`dp_version`/포트 수 등 필요한 값이 들어오면 기존 검사 코드를 사용할 수 있다. 단, 실제 데이터 수집·컬럼 매핑 작업은 필요하다. 단자 버전별 최대 주사율 표(`verify.port_modes`)는 **잠정값**이며 실측 화면 출력이나 게임 FPS를 보장하지 않는다.

주변기기 예산 안 조합을 못 찾으면 top-5 안의 최저가 조합과 `over_budget` 표시를 반환한다. 모든 종류에서 아무것도 고르지 못했으면 `empty`, 일부라도 고르면 `ready`이므로 `ready`가 “요청한 종류가 모두 있음”을 뜻하지는 않는다. 종류별 결과도 확인한다. 사용 안내 문서가 없는 주변기기는 PC용 가이드를 대신 붙이지 않는다.

**새 주변기기 규칙은 YAML 선언**으로 추가한다(`{key, op, value}` 형식, `spec_rules.py`가 평가). 새 종류를 파이썬 분기로 늘리지 않는 것이 설계 목표다.

## 14. 개발 환경과 테스트

### 14.1 처음 한 번

모든 명령은 저장소 루트에서 실행한다. Python 3.11, `uv`, Docker Compose를 준비한다. `uv`는 프로젝트의 파이썬 환경·의존성을 관리하고, Compose는 로컬 DB 컨테이너를 실행한다.

```bash
UV_CACHE_DIR=/tmp/uv-cache uv sync --group test  # HTTP 테스트용 httpx 포함
test -f .env || cp .env.example .env            # 기존 설정은 보존
```

Git에 없는 데이터 파일(팀에서 받아 이 경로에 둔다):

| 경로 | 없으면 |
|---|---|
| `data/parts_list_modify.xlsx` | PC 카탈로그 시드 실패 → 추천할 후보가 없다 |
| `data/peripherals/{mouse,monitor,speaker,keyboard}_processed.csv` | 주변기기 시드 실패 |
| `data/amazon23/pcparts_product_risk.json` | 추천은 되지만 리뷰축이 꺼진 채로 계산된다(결과가 달라질 수 있다) |

엑셀 1개와 주변기기 CSV 4개를 먼저 확인한다. 하나라도 없으면 DB 테스트 준비 실패로 취급하며, 누락을 건너뛰고 완료로 보고하지 않는다. 리뷰 산출물은 별도 선택 입력이다.

```bash
docker compose up -d db
# 수동 개발용 DB 준비: 테스트용 명령이 아님
DATABASE_URL=postgresql://truefit:truefit@localhost:5432/truefit \
  UV_CACHE_DIR=/tmp/uv-cache uv run python db/setup_all.py
```

`setup_all.py`는 마이그레이션(테이블 구조 준비)과 시드(초기 상품·설정 데이터 적재)를 실행한다. DB 준비 없이 흐름만 보려면 다음 절의 합성 데모부터 실행할 수 있다.

자세한 문제 해결은 [pc_pipeline_quickstart.md](pc_pipeline_quickstart.md)와 [db/README.md](../db/README.md).

### 14.3 테스트 ([AGENTS.md](../AGENTS.md))

```bash
# 작업 중: DB를 쓰지 않는 것으로 확인한 테스트 파일을 명시
PYTHONPATH=. UV_CACHE_DIR=/tmp/uv-cache TRUEFIT_AUTO_TEST_DB=0 TRUEFIT_REQUIRE_TEST_DB=1 MOCK_MODE=1 \
  uv run pytest -q tests/test_stage4_pc_branch_bound.py tests/test_stage5_review_line.py

# 파일 하나: 이 파일에는 DB 테스트도 있으므로 자동 DB 준비를 켠다
PYTHONPATH=. UV_CACHE_DIR=/tmp/uv-cache TRUEFIT_REQUIRE_TEST_DB=1 \
  uv run pytest -q tests/test_research_loop.py

# DB가 필요 없는 테스트 하나만 선택
PYTHONPATH=. UV_CACHE_DIR=/tmp/uv-cache TRUEFIT_AUTO_TEST_DB=0 TRUEFIT_REQUIRE_TEST_DB=1 MOCK_MODE=1 \
  uv run pytest -q tests/test_research_loop.py::test_no_alternative_keeps_round_1_result

# 완료 확인 (필수): DB 포함 전체
docker compose up -d db
PYTHONPATH=. UV_CACHE_DIR=/tmp/uv-cache TRUEFIT_REQUIRE_TEST_DB=1 uv run pytest -q
```

- 전체 테스트는 세션마다 `truefit_test_<UUID>` DB를 새로 만들고 마이그레이션·시드를 적용한 뒤 끝나면 지운다.
- **개발 DB `truefit`에 테스트를 돌리지 않는다.** `conftest.py`가 이름에 `test`가 없는 DB 접속을 막는다.
- 완료 확인에는 반드시 `TRUEFIT_REQUIRE_TEST_DB=1`을 붙인다. 없으면 DB 준비 실패가 조용한 skip으로 숨는다.
- 전체 테스트 전에는 작업 중 설정한 `TRUEFIT_AUTO_TEST_DB=0`을 해제하고, 준비되지 않은 `TEST_DATABASE_URL`도 사용하지 않는다. 위 예시처럼 명령 앞에 붙인 환경 변수는 해당 명령에만 적용된다.
- 외부 호출 없이 검증하려면 `MOCK_MODE=1`을 사용한다. DB 없는 테스트 통과와 실제 DB·API·LLM 검증 완료는 서로 다르다.
- 마커(`pyproject.toml`)의 의도는 DB 테스트에 `@pytest.mark.db`, 앱과 DB를 함께 쓰는 종단 테스트에 `@pytest.mark.integration`을 붙이는 것이다. **현재는 마커 누락이 있어, 마커가 없다고 DB와 무관한 테스트는 아니다.**

**`-m "not db and not integration"`만으로 DB 없는 실행을 보장하지 못한다.** 예를 들어 `tests/test_upgrade_questions.py`의 `test_end_to_end_*` 4개는 현재 DB를 쓰지만 마커가 없다. 자동 DB 준비를 끄고 마커만으로 고르면 이 테스트들도 실행되어 DB 준비 오류가 난다. 이때 `TRUEFIT_REQUIRE_TEST_DB=1`이나 개발 DB 보호를 끄지 않는다. DB 없는 작업은 위처럼 본문·픽스처를 확인한 파일이나 `파일::테스트함수`(node ID)를 명시하고, DB가 필요한 테스트는 자동 DB 준비를 켜서 실행한다. 마커 누락 정비는 테스트 코드의 별도 작업이며, 전체 완료 확인을 선택 테스트 통과로 대체하지 않는다.

### 15.1 "왜 이 결과가 나왔나" 질문별 확인 위치

| 질문 | 볼 곳 |
|---|---|
| 요구 등급이 왜 이 값인가 | [2] 로그의 "게임 요구: GPU tier≥…" 줄, `RequirementSpec.targets`, `flags`(`games_applied`, `resolution_assumed`) |

| 이 후보가 왜 1위인가 | [3-B] 후보의 `breakdown`과 `RankResult.weights_used`. §9.1처럼 손으로 계산해 본다 |
| 1위 부품이 왜 세트에 안 들어갔나 | [4]는 **점수 합**을 최대화한다. 다른 슬롯과 비호환이거나 예산을 넘기면 2위 이하가 들어간다. `pc_compat_details(chosen, spec, rules)`로 축별 상태를 본다 |
| 세트가 왜 예산을 넘었나 | `BuildResult.alternatives`의 `feasible`/`widened`/`compatible`/`capped`와 `budget` — 탐색한 범위·상한 내에서 예산 안 호환 세트를 못 찾은 경우다 |
| 신뢰도가 왜 낮은가 | `VerificationTarget.issues`의 `axis`/`judge`/`penalty`. "확인 필요"가 많으면 스펙 데이터 결손 문제다 |
| 재탐색이 왜 안 돌았나 / 왜 멈췄나 | `transcript`의 `stop_reason`, `excluded` |
| 리뷰 줄이 왜 "관측 없음"인가 | 리뷰 산출물 파일 유무(`⚠ 리뷰축 비활성`), [5]에 `rank=`를 넘겼는지, 선택 상품이 `ranked`에 있는지 확인. `pool`에만 있으면 플래그가 있어도 현재 [5]가 읽지 못한다(§8.9) |

### 15.2 실제 검증 함수를 API·DB 쓰기 없이 재현하기

다음 코드를 `/tmp/truefit_replay.py`로 저장하고 **저장소 루트에서** 실행한다. 신규 조립의 [2]~[5]를 잇는 최소 도구다. API의 저장·트랜잭션·업그레이드 처리 전체를 복제한 것은 아니다.

```python
# /tmp/truefit_replay.py
import os

from src.categories import load_category
from src.engine import (research_loop, stage2_requirement, stage3a_hardfilter,
                        stage3b_rank, stage3c_verify, stage5_explain)
from src.engine.slots import slots_from_conditions

values = {"category": "computer", "mode": "build", "purpose": "game",
          "budget_max": 1_500_000, "priority": "value", "resolution": "QHD_165"}
log = print
cat_def = load_category("computer")
slots = slots_from_conditions("computer", cat_def, values)
spec = stage2_requirement.run(slots, cat_def, log)
rules = stage2_requirement.load_computer_rules()
compat = rules["verification"]
impact = frozenset(rules["ranking"].get("impact_slots", []))

source = os.environ.get("CATALOG_SOURCE", "db")
if source == "mock":
    from src.repo.catalog_repo import load_candidates_by_slot
    by_slot = load_candidates_by_slot()
elif source == "db":
    from src.db import get_conn
    from src.repo.catalog_repo import load_candidates_by_slot_from_db
    with get_conn() as conn:
        by_slot = load_candidates_by_slot_from_db(conn)  # SELECT만 실행
else:
    raise ValueError("CATALOG_SOURCE는 mock 또는 db를 사용하세요")

missing = [slot for slot in spec.targets if not by_slot.get(slot)]
if missing:
    raise RuntimeError(f"카탈로그에 후보가 없는 슬롯: {missing}")
print("데이터:", source, "정책:", rules["rule_set_version"], "가정:", slots.assumed_keys)
hf = stage3a_hardfilter.run(spec, by_slot, log)
rank = stage3b_rank.run(hf, spec, slots, log)

def verify(build, _round_index):
    chosen = research_loop.resolve_chosen(rank, build)
    return stage3c_verify.verify_build(
        build, "computer", log, chosen=chosen, spec=spec, rules=compat)

def choose(build, verification):
    chosen = research_loop.resolve_chosen(rank, build)
    return research_loop.rule_based_exclusion(
        build, verification, chosen, spec, compat, impact_slots=impact)

build, verification, rounds = research_loop.run_set_with_research(
    rank, spec, log, verify=verify, choose_exclusion=choose)
explanation = stage5_explain.run(
    build, verification, log, rank=rank, conditions=values)
target = verification.targets[0]
print("선택:", [(i.slot, i.name, i.price) for i in build.items])
print("예산:", build.budget, "호환:", build.link_check)
print("탐색:", build.alternatives)
print("내부 신뢰도:", target.confidence, "내부 문턱 통과:", target.passed)
print("시도 라운드:", len(rounds), "채택 라운드:", target.rounds)
print("종료 이유:", rounds[-1].stop_reason)
print("쟁점:", [(i.axis, i.judge, i.penalty) for i in target.issues])
print("설명:", explanation.summary)
```

첫 명령에서도 [3-C]는 시나리오 정답 주입이 아니라 실제 규칙 집계다. 두 번째 명령의 DB는 `DATABASE_URL`로 정하며 조회만 한다. 새 데이터를 적재하지 않는다. 출력에서 신뢰도와 `passed`는 내부 개발 값이라는 점을 기억한다.

한 번에 조건 하나씩 바꿔 비교한다. 예를 들어 `priority`를 `performance`로 바꾸면 가중치가, `resolution`을 `4K`로 바꾸면 요구사양이 바뀌는지 확인한다. 상품 구성까지 반드시 바뀌어야 하는 것은 아니다. 현재 예제는 게임 제목·업그레이드 전용 안내를 만들지 않으므로 해당 경로는 `execute_recommendation`과 관련 테스트를 참고한다.

### 15.3 저장된 결과를 DB에서 보기

-- 가장 최근 실행 10건
SELECT id, revision_id, status, explanation_status, created_at
FROM engine.recommendation_run ORDER BY created_at DESC LIMIT 10;

-- 한 실행의 선택 부품
SELECT c.score, c.reason_status, c.checks_status, c.selected, c.qty, p.brand, p.model
FROM engine.recommendation_candidate c
JOIN catalog.product_variant v ON v.id = c.variant_id
JOIN catalog.product p ON p.id = v.product_id
WHERE c.run_id = '<run_id>';

-- 한 실행의 쟁점(검증)
SELECT rule_key, severity, message, measured_values->>'penalty' AS penalty, measured_values->'evidence' AS evidence
FROM engine.validation_result WHERE run_id = '<run_id>';

-- 재탐색·리뷰 등 추론 기록
SELECT jsonb_pretty(reasoning_log) FROM engine.recommendation_run WHERE id = '<run_id>';

| `ModuleNotFoundError: src` | 저장소 루트에서 `PYTHONPATH=.`로 실행 |

## 16. 자주 하는 작업 레시피

### 16.1 가중치·요구 등급 같은 정책값을 바꾼다

1. `computer_verification_rules.yaml`에서 값을 바꾸고 `rule_set_version`을 올린다.
2. 빠른 테스트 → 골든 테스트가 깨지면 **의도한 변화인지** 확인한다. 의도했다면 골든 기대값을 갱신하고 PR에 전/후 차이를 적는다.
3. §15.2 스크립트로 대표 조건 몇 개의 결과가 어떻게 바뀌는지 확인해 PR에 적는다.

### 16.2 새 PC 호환 축을 추가한다 (예: "케이스 전면 USB-C")

1. 스펙이 DB에 있는지 확인한다. 없으면 데이터 요청이다(엔진 범위 밖).
2. `catalog_repo._SPEC_QUERIES`의 SELECT에 컬럼을 추가하고 `_specs_from_row`에서 엔진 키로 옮긴다.
3. `verification` 절에 스펙 키 매핑을 추가한다(로더 검증도 함께).
4. `stage4_optimize._pc_known_failures`에 **양쪽 값을 알 때만 fail**인 규칙을 추가한다.
5. `pc_compat_details`에 같은 축의 상세 행(`state`, `missing_slots`, `inputs`)을 추가한다.
6. `stage3c_verify._AXIS_LABEL`(화면 이름), `AXIS_SLOTS`(축→슬롯), 필요하면 `_KEY_LABEL`을 추가한다.
7. 값이 비면 "근사"가 되는지, 양쪽 값이 있고 어긋나면 fail인지, 탐색이 fail 조합을 피하는지 테스트한다.

### 16.3 새 게임 제목을 추가한다
`requirements.game_titles`에 `{aliases, tier}`를 추가한다. 출처를 확인했다면 `status: approved`와 `source: {url, excerpt, checked_at}`을 함께 적는다(없이 approved면 로더가 거부한다).

### 16.4 새 조건 필드를 엔진이 읽게 한다
엔진은 `Slots.values`에 **들어온 값을 읽기만** 한다. 필드를 대화에 노출하는 일(`computer.yaml`, 질문 칩)은 대화 계층·프론트 합의 사항이다. 엔진 쪽은 값이 없을 때 **동작이 기존과 완전히 같도록** 만들고, 그것을 테스트로 고정한다.

### 16.5 주변기기 선호 규칙을 추가한다
`peripherals.yaml`의 `requirements.<kind>.soft`에 `{when: {조건}, prefs: [{key, op, value}]}`를 추가한다. `key`는 그 종류의 판정 가능 키(컬럼 매핑 ∪ 파서 산출 키)여야 한다(로더가 검증). 파이썬 코드는 고치지 않는다.

### 16.6 응답에 새 정보를 내보내고 싶다
엔진에서는 **계약 모양 dict를 만드는 순수 함수**까지만 만든다(예: `verification_issue_payload`, `review_highlights`, `peripheral_payload`). `schemas.py`·라우터 변경은 프론트 합의 후 별도 작업이다.

| 함정 | 설명 |
|---|---|
| 데모 [3-C]는 정답 주입 | `verify_set`은 시나리오의 점수를 읽는다. [4]에서는 호환 규칙이 실행되지만, 실제 감점 집계는 `verify_build`와 §15.2로 확인한다 |
| 합성 카탈로그의 tier는 실측이 아님 | 모든 슬롯에 해시 또는 보정 CSV의 tier를 붙인다. 매번 무작위로 달라지는 값은 아니지만 실제 성능 의미도 없다. DB 후보는 CPU·GPU에만 tier가 있다 |
| 리뷰 산출물 유무로 결과가 달라질 수 있음 | `pcparts_product_risk.json`이 없으면 리뷰축 0.5 고정. 숫자가 다르다고 반드시 계산 오류는 아니다. `⚠ 리뷰축 비활성` 로그 확인 |
| 내부 통과와 예산 충족은 다름 | 다른 쟁점 없이 예산 사용률이 100% 초과·110% 이하면 감점 20 → 신뢰도 80 → 내부 통과다(§8.7). 확정 API는 예산 초과를 별도로 거절한다 |
| [3-A]의 Fail 후보 복구 | Pass·Pending이 모두 없으면 Fail 후보까지 남기는 예외가 **데모·API 모두에 적용**된다. [3-C]가 요구사양 전부를 재검사하지 않으므로 최소 요구 충족을 보장하지 않는다 |
| 리뷰 플래그 전달 누락 | [5]에 `rank`를 안 넘기면 리뷰 관측이 전부 "없음"이 된다. 넘겨도 `pool`에만 있는 선택 후보는 `_ranked_flags`가 읽지 못한다(§8.9) |
| `specs`와 출처 혼합 | URL·확인일은 `provenance`에 넣는다. 계산 입력과 출처를 분리해야 근거를 추적할 수 있다 |
| 정보 없음은 호환 확인이 아님 | [4]는 값이 없는 쌍을 막지 않는다. 일부는 [3-B] 결손 감점·[3-C] 확인 필요로 드러나지만 모든 결손이 집계되는 것은 아니다 |
| `RankResult` 안은 dict | `ranked`/`pool` 항목은 `model_dump()` dict다. `Candidate.model_validate`로 되살린다 |
| 로더 캐시 | `load_computer_rules`/`load_peripheral_rules`는 `lru_cache`다. 테스트에서 YAML을 바꾸면 별도 경로(`tmp_path`)를 넘긴다 |
| 같은 조건만으로 결과 재현 불가 | [3-B] 동점은 입력 순서에 의존한다. 정책·카탈로그·리뷰 산출물·후보 순서를 함께 맞추고, 실호출 LLM 문장은 별도로 본다 |
| 판정어 검사 범위 | [3-C] 쟁점 `text`의 판정어를 검사한다. [5]는 별도 검사다. 두 가드가 모든 허위 문장을 잡는 것은 아니다 |
| 신뢰도 숫자의 공개 범위 | 사용자 설명·`reasoning_log`에는 넣지 않는다. API의 `verification.confidence`, 내부 DTO·콘솔 로그·DB 감점 정보에는 남는다(결정 0003) |
| LLM 호출 시그니처 | `call_llm()` 시그니처는 여러 브랜치가 공유한다. 바꾸지 않는다. 프롬프트 문안(`prompts.py`) 변경은 팀 승인 대상 |

## 18. 협업 규칙

- **파일 소유가 나뉘어 있다** ([src/CLAUDE.md](../src/CLAUDE.md)). 대략 `src/services/`·`src/routers/`·`src/repo/`는 `develop` 담당, `src/rag/`는 `rag` 브랜치, LLM 연동(`prompts.py`, `stage3c_verify.py`·`stage5_explain.py`의 문장 부분, `src/agent/`)은 `sllm` 담당이다. 다른 담당의 파일을 고치면 **PR 전에 공유**한다.
- **공용 파일**(`requirements.txt`, `pyproject.toml`, `src/config.py`)은 줄 추가만 하고 기존 줄을 재배열하지 않는다(브랜치 간 충돌 지점).
- **범위 밖 작업은 요청 문서로.** 데이터 보강, DB 스키마, API 계약, 프론트 변경이 필요하면 직접 하지 말고 [추천엔진_범위외_요청.md](추천엔진_범위외_요청.md)에 R-번호로 적는다.
- **PR에 적을 것**: 무엇을 왜 바꿨는지, 결과가 바뀌는 변경이면 전/후 차이(수치), 완료 확인 테스트 결과(`TRUEFIT_REQUIRE_TEST_DB=1` 전체), 키가 없어 확인 못 한 LLM 흐름은 "미확인"으로 명시.
- **결정을 바꾸려면** `docs/decisions/`에 새 결정 기록을 먼저 쓴다. 기존 결정을 코드로 조용히 뒤집지 않는다.
- **`.env`와 API 키**는 코드·문서·커밋·로그에 넣지 않는다.

## 19. 현재 한계와 열린 과제

여기는 발표 마지막 장의 근거다. 구현된 함수가 있다는 것, 실제 서비스 경로에 연결됐다는 것, 품질이 검증됐다는 것을 각각 구분한다.

| 항목 | 현재 상태와 의미 | 다음에 확인·보완할 것 |
|---|---|---|
| 요구사양 강제 | [3-A]에 Fail 후보를 되살리는 예외가 있음 | 최소 요구 위반 시 빈 결과·조건 조정 안내 정책을 정하고 검증 |
| 성능·소음 정확도 | tier는 제조사 등급 대용값, 소음은 전력·쿨러 유형으로 추정 | FPS·벤치마크·소음 실측으로 기준 검증 |
| 상품 옵션 정밀도 | 일부 복수 용량 표기는 최댓값으로 해석하고 기본 variant를 사용 | 선택 스펙이 실제 가격의 판매 옵션과 같은지 검증 |
| 최적성·탐색 시간 | top-N에서 답을 찾으면 종료, 확장 탐색에는 상한 있음 | 후보 수별 시간·탐색 절단률·전체 탐색 대비 품질 차이 측정 |
| 신뢰도 의미 | 규칙 감점이며 [4]와 독립된 검증이 아님. 통과해도 미확인·예산 위반이 남을 수 있음 | 확정 실패와 미확인을 구분한 종료·표시 정책 검토 |
| 문서 근거 | 실경로 검증은 카탈로그 출처 연결까지. 사용 안내 검색은 별도로 연결됨 | 매뉴얼·규격 기반 호환 검증은 R-14 |
| 재탐색 실효 | 최대 3라운드 흐름은 구현됨. 개선 효과는 조건·데이터에 의존 | 고정된 요청 묶음에서 쟁점 감소·가격·성능 변화를 함께 측정 |
| 결과 보존·공개 | 탐색 통계·전체 라운드 기록·출처 근거를 모두 API에 공개하는 상태는 아님 | 저장·응답 계약 확장, R-6·R-7 |
| 주변기기 | 계산 함수·데모 연결 구현, API 실행·저장·응답은 미연결 | R-6·R-7·R-8 |
| GPU 출력 단자 | 현재 DB 로더 입력에 없음 | 모니터 교차 검사용 데이터 보강, R-1 |
| 리뷰 설명 데이터 | 리뷰 요약에 합성 데모 데이터가 포함됨. 랭킹 관측 산출물과는 다른 자료 | 실수집·검수 자료 확대, R-13 |
| [6] 피드백 반영 | 노출·교체·확정 이벤트 기록은 있지만 가중치 자동 학습은 미구현 | 이벤트 충분성·평가·승인 절차 설계 |

`R-번호`의 내용은 [추천엔진_범위외_요청.md](추천엔진_범위외_요청.md)에 있다.

기존에 기록된 몇 건의 시연 시간이나 특정 조건의 추천 금액은 일반 성능 지표로 쓰지 않는다. 입력 묶음·데이터 버전·측정 환경이 함께 보존된 실험만 비교 근거로 사용한다(§21.3).

### 21.2 평가 담당자의 예상 질문

| 질문 | 답변 요지 |
|---|---|
| “그냥 LLM에 견적을 물어보는 것과 무엇이 다른가요?” | 상품·가격은 카탈로그에서, 요구·점수·호환은 코드와 정책에서 정한다. 어느 기준으로 후보가 빠지고 선택됐는지 추적할 수 있다. LLM이 고른 견적을 사후 설명하는 구조가 아니다. 다만 생성 문장의 사실성을 완전히 검증하는 장치는 아직 아니다. |
| “왜 규칙 기반인가요? 학습 모델은 없나요?” | 현재 추천에는 학습된 사용자 선호 모델이 없다. 명시 조건과 물리 제약을 추적 가능한 규칙으로 처리한다. 피드백 이벤트 기록은 있지만 가중치를 자동 학습하는 [6]은 미구현이다. |
| “가중치는 어떻게 정했나요?” | 현재 팀이 설정 파일로 관리하는 정책값이다. 사용자 우선순위가 정해진 세트를 고른다. 사용자 만족도 실험으로 최적 가중치를 입증한 것으로 설명하지 않는다. |
| “가장 좋은 PC를 보장하나요?” | top-N 안에서 예산·확인된 호환 조건을 만족하는 최대 점수 조합을 찾는다. 전체 카탈로그의 전역 최적해나 실측 성능 최고를 보장하지 않는다. 제한된 탐색에서 못 찾으면 풀 확장·대체 결과 처리를 한다. |
| “왜 전수 탐색하지 않나요?” | 각 슬롯의 후보 수를 곱한 만큼 조합이 늘어난다. 8슬롯에 100개씩이면 100⁸=10¹⁶개다. top-N이 모두 찼다면 5²×3⁶=18,225개로 줄고, 분기한정으로 일부만 방문한다. 최악의 경우에는 여전히 많은 조합을 볼 수 있다. |
| “신뢰도 80이면 80% 믿어도 되나요?” | 아니다. 100에서 정책 감점을 뺀 내부 종료 기준이다. 실제 성공 확률로 보정되지 않았으며, 예산 105% 사용만으로도 80이 될 수 있다. 쟁점과 예산 표시를 함께 봐야 한다. |
| “데이터가 없으면 왜 제외하지 않나요?” | 데이터 결손과 비호환을 구별하기 위해 Pending으로 둔다. 후보 부족 시 선택 가능성을 남기고 감점·확인 필요로 알린다. 모든 결손이 감점되는 것은 아니므로 “모두 검증됐다”고 말할 수는 없다. |
| “최소 사양 미달 상품은 절대로 안 나오나요?” | 현재는 아니다. PC 하드 필터가 전부 Fail인 슬롯의 후보를 복구하는 예외가 실제 경로에도 있다. 이 제한은 알려져 있으며, 빈 결과나 조건 조정으로 처리할 정책 보완이 필요하다. |
| “재탐색하면 항상 더 좋아지나요?” | 시도한 결과 중 내부 신뢰도가 가장 높은 것을 유지한다. 가격·성능까지 항상 좋아지지는 않는다. 같은 후보 풀을 쓰므로 데이터가 전부 비어 있으면 개선되지 않을 수 있다. |
| “RAG로 제조사 매뉴얼을 검증하나요?” | 현재 API의 [3-C]는 카탈로그 스펙 출처를 연결한다. 구매 전 안내 검색은 별도 문서 검색이다. 매뉴얼 검색을 통한 독립 호환 판정은 미연결이다. |
| “가짜 리뷰를 찾아내나요?” | 리뷰축은 상품 단위 관측 신호로 순위를 조정한다. 개별 리뷰 진위를 판정하거나 정제 후 평점을 만드는 기능은 아니다. 관측 없음·합성 설명 자료도 구분한다. |
| “업그레이드와 주변기기도 되나요?” | 업그레이드는 교체할 슬롯만 구매 대상으로 삼고 유지 부품을 호환 검사에 쓴다. 주변기기는 별도 계산과 데모 연결은 구현됐지만 실제 API 실행·저장·응답 노출은 아직이다. |
| “테스트를 통과했으면 추천 품질도 좋은가요?” | 테스트는 준비한 조건에서 계산·계약·흐름이 기대대로 동작하는지 확인한다. 실제 성능·조립 성공·만족도·실시간 가격 정확도는 별도 평가가 필요하다. 모의 LLM 테스트는 실호출 문장 품질을 검증하지 않는다. |

### 21.3 어떤 증거로 구현과 품질을 설명할 것인가

발표 전에 평가 요청 목록을 고정한다. 게임·사무·창작, 충분한 예산·부족한 예산, 알려진 스펙·누락 스펙, 신규 조립·부분 업그레이드를 포함한다. 하나의 잘 나온 견적만으로 전체 품질을 설명하지 않는다.

| 주장 | 보여 줄 증거 | 해석의 한계 |
|---|---|---|
| 요구가 계산에 반영된다 | 같은 후보 데이터에서 조건 하나를 바꾸고 `targets`, `weights_used` 비교 | 요구가 바뀌어도 최종 부품이 같을 수 있음 |
| 탐색이 계산한 목적을 따른다 | 작은 후보 풀의 모든 조합과 선택 결과 비교. `test_stage4_pc_branch_bound.py::test_small_pool_matches_brute_force_oracle` 참고 | 작은 풀 검증이 전체 상품 최적성의 증명은 아님 |
| 알려진 비호환을 피한다 | 소켓·GPU 길이·전력 등 축별 `compat_checks`, 호환 실패 테스트 | 데이터가 없는 항목의 안전성은 증명 못 함 |
| 재탐색이 미확인을 줄인다 | 같은 요청의 라운드별 쟁점·채택 라운드, 전후 금액·등급 | 신뢰도만 좋아지고 가격·성능이 나빠졌는지도 확인 |
| 응답·저장 흐름이 이어진다 | 일회용 DB에서 추천 → 조회 → 교체 → 재검증 → 확정 테스트 | 프로세스 장애 복구·운영 부하·실호출 LLM 품질은 별도 |
| 계산 시간이 적절하다 | 고정 환경·후보 수에서 단계별 시간, 중앙값과 상위 95% 지점(p95), 절단 여부 | 합성 데이터 시간과 DB·외부 호출 포함 시간을 섞지 않음 |
| 데이터 기반 설명이다 | 선택 상품의 가격 관측 ID·스펙 출처와 쟁점의 연결 | 출처가 있다는 것만으로 그 내용이 최신·정확하다고 증명되지는 않음 |

결과를 남길 때는 날짜, 코드 커밋 및 미커밋 변경 여부, 정책 버전, 카탈로그·리뷰 산출물 버전, 환경 변수, 입력 조건, 기대 결과, 실제 결과, 실패·제외 건수를 함께 기록한다. 성공한 건수만 제시하거나 DB 미연결로 건너뛴 테스트를 통과로 세지 않는다. 측정하지 않은 정확도·속도·개선율은 “미측정”이라고 답한다.

### 21.4 시연과 이해도 점검

시연은 먼저 §9.2의 콘솔 데모로 흐름을 보여 주고, 실제 검증 함수가 필요하면 §15.2를 사용한다. 서비스 연결을 보여 줄 때는 §10.5의 API 흐름을 사용한다. 각 화면을 띄우기 전에 **정답 주입 여부·데이터 출처·외부 호출 모드**를 한 문장으로 알린다.

- [ ] GPU의 하드 필터 Pass와 세트 호환 통과의 차이를 설명할 수 있다.
- [ ] §9.1의 가중합과 B+C 선택을 손으로 다시 계산할 수 있다.
- [ ] 슬롯 배분 예산과 전체 예산, 점수와 신뢰도와 기여도를 구분할 수 있다.
- [ ] “확인 필요가 4건이면 무엇이 다시 실행되는가”에 [4]→[3-C], 최대 3라운드라고 답할 수 있다.
- [ ] 데모의 86점이 감점 4로부터 계산된 값이 아님을 설명할 수 있다.
- [ ] 현재 API에 연결된 기능과 계산 함수만 구현된 기능을 나눠 말할 수 있다.
- [ ] 추천이 이상할 때 `targets` → `reasons` → `breakdown` → `link_check` → `issues` 순으로 원인을 찾을 수 있다.

## 부록 A. FAQ

**Q. 같은 조건인데 내 PC와 동료 PC의 추천 결과가 다르다.**
리뷰 산출물·정책 버전·DB 시드·카탈로그 출처를 비교한다. [3-B] 동점은 입력 순서에 의존하고 실호출 LLM 문장도 달라질 수 있다. 조건만 같다는 이유로 같은 결과라고 기대하지 않는다.

**Q. 왜 모니터 추천이 항상 "없음"인가.**
API에서 보이지 않는다면 아직 미연결인 상태다. 주변기기 계산 함수의 결과가 `empty`라면 카탈로그에 목표 해상도·주사율을 만족하는 후보가 있는지 확인한다. 후보가 없을 때 조건을 완화하지 않는 것은 의도된 동작이다(§12.3).

**Q. 가격이 실시간이 아니다.**
PC 가격은 수집 파일에서 적재한 가격 관측이다. 결과 응답의 `data_notice`가 이를 알린다.

**Q. 신뢰도 점수를 화면에 보여 주면 안 되나.**
결정 0003에 따라 사용자 설명 문장에서는 뺐다. 현재 값은 규칙 감점이라 실제 성공 확률처럼 보이면 오해가 생긴다. 내부 계산·DB·API의 수치 필드까지 삭제한 것은 아니다.

**Q. LLM이 조건을 뽑게 하면 더 똑똑하지 않나.**
기본 [1]은 규칙 추출이다. Strands 조건 에이전트는 `CONDITIONS_AGENT=1`과 실호출 조건을 갖춘 경우의 선택 기능이다. 그 기능의 존재와 추천 본체의 판정 방식을 혼동하지 않는다.

**Q. 재탐색 루프가 실제로 도는 걸 보고 싶다.**
§9.2는 시나리오로 2라운드 실행을 시연한다. §15.2의 합성 카탈로그 모드는 실제 규칙으로 데이터 결손을 집계한다. 후자는 데이터·제외 가능한 후보에 따라 시도 횟수가 달라진다. `tests/test_research_loop.py`에는 재탐색 개선·미개선·종료 사례가 각각 있다.

**Q. 테스트가 느리다.**
작업 중에는 §14.3처럼 DB를 쓰지 않는 것으로 확인한 파일이나 node ID를 선택한다. 단위·DB 테스트가 한 파일에 함께 있을 수 있고 마커 누락도 있으므로, 파일 이름이나 마커만으로 DB 불필요라고 가정하지 않는다. 완료 확인 명령에서는 DB 실패가 오류로 드러나게 한다.
