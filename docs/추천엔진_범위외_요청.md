## R-1. GPU 출력 단자 데이터 수집과 `catalog.gpu_spec` 컬럼 추가

- **대상**: GPU 원천 데이터(`data/parts_list_modify.xlsx`의 GPU 시트), `catalog.gpu_spec`, `db/seed*.py`, `src/repo/catalog_repo.py`의 GPU SELECT(스키마 반영 뒤 엔진이 추가)
- **이유**: 모니터↔그래픽카드 연결 검사(계획 E12)의 반대편 데이터가 없다. `gpu_spec`에 출력 단자 컬럼이 **하나도 없다**(0000_schema.sql 확인). 모니터 쪽은 `hdmi_version`·`hdmi_ports`·`dp_version`·`dp_ports`·`usb_c_video_input`이 이미 있다. 엔진은 이 검사를 "데이터가 생기면 자동으로 켜지는" 형태로 만들고, 그 전에는 항상 Pending("출력 단자 정보가 없어 확인하지 못했습니다")으로 둔다.
- **제안 컬럼**: `hdmi_version text`, `hdmi_ports int`, `dp_version text`, `dp_ports int`, `usb_c_video_out boolean`, `ports_source_url text` (다른 spec 테이블의 `*_source_url` 관례를 따름). 모니터 쪽과 같은 표기(`"2.1"`, `"1.4"`)로 적는다.
- **주의**: AGENTS.md는 DB 기준선이 **정확히 네 파일**(`0000`~`0003`)이어야 한다고 규정한다. 새 마이그레이션 파일을 추가하지 말고 기준선 파일을 고치는 방식이 맞는지 DB 담당이 판단해 주세요.
- **시급도**: 즉시 — 수집 리드타임이 가장 길다. 계획 M3의 1단계는 이 데이터 없이 진행되지만, 2단계(모니터 세트 편입 재판단)는 이 데이터의 실측 비호환률로 결정한다.
- **담당 영역**: 데이터 수집 · DB

## R-2. 주변기기 데이터 보강

- **대상**: `data/peripherals/monitor_processed.csv`, `mouse_processed.csv`
- **이유**:
  1. 기본 해상도 조건 `FHD_144`(computer.yaml `defaults.resolution`)를 만족하는 모니터가 **0건**이다. 1920x1080은 `VA24DQSB` 1행뿐이고 75Hz다. 모니터 33행 중 60Hz가 11행이다. 엔진은 조건을 조용히 완화하지 않으므로, 이대로면 해상도를 따로 말하지 않은 사용자 대부분이 "맞는 모니터 없음"을 받는다.
  2. 마우스 `폴링레이트`가 84행 중 **57행 공란**이다. 게임 용도의 선호 조건이 대부분 Pending이 된다.
- **제안**: FHD 144Hz 이상 모니터 10종 이상, QHD 165Hz 대 가격 분포 보강, 마우스 폴링레이트 채움. 모든 값에 출처 URL을 둔다.
- **시급도**: 즉시
- **담당 영역**: 데이터 수집

## R-3. 주변기기 가격의 판매처·관측일 확보 (Q8)

- **대상**: 주변기기 가격 원천, `catalog.offer`/`offer_observation` 적재
- **이유**: 지금 주변기기 가격은 `peripheral_price_snapshot`에만 있다. 판매처와 관측일을 모르는 값이다. 엔진은 이를 `price_source: "reference_snapshot"`와 "구매 가능 가격이 아닙니다" 안내로 표시하고 PC 총액에 합치지 않는다(계획 §3.3). 또 확정 흐름(`list_service`)이 `offer_id`를 요구하므로, 이 상태에서는 주변기기를 **구매 리스트로 확정할 수 없다.**
- **제안**: 판매처·관측일이 있는 가격을 수집해 PC 부품과 같은 `offer` 경로로 적재한다. 적재되면 엔진 로더가 offer 가격을 우선하고 `price_source`를 `observed`로 바꾼다(엔진 쪽 변경은 작다).
- **시급도**: M3 (없으면 참고가 표시로 동작)
- **담당 영역**: 데이터 수집 · DB

## R-7. 주변기기 결과 저장 위치

- **대상**: `engine` 스키마, `EngineRepo`
- **이유**: 추천 결과는 저장된 것을 읽어 보여 준다(`get_stored_result`). 그런데 주변기기는 기존 후보 테이블(`engine.recommendation_candidate`)에 넣을 수 없다. ① 결과 화면이 `items`를 PC 8슬롯으로 그리고 ② 총액·예산 계산이 `items`를 합산하며 ③ 확정 흐름이 `offer_id`를 요구하기 때문이다(계획 C7·C8). 저장할 곳이 없으면 엔진이 계산해도 결과가 버려지므로, 엔진은 실행 연결을 이 결정 뒤로 미뤘다.
- **제안** (택1)
  - A. `engine.recommendation_run.peripheral_result jsonb` — `peripheral_payload` 결과를 그대로 저장한다. 가장 작다. **권장.**
  - B. `engine.recommendation_candidate`에 `kind`(pc | peripheral) 열을 추가한다. `items` 조회·총액 계산·확정 흐름이 모두 이 열로 걸러야 해서 파급이 크다.
- **참고**: AGENTS.md의 "기준선 네 파일" 규정은 R-1과 같다.
- **시급도**: M3
- **담당 영역**: DB · 백엔드 (develop)

## R-8. 대화 단계 — 주변기기 조건 수집과 예산 정책 확인

- **대상**: `config/categories/computer.yaml`의 `question_sets`·`slot_schema`·`fields`, `src/engine/slot_rules.py`의 추출 규칙, `session_service`, 프론트 영문 질문 매핑(`TF_QUESTION_BY_ID_EN`), 조건 에이전트 도구 필드
- **이유**: 엔진은 `peripherals: list[monitor|keyboard|mouse|speaker]`와 `peripheral_budget_max: int | None` 조건이 **들어오면** 주변기기 단계를 돌린다. 이 값을 사용자에게 묻는 것은 대화 단계의 일이다. 질문 칩은 서버의 `question_sets`로 자동 표시되지만, 영문 매핑·질문 순서·필수 여부는 대화와 프론트 설계의 문제다. `slot_schema`에 넣으면 조건 에이전트(기본 꺼짐)의 도구 필드도 바뀐다.
- **확인 요청 (정책)**:
  1. 주변기기 예산을 PC `budget_max`와 **분리**하는 엔진의 기본 정책(계획 §3.3)이 맞는가. 합쳐야 한다면 PC 예산 배분(`budget_allocation`)의 합=1 규칙부터 다시 설계해야 한다.
  2. 모니터 질문 시점: 해상도 질문(`q_resolution`) 직후가 자연스럽다. 해상도 조건이 이미 모니터를 전제하고 있기 때문이다.
- **제안 질문(초안)**: `q_peripherals` (multi) "주변기기도 같이 추천해 드릴까요?" — 모니터 / 키보드 / 마우스 / 스피커 / 필요 없어요. `q_peripheral_budget` (free, 선택) "주변기기 예산은 따로 있으신가요?"
- **시급도**: M3
- **담당 영역**: 대화 · 프론트 · 기획

- **이유**: 게임 제목 15개의 요구 등급은 "팀 확인 전 잠정값"인데 `perf_tier_min`을 올려 **후보를 실제로 탈락시킨다**. 계획 E7은 엔진이 출처와 승인 상태를 담고 검증하게 만든다. 하지만 값을 모으고(수집), 등급 눈금에 옮기고(추출), 승인하는 일은 데이터 작업이자 사람의 판단이다. [6] 설계의 승인 게이트도 `game_req`를 사람 승인 대상으로 분류한다.
- **제안**: 제목별로 배급사 공식 페이지 URL, 권장 사양 발췌, 확인일, 등급 매핑 근거를 표로 만든다. 팀이 승인하면 해당 항목을 `status: approved`로 바꾼다. 15개 외 인기 제목 확장도 같은 절차로 한다. 추출에 LLM을 쓰더라도 결과는 사람이 승인한 YAML만 반영한다(런타임 검색 금지 — 현황 §6.0).
- **시급도**: M2
- **담당 영역**: 데이터 · 팀 승인
