## 한 줄 요약

**1위 카드를 600px 안팎으로 줄이려면 화면이 "사용자가 말한 것 / 필수 스펙 값 / 점수 축 3개 / 대안의 근거"를 서버 응답에서 바로 꺼낼 수 있어야 한다.** 지금은 이 네 가지를 화면이 만들 수 없어서 목업은 임시로 손으로 연결했다.

## S1. 대안에도 체감 근거 블록 (`alternatives[].feel`)

**지금:** `attach_feel`은 통과한 후보 전부(`kept`)에 `feel_detail`을 계산해 붙인다(`peripheral_select.py:503`). 그런데 화면에 나가는 블록은 `_feel_blocks(picks, …)`가 **1위(pick.candidate)만** 만든다(`peripheral_select.py:422`). 그래서 화면에서 대안을 "이 제품으로 바꾸기"로 큰 카드로 올리면 사용기 타일이 비어 있다.

**요청:** 대안 2개도 같은 `build_feel_block(...)`으로 블록을 만들어 `items[].alternatives[].feel`에 싣는다(없으면 `null`, 1위와 같은 모양). 새 계산은 없다 — 이미 계산된 `feel_detail`을 문구로 바꾸기만 한다.

**수락 기준**
- 모니터 "디자인이 예쁜" 시나리오에서 대안 2개의 `feel.attributes`가 `looks`(외관 만족)를 포함한다(사용기가 있는 제품).
- 사용기가 없는 대안은 `feel: null`이고 `feel_note`는 기존 규칙(스펙과 가격 기준)을 따른다.
- 응답 크기: 대안 `feel`의 `quotes`는 1위와 같은 상한(`quotes_per_attribute`)을 따른다.

## S2. 요청한 속성이 인용을 먼저 고르게

**지금:** `compute_feel`이 속성을 설정 파일 순서(`alphas.items()`)로 돌며 "한 제품에서 한 글은 한 번만 인용"(커밋 3b9f55f)을 적용한다. 앞선 속성이 글을 먼저 가져가므로 **사용자가 요청한 속성(`purpose_boost`로 중요도가 오른 것)이 앞선 속성에 글을 빼앗겨 인용 없이 건수만 남는** 경우가 생긴다.

**요청:** 속성 순회 순서를 `(요청한 속성(boosted) 먼저, 그다음 alpha 큰 순, 코드 순)`으로 바꾼다. 집계·점수는 그대로이고 **인용 선택 순서만** 바뀐다. 응답 속성 배열의 정렬(`alpha` 내림차순)은 지금과 같다.

**수락 기준**
- 같은 입력에서 점수·`state`·건수는 한 글자도 안 바뀐다(기존 체감 테스트 통과).
- `situations: ["design"]`인 모니터에서 `looks`의 `quotes`가 비어 있지 않다(사용기에 `looks` 문장이 있는 제품). 요청하지 않은 속성이 그 글을 가져가지 않는다.
- 요청한 속성이 여럿이면 중요도(alpha) 큰 쪽이 먼저 고른다.

## S3. 비슷한 문장 인용 건너뛰기

**문제:** 목업에서 모니터 1위의 인용 2개가 "베젤이 얇아서 깔끔 / 뒷면은 게이밍 느낌"처럼 사실상 같은 말이었다. 글(`post_id`)이 달라도 한 사람이 같은 말을 되풀이한 글이거나 예시 글이 비슷하면 이런 일이 생긴다.

**요청:** `_quotes`에서 이미 고른 문장(같은 제품의 앞선 속성에서 고른 것 포함)과 **너무 비슷한 문장은 건너뛴다**. 유사도 판정은 서버 규칙으로 두고 값은 설정으로 뺀다.

```yaml
feel:
  quote_similarity_max: 0.6    # 정규화한 한글 문자 2-gram 자카드 유사도가 이 이상이면 같은 말로 본다
```

- 정규화: 공백·문장부호·조사 어미를 지우는 수준이면 충분하다(형태소 분석 불필요). 규칙은 `peripheral_rules.py`에서 검증한다.
- 건너뛴 뒤 후보가 없으면 인용 없이 점수·건수 문구만 보인다(지금 규칙과 같다).

**수락 기준:** 목업 데이터(모니터 · 디자인이 예쁜)에서 1위의 인용 2개가 서로 다른 내용이다. 서로 다른 두 문장은 건너뛰지 않는다(단위 테스트에 두 쌍을 고정한다).

## S4. 요청 항목 목록 `requested[]`

**배경:** 화면의 "요청하신 ○○" 블록은 **사용자가 말한 것만** 보인다(결정 Q2). 지금 응답에는 사용자가 말한 항목의 이름도, 그 항목을 판단한 근거가 스펙인지 사용기인지도 없다. 목업은 이 연결을 시나리오마다 손으로 넣었다.

**요청:** `items[]`와 `items[].alternatives[]`에 `requested`를 싣는다.

```json
"requested": [
  {
    "label": "조용한",                       // 사용자가 말한 뜻을 화면에 쓸 이름으로(상황·목적·직접 말한 조건 라벨)
    "source": "situation",                   // stated | situation | purpose
    "type": "evidence",                      // spec: 스펙 값으로 판정 / evidence: 사용기·외부 리뷰로 판단
    "spec_checks": [                         // 스펙으로 확인된 것. 없으면 []
      {"key": "switch_clicky", "text": "클릭형 스위치 아님", "ok": true}
    ],
    "feel_codes": ["key_noise", "hollow"],   // feel.attributes[].code 와 연결되는 사용기 속성
    "external_aspects": ["typing_noise"]     // review.contributions[].aspect_code 와 연결되는 외부 리뷰 항목
  },
  {
    "label": "가벼운",
    "source": "stated",
    "type": "spec",
    "spec_checks": [{"key": "weight_g", "text": "무게 76g · 80g 이하", "ok": true}],
    "feel_codes": [],
    "external_aspects": []
  }
]
```

- 항목의 출처는 이미 서버가 가진다: `resolved[kind]`의 stated 조건, 상황(`situations`)이 가리키는 `feel` 속성(`purposes.*.feel`·`only_when: design`), `spec_conditions`. 새 해석은 하지 않고 **연결을 응답에 싣는 것**이다.
- 같은 뜻의 항목은 하나로 묶는다(예: "무선"이 `stated`와 `purpose`에서 둘 다 나오면 한 줄).
- 목록 순서: 사용자가 말한 순서(없으면 `source` 순 stated → situation → purpose).
- `type`이 `spec`이어도 `feel_codes`가 있으면 사용기 보조 근거로 쓸 수 있다.
- 사용자가 아무것도 말하지 않은 종류(예: 종류만 고른 경우)는 `requested: []`로 둔다. 화면은 이때 요청 블록을 그리지 않는다.

**수락 기준:** 시나리오 3개에서 위 예시와 같은 모양이 나온다(모니터 "디자인이 예쁜" → `feel_codes: ["looks"]`, 키보드 "조용한" → 소음 속성 + 외부 `typing_noise`, 마우스 "가벼운 무선" → 스펙 2건).

## S5. 필수 스펙 값 `key_specs[]`

**지금:** 응답에는 조건 충족 태그(`requirement`·`checks`)만 있고 값이 없다. 목업은 후보의 `specs`를 직접 읽어 한 줄을 만들었다.

**요청:** `items[]`와 `items[].alternatives[]`에 종류별 고정 순서의 `key_specs`를 싣는다. 값이 없는 항목은 **넣지 않는다**(0·—로 채우지 않는다).

```json
"key_specs": [
  {"key": "refresh_hz",      "label": "주사율", "value": "165Hz"},
  {"key": "resolution_raw",  "label": "해상도", "value": "QHD"},
  {"key": "screen_size_inch","label": "크기",   "value": "27인치"}
]
```

| 종류 | 키(순서) |
|---|---|
| 모니터 | 크기·해상도·주사율·패널·응답속도·(USB-C 영상 입력 있을 때) |
| 키보드 | 스위치·배열/크기·무게·연결 |
| 마우스 | 무게·크기·연결·(폴링레이트)·배터리 |
| 스피커 | 형태·출력·채널·연결 |

- `value`는 화면에 그대로 쓰는 문자열이다(단위 포함). 목록은 종류별로 `config/peripherals.yaml`의 `display.key_specs`에 두고 규칙 로더가 검증한다.
- 화면은 대안과 1위의 `key_specs`를 키로 비교해 "다른 점"을 만든다. 같은 키는 같은 단위·표기를 쓴다.

## S6. 점수 축 사용자말 라벨 + 가격 위치

**지금:** `score_detail.axes[].axis`가 내부 이름(`손맞춤`·`화질사양`·`리뷰`…)이고, 화면이 이름을 따로 매핑한다(목업도 임시 표를 썼다). 또 "가격 76점"이 무슨 뜻인지 사용자가 알 수 없다.

**요청**
1. `score_detail.axes[]`에 `label`을 더한다(`"후기·사용기"`, `"가격"`, `"손에 맞는 정도"`…). 표는 `config/peripherals.yaml`에 둔다.
2. `items[]`에 `price_position`을 더한다: `{"rank": 3, "of": 20}` — 통과한 후보 안에서 싼 순서. 화면은 "후보 20개 중 3번째로 저렴"으로 보인다. 후보 수가 1이면 `null`.

점수 계산은 바뀌지 않는다.

## S7. 외부 리뷰 항목별 대표 문장

**지금:** `review.contributions[].members[].evidence_sentences`에 문장이 있고 방향(`direction`)이 멤버 단위로 붙어 있다. 어느 문장을 대표로 보일지는 화면이 정해야 하는데, 긍정 7·부정 2인데 부정 문장을 대표로 보이면 오해가 된다.

**요청:** 항목(`contributions[]`)마다 `quote: {"text": str, "direction": "positive"|"negative"|"mixed"}`를 더한다. 선택 규칙: 건수가 더 많은 방향의 문장 중 한글이 든 가장 짧지 않은 것(규칙은 구현 쪽에서 정하되 결정적이어야 한다). 문장이 없으면 `quote: null`.

- 목록에 반대 의견이 있으면 `dissent: true`로 알려 화면이 "갈리는 점"을 따로 보일 수 있게 한다(선택).

## 건드리지 말 것 / 확인할 것

- **점수·순위는 바꾸지 않는다.** S1~S7은 표시 데이터와 인용 선택만 다룬다. 기존 순위 테스트·체감 테스트가 그대로 통과해야 한다.
- 키보드 "조용한"에서 사용기 0건 제품이 1위가 되는 것은 이 요청의 범위가 아니다(점수식 판단, 관련: `개발요청_주변기기_추천_점수식_개선.md`). 화면은 사실대로 "외부 리뷰 기준"으로 보인다.
- 응답 크기: 대안 2개에 `feel`·`requested`·`key_specs`가 더해진다. 인용 상한을 유지하면 1위 응답의 약 2~3배 이내다. 문제가 되면 대안 `feel`은 `?detail=alternatives` 같은 옵션으로 나누는 대신 먼저 상한부터 줄인다.
