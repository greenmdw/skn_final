# 사용자 선호·비선호 기록 — 설계 및 구현 기획

- 상태: **1~4단계 구현 완료** (5단계 명시적 선호 도구, 6단계 엔진 반영은 미착수 — §8 참고). 아래 SQL·코드 스니펫은 설계 당시 초안이라 실제 구현과 세부 차이가 있다 — 정확한 현재 상태는 §10을 본다.
- 실제 테이블명은 `identity.preference_signal`이다(아래 초안의 `identity.user_preference_signal`이 아님 — `tests/test_schema_reduction.py`의 `REMOVED_TABLES`에 있는 옛 `identity.user_preference`와 문자열이 겹치지 않도록 구현 시 바꿨다, §10 참고).
- 배경: [`채팅기록_다음세션_시나리오.md`](../history/채팅기록_다음세션_시나리오.md) B4("지난번 A사 파워는 소음 때문에 빼셨죠, 이번에도 제외할까요?") / A4(설명 수준 맞추기) 시나리오가 공통으로 요구하는 "선행 작업"을 실제로 설계한다.
- 확인된 현재 상태: **완전 백지.** `brand_pref` 필드는 스키마엔 있으나 아무 코드도 채우지 않음(`stage2_requirement.py:304`가 항상 `"none"`으로 읽음). `identity.app_user.ui_settings`도 쓰는 코드 없음. `engine.feedback_event`(부품 교체/제거 이벤트)는 쌓이지만 `user_id`도, 이전/이후 부품 정보도 안 채워짐(`recommendation_service.py:703, 885`에서 `emit_removed`/`emit_replaced`를 `payload` 없이, `user_id` 없이 호출).

## 1. 범위 — 두 갈래를 분리해서 설계한다

| 갈래 | 예 | 소스 |
|---|---|---|
| **명시적 선호** | 채팅에서 "인텔은 별로예요", "라데온으로 해줘" | 대화 텍스트 |
| **암묵적 선호** | 같은 슬롯에서 브랜드 A→B로 반복 교체, 특정 부품 반복 제거 | `feedback_event`(item_replaced/removed) |

두 갈래 다 최종적으로 같은 저장소(`identity.user_preference_signal`, 3절)에 쌓이지만, 만드는 경로와 신뢰도 계산 방식이 다르다.

## 2. 설계 원칙 (기존 프로젝트 철학 그대로 계승)

- **판정은 규칙, 설명만 AI.** "3번 반복했다"는 규칙(카운트)이 정하고, "왜 그랬을지"를 한 문장으로 다듬는 것만 LLM이 한다(선택 사항, 5절).
- **자동 적용 금지, 항상 되묻는다.** A1("지난번 조건 이어서 할까요?")과 같은 UX — 추론한 선호를 조용히 필터에 반영하지 않고, "이렇게 파악했는데 맞나요?" 형태로 사용자가 확인·거부할 수 있게 한다. 거부하면 신뢰도를 낮추거나 신호를 지운다(6절).
- **관측 사실만, 과잉 해석 금지.** 결정 0001의 정신을 계승 — "3번 뺐다"는 사실이지 "이 사용자는 AMD를 싫어한다"는 확정 판정이 아니다. 문구도 "~하셨어요"(관측) 톤으로, "~을 싫어하십니다"(단정) 톤을 쓰지 않는다.
- **개인정보 처리 원칙 유지.** 회원 탈퇴 시(`user_repo.withdraw()`) 다른 개인 데이터와 함께 지운다(7절).
- **추천 순위 자체를 바꾸는 건 이 설계의 범위 밖이다.** `stage3b_rank.py`의 가중치·필터는 담당3(추천엔진) 소유 영역 — 이 설계는 "저장·표시·되묻기"까지만 하고, 실제 순위 반영은 별도 협의 사항으로 남긴다(8절 미결정 사항).

## 3. 스키마 설계

### 3.1 저장소: 새 테이블 (기존 `ui_settings` jsonb 재사용 안 함)

`ui_settings`는 이미 "안 쓰는 자리"로 방치된 전례가 있고, 구조화된 신뢰도·근거·시점 추적이 안 된다. 대신 전용 테이블을 둔다.

```sql
-- db/migrations/0005_user_preference_signal.sql (초안 — 팀 승인 전 적용 금지)

CREATE TABLE identity.user_preference_signal (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         uuid NOT NULL REFERENCES identity.app_user(id) ON DELETE CASCADE,
    dimension       text NOT NULL,      -- 'brand' (확장 여지: 'form_factor', 'noise' 등)
    slot            text,               -- 'GPU', 'CPU', ... (dimension='brand'일 때 필수)
    value           text NOT NULL,      -- 'AMD', 'Intel', ...
    direction       text NOT NULL,      -- 'prefer' | 'avoid'
    source          text NOT NULL,      -- 'explicit_chat' | 'inferred_swap'
    confidence      int  NOT NULL DEFAULT 1,   -- 관측 횟수(암묵) 또는 1(명시적 발언 1회)
    evidence_event_ids uuid[] NOT NULL DEFAULT '{}',  -- 근거가 된 feedback_event.id 들(암묵일 때)
    status          text NOT NULL DEFAULT 'active',   -- 'active' | 'dismissed'(사용자가 "아니에요" 선택)
    first_observed_at timestamptz NOT NULL DEFAULT now(),
    last_observed_at  timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT ups_direction_check CHECK (direction IN ('prefer','avoid')),
    CONSTRAINT ups_source_check CHECK (source IN ('explicit_chat','inferred_swap')),
    CONSTRAINT ups_status_check CHECK (status IN ('active','dismissed')),
    UNIQUE (user_id, dimension, slot, value)
);

CREATE INDEX ups_user_idx ON identity.user_preference_signal(user_id) WHERE status='active';
```

`UNIQUE(user_id, dimension, slot, value)`로 같은 신호는 갱신(`confidence` 증가, `last_observed_at` 갱신)만 하고 중복 행을 안 만든다.

### 3.2 기존 갭 먼저 메운다 — `feedback_event`에 근거 데이터가 없다

지금 `swap_item()`(`recommendation_service.py:850`)을 읽어보면 **old(`current`)·new(`target`) 부품 정보가 함수 안에 이미 다 있는데** `emit_replaced` 호출 시 버려진다:

```python
# 지금 (recommendation_service.py:884-887)
feedback_service.emit_replaced(
    conn, plan_id=revision["plan_id"], revision_id=revision_id,
    run_id=run["id"], item_id=item_id, version=revision["lock_version"],
)
```

`feedback_service._PAYLOAD_SCALAR_KEYS`가 `*_id`로 끝나는 키를 이미 허용하므로 스키마 변경 없이 바로 채울 수 있다:

```python
# 변경 후 (제안)
feedback_service.emit_replaced(
    conn, plan_id=revision["plan_id"], revision_id=revision_id,
    run_id=run["id"], item_id=item_id, version=revision["lock_version"],
    user_id=principal.user_id if principal else None,   # ← 신규: 함수 시그니처에 principal 추가 필요
    payload={"from_variant_id": str(current["variant_id"]), "to_variant_id": str(candidate_id)},
)
```

`swap_item(conn, revision_id, item_id, candidate_id)` 시그니처에 `principal: Principal | None = None`을 추가하고, 라우터가 이미 갖고 있는 `principal`을 여기로 넘겨줘야 한다(지금은 서비스 함수까지 안 내려옴 — 확인됨). `emit_removed` 호출부(`recommendation_service.py:700-705`)도 동일하게 `user_id`, `payload={"removed_variant_id": ...}` 추가.

## 4. 파이프라인 A — 명시적 선호 (채팅에서 직접 말한 것)

1. `conditions_agent.py`(Strands 에이전트, opt-in `CONDITIONS_AGENT=1`)에 도구 하나 추가: `record_brand_preference(slot, brand, direction)`.
2. 사용자가 "인텔은 별로예요"류 발언을 하면 에이전트가 이 도구를 호출 → `user_preference_signal`에 `source='explicit_chat', confidence=1`로 upsert.
3. 같은 세션 안에서는 기존 `brand_pref` 슬롯 값도 같이 채워서(스캐폴딩 살리기) 그 견적의 소켓 필터링에 바로 반영(`stage2_requirement.py:304`가 이미 읽는 경로 재사용).
4. **주의**: 에이전트가 "감지"만 하고 실제 저장 여부는 규칙(도구 호출 성공)이 정한다 — LLM이 "이 사용자는 인텔을 싫어한다"고 서술만 하고 안 끝나게, 반드시 구조화된 도구 호출로 강제한다(기존 [3-C]/[5] "판정은 규칙" 패턴과 동일).

## 5. 파이프라인 B — 암묵적 선호 (행동에서 추론)

기존 `src/workers/feedback_batch.py`(이미 있는 배치 워커)에 새 단계 추가.

1. 사용자별로 최근 N개(예: 최근 90일) `item_replaced`/`item_removed` 이벤트를 `payload`의 `*_variant_id`로 모아, `catalog.product_variant`(또는 상위 product)에서 브랜드를 조인해 가져온다.
2. 같은 `(user_id, slot)`에서 **"브랜드 A → 브랜드 B로 교체"가 임계값(제안: 3회) 이상 반복**되면:
   - `user_preference_signal(dimension='brand', slot=slot, value=B, direction='prefer', source='inferred_swap', confidence=반복횟수)` upsert
   - 동시에 `(value=A, direction='avoid')`도 upsert (교체돼서 빠진 쪽)
3. **이유 문장(선택 사항)**: 그 스왑 시점 전후의 채팅 메시지(`identity.message`)를 근거로 LLM이 "왜 뺐는지" 한 줄 요약 — B4 시나리오의 "소음 때문에 빼셨죠" 같은 문장. 판정이 아니라 서술이므로 [5] 설명 문장과 같은 안전장치(근거 없으면 안 씀) 적용.

## 6. 조회·표시 경로 — A1과 같은 패턴

새 세션 시작(조건 대화 그리팅) 시, `latest_previous()`가 지난 조건을 확인하는 것과 같은 자리에 선호 신호도 같이 확인:

```
"지난번에 CPU에서 Intel을 3번 빼고 AMD로 바꾸신 걸 봤어요. 이번에도 AMD 위주로 볼까요?"
[예, AMD 위주로]  [아니요, 이번엔 다르게]
```

- "예" → 그 세션의 `brand_pref` 슬롯에 반영(파이프라인 A와 같은 저장소 재사용)
- "아니요" → `user_preference_signal.status='dismissed'`로 변경(완전 삭제는 안 함 — 다음에 또 반복되면 재확인 가능하게, 단 되물을 때 신뢰도를 낮춰서 덜 확신하는 톤으로)

**추천 순위 자체에 자동 반영하지 않는다** — 사용자가 "예"를 눌러야만 그 세션의 명시적 조건(`brand_pref`)이 되고, 그다음은 기존 엔진 로직(담당3 소유)이 그대로 처리한다. 이 설계는 "신호를 만들고 되묻는 것"까지다.

## 9. 미결정 사항

- 반복 임계값(3회 제안)이 적절한지 — 데이터가 쌓이기 전엔 감으로 정한 값
- "아니요" 선택 시 완전 삭제할지, `dismissed`로 남겨 재확인 기회를 줄지
- `dimension`을 브랜드 외에(폼팩터, 소음 민감도 등) 언제 확장할지 — 지금은 브랜드 하나만 우선 구현 범위로 좁힘
