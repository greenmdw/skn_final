# 실제 서비스 UI에서 리뷰 추천 반영 확인

2026-10-02, 스테이징된 변경 3개 파일을 `134939cb` (`Record production review aggregate application and smoke results`)로 커밋한 뒤 실제 FastAPI 서비스와 빌드된 React 화면을 Chromium으로 확인했다.

## 결론

PC 추천에는 실제 리뷰 관측이 반영되며 결과 화면에도 리뷰 기여도가 표시된다. 그러나 사용자가 **어떤 리뷰 때문에 점수가 달라졌는지** 상세히 확인하기에는 UI 연결이 부족하다. 특히 관측을 사용한 상품에도 “이 제품의 리뷰 관측이 아직 없어요”라고 표시한다. 주변기기 추천 화면은 아직 API를 호출하지 않는다.

## 실행 환경과 확인 절차

- `web`에서 `npm run build` 성공. TypeScript 검사와 Vite 빌드 완료.
- `CATALOG_SOURCE=db`로 실제 catalog와 이미 적용된 리뷰 집계를 사용했다. 기존 LLM 설정을 사용했으며 mock 모드로 전환하지 않았다.
- 로컬 HTTP 실행을 위해 프로세스에만 `APP_ENV=development`, `AUTH_COOKIE_SECURE=0`, `COOKIE_SECURE=0`을 지정했다. `.env`는 변경하지 않았다.
- 서비스 주소: `http://127.0.0.1:8000`.
- 게스트 UI에서 “게임용으로 예산 200만원, 정숙 우선 PC를 추천해주세요.” 입력 → 추가 질문에서 “조용한 게 좋아요” 선택 → “추천 받기” 클릭 → 실제 결과 페이지 이동 → CPU 상세 펼치기.
- 추천 요청은 HTTP 202, 결과 조회는 성공했고 브라우저 JavaScript 오류는 없었다. 추천 실행 ID는 `76826a8e-f8b7-4084-8183-e5eee102af80`이다.
- 이 확인은 실제 게스트 세션과 추천 실행을 생성했다. 리뷰 원본·규칙·집계를 수정하거나 개발 DB에 pytest를 실행하지 않았다.

## PC 추천 결과

총액 1,670,111원, 예산 잔액 329,889원의 8부품 견적이 표시됐다. 상단 기여도는 소음 29%, 가격 21%, **리뷰 19%**, 성능 15%, 밸런스 12%, 호환여유 4%였다. 이 19%는 추천 축별 기여 비중이며, 리뷰 적합도 R 자체나 긍정 리뷰 비율이 아니다.

API의 `reasoning_log`에는 슬롯별 R/조건별 Q/α/P/N/mixed와 실제 적용 관측 근거가 있었다.

| 슬롯 | 리뷰 적합도 R | 적용 관측 근거 수 |
|---|---:|---:|
| CPU | 0.533 | 1 |
| GPU | 0.539 | 8 |
| RAM | 0.625 | 4 |
| 메인보드 | 0.500 | 0 |
| 저장장치 | 0.500 | 0 |
| 파워 | 0.500 | 0 |
| 케이스 | 0.475 | 1 |
| 쿨러 | 0.500 | 0 |

실제 DB를 읽기 전용으로 조회해 이 실행에 8개 부품의 요구조건 프로필이 저장됐음을 확인했다. 실행의 `engine_versions`와 저장된 프로필은 `review-profile-v1-20261002` / `review-aspect-v6-prod-20261002`로 일치했다.

이는 실제 UI 요청이 리뷰 점수 계산·저장·결과 전달 경로를 통과했다는 증거다. 이번 확인에서는 리뷰를 제거한 대조 실행을 하지 않았으므로, 최종 선정 제품이 리뷰 때문에 교체됐다고 주장하지 않는다. 점수 변화의 독립 검산은 기존 `리뷰점수_실데이터_검증결과.md`에 기록돼 있다.

## 발견한 UI 연결 문제

### 1. 실제 관측을 사용해도 “관측 없음”으로 표시

CPU `AMD Ryzen 5 7600`은 긍정 관측 1건을 사용해 R=0.533으로 계산됐다. 그런데 CPU 상세 리뷰 영역은 “이 제품의 리뷰 관측이 아직 없어요”라고 표시했다.

`web/src/api/http/mapping.ts`의 `itemFromWire`는 기존 `item.review`의 별점·총 리뷰 수만 매핑한다. 해당 응답은 `total_count`와 `rating_refined`가 null이고 기존 분석 상태는 unavailable이다. `PlanPage.tsx`는 이 값으로 관측 부재를 판정한다. 새 추천 관측이 없다는 의미로 바꿔 표시하면 실제 적용 근거와 모순된다.

### 2. 추천에 적용한 상세 근거가 UI에 전달되지 않음

서버는 `reasoning_log`에 리뷰 적합도와 관측 근거를 반환하지만 프런트엔드 `WireResult`에는 이 필드가 선언돼 있지 않으며 `planFromResult`도 화면 모델로 옮기지 않는다. 서버 설명의 `text`도 이 화면에 매핑되지 않는다. 현재 화면만으로는 속성·요구조건·긍정/부정/혼합 관측·선택 조건에 관측이 없는 경우를 구분할 수 없다.

우선 부품별 구조화된 리뷰 근거를 화면 모델에 연결하고, 기존 별점 분석의 미제공 상태와 추천 관측 부재를 구분해야 한다. 상세 패널에는 사용자가 이해할 수 있는 속성/조건/관측 요약과 점수에 반영된 방향을 보여주는 것이 다음 작업이다.

### 3. 주변기기 화면은 추천 API 미연결

`/peripherals`에서 4개 품목을 선택한 기본 상태로 “추천 받기”를 눌렀다. “실제 제품 추천을 받으려면 전용 백엔드 API 연결이 필요합니다”라는 안내만 표시됐고 클릭 후 POST 요청은 0건이었다. `PeripheralsPage.tsx`의 `requestRecommendation`도 안내문만 설정한다.

따라서 백엔드 주변기기 scorer의 구현 여부와 별개로, 현재 주변기기 UI에서는 실제 상품 추천과 리뷰 근거 확인이 불가능하다. 조건 입력 → 추천 API → 상품/리뷰 근거 표시를 연결해야 한다.

## 화면 증거와 범위

- PC 상단 리뷰 기여도와 CPU 상세의 잘못된 부재 표시: `outputs/review_ui_20261002/pc_review.png`.
- 주변기기 추천 미연결 안내: `outputs/review_ui_20261002/peripherals.png`.

이미지는 로컬 검토 산출물이며 Git에서 제외되는 `outputs`에 저장했다. 이번 작업에서는 UI 기능을 수정하지 않았고, 서비스는 로컬에서 실행해 둔 상태다. 로그인·저장·결제 흐름은 이번 검토 범위에 포함하지 않았다.
