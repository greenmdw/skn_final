# 리뷰 관측 결과의 추천 점수 연결 계획

작성일: 2026-10-02. 상태: 구현 계획. 이 문서 작성으로 집계나 추천 점수 변경을 실행하지 않는다.

## 1. 목표와 적용 범위

DB의 리뷰 속성 관측을 상품별 점수 Q로 집계하고, 요청별 요구 프로필로 리뷰 적합도 R을 계산하여 기존 추천 엔진의 리뷰 축을 완전히 대체한다. 우선 목적은 원문 → 관측 → 집계 → 요청별 점수 → 후보 순위 → 최종 견적 설명의 연결 동작 확인이다.

사용자 결정에 따라 현재 `evidence.review_aspect_observation`의 관측은 승인/초안 구분 없이 사용한다. 과거 JSON의 승인 여부를 다시 필터로 적용하거나 이전 승인 45건만 사용하지 않는다. 별도 초안 테이블·승인 필드를 신설하지 않는다. 이는 전수 의미 품질 검토 완료를 의미하지 않으며, 데이터 품질 개선은 후속 작업으로 분리한다.

유지할 사항:

- 최종 평가 축, 축별 외부 가중치 및 기존 요청별 가중치 조정 규칙.
- 가격·성능·밸런스·호환 여유·소음 계산, 패널티, RAM 보너스, 반올림, 동점 정렬, 조합 최적화.
- 리뷰 원문 전체 임베딩 설계. 이번 구현에는 임베딩 생성·벡터 검색·LLM 호출이 필요하지 않다.
- 기존 리뷰/요약 테이블과 다른 기능. 랭킹과 랭킹 설명에서만 과거 행동 지표 의존을 제거한다.

관측 재추출, 미매칭 원문 추가 적재, 전수 의미 검토, 집계 수정 이력 및 전체 추천 점수 이력 설계는 범위 밖이다.

다음 DB 수치는 직전 적재 확인 시점의 기준값이며 구현 시작 시 다시 조회한다.

| `evidence.review_document` | 5,653건 | 관측 → `catalog.product.id` 연결 |
| `evidence.review_aspect_rule` | 102건 | PC 82개·주변기기 20개, 속성/조건/k 정의 |

## 3. 전체 데이터 흐름

```text
review_document + review_aspect_rule + review_aspect_observation
  → 명시한 분석 버전의 상품/규칙별 전체 집계(P,N,mixed,k,Q)
  → aggregate_member로 관측 근거 연결

요청의 slots.values + 부품 종류
  → 적용 속성·조건·중요도 α를 고정한 요구 프로필
후보의 product_id + 집계 일괄 조회
  → R = Σ(α × Q)
  → Candidate.breakdown["리뷰"] = R
  → 기존 가중합/패널티/보너스
  → 기존 조합 선택/호환 검증
  → 계산에 사용한 근거와 중립 처리 이유 설명
```

요청 경로에서는 집계 조회와 산술 계산만 한다. 요청마다 원문을 재분석하거나 관측 전체를 GROUP BY하지 않는다.

## 4. 집계 생성과 갱신

### 집계 규칙

1. 관측을 document_id로 원문에 연결하고 product_id를 얻는다.
2. 지정 analysis_version의 rule_id별로 묶는다. 서로 다른 조건·버전의 관측을 합치지 않는다.
3. 원문 `is_synthetic=false`를 확인한다. 상품 유형과 규칙 part_type의 불일치·FK 이상은 사전 검증 오류로 보고한다.
4. 현재 테이블의 모든 구조적으로 유효한 관측을 센다. 의미 검수 상태 필터는 없다.
5. `(document_id, rule_id)` UNIQUE를 활용하여 리뷰당 같은 규칙을 한 번만 센다.
6. positive→P, negative→N, mixed→mixed. mixed는 P/N에 분할하거나 0.5건씩 넣지 않는다.

```text
Q = (P + k × 0.5) / (P + N + k)
```

k는 해당 규칙의 양수·유한 값이다. `review_aspect_aggregate.q`는 DB generated column이므로 INSERT하지 않는다. P=N=0이면 Q=0.5이며 mixed만 있어도 같다. 근거가 없는 조합은 집계 행을 만들지 않고 조회 시 Q=0.5로 처리한다.

### 갱신 절차

새 CLI `db/rebuild_review_aspect_aggregates.py`를 구현한다. `--analysis-version`을 필수로 받고 기본 dry-run, `--apply`로 쓰기를 수행한다.

- dry-run: 대상 관측 수·그룹 수·P/N/mixed 합계·기존 집계 차이·규칙 유효성 보고.
- apply: 대상 관측/규칙 변경과 경합하지 않는 일관된 스냅샷 및 잠금으로 한 트랜잭션에서 처리.
- `(product_id, rule_id)`로 upsert하여 남아 있는 집계 ID를 유지하고, 대상 버전의 member를 교체한다. 관측이 사라진 대상 버전 집계만 제거한다. 다른 버전은 건드리지 않는다.
- member에는 mixed를 포함한 모든 기여 관측을 연결한다.
- 쓰기 중 실패하면 전부 rollback. 커밋 후 건수·Q·member를 원본 그룹 집계와 대조한다.
- 동일 입력으로 재실행해 결과와 집계 ID가 유지되는지 확인한다.

현재 관측 importer는 집계가 있는 상품의 관측 변경을 차단한다. 첫 집계 이후에는 관측 변경과 대상 집계 재생성을 조정하는 갱신 절차가 필요하다. 보호 조건을 삭제하지 않는다. 초기 연결 작업은 원문/관측 쓰기를 중단한 유지보수 구간에 실행하고, 재개 전 원자적으로 집계를 확정한다.

## 5. 요구 프로필과 α의 초기 정책

연결 확인용 초기 설정을 `config/review_aspect_profiles.yaml`에 버전과 함께 둔다. 수치는 검증된 최적값이 아니라 재현 가능한 시작 정책이다. LLM이 α를 결정하지 않는다.

- 기본: 해당 부품에 등록된 고유 aspect_code 각각의 원점수 b=1.
- `priority=quiet` 또는 `noise_sensitive=true`: 등록된 fan_quietness/coil_quietness/pump_quietness의 b=3. 두 조건이 함께 있어도 한 번만 적용.
- 그 밖의 원점수는 1로 유지. 없는 속성을 새로 만들지 않는다.
- `α=b/Σb`; 적용 가능한 속성이 없으면 R=0.5.
- 용도는 아래 조건 선택에 반영한다. 리뷰 빈도·관측 유무로 α를 바꾸지 않는다.
- 같은 요청·같은 부품 후보에는 같은 프로필을 적용한다. 후보별 근거 유무나 사양에 따라 α를 다시 정규화하지 않는다. 예: 펌프가 없는 쿨러는 펌프 근거를 중립 처리하며, 세부 분류 프로필은 후속 정책으로 분리한다.

### 조건 선택

규칙 등록 내용을 읽어 `(part_type, aspect_code, context_code)`의 명시적 매핑표를 구성한다. 아래는 초기 선택 원칙이다.

| 속성 종류 | 초기 선택 조건 |
|---|---|
| 설치·조립·BIOS·포트·버튼 편의 | 등록된 `installation_or_use` |
| 케이스 마감 | `visual_or_physical_inspection` |
| 인식·동작·연결 안정성 | `duration_unknown`; 초기/장기 조건은 요청이 이를 명시하고 지원 규칙이 있을 때만 선택 |
| 작업 부하 관련 성능·열·정숙성·공기흐름 | 명시적 게임→gaming_load, 명시적 가벼운 사용→low_load, 구체적 비게임 작업→named_non_gaming_workload, 불명→workload_unknown |
| 주변기기 규칙 | 신규 20개 정의를 읽고 각 속성의 실제 등록 context_code로 명시 매핑; PC 조건명을 추정해서 사용하지 않음 |

`purpose`의 실제 허용값과 기본값 출처를 조사해 매핑표를 확정한다. 단순 office 목적을 곧바로 low_load로 단정하지 않는다. 인코딩 등 구체적 작업이 확인될 때만 named_non_gaming_workload를 고른다. 팬 최대 RPM 같은 특정 조건은 명시 요청 없이는 선택하지 않는다.

조건을 요청에서 선택한 뒤 해당 후보에 그 조건의 관측이 없으면 Q=0.5다. 이때 workload_unknown/low_load 등 다른 집계로 후보별 fallback하지 않는다. 필요한 규칙 자체가 없으면 설정 누락으로 진단하고 해당 속성은 중립 처리한다. 같은 경험의 일반/세부 조건을 동시에 가중하지 않는다.

현재 조건 코드는 넓은 범주이며 GPU 조합, 해상도, 드라이버 등 모든 세부 조건을 구조화하지 않았다. 본 연결은 해당 범주 수준의 적합도다. 근거 문장의 세부 설정을 자동 필터링했다고 설명하지 않는다. 이를 엄격히 비교할 조건 추출·정규화는 후속 설계다.

## 6. R 계산과 최종 점수 적용

```text
R(product, profile) = Σ α_a × Q(product, selected_rule_a)
```

관련 관측이 없는 속성은 Q=0.5를 사용하고 α는 유지한다. 유한 관측과 양수 k에서 Q/R은 0과 1 사이이며 중립은 0.5다. Q=0.5만으로 근거 없음을 판정하지 않는다. 균형 P=N 및 mixed-only도 0.5이므로 P/N/mixed와 적용 rule_id를 함께 전달한다.

예: 게임용 GPU 기본 프로필에서 fan_quietness의 α=0.2, P=3/N=1/k=4라면 Q=0.625다. 나머지 속성이 모두 중립이면 R=0.525다. 기존 행동 지표 0.75/0.25로 재양자화하거나 100점으로 확대하지 않는다.

```text
최종점수 = round(Σ 기존실제가중치[축] × 축점수
                 - 기존 Pending 패널티 - 기존 데이터누락 패널티
                 + 기존 RAM 보너스, 3)
```

리뷰 외 조건이 같으면 반올림 전 차이는 `w_review × (R_new - review_old)`여야 한다. 위 예에서 실제 w_review=0.20이고 이전 리뷰 값이0.5라면 +0.005다. 다른 축의 기존 값 범위나 정규화 방식을 이번에 수정하지 않는다.

## 7. 엔진·DB 연결 구조

### 후보 식별과 조회

`Candidate.product_id: str | None`을 추가하고 catalog_repo의 PC/주변기기/variant 재조회 등 모든 DB 생성 경로에 p.id를 넣는다. product_key 문자열로 상품을 추측하지 않는다. 기존 데모 후보처럼 product_id가 없으면 R=0.5와 식별자 없음 이유를 반환한다.

새 `src/repo/review_aspect_repo.py`는 지정 버전·전체 후보 product_id의 집계를 한 번에 조회한다. 상품별 N+1 조회를 피한다. 추천 요청에서는 하나의 일관된 집계 스냅샷을 사용하고, 전역 캐시를 도입하면 갱신/무효화 정책을 별도로 명시한다. 초기에는 요청 범위 캐시만 사용한다.

새 `src/services/review_aspect_score.py`는 프로필 선택과 순수 산술 계산을 담당한다. DB 호출과 계산을 분리하여 테스트에서 집계를 주입할 수 있게 한다. 후보별 반환값은 R, 프로필/분석 버전, 사용 rule_id·α·P/N/mixed/Q·αQ, 중립 이유, 집계 ID다.

API 추천 경로와 로컬 pipeline 모두 같은 서비스를 사용한다. 기존 순수 엔진의 단위 테스트에 DB 연결을 강제하지 않도록 조회 결과를 랭킹에 주입한다. 명시된 오프라인/데모 실행만 중립 모드를 허용한다. DB 오류·미생성 집계를 정상적인 “리뷰 없음”으로 조용히 숨기지 않는다. DB 추천 경로에서 저장소 오류는 요청 실패와 명확한 진단으로 처리한다.

### 요구 프로필 보존

추천 run_id가 있는 API 실행은 `engine.review_requirement_profile`에 run_id당 한 행을 저장한다. parts에는 부품별 α·선택 조건·적용 이유·선호 출처를 넣는다. profile_version과 analysis_version을 명시한다. run_id 없는 로컬 pipeline은 동일 프로필을 실행 결과에 반환하고 가짜 run을 만들지 않는다.

전체 축별 점수 이력은 상위 추천 결과 설계의 책임이다. 이번에는 새 전체 점수 이력 테이블이나 배치 이력을 만들지 않는다.

## 8. 설명·로그 전환

랭킹과 설명에서 default_risk_store, REVIEW_OBS 행동 플래그, 과거 “검토 권장/중앙값 대비 특이 없음” 문구를 제거한다. 다른 기능에서 사용 중인 저장소 자체를 삭제하지 않는다.

- `breakdown["리뷰"]`는 R로 유지하고 상세는 별도 DTO 필드로 전달한다. specs에 섞어 데이터누락 패널티를 바꾸지 않는다.
- stage5는 실제 랭킹에 사용한 프로필·집계 정보를 받아 설명한다. 별도로 현재 DB를 다시 조회해 다른 시점의 근거를 표시하지 않는다.
- 긍정/부정/mixed를 균형 있게 제시하고 관측 ID·원문 ID로 근거를 추적한다. 외부 URL이 없으면 링크를 만들어내지 않는다. 기존 Amazon URL을 붙이지 않는다.
- 점수0.5 여부 대신 건수/조회 결과로 “관측 있음”, “균형”, “mixed만 있음”, “요구 조건 근거 없음”을 구분한다.
- 기여도는 기존 전체 축 기여도 처리와 실제 w_review를 사용한다. Q/R을 확률이나 진위 판정으로 표현하지 않는다.
- 주변기기는 R과 외부 가중치0을 함께 설명하여 관측이 순위를 바꿨다고 오해시키지 않는다.

## 9. 구현 순서와 검증

| 순서 | 작업 | 완료 확인 |
|---|---|---|
| 1 | DB 입력/버전/상품 유형 재확인, 프로필 설정 및 룰 매핑 동결 | 관측3676 기준에서 차이 발생 시 이유 기록; 승인 필터 없음 |
| 2 | 집계 CLI·저장소 구현 | dry-run 수치, 트랜잭션 갱신, 근거 membership 검증 |
| 3 | 후보 product_id 전달·프로필·R 순수 계산 구현 | 식별자·조건·중립·동일α 테스트 |
| 4 | stage3b 및 두 추천 호출 경로 연결 | 리뷰 축만 변경, 기존 가중치/패널티 유지 |
| 5 | stage5/통계/주변기기 연결 | 계산 근거와 설명 일치, 주변기기 순위 불변 |
| 6 | 격리 DB 통합 테스트 | 원문→관측→집계→R→최종점수 검증 |
| 7 | 실제 집계 apply 및 요청별 smoke 실행 | 실제 후보 점수와 손계산 비교, 변경 근거 보고 |

필수 검증 사례:

- P=3,N=1,k=4→Q=0.625; mixed만3건→0.5; 무관측→0.5.
- mixed를 추가해도 P/N/Q는 불변이고 member와 mixed 건수만 증가.
- 후보별 관측 누락 시 α 유지, 관련 조건 부재 시 다른 조건 fallback 금지.
- 게임 정숙성과 저부하 정숙성을 분리하고 quiet+noise_sensitive 중복 증폭 금지.
- 분석 버전 혼합 금지, 다른 상품 관측 유입 금지, 합성 제외, 현재 DB 관측의 과거 승인상태 무관.
- 집계 재실행 멱등성, 삭제된 관측 반영, 중간 오류 rollback, 변경 동시성 보호.
- 같은 나머지 축에서 반올림 전 점수 차이가 w_review×ΔR과 일치.
- 기존 priority/noise_sensitive 외부 가중치, Pending/데이터누락 패널티·RAM 보너스·동점 규칙 불변.
- 주변기기 리뷰 가중치0일 때 순위 불변. product_id 없는 데모는 명시적 중립.
- R=0.5인 실제 관측을 “근거 없음”으로 오표시하지 않고, 설명 근거가 적용 rule/member에 포함됨.

DB 테스트는 다음 원칙을 따른다. 개발 DB truefit에 테스트 픽스처를 넣지 않는다.

```bash
docker compose up -d db
PYTHONPATH=. UV_CACHE_DIR=/tmp/uv-cache TRUEFIT_REQUIRE_TEST_DB=1 uv run pytest -q
```

구현 중에는 관련 테스트를 우선 실행하고 완료 시 저장소의 필수 검증을 수행한다. 필수 seed 누락은 테스트 준비 실패로 처리한다. 실제 DB 집계 적용과 읽기 검증은 테스트와 구분하여 기록한다.

## 10. 완료 조건

1. 현재 DB의 전체 대상 관측을 승인 구분 없이 선택 버전으로 집계하고 P/N/mixed·Q·근거가 일치한다.
2. DB 후보의 실제 product_id로 집계를 읽고 요청별 동일 프로필을 적용한다.
3. PC의 기존 행동 지표 리뷰 축을 R이 완전히 대체하며 기존 외부 가중합은 유지된다.
4. 주변기기 R을 조회할 수 있으나 기존 가중치0 정책과 순위는 유지된다.
5. 최종 견적의 리뷰 설명이 실제 점수 계산에 사용한 데이터와 일치한다.
6. 미관측 중립 처리, 저장소 오류 처리, 기존 관측 갱신 보호가 검증된다.
7. 격리 DB 테스트와 실제 데이터 연결 확인 결과를 보고한다. 이 완료는 추천 품질·관측 의미 정확성의 전수 인증이 아니다.

## 11. 기존 문서와의 관계

`추천엔진_리뷰속성_반영계획.md`와 `추천엔진_리뷰적합도_계산알고리즘.md`의 Q/R·외부 가중합 유지 원칙을 따른다. 다만 과거 문서의 “검수된 관측만” 및 “k=4는 미확정 예시” 서술은 이번 연결 범위에서는 최신 사용자 결정과 DB 등록 상태로 대체한다: 현재 같은 테이블에 통합된 모든 관측을 사용하고 등록 k를 읽는다.

본 문서의 균등 기본 α와 quiet 배수, 요약/설명 연결 정책은 연결 확인용 초기 구현 결정이다. 구현 완료 후 관련 기존 문서와 오래된 리뷰 설명 주석을 함께 정리하되, 이번 계획 작성에서는 코드·DB·기존 문서를 변경하지 않는다.
