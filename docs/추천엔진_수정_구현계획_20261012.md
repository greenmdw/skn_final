# 추천 엔진 수정 구현 계획

작성일: 2026-10-12
상태: 구현 전 계획. 2026-10-12 D1~D5와 정책 대조 검토의 다섯 가지 수정 사항 반영(광고 선택과 탐색 범위 확장은 이번 구현에서 제외). 정책 근거는 [추천엔진_수정계획.md](추천엔진_수정계획.md)(이하 "정책 문서")이며, 이 문서는 그 정책을 실제 코드 변경 단위로 나눈 것이다. 이 문서 작성으로 코드·설정·DB는 바뀌지 않는다.

## 1. 요약

- 정책 문서의 변경을 0~7단계로 나눈다. 단계마다 커밋을 따로 두되, **1~5단계는 같은 규칙 버전(`computer-rules-v12`)으로 묶어 한 번에 배포**한다. 단계 사이의 중간 상태가 사용자에게 나가지 않게 하기 위해서다. 예를 들어 RAM 가산점만 빠지고 2개 구성이 아직 없으면 단품 RAM이 다시 키트를 이긴다(개발요청 7번 회귀).
- **광고 선택(6단계)은 이번 구현에서 제외한다**(2026-10-12 결정). 6단계 절은 다음 구현을 위한 계획으로만 남긴다. 이번 구현의 최종 선택은 기존대로 원래 추천 점수 합 최대화다.
- 화면 변경은 `web/`을 직접 고치지 않고 `docs/개발요청_프론트엔드_추천점수표시.md`로 요청한다. API 변경은 기존 필드를 유지하고 필드를 추가하는 방식으로만 한다.
- 주변기기 추천 경로(`peripheral_*`, `verify_per_item`)는 바꾸지 않고 회귀만 확인한다.
- 유지 부품에도 구매 부품과 같은 필수 정보 기준을 적용한다. 필수 정보는 실제 조합·사용자 요구별로 정하고, 누락이면 보완·재평가 후에도 해결되지 않은 조합을 보류한다. 전력·크기 여유를 단위·출처와 함께 기록하고, 표시에는 snapshot의 원본 정밀도를 사용한다.

### 3.1. D4 상세 — 조합 필수 호환 축

**필수 정보의 의미**: 선택된 조합에서 그 검사에 필요한 **구매·유지 부품의** 값이 하나라도 없으면 그 조합을 보류하고 일반 추천용 탐색에서 뺀다. 다른 유효 조합이 있으면 그것을 고르고, 없으면 기존 데이터 조회·수집·재탐색 한도 내에서 보완 후 재평가한다. 미해결이면 `not_recommendable`과 `required_info_missing` 사유를 낸다(D3). 값이 있고 적용되는 호환 조건을 어기면 해당 조합은 무조건 탈락한다. 신뢰도 감점(위반 20, 확인 필요 6)과 80점 기준은 바꾸지 않는다.

**필수가 아닌 경우**: 사용자 필수 요구나 해당 조합의 작동·장착 조건에 필요하지 않은 정보는 없다는 이유만으로 조합을 빼지 않는다. 기존 '확인 필요' 또는 정보 부족 표시·감점 정책을 유지한다. '어댑터 필요'나 '낮은 속도로 동작'은 그 상태만으로 필수 정보 누락이라고 단정하지 않되, 실제 연결 경로의 필수 정보와 사용자 필수 성능은 별도로 확인한다. '확인 필요'의 중요도별 판정 세분화·새 감점은 이번에 도입하지 않는다.

필수 목록은 축 이름만으로 끝내지 않고 세부 조건·필요 키·적용 조건을 함께 정의한다. `gpu_connector`는 실제 직접 연결 또는 제조사가 허용한 어댑터 연결 경로에 필요한 종류·개수를 검사한다. 쓰지 않는 커넥터 개수는 요구하지 않는다. `ram_speed`는 일반 안내일 때와 사용자 필수 속도일 때를 구분하며, 후자이면 해당 CPU·메인보드·RAM 2개 구성에서 지원되는 속도의 근거가 필요하다.

누락 수는 2026-10-12 개발 DB 카탈로그 기준이다.

| gpu_connector(개수) | 실제 연결 경로에 필요한 8핀·16핀 개수가 충분한가 | 해당 경로에서 필요하면 필수 | 종류만으로 필요한 개수를 충족했다고 판단하지 않음. 보조 전원이 필요 없거나 쓰지 않는 커넥터 정보는 비적용 | 파워 2개에 개수 정보 누락. 필요한 경로에서 보완·보류하며 수정된 적용 조건으로 영향 재측정 |
| ram_slots | RAM 모듈 수 ≤ DIMM 슬롯, 그리고 총용량 ≤ 최대 용량 | 필수(두 조건 모두) | 지금은 한쪽만 알아도 통과(F5)라 고친다 | 없음 |
| m2 | M.2 SSD면 메인보드 M.2 슬롯이 1개 이상 | 필수(M.2 SSD만) | 슬롯이 없으면 장착 불가. SATA SSD는 비적용. PCIe 세대 차이는 속도 저하라 '확인 필요' 유지 | 없음 |
| ram_speed | 선택한 CPU·메인보드·RAM 2개 구성의 지원 속도와 사용자 요구 | 사용자 필수 속도가 있으면 필수, 그 밖에는 기존 안내 | 낮은 속도로의 동작이 허용되는 요청은 기존 '확인 필요' 유지. 사용자 필수 속도 미확인은 보류, 확인된 미달은 요구 미충족으로 제외 | CPU·2개 구성의 지원 속도 근거와 사용자 요구까지 포함해 영향 재측정 |

**영향 확인**: 앞서 측정한 구매 부품 기준의 누락은 파워 2개·케이스 3개의 길이 정보와 케이스 5개의 수랭 지원 정보 등이다. 이 숫자는 수정된 정책 전체의 영향이 아니다. 유지 부품 누락·필요 커넥터 개수·사용자 필수 속도 조건을 포함해 0·7단계에서 다시 측정한다. 보류 대상을 데이터 보완 목록에 남기고, 값이 채워지면 필터·조합 조건을 다시 확인한 뒤에만 후보로 복귀시킨다.

**다른 선택지**
- **장착 가능 여부만 필수로**(socket, memory, motherboard_case, gpu_len, cooler_height, power)
  - 장점: 지금 데이터로는 빠지는 부품이 없다.
  - 단점: data_gap 감점을 없앤 뒤 psu_length·gpu_slots·radiator 정보가 빈 부품이 검사를 피해 뽑힐 수 있다. 규칙 파일 주석에 적힌 "케이스가 늘 가장 싼 한 종으로 고정"된 원인이 이것이었다.
  - 수정 계획 문서 §5.2가 필수 예시로 든 "RAM 슬롯·최대 용량, 필요한 전원 커넥터"도 빠진다.
- **ram_speed·커넥터 개수를 항상 필수로**
  - 사용자 필수 속도와 실제 연결 경로를 고려하지 않으면 비적용 정보까지 누락으로 처리한다.
  - 이번에는 위 표대로 적용 조건을 사용한다. 필요한 정보는 보유율과 무관하게 확인하고, 일반적인 속도 제한 안내는 기존 정책을 유지한다.

**후보 부족·정보 보완·재평가 흐름**
- Pass가 0인 슬롯이 있으면 [3-B]로 진행하지 않고 Pending을 보완 대상으로 모은다. 후보의 누락 키·사유와 보완 시도 상태를 보존하며, Pass가 적다는 이유로 Pending·Fail을 승격하지 않는다.
- 서비스가 기존 데이터 조회·수집 경로에서 카탈로그·기존 스펙 캐시·이미 제공된 사용자 정보를 다시 확인한다. 기존 경로가 지원하는 보완만 기존 재탐색 횟수·시간 한도 안에서 수행한다. 사용할 수 있는 경로가 없거나 조회가 실패하면 그 사유를 기록하고 미확인 상태를 유지한다. 근거 없는 스펙·성능 등급을 만들어 채우지 않는다.
- 새로운 근거를 얻으면 판매 단위·RAM 2개 구성·부품 필터를 다시 적용하고, Pass로 확인된 후보만 점수 계산·조합 탐색으로 복귀시킨다. 보완 중 가격이나 구성 입력이 바뀌었으면 기존 점수를 재사용하지 않고 다시 계산한다.
- 엔진에 `CandidateShortage(slots: dict[slot, {pass, pending_reasons, fail_reasons}], enrichment_attempts)` 예외를 둔다. 보완·재평가 후에도 Pass가 0이거나 보완 경로·한도가 없을 때 [3-B] 진입 전에 던진다. 보완과 조합 재탐색이 각각 별도 무제한 루프를 만들지 않도록 실행 단위의 기존 한도를 공유한다.
- [`execute_recommendation`](../src/services/recommendation_service.py): 이 예외를 잡으면 `reasoning_log`에 `{"step": "추천 불가", "code": "candidates_insufficient", "slots": ...}`를 남기고 run을 failed로 둔다. 기존 `_mark_run_failed`에 사유 인자를 추가하며, 컬럼을 새로 만들지 않아 마이그레이션은 없다.
- `get_result_status`: 이 사유가 있으면 `error.code = "candidates_insufficient"`와 슬롯별 사유 문장("GPU — 성능 등급 정보가 없는 후보 11개, 요구 등급 미달 8개")을 돌려준다.
- [`quote_compare._recommend`](../src/services/quote_compare.py): 같은 예외를 기존 `LookupError` 경로로 바꿔 "비교 불가" 사유로 낸다.
- 보류 후보 수·누락 사유·사용한 보완 경로·출처·시도 횟수·복귀 여부를 trace에 기록한다. 새 범용 수집기나 자동 카탈로그 갱신 기능은 이번에 만들지 않는다. 기존 조회 경로로 해결되지 않는 정보는 데이터 보완 목록 또는 필요한 사용자 확인 사항으로 남기고, 보완된 데이터나 사용자 정보로 다시 실행하면 동일한 필터부터 재평가한다.

**데모 경로**: `pipeline.py`의 목 카탈로그(`data/scenarios`)에 Pass가 0인 슬롯이 생기면 시나리오 데이터를 고친다. 승격을 되살리지 않는다.

**테스트**
- 수정: `test_stage3a_hardfilter_pc.py`(승격 테스트 → "Pending은 절대 keep에 없고 held에 있다"), `test_review_rank_formula.py`의 `verdict` 매개변수, `test_research_loop.py`의 Pending 픽스처.
- 신규:
  - 가격 0·음수 후보는 Pending이 된다.
  - 전부 Pending이면 기존 한도 내 보완·재평가 후에도 Pass가 없을 때 `CandidateShortage`가 난다. 전부 Fail이면 승격 없이 후보 부족을 안내한다(정책 §10 고정 시나리오).
  - 보완 성공 시에만 Pass로 복귀하고 가격·RAM 구성·점수를 재계산한다. 보완 불가·실패·한도 소진은 사유를 남기며 무한 재시도하지 않는다.
  - 외부 수집·조회는 테스트에서 대체하며 실제 LLM 호출을 기본 검증에 추가하지 않는다.
  - feasibility는 Pass만 센다.

### 3단계 — RAM 2개 구성(정책 §2.5)

**새 모듈 `src/engine/ram_config.py`**
- `as_pair(cand) -> tuple[Candidate | None, reason | None]`. 모듈 수는 기존 `parse_module_count`로 읽는다.
  - 모듈 2개 키트: 그대로 쓰고 `purchase_qty=1`.
  - 단품: `purchase_qty=2`, `unit_price=price`, `price=price*2`, `capacity_gb*=2`, `module_config="{n}GB × 2"`, `flags += ["ram_pair_from_single"]`.
  - `module_config`를 읽을 수 없음: `Pending("PENDING_SPEC_MISSING:module_config")`.
  - 3개 이상 키트: `Fail("EXCLUDED_RAM_NOT_PAIR:{n}")`. 다른 개수는 추후 고도화이며 자동 전환하지 않는다.

### 4단계 — 조합 적격성(정책 §2.3, §5.2~§5.4)

**설정**: `verification.required_axes`를 D4의 축·세부 조건·필요 키·적용 조건을 담는 규칙으로 정의한다. 사용자 필수 속도와 실제 전원 연결 경로도 입력으로 전달한다. 구매·유지 부품에 같은 규칙을 적용하고, 카탈로그 보유율에 의존하지 않는다. `ranking.data_gap`을 삭제한다(이 단계에서 필수 정보 보류가 대신한다).

**[`stage4_optimize.py`](../src/engine/stage4_optimize.py)**
- `pc_compat_details`
  - 수랭 쿨러이면 cooler_height를 `skipped`(라디에이터 검사가 대신함)로 바꾼다(F4).
  - ram_slots는 두 하위 조건(모듈 수 ≤ 슬롯, 총용량 ≤ 최대)을 모두 알아야 `ok`다. 하나만 알면 `unknown`이고 `missing_slots`는 모르는 쪽이다(F5).
  - 각 행에 `applicable`, `required`, 세부 조건별 `missing_keys`와 `required_missing`을 추가한다. `missing_slots`는 설명·보완 대상 위치를 나타내는 보조 정보다. `info_missing`은 필수·선택을 포함한 필요한 입력의 실제 누락 여부로 계산하고, `unknown` 또는 `missing_slots`의 존재만으로 판단하지 않는다. 일부 조건이 `ok`여도 나머지 필수 키의 누락을 숨기지 않는다.
- 새 공통 `required_info_findings(chosen, spec, rules)`는 실제 조합·사용자 요구·D4 조건에 따라 적용 여부, 필요한 키, 구매·유지 부품의 누락, 확인된 요구 미충족을 반환한다. 탐색·상세 검사·최종 검증·재검증이 같은 규칙을 사용한다. 사용자 필수 속도의 확인된 미달은 요구 미충족으로 제외하고, 일반 속도 제한은 기존 '확인 필요'로 유지한다.
- 새 `_pc_required_missing(chosen, spec, rules) -> set[str]`
  - 탐색 노드마다 부르는 가벼운 검사다. 문장을 만들지 않는다.
  - 공통 규칙의 필수 누락 결과를 사용한다. 아직 선택하지 않은 구매 슬롯은 확정 누락으로 가지치기하지 않으며, 상대 부품이 정해진 시점에 구매·유지 부품 모두 검사한다(D2). 해당 조합에 적용되지 않는 세부 조건은 제외한다.
  - `pc_compat_details`의 `required_missing` 및 최종 검증의 blocking과 어긋나지 않도록 고정·무작위 조합으로 세 결과를 대조한다.
- `_max_score_search`·`_cheapest_compatible`: `_pc_known_failures` 다음에 `_pc_required_missing`로도 가지를 친다. 공통 규칙에서 확인된 사용자 필수 요구 미충족도 탐색에서 제외하고 `requirement_unmet` 사유로 구분한다. 새 카운터는 `pruned_required_missing`·`pruned_requirement_unmet`이다.
- `build_computer`: `BuildResult.eligibility = {"status": "recommendable" | "not_recommendable", "reasons": [{"code": "compat_violation" | "required_info_missing" | "requirement_unmet" | "budget_exceeded" | "no_compatible_set", "axes": [...]}]}`를 추가한다(D3). 예산 초과 최저가 세트와 비호환 진단 세트는 `not_recommendable`이다. 필수 누락이면 2단계와 같은 보완 한도를 사용해 재평가하고, 미해결이면 누락 위치·키·사유가 있는 진단 결과만 제공한다.

**조합의 전력·냉각·크기 여유 평가(정책 §2.3)**
- `BuildResult.margins`와 API·trace에 항목별 상태(`available`·`unavailable`·`not_applicable`), 입력·단위·출처·확인일·평가 조건·계산식을 추가한다. 선택된 구매·유지 부품을 함께 사용한다. 여유를 부품 추천 점수나 검증 점수에 더하지 않는다.
- 전력: CPU 최대 전력(없으면 TDP와 그 한계), GPU 전력, 기타 구성품의 예상 부하와 그 산정 근거를 분리해 기록한다. 전체 예상 부하와 파워 정격 대비 남는 용량을 W로 제공한다. 기존 호환 검사식 `CPU + GPU <= PSU × 0.9`와 요구 산정의 `1.5` 계수는 유지하면서 각각의 부하 범위·목적을 명시하고, 추가 여유 계산에서 두 계수를 중복 적용하지 않는다. 기타 부하 근거가 없으면 전체 전력 여유는 `unavailable`로 두고 기존 검사 결과만으로 전체 부하까지 확인했다고 표현하지 않는다.
- 크기: 케이스 허용치에서 실제 GPU 길이·공랭 쿨러 높이·파워 길이를 뺀 차이를 mm로 기록한다. GPU 두께와 라디에이터 장착 위치·다른 부품과의 간섭 조건도 함께 남긴다. 이미 확인된 음수 여유·장착 불가는 호환 위반으로 탈락시키고, 정보가 없으면 충분한 공간으로 대체하지 않는다.
- 냉각: CPU·쿨러·케이스·전력 설정·장착 조건을 기록한다. 기존 자료 중 조건이 비교 가능한 시험 근거가 있으면 그 조건의 온도·전력 여유를 기록한다. 자료가 없거나 비교 불가능하면 '확인 불가'와 사유를 낸다. 제조사별 쿨러 TDP 값의 단순 차이를 냉각 여유로 확정하거나 새로운 종합 점수·감점·시험 수집 기능을 만들지 않는다.

**[`stage3c_verify.verify_build`](../src/engine/stage3c_verify.py)**
- 신뢰도 산식·감점(위반 20, 확인 필요 6, 예산 20/15)·80점 기준은 그대로 둔다.
- `VerificationTarget`에 `eligible: bool`, `blocking: list[dict]`를 추가한다. blocking은 확인된 호환 위반 + 예산·사용자 필수 요구 미충족 + 공통 규칙의 `required_missing` 결과다. 구매·유지 부품 예외를 두지 않으며 감점 집계에서 빠진 필수 누락도 포함한다. 정상 추천·재검증 경로는 `chosen`·`spec`·`rules`를 필수로 전달하고, 필요한 검증 입력 자체가 없으면 적격으로 기본 처리하지 않는다.
- `passed = confidence >= CONFIDENCE_THRESHOLD and eligible`.
- `verify_set`(데모 주입)과 `verify_per_item`(주변기기)은 바꾸지 않는다.

**[`research_loop.py`](../src/engine/research_loop.py)**
- `_pick_best` 키를 `(eligible, confidence, -round)`로 바꾼다. 적격 라운드가 신뢰도만 높은 부적격 라운드에 밀리지 않게 하기 위해서다.
- 통과 종료는 바뀐 `passed`를 그대로 쓴다.
- 보완 가능한 필수 누락은 기존 조회·수집·재탐색 한도 안에서 보완하고 필터·점수·조합·검증을 다시 실행한다. 이미 확인된 비호환을 미확인으로 바꾸거나 보완 없이 적격으로 승격하지 않는다.
- 적격 라운드가 없으면 채택 라운드의 `eligibility`를 `not_recommendable`로 둔다.

**[`recommendation_service`](../src/services/recommendation_service.py)**: 부적격 결과도 부품표는 저장한다. reasoning_log에 `"추천 적격성"` 단계(사유 포함)를 남기고, 설명 요약 앞에 코드가 만든 안내 문장을 붙인다. LLM에 맡기지 않는다. `reverify_set`도 같은 적격성을 다시 계산한다.

### 5단계 — 저장·API·설명(정책 §6, §9)

**저장**
- `score_method_version`의 하드코딩 `"v1"`을 `ranking.score_method`(`pc-fit-v2`)로 바꾼다.
- run의 `engine_versions`에 `computer_rules: computer-rules-v12`를 추가한다.
- 리뷰 snapshot의 후보 항목에 `rank_breakdown`, `rank_weights`, `score_method`를 **선택 키로 추가**한다. `SNAPSHOT_VERSION`은 올리지 않는다. 읽는 쪽이 키가 없으면 "구 방식"으로 처리하므로 기존 run도 계속 읽힌다.
- snapshot의 `rank_score`·축별 점수·가중치는 중간 반올림 없는 계산값을 보존한다. 새 방식의 부품 표시·견적 평균·설명은 이 원본 값을 공통 함수로 읽는다. `numeric(8,4)`의 후보 점수는 기존 저장 계약으로만 유지하고 표시·평균·재순위의 원본으로 사용하지 않는다. 새 방식인데 원본 snapshot이 없거나 유효하지 않으면 `unavailable`로 표시하며 네 자리 값으로 조용히 대체하지 않는다.
- 적격성의 누락 키·보완 시도·재평가 결과와 4단계의 여유 평가 입력·출처·조건은 기존 run trace에 구조화해 보관한다. 새 컬럼이나 마이그레이션을 추가하지 않으며, 결과 API·재검증에서도 해당 근거를 일관되게 사용한다.

**API**(추가 필드만, [`src/schemas.py`](../src/schemas.py))
- 부품마다 `fit`을 추가한다.

  ```json
  {"status": "scored|legacy_method|unavailable",
   "score": 66.5,
   "axes": [{"axis": "가격", "points": 80.0, "weight": 0.45, "weighted_points": 36.0}],
   "method_version": "pc-fit-v2"}
  ```

  - 표시값은 snapshot의 원본 `x`에서 `Decimal(repr(x)) * 100`을 구한 뒤 `ROUND_HALF_UP`으로 소수 첫째 자리까지 한 번만 반올림한다. 이는 저장 반올림을 되돌리는 방법이 아니며, 계산 자체의 부동소수점 오차까지 제거한다고 가정하지 않는다. 정책 §7의 0.665 → 66.5, 0.605 → 60.5와 이중 반올림 경계를 테스트한다.
  - 사용자가 교체한 부품도 snapshot 풀에 있으면 그 점수를 쓴다. 없으면 `unavailable`이다.
  - 기존 `v1` run은 `legacy_method`로 표시하고 점수를 100점으로 변환하지 않는다.
- `totals.avg_fit_score`: 점수가 있는 선택 부품의 snapshot 원본 `S_final` 평균 × 100이다. 개수를 함께 준다. 부품별 표시 점수나 네 자리 저장값을 평균하지 않고 평균 계산 후 표시 단계에서만 반올림한다. 광고 가산점은 넣지 않는다.
- 결과에 `eligibility`(4단계)를 추가하고, 상태 API에 `candidates_insufficient`(2단계)를 추가한다.
- 결과에 `margins`(4단계)를 추가한다. 필수 미확인은 `required_info_missing`과 필요한 구매·유지 부품의 키를 전달하고, 보완 경로·시도·재평가 결과도 trace와 함께 설명한다. 선택적 여유 자료 부족은 추천 부적격 사유와 구분한다.
- 기존 `budget_share`와 `explanation.contribution`(합 100% 비율)은 그대로 둔다. 정책 §9 끝 문단에 따라 새 값은 `points`·`weighted_points`라는 다른 이름을 쓴다.

**설명**
- [`stage5_explain`](../src/engine/stage5_explain.py)의 기여도는 3축 비율로 자연히 바뀐다. 머리글을 고친다.
- `result_advice.pick_basis`는 snapshot의 점수를 100점 표시로 바꾼다.

### 6단계 — 광고 선택(정책 §8) — 이번 구현 제외, 계획만 유지

2026-10-12 결정으로 이번 구현에서는 아래 내용을 만들지 않는다. 다음 구현 때 탐색 범위 확장 실험(D5) 결과와 함께 다시 검토한다. 아래 내용은 전체 풀 탐색을 전제로 한다. 이번 구현에서는 광고 관련 필드·설정·마이그레이션을 추가하지 않는다.

**데이터(D1 권장안)**
- `db/migrations/0013_product_promotion.sql`: `catalog.product_promotion(id, product_id → catalog.product, contract_ref, status ∈ {active, paused, ended}, starts_at, ends_at > starts_at, created_at)`와 `(product_id, starts_at, ends_at) WHERE status='active'` 인덱스.
- 함께 갱신할 것: `AGENTS.md` 기준선 목록(13 → 14개), `tests/test_schema_reduction.py`의 `EXPECTED_CHAIN`·`EXPECTED_TABLES`.
- `src/repo/promotion_repo.py`의 `active_product_ids(conn, product_ids, at) -> set[str]`는 계약이 여러 개여도 `DISTINCT product_id`다. 후보 적재와 같은 트랜잭션에서, 판정 시각을 고정해 읽는다.

**정책 설정**: `selection.ad_preference: {enabled: false, policy_version: ad-select-v1, beta: 0.01, epsilon: 0.01, node_cap: 150000}`. 검증 규칙은 다음과 같다.
- `beta`·`epsilon`은 유한한 0~0.01이다.
- `enabled`는 bool이다.

음수·NaN·상한 초과는 `RequirementRuleError`를 낸다.

**엔진(DB 없음)**
- 서비스가 Pass 후보에 `ad_bonus`(광고 대상이면 beta, 아니면 0)를 붙인다. 이 값은 `score`·`breakdown`과 별도 필드이며, 보류·제외 후보에는 붙이지 않는다.
- `stage4_optimize`에 `_select_with_ad_preference(pools_full, baseline, policy, …)`를 추가한다.
  1. 꺼져 있거나 풀에 광고 후보가 없으면 baseline을 그대로 반환한다. 정책 §8.3의 "광고가 없으면 원래 결과와 같다"는 이 분기로 보장한다.
  2. 1차 탐색: 전체 Pass 풀에서 `Q_best`를 구한다(D5). 적격성 가지치기를 함께 쓰고, top-N 결과를 초기 해로 쓴다.
  3. 슬롯별 허용 하한: `S_i + Σ_{t≠s} maxS_t >= N·(Q_best − ε)`를 만족하지 않는 후보는 E에 들어갈 수 없으므로 미리 뺀다. 정확성을 해치지 않는 축소다.
  4. 2차 탐색: `Q(C) >= Q_best − ε`인 조합 중 `R(C) = Q + B`를 최대화한다. 상한은 "현재 R + 남은 슬롯의 max(S+b)", 하한 가능성은 "현재 ΣS + 남은 max S"로 가지를 친다. 비교는 반올림 전 `fsum` 평균으로 한다.
  5. 동점이면 Q가 높은 쪽, 가격이 낮은 쪽, 제품 키 순서로 정한다.
  6. 어느 탐색이든 노드 한도에 걸리면 광고 우대를 중단하고 baseline을 쓴다(`search_complete=false`).
  7. 진단 세트(`not_recommendable`)에는 적용하지 않는다.
- `BuildResult.selection`: `policy_version`, `beta`, `epsilon`, `search_complete`, baseline(키·Q·가격), 선택(Q·B·R), 광고 적용 품목, `changed_by_ad`. `totals.avg_score`는 Q 그대로다.
- 재탐색 루프는 라운드마다 `build_computer`를 다시 부르므로, 최종 선택 조합은 기존 검증을 다시 받는다. 가산점은 매번 새로 계산되어 누적되지 않는다.
- 견적 비교(`quote_compare`)와 데모(`pipeline.py`)에는 광고를 넘기지 않는다. 같은 돈으로 우리가 추천하는 결과를 비교하는 기능에 광고 우대를 섞지 않는다.

**저장·설명**
- reasoning_log에 `"광고 선택 정책"` 단계(위 selection 메타)를 저장하고, `engine_versions`에 `ad_policy`를 저장한다.
- 부품 API에 `ad: {is_ad, bonus, preferred_by_ad}`를 추가한다.
- 설명 안내 문장은 코드가 만든다. "원래 적합도가 비슷한 후보 중 광고 제품을 우대해 선택했습니다"와 원래 적합도를 표시하고, LLM 입력에는 넣지 않는다.

**테스트**: 신규 `tests/test_ad_selection.py`(순수 엔진)와 DB 테스트. 정책 §8.6의 광고 관련 10개 항목을 각각 다룬다.
- 광고를 켜고 꺼도 S·avg·신뢰도가 같다.
- 제품당 1회만 적용되고 RAM 수량에 따라 늘지 않는다.
- `B(C) <= beta`이고, ε 경계값(정확히 ε 차이)에서도 판정이 일관된다.
- top-N 밖의 광고 후보도 평가된다.
- 탐색 한도에 걸리면 광고 우대를 중단한다.
- 기간이 끝난 광고는 0이다.
- Pending·비호환 광고 후보는 선택되지 않는다.
- 광고가 없으면 결과가 같다.

## 7. 이번 범위 밖

정책 문서의 추후 고도화 항목은 구현하지 않는다.

- '확인 필요' 판정 세분화
- RAM의 다른 개수와 기존 부품 재사용
- 벤치마크 기반 성능
- 소음 측정 축
- 예산 배분 실증 보정
- `α ≠ 1` 가격 민감도
- 주변기기 점수·광고 확장
- 광고 가산점에 따른 최종 선택(6단계, D1)
- 기본 조합 탐색 범위를 전체 후보 풀로 넓히는 실험(D5). 실험 때는 요청별 결과 차이와 탐색 단계 수·시간을 함께 측정한다
- 새로운 냉각 시험 수집·정량 모델·종합 점수 개발. 기존의 비교 가능한 자료가 있으면 조건과 여유를 기록하는 기능은 4단계에 포함하며, 자료가 부족하면 '확인 불가'를 표시한다.
- 기존 조회·수집 경로를 넘어서는 범용 스펙 수집기·자동 카탈로그 갱신. 기존 경로의 보완·재평가 연결과 미해결 사유 안내는 2·4단계에 포함한다.
