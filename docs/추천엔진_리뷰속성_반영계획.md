## 1. 핵심 결정

**상품의 리뷰를 속성별 평가표로 만들고, 사용자가 중요하게 생각하는 속성에 높은 비중을 주어 추천한다.**

다음 원칙을 적용한다.

1. 기존 리뷰 행동 지표를 **리뷰 속성 적합도**로 완전히 교체한다. 리뷰 몰림 등 작성 패턴은 새 추천 점수에 사용하지 않는다.
2. **최종 점수의 평가 축 가중합, 축별 가중치와 기존 요청별 가중치 조정 규칙을 그대로 유지한다.** 바꾸는 것은 기존 리뷰 축의 입력값뿐이다. 기본 설정에서는 기존 리뷰 가중치 `0.20`에 새 리뷰 적합도를 곱한다.
3. 리뷰 분석은 수집·갱신 시 미리 수행한다. 추천 시에는 저장된 속성 점수를 조회해 코드로 계산한다.
4. 속성 중요도는 근거와 버전이 있는 수동 설정으로 시작한다. 실제 선택 데이터가 충분해지면 학습으로 보정한다.
5. 관련 리뷰가 없으면 중립값을 사용한다. 근거 없음과 부정적 평가는 구별한다.
6. 추천 점수와 설명은 같은 속성 평가와 근거를 사용한다.
7. **저장·검색 기술은 PostgreSQL + pgvector로 고정한다.** 리뷰·속성 집계와 검색 임베딩을 같은 PostgreSQL에서 관리한다. 별도 벡터 DB는 도입하지 않는다.

기존 행동 지표에 일부 가중치를 남기는 방식이나, 기존 점수에 새 리뷰 점수를 추가하는 방식은 적용하지 않는다. 기존 지표를 리뷰별 신뢰 가중치로 바꾸어 간접 반영하는 것도 포함하지 않는다. 중복 리뷰 수집은 수집 단계에서 방지하며, 정확한 상품 식별은 별도의 데이터 품질 처리다.

가격·성능·밸런스·호환 여유·소음 등 다른 축의 계산과 기존 패널티는 변경하지 않는다. 리뷰 속성 적합도를 별도 평가 축으로 추가하거나 전체 축의 가중치를 재배분하지 않는다. 이 계획에서 설정·학습할 중요도는 리뷰 축 내부의 `α`다.

## 2. 방식과 용어

### 2.1 계산에 사용하는 네 가지 값

| 기호 | 이름 | 의미 |
|---|---|---|
| `Q` | 속성 점수 | 특정 상품의 특정 속성이 리뷰에서 얼마나 긍정적으로 평가됐는가 |
| `α` | 속성 중요도 | 이번 사용자가 해당 속성을 얼마나 중요하게 보는가 |
| `R` | 리뷰 속성 적합도 | 속성 점수와 중요도를 결합한 상품별 리뷰 점수 |
| `w_review` | 리뷰 축 가중치 | 가격·성능 등을 포함한 전체 추천 점수에서 리뷰가 차지하는 비중 |

`Q`는 상품 평가이고, `α`는 사용자 선호다. 리뷰 수가 많다고 중요도가 높아지거나, 사용자가 중요하게 생각한다고 상품의 속성 점수가 좋아지는 것은 아니다.

`α`의 합계를 1로 맞추는 것은 리뷰 축 내부의 계산이다. 전체 평가 축의 가중치를 다시 정규화하는 작업이 아니며, `w_review`를 포함한 기존 외부 가중치는 그대로 사용한다.

### 2.2 속성 기반 방식의 예

리뷰가 다음과 같다고 가정한다.

> 웹서핑할 때는 조용하지만 게임을 실행하면 팬 소리가 커집니다.

분석 결과는 두 관측이다.

| 상품 | 속성 | 사용 조건 | 평가 방향 |
|---|---|---|---|
| GPU A | 팬 정숙성 | 웹서핑·낮은 부하 | 긍정 |
| GPU A | 팬 정숙성 | 게임 부하 | 부정 |

조용한 게임용 PC를 요청받으면 `게임 부하` 조건의 정숙성 점수를 선택하고 중요도를 높인다. 해당 조건의 리뷰가 없으면 낮은 부하의 긍정 평가로 대신 채우지 않는다.

이 과정에서는 매 요청마다 요구 문장과 리뷰 문장을 LLM에 넣어 지지·반박을 판단하지 않는다. 사전에 추출한 속성·조건과 정해진 매핑 규칙으로 계산한다.

### 2.3 pgvector의 역할

임베딩은 OpenAI Embeddings API의 `text-embedding-3-small`을 사용하며 기본 출력 차원인 **1536차원**으로 고정한다. 리뷰 원문 전체와 검색 질문 모두 같은 모델·차원으로 임베딩한다. 공통 설정은 `model="text-embedding-3-small"`, `dimensions=1536`이며 행마다 모델·차원을 중복 저장하지 않는다. 이 모델은 검색 벡터 생성용이며 속성 관측 추출 모델의 결정과는 별개다.

pgvector는 관련 리뷰 문장을 검색하는 데 사용한다. 추천 점수는 검수된 전체 유효 관측을 집계한 Q와 중요도 α로 계산한다. 검색 유사도나 검색 상위 일부 리뷰로 Q를 대신하지 않는다.

상품·실제/합성 여부로 검색 범위를 제한하고, 반환한 문장은 현재 원문과 리뷰 ID에 연결한다. 검색한 근거를 LLM에 전달해 설명을 생성하는 기능은 이후 결합할 수 있지만, 추천 가중합 계산 자체는 바뀌지 않는다.

## 3. 전체 처리 흐름

```text
[리뷰가 수집되거나 갱신될 때]
원본 확보
  → 적재 전 실제/합성·출처·상품/옵션 확인
  → 사용 가능한 리뷰만 DB 적재
  → 속성·평가 대상·사용 조건·평가 방향·근거 추출
  → 상품별 속성 점수 Q 집계
  → 분석 버전과 함께 저장

[추천을 요청받을 때]
사용자 요구 해석
  → 부품별 속성 중요도 α와 적용 조건 결정
  → 필수 조건을 검사한 후보들의 속성 평가 조회
  → 리뷰 적합도 R 계산
  → 기존 가중합에서 리뷰 축의 입력값만 R로 교체하여 후보 점수 계산
  → 상위 후보 선택 → 조합 탐색 → 최종 검증
  → 리뷰 계산값과 근거를 상위 전체 점수 계산·설명에 전달
```

리뷰 점수는 후보를 상위 N개로 줄이기 전에 반영한다. 최종 선택 후 설명만 추가하는 것으로 완료하지 않는다. 높은 리뷰 점수가 예산·필수 스펙·호환성 위반을 상쇄하지 않도록 검증한다.

## 4. 리뷰 데이터 준비와 속성 분석

### 4.1 사용 가능한 리뷰

DB에는 사용 가능한 리뷰만 적재한다. 실제 자료 여부, 출처, 상품과 옵션의 일치 여부는 적재 전에 확인한다. 같은 제품군이라는 이유만으로 다른 용량·제조사·세부 모델의 평가를 합치지 않는다.

리뷰별 검수 상태는 저장하지 않으며, 검색·집계에도 검수 상태 필터를 두지 않는다. 확인이 끝나지 않았거나 상품이 불일치하는 자료는 운영 리뷰 DB에 적재하지 않는다. 합성 리뷰는 테스트에만 사용한다. 적재 후 삭제·철회된 자료는 검색과 집계에서 제외한다.

### 4.2 부품별 속성 초안

2026-10-01에 `data/reviews/computer_review_processed.jsonl`의 실제 표시 리뷰(`data_kind=real`) 2,548건에서 속성 관련 문장을 탐색하고 상세 사례와 반례를 확인하여 초안을 수정했다. 합성 리뷰 3,030건은 근거에서 제외했다. 이는 속성 후보를 정하기 위한 검토이며, 전체 리뷰의 상품·옵션 검수 완료나 운영 집계 승인을 의미하지 않는다. 세부 모델 매핑은 후속 작업으로 진행하며, 운영 적재에는 4.1의 상품 일치 기준을 적용한다.

| 부품 | 평가 속성 후보 | 구분할 대상·조건 |
|---|---|---|
| GPU | 팬 정숙성, 코일 소음 억제, 발열 관리, 동작 안정성, 게임 성능 만족도 | 소음원, 낮은 부하/게임 부하, 게임·해상도·설정·프레임 생성 사용 여부, 연결 부품, 정확한 모델 |

| 쿨러 | 냉각 성능, 팬 정숙성, 펌프 정숙성(수랭), 설치 편의 | 부하, 팬·펌프 설정, 사용 CPU, 장착 환경, 설명서·브라켓·체결·간섭 대상 |

| RAM | 인식·동작 안정성, 장착 편의 | 기본/XMP/EXPO/수동 오버클럭 설정, CPU·메인보드, 모듈 수·용량, 간섭 대상 |

| 케이스 | 조립 편의, 통풍, 마감·견고함, 포트·버튼 접근 편의 | 팬 구성, 장착 부품, 선정리 공간, 설치 위치 |
| 파워 | 팬 정숙성, 코일 소음 억제, 케이블 설치 편의 | 소음원, 낮은 부하/게임 부하, 제로팬 설정, 용량, 케이블 구성, 세부 모델 |

CPU의 전력 소모 만족도, SSD의 지속 쓰기 경험, 케이스의 진동·소음 억제는 근거 보강 후 검토할 후보로 둔다. 일반적인 파일 전송이나 읽기·쓰기 개선 경험을 캐시 소진 후 지속 쓰기 성능으로 해석하지 않는다. 디자인·RGB는 선호 방향이 달라 초기 공통 평가 속성에서 제외한다.

최종 속성 목록은 상품·옵션과 유효 관측을 검수한 뒤 확정한다. 첫 구현 후보는 GPU와 쿨러이며, 검수된 근거가 충분한 속성부터 적용한다.

관측 추출 시 다음 기준을 적용한다.

- 원문에 없는 사용 조건과 소음원은 미상으로 보존한다. “조용하다”만으로 게임 부하의 팬 정숙성을 판정하지 않는다. 팬 소음과 고주파 평가는 분리한다.
- 실제 사용 경험과 기대·전언을 구분한다. “펌프 문제 없길”, “오래 쓰겠죠”, “성능이 좋았으면”은 긍정 관측으로 집계하지 않는다.
- 초기 정상 작동과 장기간 무고장 경험을 구분한다. “온도가 안정적”은 냉각·발열 평가로 분류하며 동작 안정성에 중복 집계하지 않는다.
- 설치 편의는 실제 설명서 사용·체결·선정리·간섭 경험으로 판단한다. 단순 장착 후 인식 성공은 인식·동작 안정성으로 분류한다.

각 속성은 높은 점수가 무엇을 의미하는지 정의한다. 작성자가 “소리가 커서 좋다”고 말해도 정숙성 관점에서는 낮은 평가다. 선호 방향이 사람마다 다른 속성은 관측 내용을 보존하고, 단일 긍정 점수로 표현하기 어렵다면 초기 대상에서 제외한다.

리뷰가 등록된 상품 자체의 관측만 저장한다. CPU 리뷰의 “기본 쿨러가 시끄럽다”처럼 다른 부품·부속품을 평가한 문장은 관측과 집계에서 제외하며 다른 상품으로 재연결하지 않는다. 리뷰 경험을 소음 측정값·벤치마크·고장 확률로 바꾸어 표시하지 않는다.

### 4.3 문장별 관측 형식

```json
{
  "product_key": "gpu-example-a",
  "review_id": "review-123",
  "target": "gpu",
  "aspect": "fan_quietness",
  "context": "gaming_load",
  "observation": "게임 중 팬 소리가 거의 들리지 않음",
  "direction": "positive",
  "evidence_text": "게임 중 팬 소리는 거의 안 들립니다",
  "analysis_version": "aspect-v1"
}
```

상품 정보, 현재 원문, 출처, 게시 시각, 실제/합성 여부도 함께 추적한다. 리뷰와 연결할 정확한 카탈로그 상품을 식별한다.

리뷰에 여러 속성이 있으면 각각 추출한다. “배송이 빠르다”, “최고다”처럼 부품 속성의 근거가 없는 문장은 집계하지 않는다. 추출에 LLM을 사용하더라도 등록된 속성·조건과 실제 원문 근거를 반환하게 하고, 없는 사실이나 집계 숫자를 생성하게 하지 않는다.

## 5. 속성 점수 Q

### 5.1 계산식

상품·속성·사용 조건별로 다음 식을 사용한다.

```text
Q = (P + k×0.5) / (P + N + k)

P: 유효한 긍정 근거 수
N: 유효한 부정 근거 수
k: 중립값으로 보정하는 강도, k > 0
```

리뷰 한두 건만으로 극단적인 점수가 나오지 않도록 `k`가 점수를 `0.5` 쪽으로 보정한다. 근거가 많아질수록 실제 긍정·부정 비율의 영향이 커진다.

`P,N ≥ 0`이고 근거 수가 유한하면 `0 < Q < 1`이다. 긍정 우세는 `0.5` 초과, 부정 우세는 `0.5` 미만이다. 이 값은 추천용 지표이며 요구 충족 확률이 아니다.

| 긍정 P | 부정 N | k=4일 때 Q |
|---:|---:|---:|
| 1 | 0 | 0.600 |
| 8 | 2 | 0.714 |
| 2 | 8 | 0.286 |
| 0 | 8 | 0.167 |
| 0 | 0 | 0.500 |
| 8 | 0 | 0.833 |

`k=4`는 설명용 예시다. 개발 평가에서 값을 선택하고 최종 시험 전에 고정한다.

### 5.2 집계와 결손 처리

- 같은 리뷰가 같은 속성·조건을 반복해서 말해도 한 번만 센다. 복제·재게시를 포함한 중복 리뷰 수집은 수집 단계에서 방지된다는 전제다.
- 서로 다른 속성이나 명확히 다른 사용 조건은 별도 관측으로 보존한다.
- 같은 속성·조건에서 긍정·부정을 분리할 수 없으면 `mixed`로 저장한다. 초기 버전에서는 P/N에서 제외하고 건수를 따로 기록한다.
- 언급 없음과 판단 불가는 P/N에 포함하지 않는다.
- 작성자 식별이 불가능하면 유효 리뷰 수를 독립 사용자 수로 표현하지 않는다.
- 속성 집계에 별도 상태 필드를 저장하지 않는다. 근거 없음은 `P=N=mixed=0`, 긍정·부정 균형은 `P=N>0`, mixed만 있는 경우는 `P=N=0, mixed>0`으로 건수에서 판별한다. 세 경우 모두 `Q=0.5`지만 설명은 건수에 맞게 구분한다.
- 분석·조회 실패나 잘못된 분석 버전은 실행 로그에 오류를 기록하고 해당 계산에 중립값을 적용한다. 실패를 건수 0의 정상 집계로 저장하지 않는다.

## 6. 요구 프로필과 속성 중요도 α

### 6.1 부여 원칙

중요도의 단위는 `사용자 요구 × 부품 종류 × 속성`이다. 같은 저소음 요구라도 GPU와 RAM에 동일한 속성표를 적용하지 않는다.

1. 부품별 기본 속성과 중요도를 선택한다.
2. 사용 용도에서 추론한 관심을 반영한다.
3. 사용자가 직접 표현한 우선순위와 양보 관계를 우선 적용한다.
4. 관련 없는 속성을 제외하고 중요도 합계를 1로 정규화한다.
5. 적용 이유와 명시적 선호·추론·기본값 여부를 기록한다.

“저소음 우선”과 “소음에 민감함”이 같은 요구를 표현한다면 중복 증폭하지 않는다. LLM은 선호 수준과 대상을 구조화할 수 있지만, 최종 수치 변환은 버전이 있는 규칙으로 수행한다.

### 6.2 초기값을 정하는 방법

“정숙성 > 냉각 성능 > 설치 편의”라는 순서는 정확한 비율까지 결정하지 않는다. 각 속성이 나쁜 상태에서 좋은 상태로 바뀔 때 어느 개선이 더 중요한지 비교하여 잠정값을 정한다.

아래는 정숙성 우선 쿨러 프로필의 비교 후보다. 확정된 운영값이 아니다.

| 후보 | 정숙성 | 냉각 성능 | 설치 편의 |
|---|---:|---:|---:|
| A | 0.45 | 0.35 | 0.20 |
| B | 0.60 | 0.30 | 0.10 |
| C | 0.75 | 0.20 | 0.05 |

실제 후보 제품에 적용해 순위와 최종 구성이 어떻게 달라지는지 확인하고 대표 사용자·담당자의 비교 평가로 초기값을 선택한다. 모든 속성 점수가 0~1이어도 같은 점수 차이의 체감 가치가 같다고 전제하지 않는다.

리뷰가 많거나 특정 속성이 자주 언급된다는 이유만으로 중요도를 높이지 않는다. 자료의 양은 Q의 보정에 반영한다.

### 6.3 후보 간 동일한 비교 기준

같은 요청의 같은 부품 후보에는 동일한 중요도를 적용한다. 한 제품에 특정 속성 리뷰가 없으면 그 속성의 Q를 중립으로 두고 중요도는 유지한다. 자료가 있는 속성만으로 후보별 중요도를 다시 나누지 않는다.

적용할 속성이 전혀 없으면 `R=0.5`로 처리한다. 적용 속성 목록과 P/N/mixed 건수를 이용해, 관련 속성은 있지만 자료가 없는 경우와 구분한다.

### 6.4 머신러닝은 후속 보정

데이터 수집 계약, 제약 선형 순위 모델, 평가·적용 절차는 [리뷰 속성별 가중치 머신러닝 적용 상세 계획](리뷰속성_가중치_머신러닝_적용계획_20261006.md)에 구체화한다.

학습하려면 다음과 같은 비교 사례가 필요하다.

```text
사용자 요구 + 실제로 비교한 후보들 + 후보별 속성 점수 + 사용자의 선택
```

초기 모델은 가중치 탐색 또는 제약을 둔 선형 순위 모델로 검토한다. 중요도는 음수가 아니고 합계가 1이어야 하며, 명시적 최우선 조건을 보존한다.

학습 대상은 리뷰 내부의 중요도 `α`로 한정한다. 기존 가격·성능 등 외부 축의 가중치와 요청별 조정 규칙은 학습·변경하지 않는다.

가격·성능·브랜드 때문에 선택한 결과를 소음 선호로 오해하지 않도록 비교 조건을 통제하거나 해당 요인을 함께 다룬다. 노출되지 않은 상품을 거절된 상품으로 보지 않는다. 리뷰 분석 라벨과 실제 선택 라벨을 구분한다.

별도 평가 자료에서 개선이 확인된 프로필만 학습값으로 전환한다. 자료가 부족한 프로필은 수동값을 유지한다. 리뷰 추출 모델을 학습했다는 이유만으로 중요도까지 학습됐다고 표현하지 않는다.

## 7. 리뷰 적합도와 최종 점수

### 7.1 리뷰 적합도

```text
R = Σ(α × Q)

α ≥ 0, 속성 중요도 합계 = 1
```

사용 조건은 요청에서 정한 규칙으로 선택한다. 같은 관측을 일반 조건과 세부 조건 양쪽에서 중복 계산하지 않는다.

가상 GPU 두 제품에 중요도 `정숙성 0.60 / 발열 관리 0.25 / 안정성 0.15`를 적용하면 다음과 같다.

| 후보 | 정숙성 Q | 발열 관리 Q | 안정성 Q | R |
|---|---:|---:|---:|---:|
| A | 0.80 | 0.70 | 0.90 | 0.790 |
| B | 0.30 | 0.90 | 0.90 | 0.540 |

같은 제품도 사용자 중요도가 달라지면 R이 달라질 수 있다. 제품의 Q 자체는 사용자마다 바뀌지 않는다.

### 7.2 기존 가중합 유지와 리뷰 축 입력값 교체

최종 점수의 계산 구조는 기존 평가 축의 가중합을 그대로 사용한다. 기존 기본 설정에서 유지하는 가중치는 다음과 같다.

| 평가 축 | 가중치 |
|---|---:|
| 가격 | 0.35 |
| 성능 | 0.25 |
| 밸런스 | 0.15 |
| 리뷰 속성 적합도 | 0.20 |
| 호환 여유 | 0.05 |
| 소음 | 0.00 |

```text
기존: S_old = Σ_j(w_j × x_j) − penalty
변경: S_new = Σ_j(w_j × x'_j) − penalty

x'_리뷰 = R
x'_j = x_j  (리뷰 이외의 모든 축)
w_j와 penalty는 동일 요청·동일 후보 기준으로 기존 계산값 유지

따라서 반올림 전 점수 차이:
S_new − S_old = w_review × (R − x_리뷰)
```

구현에서는 기존 리뷰 축이 반환하던 행동 지표 점수를 `R`로 바꾸고, 기존 가중합 계산에 그대로 전달한다. 새 리뷰 항을 가중합 바깥에 추가하지 않는다. 다른 축의 점수·패널티·반올림·동점 처리 규칙도 유지한다.

요청별로 외부 가중치를 조정하던 기존 규칙은 계속 적용한다. 그 규칙이 계산한 실제 `w_review`를 사용하며, 기본값 0.20을 모든 요청에 하드코딩하지 않는다. 이번 변경을 이유로 별도 가중치 조정이나 재정규화를 추가하지 않는다.

위 예에서 리뷰 외 기여도가 A는 `0.48`, B는 `0.51`이고 리뷰 비중이 `0.20`이면 최종 점수는 다음과 같다. 예시는 패널티가 없다고 가정한다.

```text
A: 0.48 + 0.20×0.790 = 0.638
B: 0.51 + 0.20×0.540 = 0.618
```

리뷰 반영으로 A가 앞서지만 최종 부품 구성은 예산·호환성·조합 탐색 결과에 따라 결정된다. 관련 근거가 없어 R이 0.5가 되더라도 과거 행동 지표 점수와 달라질 수 있으므로 이전 순위가 보존된다고 가정하지 않는다.

### 7.3 기존 소음 축 유지와 영향 확인

기존 소음 축의 소비전력·쿨러 유형 기반 계산, 가중치와 요청별 조정 규칙은 유지한다. 리뷰 정숙성은 리뷰 축 내부에서만 사용하며 기존 소음 축의 입력값으로도 넣지 않는다.

`w_review×α_noise`와 기존 소음 축의 비중을 함께 기록하여 최종 순위에 미치는 영향을 평가한다. 이 평가는 외부 가중치를 변경하기 위한 작업이 아니다. 조정이 필요하면 리뷰 내부의 중요도 `α` 후보를 비교하고 근거를 남긴다. 외부 축의 가중치 재배분은 이번 계획의 범위에 포함하지 않는다.

## 8. 초기 저장 범위와 기존 구조

원문은 review_document에 최신 본문 하나만 저장한다. review_document_revision, current_revision, revision_no, review_aspect_batch, batch_id, aggregate_batch_id는 초기 구조에서 제외한다. 과거 데이터 보호 트리거·배치 발행 상태·이력 보존 목적의 삭제 제한은 지금 구현하지 않는다.

수정 시 같은 리뷰 ID의 본문을 갱신하고 임베딩·관측·집계를 재생성한다. 과거 원문·Q·근거는 복원할 수 없다. 실행별 요구 프로필은 계산 입력으로 저장할 수 있지만 과거 집계에 연결되지 않으므로 과거 추천의 리뷰 근거를 재현한다고 표시하지 않는다. 최종 추천 결과의 저장은 상위 설계 범위다.

안정적인 리뷰 ID, rule_id, 관측 ID와 집계 ID는 유지한다. 분석 버전과 프로필 버전은 현재 계산 설정을 식별하는 메타데이터이며 이전 결과 보존을 의미하지 않는다. 설정 변경 시 전체 관측·집계를 교체하고 이전 규칙도 정리한다. 정상 서비스에서는 하나의 분석 설정만 사용한다.

기존 리뷰 테이블은 재사용하지 않는다. 신규 구조의 외부 FK는 catalog.product와 engine.recommendation_run만 참조한다. 상품별 default 옵션만 존재하는 현재 데이터에 맞춰 product_id를 직접 사용한다. review_target과 옵션 FK는 만들지 않는다.

출처는 source_code로 저장하고 이름·종류는 공통 설정에서 관리한다. 출처 테이블·URL·외부 리뷰 키·수집 시각은 저장하지 않는다. 중복 수집은 수집 단계에서 방지한다. 수정·재적재에는 최초 발급한 내부 리뷰 ID를 다시 전달한다.

검수 상태·중복 그룹·집계 상태는 만들지 않는다. 원문 전체만 저장한다. is_synthetic=false가 실제 리뷰이며 운영에는 실제 리뷰만 적재한다. 임베딩은 리뷰 ID와 벡터 두 컬럼만 저장하고 모델·차원·파이프라인은 공통 설정에서 관리한다.

추천 결과의 저장 단위·필드·다른 평가 축은 상위 전체 점수 설계에서 정의한다. 이 경로는 R과 현재 속성 집계·요구 프로필·근거를 전달한다. 화면 명칭은 ‘리뷰 속성 적합도’이며, 계산에 사용하지 않은 장점을 선택 이유로 생성하지 않는다.

예시는 실제 DB 값이 아니다. uuid는 식별자, text는 문자열, integer는 정수, numeric은 십진수, boolean은 true/false, jsonb는 구조화된 JSON이다. vector(1536)은 공통 임베딩 설정의 1536차원 벡터다. 같은 UUID는 같은 행을 가리킨다. 카탈로그 상품과 추천 실행은 먼저 존재해야 한다.

### 9.1 `evidence.review_document`

리뷰 자체의 식별 정보다. product_id는 catalog.product.id에 직접 연결한다.

| 컬럼 | 자료형 | NULL 허용 | 예시 값 | 키·제약조건·의미 |

### 9.8 `parts` JSON 계약

최상위 키는 부품 종류이고 값은 적용할 속성 배열이다. 아래 숫자는 설명용이며 운영값은 평가 후 고정한다.

```json
{
  "cooler": [
    {"aspect_code": "fan_quietness", "context_code": "gaming_load", "alpha": 0.6, "reason": "게임 중 저소음 우선", "preference_source": "explicit"},
    {"aspect_code": "cooling", "context_code": "gaming_load", "alpha": 0.4, "reason": "게임 용도 냉각 요구", "preference_source": "inferred"}
  ]
}
```

aspect_code는 평가할 속성, context_code는 사용할 Q의 조건, alpha는 리뷰 내부 중요도다. reason은 적용 이유이고 preference_source는 explicit/inferred/default 중 하나다. 부품별 alpha 합은 1이며 적용 속성이 없으면 빈 배열과 R=0.5를 사용한다. 후보별 Q·최종 점수는 이 JSON에 저장하지 않는다. run_id 하나의 여러 후보는 같은 프로필을 공유한다.

관측 내용은 원문을 해석해 정리한 의미이고 evidence_sentences는 이를 뒷받침하는 원문 문자열이다. 원문에 없는 측정값을 만들지 않는다. aggregate_member는 집계에 포함된 모든 관측을 연결하며 일부 대표 문장만을 전체 집계 근거로 취급하지 않는다.

## 10. DB 제약조건과 적재 검증

DB는 FK, UNIQUE, NOT NULL, CHECK로 행의 존재·중복·유효값을 검증한다. 규칙의 k는 양수·유한값이며 NaN/Infinity는 거부한다. Q는 numeric GENERATED ALWAYS STORED로 `(p+k×0.5)/(p+n+k)`를 계산한다. 계산 중 정수 합산 오버플로를 피하도록 numeric으로 변환한다.

다음은 저장소 계층에서 트랜잭션 단위로 검증한다.

- 관측의 근거 배열은 비어 있지 않은 문자열 배열이고 현재 본문에 존재해야 한다.
- 관측이 등록 상품을 평가하며 규칙의 part_type과 상품 종류가 일치해야 한다.
- 집계 멤버의 리뷰 product_id와 rule_id가 집계와 일치해야 한다.
- 멤버의 방향별 개수가 P/N/mixed와 일치하고 k가 규칙과 같아야 한다.
- 프로필 parts는 부품별 속성·조건·α·이유·선호 출처를 저장한다. α는 유한·비음수이며 적용 속성이 있는 부품의 합은 1이다. 선호 출처는 explicit/inferred/default다. 규칙 존재와 현재 analysis_version 일치도 확인한다.
- LLM은 요구를 해석하고 숫자는 규칙으로 결정한다. 적용 속성이 없으면 R=0.5, 선택 조건에 근거가 없으면 Q=0.5다. 분석 실패를 정상 0건 집계로 저장하지 않는다.

요구 프로필은 배치를 참조하지 않는다. 이전 실행의 프로필이 남아 있어도 새 집계를 결합해 당시 R인 것처럼 표시하지 않는다. 생성된 추천 실행을 삭제하면 프로필도 CASCADE로 삭제한다. 기존 카탈로그·원문·규칙·관측의 RESTRICT는 현재 참조 무결성을 위한 제약이며 과거 이력 보존 장치가 아니다.

## 11. 리뷰 검색·점수 조회와 인덱스

```sql
SELECT d.id, d.body, e.embedding <=> $1::vector AS distance
FROM evidence.review_document d
JOIN evidence.review_embedding e ON e.review_id = d.id
WHERE d.product_id = $2 AND d.is_synthetic = false
ORDER BY e.embedding <=> $1::vector, d.id
LIMIT $3;
```

공통 모델은 `text-embedding-3-small`(1536차원)이다. 코사인 거리는 예시이며 거리 함수는 검색 평가에서 확정한다. 정확 검색부터 시작하고 근사 인덱스는 측정 후 도입한다. Q는 검색 top-k로 계산하지 않는다. 프로필의 분석 버전·부품·속성·조건으로 rule_id를 찾고 `(product_id, rule_id)` UNIQUE 인덱스로 현재 집계를 일괄 조회한다.

문서 product_id 인덱스는 상품별 검색, 관측·집계 rule_id 인덱스는 규칙별 조회, 멤버 observation_id 인덱스는 변경 영향 파악에 사용한다. 관측 document_id 조회는 복합 UNIQUE의 선두 컬럼을 활용한다.

## 12. 서비스 중단 후 갱신·삭제·복구

1. 검색/추천 서버, 리뷰 수집·변경, 기존 분석·임베딩 작업을 중단하고 진행 중 작업 종료를 확인한다.
2. 최신 본문과 공통 설정을 고정한다. 초기 구현은 전체 리뷰의 관측·집계를 재생성해 부분 갱신 누락을 줄인다. 수정 리뷰는 전체 본문으로 재임베딩하며 모델·차원·파이프라인 변경 시 모든 리뷰를 재임베딩한다.
3. 외부 모델 호출 결과는 임시 작업 영역에서 준비한다. 장시간 API 호출을 하나의 DB 트랜잭션에 넣지 않는다. DB 반영 시 기존 멤버 → 집계 → 관측 순서로 정리하고, 본문·규칙·새 관측·집계·멤버·벡터를 같은 유지보수 작업에서 일관되게 교체한다. FK가 참조 중인 데이터를 임의 순서로 삭제하지 않는다.
4. 규칙 변경 시 구 규칙을 참조하는 관측·집계를 정리한 뒤 새 규칙과 전체 결과를 적용한다. 상품·속성당 최신 집계만 유지한다. 사용 중인 설정과 결과가 다른 상태로 서버를 재개하지 않는다.
5. 철회·삭제 리뷰는 벡터와 관련 멤버·관측을 제거하고 집계를 다시 계산한 뒤 문서를 삭제한다. 이 단계에서는 이전 원문·근거를 남기지 않는다.
6. 대상 ID별 임베딩 누락·차원·집계 건수·근거 연결·프로필 규칙을 확인한 뒤 재개한다. 모델 입력 한도 초과는 자동 절단하지 않고 실패로 처리한다. 실패 시 서비스를 중단한 채 재시도하거나 유지보수용 일시 백업으로 일관된 변경 전 상태를 복구한다. 이 백업은 장애 복구용이며 DB 이력 조회 기능이나 영구 이력 저장이 아니다.

## 13. 기존 리뷰 테이블 폐기와 DB 적용

community.review, community.review_revision, evidence.review_subject, evidence.review_summary, evidence.review_aggregate, evidence.review_aggregate_member를 전환 후 삭제한다. 2026-10-01 조회에서 확인한 대상 23건과 요약 69건은 보존·백업·이관하지 않는다. 나머지 구 리뷰 테이블 네 개는 당시 0건이었다. 신규 리뷰는 새 입력에서 적재한다.

공용 evidence.source/evidence.evidence는 유지한다. evidence.evidence의 구 review_aggregate FK·CHECK·kind 참조를 상위 근거 설계에 맞춰 먼저 전환한다. 당시 참조 행은 0건이었으나 삭제 직전 다시 확인한다. 기존 API·review_repo·정제 작업자·시드 및 setup_all의 구 리뷰 시드 경로도 전환한다.

의존성을 조사한 뒤 구 aggregate_member → summary → aggregate 순서로 제거하고, community.review의 current_revision FK를 제거한 뒤 구 review_revision → review → review_subject를 DROP RESTRICT로 제거한다. 예상하지 못한 참조를 CASCADE로 삭제하지 않는다. 실제 삭제는 별도 전환 migration에서 수행한다.

마이그레이션은 기존 0000~0007을 유지하고 `0008_review_aspect.sql`을 추가한다. 새 마이그레이션은 pgvector 확장과 신규 테이블·인덱스를 생성하며 `vector(1536)`을 사용한다. 트랜잭션은 마이그레이션 러너가 관리한다. 기존 리뷰 테이블 삭제와 시드·서비스 전환은 후속 마이그레이션 및 구현에서 수행한다.

| 7. 후속 학습 | 비교·선택 데이터로 중요도 보정 | 수동값 대비 평가와 학습 버전 |

PC 부품 전체에 새 계산 경로를 적용하되 자료가 없는 속성은 중립으로 처리한다. 검수 자료가 부족한 경우 적용 범위를 축소하고 부족한 부분을 기록한다. 합성 자료로 빈 부분을 채워 실제 추천 품질이 검증됐다고 주장하지 않는다.

## 15. 검증과 전환 기준

### 15.1 필수 검증

| 영역 | 확인할 사항 |
|---|---|
| 계산 | Q 범위·단조성·중립 보정, α 합계, R과 최종 기여도 |
| 가중합 유지 | 동일 요청·후보의 외부 가중치·다른 축 점수·패널티가 기존과 동일하며, 반올림 전 점수 차이가 `w_review×(R−기존 리뷰 값)`과 일치 |
| 입력 | 음수 건수, k≤0, NaN·무한대, 잘못된 버전 거부 |
| 리뷰 적재 | 적재 전 확인을 통과한 리뷰만 저장하고, 사용 불가 자료는 운영 리뷰 DB에 적재하지 않음 |
| 문장 분석 | 부정 표현, 비교 대상, 혼합 조건, 부품과 부속품 혼동 |
| 집계 | 같은 리뷰의 동일 속성·조건 반복 집계 방지, 근거 없음과 혼합 의견 구분, 실데이터·합성 분리 |
| 벡터 검색 | 공통 모델·차원 일치, 현재 원문 연결, 상품·실제/합성 필터, 철회 자료 제외, 수정 후 전체 재임베딩, 전체 재생성 시 일괄 전환, 갱신 중 서비스·리뷰 변경 중단, 대상별 생성 완료 확인 후 재개 |
| 엔진 | 행동 지표만 바꿔도 새 점수 불변, 속성 변경이 순위·선택에 반영 |
| 대체 범위 | R에 기존 리뷰 값을 대입하면 기존 최종 점수와 같음. 리뷰 항 중복 추가·새 외부 정규화·소음 축 변경이 없음 |
| 제약 | 리뷰 점수 때문에 예산·필수 스펙·호환 위반을 정상 추천으로 처리하지 않음 |
| 설명 | 실제 집계·중요도·버전과 설명 일치, 과거 행동 감점 문구 제거 |
| 실패 처리 | 실행 오류와 정상 집계의 근거 부재 구별, 실패 시 건수 0의 정상 집계 저장 방지, 중립 처리·복귀 재현 |

리뷰 분석의 정확도와 추천 품질을 따로 평가한다. 문장을 잘 분류했다는 사실만으로 사용자가 더 적합한 부품을 추천받는다고 결론내리지 않는다.

### 15.2 추천 품질 비교

동일한 후보·제약·카탈로그에서 다음 결과를 비교한다.

1. 과거 행동 지표 기반 결과: 오프라인 비교용.
2. 모든 리뷰 값을 중립으로 둔 결과: 리뷰의 기여 확인용.
3. 속성 점수와 수동 중요도를 사용한 결과: 초기 적용 대상.
4. 속성 점수와 학습 중요도를 사용한 결과: 후속 비교 대상.

사용자 A/B 선호 일치율, 정답 순위가 있는 경우의 순위 품질, 최종 구성 적합성, 요구별 결과, 근거 보유 비율과 응답 지연을 평가한다. 허용 기준은 평가 시작 전에 고정한다.

같은 원본 리뷰에서 파생된 문장은 같은 데이터 분할에 배치한다. 새 상품·새 사용자·미래 선택 중 무엇을 평가하는지 정하고 그 목적에 맞게 평가 자료를 분리한다. 선택 이후에 작성된 리뷰나 정답 생성에 사용한 리뷰가 입력으로 들어가 결과를 부풀리지 않도록 한다.

### 15.3 구현 완료 검사

문서 수정에는 엔진 테스트가 필요하지 않다. 이후 엔진·DB 구현을 완료할 때는 다음 명령으로 테스트 DB를 필수로 요구한다.

```bash
docker compose up -d db
PYTHONPATH=. UV_CACHE_DIR=/tmp/uv-cache TRUEFIT_REQUIRE_TEST_DB=1 uv run pytest -q
```

필수 시드 입력은 다음과 같다. 누락은 설정 실패이며 테스트 성공으로 처리하지 않는다.

```text
data/parts_list_modify.xlsx
data/peripherals/mouse_processed.csv
data/peripherals/monitor_processed.csv
data/peripherals/speaker_processed.csv
data/peripherals/keyboard_processed.csv
```

개발 DB `truefit`에 테스트하지 않는다. 테스트는 이름에 `test`가 포함된 격리된 DB에서 수행하고, DB 설정 실패나 검사 생략을 완료로 보고하지 않는다.

### 15.4 전환과 복귀

전환 전에는 새 계산을 실제 추천과 별도로 실행하여 결과를 비교한다. 전환 후에는 리뷰 속성 적합도만 리뷰 축에 사용한다.

비활성화 시 리뷰 축을 중립으로 처리하거나 이전에 검증된 설정과 일시 복구용 데이터를 함께 복원한다. DB에 보존하지 않은 과거 집계를 조회해 복귀할 수 있다고 가정하지 않는다. 오류나 자료 부족을 이유로 기존 행동 지표를 자동 복원하지 않는다.

### 15.5 최신 데이터 갱신 검증

- 현재 원문 변경 후 이전 관측·근거가 남지 않고 임베딩·P/N/mixed·Q가 함께 갱신된다.
- 같은 리뷰 ID 재적재와 동일 상품·규칙 집계 교체 시 중복되지 않는다.
- 삭제 리뷰의 멤버·관측·벡터가 제거되고 새 집계가 일치한다.
- 전체 분석 설정 변경 후 예전 규칙의 결과가 검색·추천에 섞이지 않는다.
- 중간 실패 시 서비스가 재개되지 않고 재시도·복구 후 일관성이 확인된다.
- FK/UNIQUE/CHECK 거부, NaN/Infinity 거부, α 합·근거 일치, 기존 리뷰 테이블 폐기와 리뷰 외 데이터 보존을 검증한다.

신규 DDL은 자동 마이그레이션에 포함한다. DDL과 기존 서비스 호환성 검증은 별도 테스트 DB에 적용하고 TRUEFIT_REQUIRE_TEST_DB=1로 실행한다. 개발 DB truefit에서 테스트하지 않는다.

## 16. 후속 이력 보존 전환

서비스 동작 검증 이후 다음 순서로 확장한다. 지금은 해당 테이블·FK·불변 트리거를 만들지 않는다.

1. 리뷰 ID를 유지하면서 원문 리비전 테이블을 추가한다. 전환 시점의 body·posted_at을 첫 리비전으로 이관하고 관측의 원문 버전 연결을 채운다.
2. 집계 배치 헤더를 추가한다. 당시 최신 집계를 첫 배치로 묶고 이후 새 배치를 누적한다. UNIQUE를 (product_id, rule_id)에서 (batch_id, product_id, rule_id)로 변경한다.
3. 원문 버전을 포함하는 관측 UNIQUE와 추천 프로필의 배치 FK를 도입한다. 배치가 없는 기존 추천 실행에 전환 당시 배치를 과거 배치인 것처럼 연결하지 않는다. 기존 실행은 근거 이력 미보존으로 구분하고 신규 실행부터 정확한 이력을 연결한다.
4. 수정·삭제 방지 트리거, 배치 발행 검증·잠금, 실행 삭제 RESTRICT와 권한 분리를 함께 도입한다. 상위 보고서/대화 삭제 정책과 충돌하지 않게 조정한다.
5. 덮어쓰기로 사라진 과거 원문·집계는 복원할 수 없다. 전환 시점 이후만 이력 재현을 보장한다.

저장·조회는 repository 계층의 리뷰 저장, 관측 교체, 집계 조회 함수로 모으고 상위 서비스가 테이블에 직접 접근하지 않게 한다. Q 조회 인터페이스는 현재 상품·규칙 기준을 사용하고 후속 버전에서 배치 선택을 확장할 수 있게 한다. 내부 ID를 배열 순서·상품명·본문 해시로 재발급하지 않는다. 분석·프로필 설정의 코드 이력 관리는 계속 유지한다.

## 17. 확정할 값과 최종 완료 정의

다음 값은 구현·평가 과정에서 확정한다.

- 실제 적용할 부품·속성·사용 조건과 데이터 범위.
- 보정 강도 k와 요구 프로필별 중요도 α.
- 추출 모델·프롬프트 및 검수 기준.
- 기존 외부 가중치를 유지한 상태에서 리뷰 내부 중요도에 따른 전체 영향도.
- 저장 구조의 세부 필드와 버전 규칙.
- 검색 거리 함수와 검색 인덱스 설정. PostgreSQL + pgvector, 리뷰 전체를 하나로 임베딩하는 방식, OpenAI `text-embedding-3-small`과 기본 1536차원은 확정이다.
- 품질·근거 보유 비율·지연 시간의 허용 기준.

완료는 다음 조건으로 판단한다.

- [ ] 검수된 실제 리뷰에서 상품·속성·조건·근거를 추적할 수 있다.
- [ ] Q 집계와 α 부여 규칙이 고정되고 같은 입력을 재현할 수 있다.
- [ ] 기존 행동 지표가 새 추천 점수에 남아 있지 않다.
- [ ] 기존 평가 축의 가중합·외부 가중치 조정·다른 축의 계산·패널티·반올림 규칙이 유지되고 리뷰 입력값만 교체된다.
- [ ] 리뷰 평가가 상위 후보 선정과 최종 선택에 반영된다.
- [ ] 상위 계산에 전달하는 R·설명·근거가 같은 속성 집계와 요구 프로필을 사용한다.
- [ ] PostgreSQL + pgvector에서 전체 리뷰 임베딩으로 유효한 리뷰를 검색하고 원문·상품·분석 버전을 추적할 수 있다.
- [ ] 결손·오류·과거 결과·복귀·제약 처리를 검증했다.
- [ ] 수식 검사와 실제 추천 품질 평가를 모두 수행했다.
- [ ] 적용 범위와 미검증 부분을 명확하게 기록했다.
