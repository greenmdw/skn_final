# DB 미보유 부품·주변기기 실시간 스펙 검색 — 설계 기획

- 상태: **설계 초안 — 미착수** (팀 검토 전, 코드 변경 없음)
- 배경: Self-RAG(https://selfrag.github.io/) 적용 가능성을 검토하다 나온 아이디어. 결론은 논문 자체(검색 관련성·근거를 판단하는 critic 모델을 직접 파인튜닝)를 그대로 들여오는 건 과하고, **"검색 결과가 질문에 실제로 답이 되는지 생성 전에 한 번 검증한다"는 핵심 아이디어만 프롬프트 레벨로 흉내낸다** — 기존에 이미 쓰고 있는 "엄격한 프롬프트 + 구조화 출력" 패턴([src/agent/spec_extraction_agent.py](../src/agent/spec_extraction_agent.py), [src/engine/stage5_explain.py](../src/engine/stage5_explain.py))과 같은 방식이다.
- 확인된 현재 상태: 카탈로그에 없는 부품은 [src/engine/owned_parts.py](../src/engine/owned_parts.py)의 `_match_catalog`/`_match_nearest`가 "unmatched"로 두고, 글에서 바로 읽히는 값(소켓, DDR 세대, 파워 용량 정도)만 규칙으로 뽑는다(`_MATCH_STATUS`). 정확한 성능 티어·상세 스펙은 카탈로그에 없으면 **전혀 못 가져온다** — 지어내지도 않지만 찾아보지도 않는다. 실시간 웹 검색 연동은 코드 어디에도 없다(`web_search`/외부 검색 API 전부 미사용, grep 확인).

## 1. 범위

| 대상 | 현재 동작 | 이 설계가 바꾸는 것 |
|---|---|---|
| 받은 견적 점검(pc_check)에서 "대응 안 됨"/모호함으로 뜬 부품 | 글에서 읽은 값만, 나머지는 공백 | 사용자가 누르면 실시간 검색 시도 |
| 업그레이드 모드에서 적은 "현재 사양" 중 카탈로그에 없는 신제품 | 소켓·세대만 추정, 성능 등급(tier) 모름 → 업그레이드 하한 못 검 | 검색으로 tier 추정 근거 확보(선택) |
| 조건 대화 중 언급된 신제품 | 해당 없음(지금 구조에서 조건은 카탈로그 질의가 아님) | **범위 밖** — 조건 대화는 그대로 둔다 |

범위 밖: 가격 수집(기존 크롤링/관측 파이프라인 영역), 검색 결과를 카탈로그 정식 등재로 승격하는 프로세스(운영팀 결정 사항).

## 2. 설계 원칙 (기존 프로젝트 철학 계승)

- **판정은 규칙, 서술만 LLM** 원칙을 "검증" 단계에 맞게 변형 적용 — 여기서는 "이 검색 결과가 이 부품에 대한 것이 맞는가"를 코드가 아니라 LLM이 판단해야 하지만(Self-RAG의 critique가 바로 이 역할), 그 판단을 **자유 서술이 아니라 구조화된 출력(`relevant: bool`, `supported_fields: {...}`)으로 강제**해서 "판정 과정"은 기존처럼 검증 가능하게 남긴다.
- **스니펫에 없는 값은 만들지 않는다** — 이미지 추출 프롬프트의 "읽은 글자 그대로, 모르면 ?" 규칙([src/engine/prompts.py](../src/engine/prompts.py) `spec_extraction_image_system`)을 그대로 재사용한다.
- **항상 출처를 같이 보여준다** — 사용자가 검증할 수 있게 `source_url`을 반드시 함께 저장·노출한다. 출처 없는 스펙은 애초에 화면에 안 보인다.
- **자동 실행 금지, 사용자가 명시적으로 트리거** — 비용과 지연이 있는 기능이라 추천/점검 흐름 중에 조용히 실행하지 않는다. "지난번 조건 이어서 할까요?"(A1) 같은 기존 되묻기 UX와 같은 방향 — 항상 사용자 확인을 거친다.
- **기존 동작을 절대 악화시키지 않는다** — 검증 실패(`relevant=false` 또는 모든 필드 `null`)면 지금과 똑같이 "모름"으로 폴백. 이 기능이 꺼져 있거나 실패해도 pc_check의 현재 동작은 그대로다.
- **Opt-in 플래그로 시작** — `CONDITIONS_AGENT`/`RESULT_AGENT`와 같은 패턴으로 `LIVE_PART_LOOKUP=0` 기본값.

## 3. 아키텍처 — 2단계(검색 → Self-RAG식 검증)

```
사용자가 "실시간으로 찾아볼까요?" 버튼 클릭
        │
        ▼
[1단계] 검색 도구 호출 — "{브랜드} {모델명} 정식 스펙" 질의
        │  (OpenAI 내장 web_search 도구 또는 외부 검색 API — 8절 미결정)
        ▼
[2단계] 관련성·근거 검증(critique) — 검색 스니펫 + 원래 질문을 LLM에 넣고
        구조화 출력 강제:
          { "relevant": bool,
            "supported_fields": { "socket": "AM5" | null, "tdp_w": 65 | null, ... },
            "source_url": "..." }
        스니펫에 명시적으로 적힌 값만 채운다 — 추론·일반 지식으로 채우지 않는다
        │
        ▼
relevant=false 이거나 supported_fields 전부 null
        │                              │
        ▼ 예                           ▼ 아니오
  기존처럼 "모름" 폴백           source_url과 함께 화면에 노출,
  (신규 기능 이전과 동일)        "카탈로그 정식 등재 값이 아닙니다" 안내
```

2단계 스키마는 `owned_parts.py`가 이미 다루는 필드(소켓, 메모리 타입, 전력, 길이 등)에 맞춰 설계해 기존 호환성 검사 로직이 그대로 쓸 수 있게 한다.

## 4. 저장/캐시 설계 (초안 — 팀 승인 전 적용 금지)

같은 부품을 볼 때마다 다시 검색하면 느리고 비용도 쌓인다. 전용 캐시 테이블을 둔다.

```sql
-- 마이그레이션 번호는 db/ 쪽과 조율 필요 — 초안
CREATE TABLE catalog.live_spec_lookup_cache (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    query_text      text NOT NULL,          -- 검색에 쓴 질의 원문
    brand           text,
    model           text,
    relevant        boolean NOT NULL,
    supported_fields jsonb NOT NULL DEFAULT '{}',
    source_url      text,
    fetched_at      timestamptz NOT NULL DEFAULT now(),
    UNIQUE (query_text)
);
```

TTL(캐시 만료 기준)은 미결정 — 신제품 스펙은 출시 초기에 정정되는 경우가 있어 영구 캐시는 위험하고, 매번 재검색은 비용이 든다(8절).

## 5. UI 노출 (pc_check 기준)

- "대응 안 됨"/모호함 뱃지 옆에 **"실시간으로 찾아볼까요?"** 버튼 — 명시적 트리거
- 결과가 나오면: 채워진 필드 + `출처: {source_url}` + "카탈로그 정식 등재 값이 아니라 실시간 검색 결과입니다" 고정 안내문
- 결과가 없으면(검증 실패): 기존과 동일하게 공백 유지, 버튼은 "결과를 찾지 못했어요"로 비활성화

## 6. 비용·지연 고려

- 검색 1회 + LLM 검증 1회가 사용자가 버튼을 눌렀을 때만 발생 — 추천 파이프라인에는 영향 없음
- 캐시 히트 시 호출 생략
- 모델 선택은 이미지 추출 때와 같은 기준(저빈도·단건 호출이라 가격보다 정확도·정직한 "모름" 응답이 더 중요) — `gpt-6-sol` 비교 테스트(2026-10-01)에서 애매한 값에 "?"로 정직하게 답하는 경향이 확인된 바 있어 이 용도에 참고할 만하다.

## 7. 단계별 구현 순서 (제안)

| 단계 | 내용 | 선행 조건 |
|---|---|---|
| 1 | 검색 소스 결정(8절 미결정 사항 ①) | 팀 결정 |
| 2 | `live_spec_lookup_cache` 마이그레이션 | 팀 승인 |
| 3 | 검증(critique) 프롬프트 + 구조화 출력 스키마 설계 | 1 |
| 4 | pc_check 라우터에 엔드포인트 추가(버튼 트리거) | 2, 3 |
| 5 | 프론트 버튼·출처 표시 UI | 4 |
| 6 (선택) | 업그레이드 모드(현재 사양 tier 추정)까지 확장 | 4 검증 후 |

## 8. 미결정 사항

- **검색 소스**: OpenAI 내장 `web_search` 도구 vs Google/Bing 계열 외부 API — 비용·정확도·실시간성 비교 필요
- **캐시 TTL** — 영구 캐시 vs 일정 기간 후 재검색
- **리뷰/RAG 담당 팀원 영역과의 경계** — `care_guides.py`와 저장소(스키마)를 분리할지, 검증 단계 프롬프트 설계를 공유할지는 그쪽 작업이 끝난 뒤 조율 필요
- **검색 결과의 카탈로그 정식 등재 승격 프로세스** — 이 설계 범위 밖으로 명시, 별도 운영 논의 필요
