## 0. 범위

### 0.1 포함 — 추천 엔진

| 영역 | 파일 |
|---|---|
| 단계 모듈 | `src/engine/*` (새 모듈 포함) |
| 오케스트레이션 | `src/pipeline.py`(데모 경로), `src/services/recommendation_service.py`의 **엔진 호출 구간** — `execute_recommendation`의 [2]~[5], `reverify_set` |
| 계약·정의 | `src/dto.py`의 엔진 DTO, `src/categories.py`, `config/categories/computer.yaml`의 엔진이 읽는 부분, `config/computer_verification_rules.yaml`, 새 엔진 설정 파일 |
| [3-0] 후보 로더 | `src/repo/catalog_repo.py`의 조회 함수 — **이미 있는 컬럼을 SELECT에 추가하는 것만** 한다. 쓰기는 하지 않는다 |

| 엔진 테스트 | `tests/` |

### 0.2 제외 — 필요하면 요청 문서로 넘긴다

| 영역 | 이유 |
|---|---|
| 프론트엔드 (`frontend/`) | 지시상 제외 |
| API 공개 계약 (`src/schemas.py` 응답 모델, `src/routers/*`) | 프론트와 맺은 계약이다. 필드를 추가하면 프론트 합의와 계약 문서 갱신이 필요하다 |
| DB 스키마·시드·데이터 수집과 정정 (`db/`, `data/`) | 엔진이 아니라 데이터 계층이다 |
| 대화 단계 (`session_service`, 질문 칩, `src/agent/*`) | [1]의 입력 수집은 대화 계층 담당이다. 엔진은 조건이 **들어오면 읽는 것**까지만 한다 |
| LLM 문안 (`src/engine/prompts.py`의 문장) | `src/CLAUDE.md`에 따라 문안 변경은 팀 승인 대상이다 |
| 저장소 문서 정리 (`docs/rag_implementation.md` 등) | 엔진 코드가 아니다 |

### 0.3 "프론트에 전달할 수 있는 형태로 가공"의 경계

- 엔진 결과는 ① pydantic DTO와 ② **공개 계약 모양의 dict를 만드는 순수 함수**로 낸다. 이 dict는 요청 문서에 제안한
  스키마와 필드 이름이 같아서, 스키마가 반영되면 코드를 바꾸지 않고 그대로 연결된다.
- 이미 공개된 필드(`items[].checks`, `verification.issues[].text`, `reasoning_log`)에 **값을 채우는 것**은 범위 안이다.
  `reasoning_log`는 이미 `list[dict]`로 공개돼 있어 단계를 추가해도 스키마가 바뀌지 않는다.
- **새 필드를 응답에 싣는 것**(`schemas.py` 변경)과 영속화(DB 컬럼)는 범위 밖이다. `RecommendResultOut`은
  모르는 키를 조용히 버리므로, 스키마가 반영되기 전까지 새 dict는 응답에 나가지 않는다. 이 점을 알고 진행한다.

## 3. 상세

### 3.1 M1 — PC의 구조적 구멍

#### E1. 실경로 재탐색 루프 (P1)

**목적** — 검증 결과가 재구성으로 이어지게 한다. 데모 경로(`_run_computer_branch`)에만 있는 루프를 실경로와 **같은 함수로** 공유한다.

**변경 파일**
- 신규 `src/engine/research_loop.py` — 루프 본체
- `src/pipeline.py` — `_run_computer_branch`가 새 함수를 호출한다(데모 동작은 그대로)
- `src/engine/stage3c_verify.py` — `AXIS_SLOTS`(축→관련 슬롯)를 여기로 옮긴다. 지금은 `recommendation_service._AXIS_SLOTS`(441행)에 있어 엔진이 쓸 수 없다. 서비스는 이것을 import한다
- `src/engine/stage4_optimize.py` — `pc_compat_details` 행에 `missing_slots`(스펙이 빈 쪽 슬롯)를 추가한다. 지금은 `data_missing` bool만 있어 어느 부품을 빼야 하는지 모른다
- `src/services/recommendation_service.py` — `execute_recommendation`의 `stage4_optimize.run` + `verify_build` 두 줄(158~163행)을 루프 호출로 바꾼다

**설계**

```python
def run_set_with_research(rank, spec, log, *, verify, choose_exclusion,
                          base_exclude=frozenset(), max_rounds=MAX_RESEARCH_ROUNDS
                          ) -> tuple[BuildResult, VerificationResult, list[RoundRecord]]
```

- `verify(build, round_index) -> VerificationResult`, `choose_exclusion(build, verification) -> (slot, product_key, axis) | None`를 주입받는다.
  - 데모: `verify_set` + 시나리오의 `problem_slot` — **지금 동작과 한 글자도 다르지 않게**(골든 테스트 보존)
  - 실경로: `verify_build` + 규칙 기반 `choose_exclusion`
- **규칙 기반 제외 대상 선택** (C5 반영)
  1. 쟁점을 감점이 큰 순으로 본다. `set`/`budget` 실패는 **재탐색 대상에서 뺀다**. [4]가 이미 전체 풀에서 호환 세트와 최저가 호환 세트를 찾아본 결과라서 후보를 빼도 풀리지 않는다. 이 경우 루프는 곧바로 끝나고 이유("재탐색으로 개선 불가")를 기록한다.
  2. "근사" 쟁점은 `missing_slots`에서 제외할 슬롯을 고른다. 그 슬롯에서 **이번에 뽑힌 후보**를 뺀다.
  3. 업그레이드의 유지 부품(`spec.owned`)과 `base_exclude`(이미 가진 부품)는 제외 대상이 될 수 없다. 뺄 수 있는 것이 없으면 종료한다.
- **채택 규칙** — 라운드마다 결과를 보관한다. 신뢰도가 가장 높은 라운드를 고르고, 같으면 **앞 라운드**를 고른다. [4]가 1라운드에서 점수를 최대화했으므로 앞 라운드일수록 점수가 높다. 재탐색이 결과를 **나쁘게 만드는 일은 없다**.
- 기준 통과(`CONFIDENCE_THRESHOLD`) 또는 `MAX_RESEARCH_ROUNDS`(3) 소진 시 종료한다.
- `reverify_set`(교체·수량 변경 뒤)에는 루프를 **붙이지 않는다**. 사용자가 직접 고른 구성을 엔진이 바꾸면 안 된다.

**출력 (프론트 전달 형태)**
- `BuildResult.round`, `VerificationTarget.rounds`, `transcript`에 라운드별 `{round, excluded: {slot, name, axis}, issue_count}`를 남긴다.
- 2라운드 이상 돌았을 때만 `reasoning_log`에 단계를 하나 넣는다. 예: `{"step": "세트 재검토", "detail": "확인 필요 4건 → 쿨러 'A'(높이 정보 없음)를 빼고 다시 구성 → 확인 필요 1건 구성 채택"}`.
  **신뢰도 숫자는 넣지 않는다**(결정 0003).
- `_store_validations`의 `measured_values`에 `round`를 넣는다. 기존 jsonb 컬럼이라 마이그레이션이 없다.

**테스트** (`tests/test_research_loop.py`, DB 불필요)
- 1라운드 쿨러의 높이 데이터가 비어 근사 쟁점이 생기고, 데이터가 있는 대체 쿨러가 풀에 있으면 → 2라운드 구성이 채택된다
- 대체가 없으면 1라운드 결과가 유지된다(악화 없음)
- 업그레이드 유지 부품은 절대 제외되지 않는다
- `set`/`budget` 실패만 있으면 1라운드에서 끝난다
- 데모 회귀: `test_pipeline_smoke`, `test_domain_refactor_golden`이 수정 없이 통과한다
- DB 통합(`-m db`): `execute_recommendation`이 저장한 후보가 채택 라운드의 구성과 같다

**완료 기준** — 위 테스트 통과. DB 카탈로그로 대표 조건 18건(현황 문서의 실측 세트)을 돌려 **라운드 분포와 `execute_recommendation` 소요시간 p95(전/후)**를 PR에 적는다. [4]를 최대 3회 다시 돌리므로(라운드당 노드 상한 150,000) 시간 증가를 숫자로 확인한다.

**위험** — 데이터가 빈 후보를 빼면 데이터가 충실한 쪽으로 쏠린다. 규칙 v10의 데이터 결손 감점과 같은 방향이라 의도에 맞다. 다만 점수가 낮은 구성이 채택될 수 있으므로, 쟁점 수가 **실제로 줄어든 경우에만** 채택한다(위 채택 규칙이 보장한다).

**남는 한계 (고치지 않고 기록만 한다)** — `verify_build`는 [4]가 만든 `link_check`를 읽는다. 권장 구조가 말하는 "[4]와 독립된 규칙"은 아니다. 같은 호환 함수를 두 번 부르는 것은 독립성을 높여 주지 않는다. E14(선언화) 뒤에 다시 판단한다.

#### E2. 조건 기반 리뷰 축 문장 정렬 (F-1)

**목적** — `priority=quiet` 요청에는 소음·발열 축 문장을 먼저 보여 준다. 축 라벨은 이미 데이터에 있는데 쓰이지 않고 있다.

- 하드 조건을 모니터에만 두는 이유: 나머지 셋은 데이터 결손이 커서(폴링 57/84 공란) 하드 조건이 곧 빈 결과가 된다. 선호로만 쓰고 결손은 Pending 감점으로 다룬다.

#### E11. `per_item` 분기 — 선언형 규칙 평가기와 [3-A]/[3-B]/[3-C] (Q4)

- 신규 `src/engine/spec_rules.py` — 규칙 평가기. 연산자는 `min`, `max`, `equals`, `member_of`, `contains_any`. 결과는 `Pass | Fail | Pending` + 이유이고 **값이 없으면 Pending**이다. 여러 규칙이면 Fail > Pending > Pass로 가장 나쁜 것을 채택한다(stage3a와 같은 의미). 주변기기 규칙은 처음부터 YAML 선언으로 둔다. 새 종류 추가가 파이썬 분기가 아니게 한다(현황 §4.3).
- [3-A] `peripheral_filter(kind, requirement, cands)` → `HardFilterResult`와 같은 모양
- [3-B] `rank_peripherals` — 축은 가격(예산이 있으면 예산 대비, 없으면 종류 중앙값 대비), 선호 적합(소프트 조건 충족 비율), 데이터 결손 감점(v10 방식 재사용), Pending 감점이다. **리뷰축은 가중치 0**으로 둔다. 대조군이 PC 부품이라 주변기기에는 영구히 "모름"이기 때문이다(현황 §4.2). 가중치는 YAML에서 합 1로 검증한다.
- 조합: 제약이 없으므로 종류별 1위가 결과다. `peripheral_budget_max`가 있으면 종류별 top-N(기본 5)의 곱(최대 625)을 **전수** 탐색해 예산 안에서 점수 합이 최대인 조합을 고른다. 절단이 있으면 그 사실을 `counts`로 보고한다.
- [3-C] `stage3c_verify.verify_per_item` → `VerificationResult(mode="per_item", targets=[품목별])`. 품목마다 Pending 축, 데이터 결손, 교차 검사(E12)를 쟁점으로 내고, 신뢰도는 같은 감점 공식을 쓴다.
- `src/pipeline.py:61`의 `NotImplementedError` 자리에 `per_item` 분기를 구현한다. 컴퓨터 `set` 분기 뒤에 주변기기 단계를 붙이는 `_run_peripherals`를 추가하고, 데모 시나리오(`tests/fixtures`)에 `peripherals` 조건이 있을 때만 돈다.
- `categories.verify_branch` docstring을 실제 구현에 맞춘다(E15).

#### E12. 모니터↔PC 교차 검사 (Q2 혼합, Q5)

`verify_per_item`의 모니터 대상에 쟁점으로 들어간다. **PC 세트의 신뢰도에는 영향을 주지 않는다.**

| 축 | 규칙 | 지금 결과 |
|---|---|---|
| `monitor_resolution` | 고른 모니터의 해상도 등급 = [2]의 PC 목표 해상도. [3-A]와 독립적으로 다시 확인한다 | ok / fail |
| `monitor_gpu_port` | 필요 대역폭(해상도×주사율)을 만족하는 공통 단자가 있는가. HDMI/DP 버전별 최대 모드 표는 YAML에 둔다(잠정, 출처 필요) | **항상 Pending — "그래픽카드 출력 단자 정보가 없어 확인하지 못했습니다"**. `gpu_spec`에 포트 컬럼이 없다(R-1) |
| `monitor_usb_c` | USB-C 영상 입력만 있는 모니터 ↔ GPU USB-C 출력 | Pending (같은 이유) |

- 단자 규칙은 **데이터가 있을 때 자동으로 켜지게** 구현한다. GPU 후보 `specs`에 `hdmi_version`/`dp_version`/포트 수 키가 생기면(R-1 반영 후 E5와 같은 방식으로 SELECT만 추가) Pending이 ok/fail로 바뀐다. 테스트는 가짜 GPU 스펙으로 세 결과를 모두 검증한다.

#### E13. 주변기기 결과 가공과 실행 연결

**가공 (범위 안)**

```python
def peripheral_payload(result: PeripheralResult) -> dict:
    # {"status": "ready" | "empty" | "skipped",
    #  "items": [{"kind", "kind_label",
    #             "product": {"name", "brand", "variant_id", "product_url", "image_url"},
    #             "price": int, "price_source": "reference_snapshot",
    #             "price_note": "판매처·관측일 미확인 참고가 — 구매 가능 가격이 아닙니다",
    #             "requirement": [{"key", "label", "value"}],
    #             "checks": [{"axis", "label", "state": "ok|unknown|fail", "detail"}],
    #             "reason": {"status": "ready", "text": <규칙 템플릿>},
    #             "alternatives": [{"name", "price", "diff"}]}],   # 차순위 2개
    #  "empty": [{"kind", "reason"}],
    #  "totals": {"reference_price": int, "note": "PC 예산과 별도"}}
```

- `checks[].state` 어휘는 기존 `CompatCheckOut`(`ok|unknown|fail`)과 맞춘다. 프론트가 같은 표현을 재사용할 수 있다.
- `reason`은 **규칙 템플릿**이다(예: "QHD 165Hz 목표에 맞는 IPS 패널, 조건 충족 후보 4개 중 1위"). LLM 문장을 쓰려면 문안 승인(R-10)이 필요하다.
- `price_note`는 코드가 고정으로 붙인다. 참고가를 구매가처럼 보이게 하지 않는다.
- "구매 전 확인" 가이드: `SLOT_GUIDE_IDS`에 종류별 항목이 없으면 `search_care_guide`가 전 문서를 검색해 PC 가이드가 붙는다. 그래서 주변기기 종류는 **명시적으로 빈 목록**으로 등록하고, 가이드가 없으면 `{"status": "none", "text": "이 품목의 사용 가이드는 아직 없습니다"}`를 낸다. 문서 작성은 R-12에 요청한다.

**실행 연결 (조건부)**
- 엔진 진입점: `run_peripherals(values, spec, candidates, log) -> PeripheralResult`
- `execute_recommendation`에 연결하는 일은 **R-7(저장 위치) 결정 뒤에** 한다. 저장할 곳 없이 연결하면 계산 결과가 버려진다. 연결할 때는 별도 try 블록에서 돌려 **주변기기 실패가 PC 결과를 실패로 만들지 않게** 한다.
- 그 전까지는 데모 파이프라인(`main.py`)과 테스트에서만 돈다.

**테스트** (`tests/test_peripherals_engine.py`) — QHD_165 + 모니터: QHD·165Hz 이상만 남는다 / FHD_144: `empty`와 이유 / 단자 검사 Pending / 예산이 있으면 합이 예산 이하 / `peripherals` 조건이 없으면 PC 결과가 전과 같다(골든) / payload 필드 집합 고정(스냅샷 테스트).

## 4. 전 작업 공통 규칙

1. **판정·수치는 코드, LLM은 서술만.** 새 LLM 호출은 만들지 않는다. 주변기기 설명도 규칙 템플릿으로 시작한다.
2. **모르는 것은 Pending.** 파싱 실패·컬럼 없음·출처 없음은 Fail이 아니다. 대신 이유를 문장으로 남긴다.
3. **근사는 근사라고 보고한다.** 절단(`counts`), 라운드, 잠정값(`provisional`), 합성 데이터(`is_synthetic`), 참고가(`reference_snapshot`)를 출력에서 지우지 않는다.
4. **결정 기록 준수** — 0001(리뷰 판정 금지·점수화 금지), 0003(사용자 문장에 신뢰도 숫자 금지), 0004(목업 표시 근거).
5. **설정 변경 규율** — YAML의 정책값을 바꾸면 `rule_set_version`을 올린다. 구조를 바꾸면 `schema_version`을 올리고 로드 시 검증을 추가한다.
6. **기존 결과 불변 원칙** — 새 조건(`peripherals`, `games` 등)이 없는 요청의 PC 결과는 바뀌지 않아야 한다. E1(재탐색)만 예외로 결과를 바꿀 수 있으며, 그 차이를 PR에 수치로 적는다.
