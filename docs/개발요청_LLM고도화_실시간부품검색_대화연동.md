- 작성: 2026-10-02 · 상태: **제안 — 검토 요청** (코드 변경 없음, 담당자 확인 후 설계 시작)
- 관련 문서: [미보유부품_실시간스펙검색_설계.md](미보유부품_실시간스펙검색_설계.md)(원 설계, 1~4단계 구현 완료 — pc_check 버튼 트리거만)
- 요청 이유: 원 설계는 "받은 견적 점검(pc_check)" 화면의 버튼 클릭으로만 범위를 좁혀뒀는데, 사용자 쪽에서 "새로 견적 맞추는 페이지"와 "챗봇"에도 같은 기능을 원한다는 요청이 나왔다. 이 둘은 `conditions_agent.py`/`result_agent.py`를 직접 건드려야 해서, **지금 LLM 고도화 작업 중인 파일과 겹칠 가능성이 커 먼저 확인을 구한다.**

## 1. 무엇을 원하는가 (예시로)

```
사용자(결과 화면 대화): "RTX 6090으로 바꿔줘"
에이전트: "RTX 6090은 저희 DB에 없는 상품으로 확인됩니다.
          외부 검색 과정을 거친 후 답변드려도 될까요?"
사용자: "응"
에이전트: (이 시점에만 실시간 검색+검증 실행) "확인해보니 ... 입니다.
          카탈로그 정식 데이터가 아니니 참고만 해주세요. 출처: ..."
```

같은 패턴을 "새로 견적 맞추는" 페이지(조건 대화, `conditions_agent.py`)에서도 원한다 — 예: 조건 대화 중 사용자가 구체적인 신제품명을 언급했을 때.

## 2. 이미 만들어져 재사용 가능한 것 (1~4단계, develop에 있음)

| 구성요소 | 위치 | 용도 |
|---|---|---|
| 핵심 조회 함수 | [src/services/live_spec_lookup.py](../src/services/live_spec_lookup.py) `lookup(conn, part_text, ...)` | 질의 문자열 하나 → 캐시 확인 → 검색+검증 → 결과. **에이전트 어디서든 그대로 호출 가능.** |
| 검색 호출 | [src/clients/llm_client.py](../src/clients/llm_client.py) `call_web_search()` | OpenAI Responses API `web_search` 도구 |
| 검증(critique) 스키마·프롬프트 | [src/services/live_spec_lookup.py](../src/services/live_spec_lookup.py) `LiveSpecLookupResult`, [src/engine/prompts.py](../src/engine/prompts.py) `live_spec_lookup_system()` | "스니펫에 실제로 적힌 값만, 모르면 null, 출처 URL 지어내지 않음" — Self-RAG식 검증 |
| 캐시 | `catalog.live_spec_lookup_cache` (마이그레이션 0009) | 같은 질의 재검색 방지, TTL 7일 |
| opt-in 플래그 | `LIVE_PART_LOOKUP`(기본 꺼짐), `live_spec_lookup.available()` | 기존 `CONDITIONS_AGENT`/`RESULT_AGENT`와 같은 게이트 패턴 |

**즉 "검색하고 검증하는 로직"은 이미 다 있다.** 이 요청은 그걸 대화 에이전트의 도구(tool)로 노출하는 것만 남았다.

## 3. 왜 기존 pc_check 연동과 다른가 — 확인이 필요한 이유

pc_check 버튼(4단계)은 버튼 클릭 한 번으로 바로 검색까지 갔다. 그런데 대화에서는 **설계 원칙(§2, 자동 실행 금지)을 지키려면 2턴이 필요하다**:

1. 1턴: 에이전트가 "DB에 없다"를 감지하고 **동의를 구하는 문장만** 답한다 (아직 검색 안 함)
2. 2턴: 사용자가 동의하면 그때 `lookup()`을 호출한다

이걸 구현하려면 `conditions_agent.py`/`result_agent.py`(Strands Agents SDK 기반)에 **새 도구를 추가**하고, "방금 그 질문에 동의를 기다리는 중"이라는 상태를 턴 사이에 들고 있어야 한다 — 지금 두 에이전트가 짜여 있는 방식(도구 호출 → `ConditionDraft`/`ResultSession`에 패치 모으기)과 어떻게 맞물릴지는 그 구조를 잘 아는 분이 설계하는 게 맞다고 판단해 요청드린다.

## 4. 결정해야 할 것 (담당자 의견 필요)

- **두 에이전트 다 적용할지, 결과 화면 대화(`result_agent.py`)만 먼저 할지** — 조건 대화(`conditions_agent.py`)는 "용도·예산·우선순위"를 모으는 게 목적이라 특정 신제품명이 나올 일이 상대적으로 적다. 범위를 결과 화면 대화로 먼저 좁히는 것도 방법.
- **"동의를 기다리는 중" 상태를 어디에 둘지** — 세션 DB에 플래그를 두는 방식 / 에이전트가 직전 메시지만 보고 판단하는 방식(상태 없음, "네"/"어"를 직전 질문과 함께 매번 LLM에 주는 방식) 등 설계 선택지가 있다.
- **"판정은 코드, 서술만 LLM" 원칙 유지 방법** — "DB에 없다"는 판정(카탈로그 매칭 실패)은 코드가 이미 하고 있다(`owned_parts.py` 계열과 같은 매칭 로직 재사용 또는 신규). 에이전트가 "DB에 없다"를 스스로 판단하게 두면 존재하는 제품을 없다고 잘못 말할 위험이 있다 — 도구 호출 결과(코드가 확정한 match 여부)를 보고 서술만 하게 강제해야 한다(기존 7개 AI 호출 지점과 같은 설계 철학).
- **Rate limit 공유 문제** — pc_check는 `LIVE_PART_LOOKUP_LIMIT_PER_MIN`(IP 기준)을 쓰는데, 대화 에이전트는 로그인 세션 기준이 더 적절할 수 있다. 같은 한도를 쓸지 별도로 둘지 결정 필요.
