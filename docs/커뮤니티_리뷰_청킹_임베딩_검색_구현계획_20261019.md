# 커뮤니티 리뷰 청킹·임베딩 검색 구현 계획

작성일: 2026-10-19  
상태: 최소 데이터 모델에 따른 코드 구현·회귀 검증 완료. DB 적용은 일회용 테스트 DB에서 검증했으며 실제 데이터 색인과 의미 검색 품질 평가는 별도 실행한다.

설계 수정: 검색 전용 테이블을 3개에서 2개로 줄이고, 문서 7개·청크 5개 필드로 구성한다. 문서 행이 작업 대기를 겸한다. 별도의 작업 대기 테이블은 생성하지 않는다.

## 1. 목적과 사용자 경험

기존 속성 분석으로 답하기 어려운 자유 질문에 대해, 커뮤니티 사용기 본문에서 참고할 구절과 출처를 찾는다.

예를 들어 “절전 후 복귀할 때 화면이 안 켜진다는 후기가 있나요?”, “특정 프로그램과 같이 사용하면 끊기나요?”처럼 사전에 등록한 속성만으로 설명하기 어려운 질문을 다룬다. 검색은 해당 내용을 담은 글의 일부를 찾아주는 역할이고, 그 내용이 질문에 실제로 답하는지 판단하거나 답변을 생성하는 단계는 구분한다.

사용 흐름은 다음과 같다.

1. 사용자가 제품을 선택한 상태에서 자유 질문을 입력한다.
2. 선택한 제품에 연결된 공개 커뮤니티 사용기와 기존 외부 리뷰를 검색한다.
3. 커뮤니티 글에서는 질문과 가까운 본문 구절, 글 제목, 작성일, 원문 링크를 반환한다.
4. 소비 화면이나 상담 기능은 해당 구절을 확인하고 답변의 근거로 인용한다. 질문에 답하는 근거가 없으면 근거 부족을 표시한다.

검색 결과를 추천 점수·속성 집계에 반영하거나 추천 당시 사용한 근거로 표시하지 않는다. 같은 리뷰를 다른 방식으로 검색한 결과를 추가적인 독립 근거로 세지도 않는다.

## 2. 현재 구현에서 확인한 사항

| 영역 | 현재 구현 | 이번 계획에 주는 의미 |
|---|---|---|
| 외부 리뷰 검색 | `src/routers/reviews.py`, `src/services/review_search.py`: `GET /reviews/search`, 상품 ID와 질문으로 검색 | 기존 경로와 검증·요청 제한을 활용할 수 있다 |
| 외부 리뷰 저장 | `evidence.review_document`, `evidence.review_embedding`; 리뷰 원문 하나에 벡터 하나 | 현재 API는 청크 ID·본문 위치·커뮤니티 출처를 표현하지 않는다 |
| 기존 검색 응답 | `src/schemas.py`의 `ReviewSearchHitOut`: `review_id`, 원문 전체 `body`, `posted_at`, `similarity` | 청크를 기존 `review_id`로 위장하거나 `body`를 설명 없이 발췌문으로 바꾸면 안 된다 |
| 임베딩 | `src/rag/embedding.py`의 `OpenAIEmbedder`; 현재 설정 기본값 `text-embedding-3-small`, 1536차원 | 새 저장소에서도 기존 임베더를 재사용한다 |
| 커뮤니티 원본 | `community.post`, `community.post_product`; 게시판, 공개 상태, `is_example`, 연결 제품을 관리 | 공개된 사용기와 현재 제품 연결을 검색 시점에도 확인한다 |
| 커뮤니티 길이 | `community_service.py`의 실제 본문 상한은 20,000자. 라우터 입력 모델의 50,000자보다 엄격하다 | 길이 기준은 서비스의 실제 제한으로 잡고, 기존 DB 글의 길이는 별도로 조사한다 |
| 기존 사용기 분석 | `peripheral_post_analysis` → `peripheral_post_pipeline` → `engine.peripheral_post_evidence` | 주변기기 4종에 대해 추출·검증된 문장을 저장하는 경로다 |
| 기존 분석 길이 | `config/peripherals.yaml`의 `feel.post_max_chars=4000`; 그보다 긴 본문은 앞부분만 분석 | 새 검색을 이 분석 결과에 의존시키면 긴 글의 뒷부분을 검색할 수 없다 |
| 기존 문장 임베딩 | `peripheral_evidence_embedding.py`, `engine.peripheral_post_evidence_embedding` | 추출된 문장만 대상으로 하며, 본문 전체 청킹을 대체하지 않는다 |
| 기존 문장 검색 부품 | `src/engine/peripheral_search.py`에 키워드·임베딩 순위 결합 함수가 있다 | 이를 범용 검색 API에 이미 연결된 전체 본문 검색으로 간주하지 않는다 |
| 본문 정리 | `src/engine/peripheral_post_text.py`의 `plain_text()` | Markdown·이미지 마커 정리 규칙을 재사용할 수 있다. 예시 안내 제거 함수는 새 검색에서 호출하지 않는다 |
| 변경 알림 | `community_service._notify_changed()`가 기존 주변기기 분석 대기를 기록한다 | 새 검색은 검색 문서 행에 대기 상태를 두고 같은 변경 지점에서 알림을 받는다 |
| 변경 감지 주의점 | 조회수 갱신도 `updated_at`을 바꾸며, 제품 개별 추가·삭제는 항상 글 `version`을 올리지는 않는다 | `updated_at`이나 `version` 하나만으로 검색 최신성을 판정하지 않는다 |

외부 리뷰의 기존 임베딩 테이블과 주변기기 체감 근거 테이블은 각각 현재 역할을 유지한다. 커뮤니티 전체 본문 검색용 데이터를 새 테이블에 둔다.

## 3. 구현 범위와 기본 결정

| 항목 | 계획 |
|---|---|
| 검색 대상 | `board_type='review'`, `status='published'`이고 카탈로그 제품이 연결된 커뮤니티 글 |
| 제품 범위 | PC 부품과 주변기기 모두. 기존 주변기기 분석기의 4종 제한을 상속하지 않는다 |
| 제품 식별 | `community.post_product.product_id`와 `catalog.product.id` 사용. 표시용 `product_kind` 문자열로 종류를 확정하지 않는다 |
| 미매칭 제품 | `product_id IS NULL`인 연결은 상품별 검색의 검색 키로 사용하지 않는다. 이름만 비슷한 카탈로그 제품에 자동 연결하지 않는다 |
| 원문 범위 | 제목과 본문 텍스트. 댓글·이미지 OCR·외부 링크 본문은 이번 범위에서 제외 |
| 색인 경로 | 속성 추출과 독립된 비동기 작업. 속성이 없거나 기존 분석이 실패한 글도 검색할 수 있다 |
| 임베딩 모델 | 이번 구현은 기존 모델·1536차원을 사용한다. 다른 모델로의 전환은 별도 재색인 작업으로 다룬다 |
| 검색 역할 | 질문과 가까운 구절을 반환하는 근거 후보 검색 |
| 기존 API 호환 | `/reviews/search`의 기본 동작을 유지하고 `version=2`로 새 응답을 선택 |
| 신규 UI·답변 생성 | 이번 구현 완료 기준은 색인·검색 API·출처 조회까지. 채팅 질문 분류, 답변 생성, 신규 질문 UI는 후속 연결 범위 |

### 3.1 실제 글과 예시 글

`community.post.is_example=true`인 가상 사용기를 실제 사용자 경험으로 제공하지 않는다.

- 운영 검색은 실제 글을 기본 대상으로 한다.
- 예시 글을 이용한 개발·시연은 명시적인 별도 모드로 제공한다. 서버 설정으로 허용된 환경에서만 선택할 수 있게 하고, 응답에 `is_example`과 `corpus_mode`를 포함한다.
- `corpus_mode='demo'`에서 커뮤니티 출처는 예시 글만 조회한다. 외부 리뷰 출처를 함께 요청하면 그 결과는 실제 외부 리뷰 출처 그룹에 별도로 남긴다.
- 시연 모드에서도 예시임을 숨기거나 안내 문구를 제거하지 않는다. 실제 사용자 경험의 근거와 합쳐 신뢰도를 계산하지 않는다.
- 최초 `--dry-run`에서 실제 글·예시 글·미매칭 글·상태별 건수를 구분한다. 새로 들어온 글이 전부 예시이면 “운영 검색 대상 0건, 시연 대상 N건”으로 보고한다.
- 기존 주변기기 추천의 예시 사용 정책은 이 작업에서 변경하지 않는다.

### 3.2 글의 제품 연결과 구절의 제품 귀속

한 글에 여러 제품이 연결되어 있다고 해서 그 글의 모든 문장이 모든 제품에 관한 경험은 아니다.

- 1차 검색 범위는 **선택한 제품이 연결된 글**이다.
- 응답에는 `matched_product_id`, 현재 `linked_products`, `association_scope='post_link'`를 담는다.
- 다중 제품 글은 `product_attribution='unverified'`로 반환한다. 단일 제품 글도 글의 연결 정보만으로 개별 구절의 제품 귀속을 검증했다고 표시하지 않는다.
- 소비 화면은 “이 제품이 연결된 사용기의 구절”로 제시한다. 답변 생성기는 구절에서 대상 제품을 확인하지 못하면 해당 제품의 장단점으로 단정하지 않는다.
- 제품별로 확실히 귀속된 구절만 제공하려면 별도의 귀속 검증이 필요하다. 기존 속성 추출기를 본문 검색의 필수 관문으로 삼지 않는다.

## 4. 처리 구조

```text
community.post / community.post_product
  ├─ 글 변경 알림 → 검색 문서 행을 pending으로 전환
  └─ 주기적 대조 → 알림 누락·직접 적재·삭제 감지
          ↓
검색 전용 worker
  공개·게시판·제품 연결·예시 정책 확인
          ↓
본문 정리 → 전체 본문 청킹 → 청크별 임베딩
          ↓
현재 원본 재확인 → 한 글의 색인을 한 트랜잭션으로 교체
          ↓
GET /reviews/search?version=2
  상품·현재 공개 상태로 필터 → 청크 검색 → 글별 중복 제한
          ↓
근거 구절 + 제목 + 출처 + 본문 위치 + 색인 범위
```

임베딩을 만드는 동안 DB 연결과 글 잠금을 유지하지 않는다. 글 저장 요청 안에서 청킹·외부 임베딩 호출을 실행하지 않는다.

## 5. 본문 정리와 청킹

### 5.1 정리 규칙

1. `plain_text()`를 활용하여 Markdown 서식과 이미지 마커를 정리한다.
2. 줄바꿈 형식은 `\n`으로 통일하되 문단 경계를 유지한다.
3. 링크의 표시 문구는 남기고 이미지의 alt 문구를 사용 경험으로 취급하지 않는다.
4. 정리된 전체 본문을 청킹과 위치 검증의 기준 텍스트로 계산한다. 별도 DB 컬럼으로 복제하지 않고 현재 원문에서 동일한 규칙으로 재현한다. 정리 규칙의 버전은 색인 키에 포함한다.
5. 원문 Markdown과 정리된 본문의 위치는 다르므로, 모든 청크 위치는 **정리된 본문 기준**이라고 명시한다.

제목은 청킹 대상 본문과 분리한다. 임베딩 입력에는 `제목: <정리한 제목>\n본문: <청크>` 형식으로 문맥을 보충하되, 검색 결과의 인용문에는 본문 구절만 반환한다. 임베딩 입력 형식도 버전에 포함한다.

### 5.2 초기 청킹 설정

| 설정 | 초기 제안값 | 의미 |
|---|---:|---|
| 목표 본문 길이 | 600자 | 가까운 문단·문장을 묶는 목표 |
| 최대 본문 길이 | 1,000자 | 문장이나 문단이 길어도 넘지 않는 상한 |
| 겹침 길이 | 최대 120자 | 경계의 문맥을 이어주기 위한 이전 구절 일부 |
| 결과의 같은 글 수 | 상품·출처별 기본 1건 | 긴 글 하나가 결과를 채우는 현상 완화 |

위 길이는 토큰 수가 아닌 Python Unicode 문자 수다. 품질을 검증한 최적값으로 취급하지 않는다. 이 단계에서는 토크나이저 의존성을 추가하지 않고, 구현 후 평가에서 길이와 겹침 값을 조정한다.

### 5.3 분할 순서와 불변 조건

- 문단 경계를 우선하고, 큰 문단은 문장 경계에서 나눈다. 한국어 종결 문장, 줄바꿈, 영문 문장, 목록을 테스트에 포함한다.
- 문장 자체가 상한을 넘거나 적절한 경계가 없으면 문자 창으로 나눈다. 겹침 후에도 시작 위치가 반드시 전진해야 한다.
- 각 청크는 정리된 본문의 연속 구간이며 `text == normalized_body[start_char:end_char]`를 만족한다. 문단들을 임의 문자열로 재조합한 뒤 원문 위치처럼 표시하지 않는다.
- 본문 시작부터 끝까지 공백 이외의 내용이 누락되지 않아야 한다. 제목·첫 4,000자만 처리하는 경로를 사용하지 않는다.
- 짧은 글은 청크 하나로 처리한다. 빈 텍스트만 남은 글은 `empty_text`로 기록하고 검색 대상에서 제외한다.
- 청킹 규칙 버전·길이·겹침을 문서의 `index_key` 계산에 포함한다. 설정이 바뀌어 키가 달라지면 재색인 대상으로 판단한다.
- 현재 서비스 상한을 넘는 기존 적재 글도 사전 조사한다. 처리 자원 한도에 걸리면 실패 사유와 미색인 상태를 남기고, 앞부분만 색인한 뒤 완료로 표시하지 않는다.

## 6. 데이터 모델

새 마이그레이션은 현재 마지막 번호 `0021` 다음인 `0022_community_review_search.sql`을 제안한다. 구현 직전에 번호 충돌을 다시 확인한다. 기존 마이그레이션은 수정하지 않는다.

### 6.1 `evidence.community_review_search_document`

글 하나의 처리 대상 식별값과 현재 작업 상태를 함께 관리한다. 새 글은 현재 원문·설정으로 계산한 `index_key`와 `status='pending'`으로 등록하며, 제목·본문은 원본 테이블에서 읽는다.

| 필드 | 타입·기본값 | 용도 |
|---|---|---|
| `post_id` | `uuid PRIMARY KEY` | `community.post(id)` FK. 하드 삭제 시 CASCADE |
| `index_key` | `text NOT NULL` | 현재 처리 대상인 원문·설정의 통합 해시. `done`이면 완성된 청크의 색인 키 |
| `status` | `text NOT NULL DEFAULT 'pending'` | `pending / processing / done / failed` |
| `attempts` | `integer NOT NULL DEFAULT 0` | 현재 요청의 시도 횟수와 재시도 상한 관리 |
| `last_error` | `text NULL` | 마지막 실패 사유. 길이를 제한하고 원문 전체는 기록하지 않음 |
| `claim_token` | `uuid NULL` | 현재 작업자 식별. 중복 실행과 오래된 작업의 완료 처리 차단 |
| `updated_at` | `timestamptz NOT NULL DEFAULT now()` | 상태 전환·heartbeat 시각. 대기 순서·재시도 간격·작업 만료 판정에 공용 |

`index_key`는 **원본 제목·본문 + 색인 프로필**을 구조화하여 해시한 값이다. 색인 프로필에는 provider·실제 모델명·1536차원·실제/MOCK 구분·본문 정리 버전·청킹 규칙과 수치·제목을 포함하는 임베딩 입력 형식 버전을 모두 포함한다. 설정값은 코드·설정에서 관리하고 문서 행에는 통합 키 하나를 저장한다.

원문과 설정을 구분자 없이 이어 붙이지 않는다. worker와 검색 쿼리가 같은 정규 직렬화·해시 규칙을 사용하도록 공통 함수와 SQL 표현식을 정한다. 저장 직전에는 현재 원본 문자열도 재확인한다. 조회수·좋아요·제품 연결 변경은 키에 포함하지 않고 현재 원본에서 판정한다.

이 구조에서는 `status='done'`이고 현재 원문·설정과 키가 일치하는 색인만 사용할 수 있다. 과거 설정을 DB 행만으로 복원하는 기능은 제공하지 않는다. 처리 설정을 바꾸면 새 키로 재색인한다. 새 변경 알림은 현재 처리 대상의 키를 기록하고 기존 작업 token을 무효화한 뒤 `pending`으로 전환한다. 청크는 교체 완료 전까지 남겨 두되 처리 중인 글은 검색에서 제외한다. 이전 완성 키와 새 요청 키를 따로 보존하는 컬럼을 생략하기 위해 선택한 제약이다.

`attempts >= 0`, 허용된 상태, `processing`일 때만 token이 존재한다는 제약을 둔다. 별도 `requested_at`, `started_at`, `indexed_at`, `lease_expires_at`, `next_retry_at`은 두지 않는다. 작업 만료는 `updated_at + 작업 제한 시간`, 다음 재시도는 `updated_at + attempts에 따른 대기 시간`으로 계산한다. 정확한 과거 처리 이력은 이 테이블의 책임에 포함하지 않는다.

제품 연결·제목 표시·공개 상태·예시 여부는 응답 시 원본에서 읽는다. 제품 연결을 청크마다 복제해 오래된 제품 연결이 검색에 남는 구조를 피한다.

### 6.2 `evidence.community_review_search_chunk`

| 필드 | 타입·제약 | 용도 |
|---|---|---|
| `id` | `uuid PRIMARY KEY` | 공개 인용에 쓰는 청크 식별자 |
| `post_id` | `uuid NOT NULL` | 검색 문서 FK. 문서 삭제 시 CASCADE |
| `start_char` | `integer NOT NULL CHECK (start_char >= 0)` | 정리된 본문의 시작 문자 위치 |
| `text` | `text NOT NULL` | 실제 인용문. 빈 문자열 금지 |
| `embedding` | `vector(1536) NOT NULL` | 구간 검색용 벡터 |

`(post_id, start_char)` 유일성 제약으로 글별 중복 구간을 방지한다. 구간 순서는 `start_char`로, 끝 위치는 `start_char + len(text)`로 계산한다. 두 계산의 길이 단위는 모두 Unicode 문자 수다. API의 `end_char`는 계산해서 반환하며 DB 컬럼으로 두지 않는다.

위치와 본문 일치, 차원·유한값·유효 벡터 검사는 저장 서비스에서 검증한다. 최초 구현은 정확 검색을 사용하고 HNSW는 성능 측정 후 도입한다. 문서의 상태·갱신 시각 인덱스와 청크의 `post_id` 접근 인덱스는 위 컬럼을 활용한다.

청크 ID는 `post_id + index_key + start_char`를 바탕으로 결정적으로 생성한다. 같은 입력 재처리에서 식별자를 유지하고, 원문·처리 설정이 바뀐 과거 청크를 새 구절로 자동 대응시키지 않는다. 모든 청크와 문서 키를 한 트랜잭션에서 교체하므로 별도 generation 컬럼을 두지 않는다.

### 6.3 제거하거나 계산으로 대체한 항목

| 종전 항목 | 최소 설계의 처리 |
|---|---|
| 검색 전용 intake 테이블 | 문서 행의 상태·시도 횟수·token·갱신 시각으로 통합 |
| 개별 원문 해시·내용 해시·모델·프로필·여러 처리 버전 | `index_key` 하나로 현재 입력·설정과 일치하는지 판단 |
| 원문 버전·정리된 전체 본문 | 현재 원문과 설정으로 재확인·재현 |
| `generation_id` | 글별 청크 전체와 문서 키의 원자적 교체로 대체 |
| `chunk_index`, `end_char` | 시작 위치와 청크 문자 길이로 계산 |
| `chunk_count` | 현재 청크 행 집계로 계산 |
| 청크별 모델·입력 해시·생성 시각 | 문서 키와 현재 설정으로 검증. 청크에 중복 저장하지 않음 |
| 요청 revision·별도 처리 시각·별도 lease 만료 시각 | 변경 시 token 무효화, `updated_at` 기반 작업 제한으로 대체 |

**자동 재처리·실패 진단·동시 처리 방지를 유지하는 실용적인 최소안은 2개 테이블, 총 12개 필드다.** 원문이 하드 삭제되면 FK로 문서와 청크가 함께 제거되어 별도 삭제 대기를 보존할 필요가 없다. 대상에서 빠진 소프트 삭제·숨김 글은 즉시 조회에서 제외하고 worker가 정리한다. 대상이 아닌 글은 주기적 대조에서도 다시 대기로 만들지 않는다. DB 초기화에는 테이블 생성만 포함하고 실제 임베딩 호출은 별도 작업에서 수행한다.

## 7. 변경 반영과 작업 실행

### 7.1 변경 알림과 누락 복구

- `community_service._notify_changed()`에 검색 문서의 대기 상태 갱신을 추가한다. 기존 분석 알림과 각각의 세이브포인트로 분리하여 한쪽 실패가 다른 알림이나 글 저장을 취소하지 않게 한다.
- 게시·수정·숨김·삭제·복원·게시판 변경·제품 연결 변경을 처리한다. 예시 여부 변경도 재판정한다.
- 알림은 성공한 글 변경과 같은 트랜잭션에서 대기를 기록한다. 호출 자체가 실패하면 로그를 남기고 주기적 대조로 복구한다.
- worker는 시작 시와 설정된 주기에 원본과 검색 문서·대기 상태를 대조한다. 직접 SQL 적재와 알림이 누락된 글도 찾는다.
- 대조는 현재 제목·본문·색인 프로필로 계산한 키와 문서의 `index_key`를 비교하고, 현재 공개 상태·게시판·예시 여부·카탈로그 제품 연결을 함께 확인한다. 별도 `last_seen_signature`를 저장하지 않는다. 키가 같으면 같은 요청이므로 처리 중인 작업을 취소하거나 실패 횟수를 초기화하지 않는다. 키가 달라진 새 입력은 실패 횟수를 초기화하여 새 키의 `pending`으로 등록한다.
- 키 불일치와 누락 문서는 재색인 대상으로 등록하고, 일시 실패는 기존 재시도 정책을 따른다. 제품 연결만 바뀐 경우 본문 벡터를 재사용하고 현재 연결을 재판정할 수 있다. 조회수·좋아요 수 변경은 재색인 사유가 아니다.

### 7.2 한 글의 원자적 교체

1. 짧은 트랜잭션에서 `FOR UPDATE SKIP LOCKED`와 claim token으로 대기 작업 하나를 점유한다.
2. 현재 원본을 읽고 대상 조건·원본 스냅샷·처리 대상 키를 확정한 뒤 연결을 반환한다. 대기 중 원본이 바뀌었으면 token 조건을 확인하여 새 대상 키로 전환한다.
3. 전체 본문을 정리·청킹하고, 임베딩을 배치 호출한다. 한 글의 모든 결과를 메모리에 준비한다.
4. 저장 트랜잭션에서 claim token, 원본 본문·제목·현재 대상 조건과 현재 설정을 다시 확인한다. 글 행과 현재 제품 연결을 확인하는 동안의 변경 경쟁도 처리한다.
5. 유효하면 기존 청크를 지우고 새 청크 전부와 문서 `index_key`를 같은 트랜잭션에서 교체한 뒤 `done`으로 전환하고 token을 비운다. 임베딩 일부만 준비된 글은 완성 상태로 저장하지 않는다.
6. 작업 중 변경 알림이 오면 해당 문서에 새 대상 키를 기록하고 token을 비운 뒤 `pending`으로 바꾼다. 이전 작업자는 token 불일치 시 저장·완료 처리를 모두 포기한다. 알림 없이 원본만 바뀌었으면 저장 직전 원문 비교로 발견하여 같은 token일 때만 재대기 처리한다.

글 전체 교체를 선택했으므로 중간 배치가 실패하면 다음 시도에서 해당 글을 다시 처리할 수 있다. 부분 배치 재사용을 위한 별도 staging 저장소는 첫 구현에 도입하지 않는다. 실제 큰 글의 비용이 문제가 되면 재시도 비용을 측정한 뒤 추가한다.

### 7.3 검색 시점의 최신성 확인

worker가 아직 실행되지 않았더라도 다음 조건으로 오래된 내용을 검색에서 제외한다.

- 원본 글이 현재 공개된 사용기여야 한다.
- 요청한 제품이 현재도 그 글에 연결되어 있어야 한다.
- 문서가 `done`이고 현재 제목·본문·색인 프로필로 계산한 키가 문서의 `index_key`와 같아야 한다.
- 예시 정책을 통과해야 하며 해당 문서에 완성된 청크가 있어야 한다.

본문 수정 또는 명시적인 재구축 직후에는 재색인 완료까지 해당 글을 검색할 수 없는 기간이 생긴다. 이 경우 검색 범위에 미반영 문서가 있음을 표시한다. 원본 조회 API와 청크 조회 API에도 같은 조건을 적용한다. 검색 중 공개 상태가 바뀌는 경우에는 임베딩 호출 후 최종 조회 시점의 DB 스냅샷을 기준으로 다시 판정한다.

### 7.4 worker 인터페이스와 운영 한도

새 진입점은 `python -m src.workers.community_review_search_index`로 제안한다.

| 옵션 | 동작 |
|---|---|
| `--dry-run` | 대상·제외 사유·예상 청크 수·미반영 문서 수 집계. 외부 API 호출·DB 쓰기 없음 |
| `--once` | 대기 작업을 한 번 처리하고 종료 |
| `--post <uuid,...>` | 지정 글만 처리 |
| `--rebuild` | 현재 처리 버전으로 대상 글을 재색인 예약. 전체 색인을 먼저 삭제하지 않음 |
| `--include-examples` | 서버가 허용한 개발·시연 환경에서 예시 글도 색인 |

배치 크기, 요청 timeout, 재시도 횟수, 한 번 실행할 최대 글·청크 수, 처리 간격을 설정한다. 일시 오류는 간격을 두고 재시도하고 최대 횟수 후 `failed`로 남긴다. 영구 오류와 원본 변경에 따른 재대기를 구분한다.

`processing` 상태의 `updated_at`이 작업 제한 시간을 넘으면 회수할 수 있어야 한다. heartbeat는 같은 token일 때만 `updated_at`을 갱신한다. 외부 호출 timeout은 작업 제한보다 짧게 두고, 긴 작업은 배치 사이에 heartbeat한다. 회수·실패·완료 처리에도 token을 검사하므로 오래된 작업자가 새 작업의 상태나 시각을 덮어쓸 수 없다. MOCK 벡터는 테스트 DB에만 저장하고 운영·개발의 실제 데이터와 섞이지 않게 한다.

## 8. 검색 API 계약

### 8.1 기존 요청 유지와 확장 요청

기본 `GET /reviews/search`는 현재 외부 리뷰 검색 응답을 유지한다. 기존 `review_id`, 전체 `body`, `coverage`, 상태, 관련도 하한의 의미를 변경하지 않는다.

새 요청은 같은 경로에서 `version=2`를 명시한다.

```http
GET /reviews/search?version=2&product_id=<uuid>&q=<질문>&sources=community&limit=3
GET /reviews/search?version=2&product_id=<uuid>&q=<질문>&sources=external_review&sources=community&limit=3
```

| 파라미터 | v2 계약 |
|---|---|
| `product_id` | 필수, 반복 가능. 기존과 같이 중복 제거 후 최대 5개 |
| `q` | 필수, 기존 NFKC·공백 정규화 및 최대 200자 유지 |
| `sources` | `external_review`, `community`. 생략 시 두 출처 모두. 중복 제거 |
| `limit` | 상품·출처별 반환 근거 수. 기본 3, 최대 10. 글별 중복 제한 이후 적용 |
| `corpus_mode` | 기본 `real`. `demo`는 서버가 허용한 환경에서만 사용 |

`version`을 생략한 기존 요청은 v1이다. v1에 `sources`·`corpus_mode`를 지정하면 조용히 무시하지 않고 422로 안내한다. 새 응답은 독립 모델로 정의하여 기존 `ReviewSearchHitOut`을 청크용 모델로 변경하지 않는다. 라우터의 response model과 실제 직렬화가 두 버전을 정확히 구분하는지 API 테스트로 확인한다.

### 8.2 v2 응답 구조

외부 리뷰와 긴 글 청크는 길이와 유사도 분포가 다르므로 초기에는 출처별 결과를 나누어 반환한다. 같은 배열에서 raw similarity만으로 전체 순위를 섞지 않는다.

```json
    {
      "product_id": "<catalog-product-uuid>",
      "sources": {
        "community": {
          "status": "ok",
          "min_similarity": 0.2,

            "documents": 8,
            "indexed_documents": 7,

            "index_complete": false
          },
          "hits": [
            {
              "source_type": "community",
              "document_id": "<post-uuid>",
              "chunk_id": "<chunk-uuid>",
              "title": "한 달 사용기",
              "text": "<정리된 본문의 해당 구절>",
              "offset_basis": "normalized_body",
              "start_char": 1200,
              "end_char": 1800,
              "posted_at": "2026-10-19T01:00:00Z",

              "linked_products": [
                {"product_id": "<catalog-product-uuid>", "name": "<제품명>"}
              ],
              "association_scope": "post_link",
              "product_attribution": "unverified",
              "is_example": false,
              "source_url": "/community?view=post&post=<post-uuid>",
              "citation_url": "/reviews/chunks/<chunk-uuid>"
            }
          ]
        }
      }
    }
  ]
}
```

숫자와 글 내용은 응답 형식을 설명하는 예시이며 실측 데이터가 아니다. 특히 예시 하한 0.2는 커뮤니티 검색 품질을 검증한 값이 아니다.

- `sources`에는 요청한 출처만 포함한다. `external_review`도 같은 출처별 상태·범위 형태를 사용한다.
- 외부 리뷰 hit은 `source_type='external_review'`, `document_id=<review_id>`, `text=<원문 전체>`를 사용하고 청크 전용 필드는 갖지 않는다.
- 문서 수와 청크 수는 별도 단위다. 한 글의 청크 10개를 리뷰 10건으로 표시하지 않는다. 여러 제품에 연결된 같은 글은 출처 인용 시 하나로 식별한다.
- `documents`는 현재 정책상 검색 대상인 원본 문서 수다. `indexed_documents`는 `done` 상태이며 현재 원문·처리 설정과 `index_key`가 일치하고 완성된 청크가 있는 문서 수다.
- `chunks`는 현재 검색 가능한 완성 문서의 청크 수다. 미색인 글의 예상 청크를 실제 저장 청크처럼 세지 않는다.
- `index_complete`는 검색 대상 문서가 모두 현재 버전으로 준비됐는지 나타낸다. 일부 색인 상태에서도 검색된 근거는 반환할 수 있다.
- `posted_at`은 커뮤니티의 `published_at`을 사용한다. 없는 외부 리뷰 날짜를 추정해서 채우지 않는다.
- 기존 화면의 `/community?view=post&post=...` 링크를 사용한다. 기존 `quote` 파라미터는 속성 추출 문장용이므로 청크 ID를 그대로 넘기지 않는다.

### 8.3 상태와 오류

각 출처별로 `ok`, `no_match`, `no_reviews`, `not_indexed`를 반환한다.

| 상태 | 의미 |
|---|---|
| `ok` | 설정한 검색 조건을 통과한 근거 후보가 있음 |
| `no_match` | 검색 가능한 문서가 있지만 검색 조건을 통과한 후보가 없음 |
| `no_reviews` | 현재 정책상 검색 대상인 문서가 없음 |
| `not_indexed` | 대상 문서는 있으나 현재 내용에 맞는 완성된 색인이 하나도 없음 |

`no_match`를 “그 문제가 없다”, `ok`를 “질문에 대한 답변이 검증됐다”로 해석하지 않는다. 검색 미완료·실패 진단은 범위 정보와 운영 상태에 남긴다.

기존과 같이 잘못된 입력은 422, 없는 상품은 404, 요청 제한은 429로 처리한다. 질의 임베딩 실패는 503이다. 기존 외부 리뷰의 벡터 불일치는 현재와 같이 `review_index_mismatch`로 503을 반환한다. 커뮤니티의 키 불일치는 현재 입력·설정에 대한 미색인으로 계산한다. 현재 키가 맞더라도 실제 벡터 검증에서 오류가 발견되면 503을 반환한다. 요청한 출처의 실제 오류를 다른 출처의 성공만으로 전체 성공처럼 응답하지 않는다.

### 8.4 인용 재조회

`GET /reviews/chunks/{chunk_id}`를 추가하여 청크의 구절·제목·본문 위치·원문 링크를 재조회한다. 공개 사용기·현재 제품 연결 존재·현재 내용·예시 정책을 다시 확인한다. 삭제·숨김·본문 수정으로 유효하지 않게 된 청크는 404로 반환한다.

영구적인 과거 원문 보존 API는 이번 범위에 포함하지 않는다. 소비 화면은 인용이 만료됐을 때 최신 원문으로 이동할 수 있게 하고, 과거 구절을 최신 원문 내용인 것처럼 표시하지 않는다.

## 9. 검색 처리와 품질 기준

### 9.1 요청 처리

1. 입력·요청 제한·코퍼스 모드를 확인하고 상품 존재 여부와 출처별 검색 범위를 조회한다.
2. 검색 가능한 문서가 없으면 유료 임베딩 호출 없이 상태를 반환한다.
3. 질의를 한 번 임베딩하고 두 출처에서 재사용한다. 외부 리뷰의 기존 벡터 표본 점검에 필요한 호출은 별도로 유지하되 같은 텍스트 캐시를 활용한다.
4. 커뮤니티는 `done` 상태와 현재 공개 상태·제품 연결·통합 색인 키 확인을 통과한 문서의 청크만 코사인 거리로 검색한다.
5. 상품·출처별로 글마다 가장 가까운 청크를 선택한 다음 상위 후보를 고른다. 전역 상위 청크를 먼저 자른 뒤 중복 제거하여 다른 글이 빠지는 구현을 피한다.
6. 관련도 하한 적용 후 `limit`까지 반환한다. 동점은 거리·글 ID·청크 순서로 안정적으로 정렬한다.
7. 청크 본문은 임의로 재작성하지 않고 저장된 구절을 반환한다. 추가 문맥 확장은 별도 표시 없이 본문 위치에 합치지 않는다.

### 9.2 관련도 하한과 재정렬

기존 `REVIEW_SEARCH_MIN_SIMILARITY=0.2`는 짧은 외부 리뷰를 평가하여 정한 값이다. 새 청크의 품질 보장 기준으로 그대로 승인하지 않는다. 커뮤니티에는 별도 설정과 평가 결과를 둔다.

처음에는 벡터 정확 검색과 글별 중복 제한을 구현하여 기준선을 만든다. 품질이 부족하면 같은 정답 세트로 키워드 혼합 검색과 재정렬을 비교한 뒤 추가한다. 기존 주변기기 문장 검색의 RRF 점수나 추천 속성 점수를 코사인 유사도와 섞지 않는다.

### 9.3 평가 데이터와 완료 기준

자유 질문 중심의 수작업 평가 세트를 최소 50문항 구성한다. 단순 속성 질문은 비교군으로 일부 포함하고, 실제 평가 주제는 등록 속성만으로 충분히 답하기 어려운 사용 맥락으로 구성한다.

포함할 사례는 다음과 같다.

- 4,000자 이후와 글 끝부분에만 답이 있는 글.
- 질문과 표현은 다르지만 같은 경험을 설명하는 구절.
- 검색어는 같으나 사용 조건·대상 제품이 다른 구절.
- “발생한다”와 “발생하지 않는다”가 함께 존재하는 글.
- 여러 제품을 비교하는 글, 실제 관련 내용이 없는 질문.
- 짧은 글과 긴 글, Markdown·표·이미지 마커가 포함된 글.
- 아직 미색인인 글과 예시 글만 존재하는 상품.

사람이 질문별 관련 글·정확한 근거 구간·질문에 답하는 정도·제품 귀속을 표시한다. 속성 관측의 존재 여부만을 정답으로 쓰면 자유 질문 기능의 가치를 평가할 수 없으므로 이를 유일한 정답 기준으로 삼지 않는다.

| 평가 항목 | 기준 |
|---|---|
| 전체 본문 포함 | 청킹 불변 조건과 뒷부분 검색 회귀 사례 100% 통과 |
| 출처·구절 정확성 | 반환 인용문과 저장 기준 본문 구간 일치 100% |
| 제외 정책 | 숨김·삭제·초안·오래된 본문·미매칭 제품·운영 모드 예시 노출 0건 |
| 상품 구분 | 다른 제품의 경험을 선택 제품의 확정된 경험으로 표시한 사례 0건 |
| 검색 관련도 | hit@3, precision@3, MRR, 무관 질문의 오검출률을 함께 기록 |
| 긴 글 편향 | 글 길이·청크 수 구간별 관련도와 노출 비율을 분리하여 확인 |
| 성능 | 대표 데이터의 cold/warm p50·p95, 질의 임베딩 횟수, 검색 SQL 시간을 별도 기록 |

하한 조정용 질문과 최종 평가 질문은 분리한다. 품질 수치는 구현 후 기준선·키워드 검색과 비교하여 배포 기준을 정하고 문서에 남긴다. 현재 단계에서 측정하지 않은 정확도나 응답 시간을 달성했다고 적지 않는다.

## 11. 테스트 계획

### 11.1 단위 테스트

- 문단·문장·강제 분할·겹침·짧은 본문·공백·이모지·한글·매우 긴 한 문장.
- 모든 청크의 구간 일치, 상한 준수, 순서 전진, 본문 끝까지 포함, 결정적 ID.
- Markdown 정리와 위치 기준, 이미지 alt 제외, 예시 안내 유지.
- v2 입력 검증, 출처별 상태·범위, 같은 글 중복 제한, 원본 제품 연결과 제품 귀속 구분.
- 임베딩 실패·잘못된 차원·비유한 값·유효하지 않은 벡터·프로필 불일치 처리.

### 11.2 DB·API·작업 생명주기 테스트

- 새 마이그레이션 및 설정 재실행의 멱등성, FK·유일성·상태 제약, 문서 7개·청크 5개 필드 계약.
- 공개 실제 사용기만 운영 검색에 포함되고, PC 부품과 주변기기가 모두 검색됨.
- 기존 v1 검색의 응답 필드·정렬·상태·오류·호출 제한이 유지됨.
- v2의 외부 리뷰 단독·커뮤니티 단독·동시 요청과 출처별 `limit` 상한.
- 같은 질의를 두 출처에서 사용해도 질의 벡터 생성이 중복되지 않음.
- 기존 4,000자 이후에만 있는 구절이 색인되고 검색됨.
- 수정 직후 worker 실행 전부터 옛 본문이 검색·청크 조회에서 제외됨.
- 숨김·삭제·게시판 변경·제품 연결 제거 후 즉시 제외, 복원·재연결 후 적절히 반영됨.
- 개별 제품 연결 API처럼 글 `version`이 오르지 않는 변경도 올바르게 반영됨.
- 직접 SQL로 본문만 바꾸어 `version`이 같아도 통합 색인 키 불일치로 제외됨.
- 임베딩 중 수정·숨김·삭제·제품 변경이 일어나면 오래된 결과를 활성화하지 않음.
- 같은 글에 대한 두 작업자의 경쟁, `updated_at` 기반 작업 만료·heartbeat·회수, 오래된 claim의 갱신·완료 거절.
- 임베딩 배치 중간 실패 시 부분 색인이 활성화되지 않으며 재실행으로 복구됨.
- 변경 알림 실패와 직접 적재 후 주기적 대조로 누락을 복구함.
- 예시 모드 허용 여부·명시적 표시·운영 모드 제외, 테스트 외 DB의 MOCK 저장 차단.
- 속성 분석이 꺼지거나 실패해도 본문 검색이 동작하고, 기존 추천 계산 결과가 바뀌지 않음.

### 11.3 검증 실행 규칙

구현 완료 시 저장소 `AGENTS.md`의 기본 명령을 따른다.

```bash
docker compose up -d db
PYTHONPATH=. UV_CACHE_DIR=/tmp/uv-cache TRUEFIT_REQUIRE_TEST_DB=1 uv run pytest -q -m "not llm_live"
```

테스트 DB는 자동 생성되는 `truefit_test_<UUID>`를 사용한다. 개발 DB `truefit`에 테스트를 실행하지 않는다. 필수 비공개 seed 입력이 없으면 환경 설정 실패로 보고한다.

실제 임베딩을 이용한 관련도 평가는 유료 호출이므로 일반 회귀 테스트와 분리한다. MOCK 임베딩은 제어 흐름 검증에만 쓰고 실제 검색 품질의 증거로 사용하지 않는다. 구현 검증은 일회용 DB와 MOCK 벡터를 사용한다. 운영 색인·유료 평가는 별도 실행한다.

## 12. 적용·운영·완료 조건

적용 순서는 스키마 → API·worker 배포 → 대상 조사 → 소량 색인·원문 대조 → 관련도 평가 → 전체 대상 처리 → v2 소비 기능 연결로 잡는다.

- 새 검색 기능은 설정으로 켜고 끌 수 있게 한다. 비활성 상태에서 v2 커뮤니티 검색을 요청하면 기능 비활성 오류를 명시하고 정상적인 빈 결과로 위장하지 않는다.
- 최초 운영 색인 전 대상 수·예상 청크 수를 검토한다. 작업 완료 로그에는 처리 글·청크·실패·원본 변경 재대기·남은 작업·호출 횟수를 남긴다.
- 로그에 리뷰 본문 전체나 API 키를 출력하지 않는다. 원문 접근은 기존 공개 정책을 따른다.
- 장애 시 worker와 v2 기능을 비활성화할 수 있어야 한다. 기존 v1 외부 리뷰 검색을 계속 사용할 수 있다.
- 재구축은 글별 완성 후 교체 방식으로 진행한다. 다시 처리하는 문서는 준비 전까지 미색인 범위로 표시한다. 향후 임베딩 모델을 전환할 때에는 해당 출처의 검색을 잠시 중지하고 새 프로필의 색인을 확인한 뒤 다시 활성화한다.
- 전역 합산 순위, 자동 답변 생성, 이미지 OCR, 댓글 검색, 미매칭 제품 자동 연결, 추천 점수 반영은 별도 작업으로 남긴다.

다음 조건을 충족하면 색인·검색 API 구현이 완료된 것으로 본다.

1. 긴 사용기 전체를 빠짐없이 청킹하고, 속성 추출과 독립적으로 임베딩할 수 있다.
2. `/reviews/search`의 v1을 유지하면서 v2에서 커뮤니티 구절을 검색할 수 있다.
3. 검색 구절의 출처·본문 위치·제품 연결 수준·예시 여부·색인 범위를 확인할 수 있다.
4. 공개 상태와 원문 변경을 검색 시점에 확인하여 유효하지 않은 구절이 제공되지 않는다.
5. 중단·재시도·동시 수정에서 색인이 복구되고, 부분 처리 결과가 완성된 색인으로 표시되지 않는다.
6. DB를 포함한 필수 회귀 검증이 통과하고, 자유 질문 평가 결과와 남은 품질 한계가 기록되어 있다.

## 13. 구현 반영 기록

- `0022_community_review_search.sql`: 문서/작업 상태 7개 필드와 청크 5개 필드만 추가한다. 별도 intake 테이블은 생성하지 않는다.
- 전체 본문 청킹, 통합 키, 변경 알림·주기적 대조, token과 heartbeat를 이용한 재시도·동시 실행 제어, 글별 원자적 교체를 구현했다.
- 기존 v1을 유지하고 `version=2`의 출처별 검색과 `/reviews/chunks/{chunk_id}` 인용 재조회를 추가했다.
- worker는 별도 프로세스로 실행한다. API 기능은 `COMMUNITY_REVIEW_SEARCH_ENABLED=1`로 켠다. 실제 DB에서는 MOCK 벡터 저장을 거부한다.
- `scripts/eval_community_review_search.py`는 수작업 정답 구간으로 hit@3·precision@3·MRR·무관 질문 오검출률과 지연을 계산한다. 기본은 입력 검증만 하며 실제 평가에는 `--execute`가 필요하다.
- 실제 의미 검색 품질, 50문항 이상의 수작업 평가 결과, 운영 데이터의 성능 기준선은 아직 측정하지 않았다. 기본 하한 0.2와 청킹 길이는 초기 설정이다.
- 신규 청킹·검색 테스트는 44개 모두 통과했다. 긴 본문 뒷부분 검색, v1 호환, 출처별 결과, 인용 위치, 공개 상태·원본 변경, 부분 색인 차단, token fencing·작업 회수·재시도, 설정 변경, MOCK 저장 제한을 검증했다.
- 최종 전체 회귀: `PYTHONPATH=. UV_CACHE_DIR=/tmp/uv-cache TRUEFIT_REQUIRE_TEST_DB=1 uv run pytest -q -m "not llm_live" --durations=10` → **4,165 passed, 3 skipped, 26 deselected, 2 xfailed**, 661.10초. 마이그레이션·시드 재실행 검증을 포함하며 pytest 종료 코드는 0이다.
- worker와 평가 스크립트의 CLI 및 평가 입력 검증 경로도 확인했다. 유료 임베딩·운영 색인·개발 DB 마이그레이션은 실행하지 않았다.
