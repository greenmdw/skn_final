## 1. 다른 선택지 선택 버튼 켜기 (PQA-024)

**지금:** 화면은 다른 선택지를 고르는 버튼을 넣었지만, 서버가 대안에 `variant_id`를 안 보내 버튼이 늘 꺼져 있었다.

**서버 변경:** `items[].alternatives[]`에 `variant_id`·`brand`·`image_url`·`product_url`을 싣는다(1위의 `product`와 같은 값, 카탈로그에 없으면 `null`).

**요청:** 따로 할 일은 거의 없다. `WirePeripheralItem.alternatives` 주석("서버는 이름·가격 차이와 리뷰 근거만 준다")만 고쳐 주고, 버튼이 켜지는지 확인해 주세요.

## 2. 강조·브랜드·손 크기를 요청에 싣기 (PQA-003·004)

**지금:** 문장 해석 응답에는 `emphasis`·`brand_like`·`brand_avoid`·`hand_size`가 있는데 화면이 버린다.

- `interpretationFromWire` / `interpretationToWire`에 네 필드가 없다 → 이어 말하면(두 번째 문장) 첫 문장의 강조·브랜드가 사라진다.
- 추천 요청 body(`peripherals.recommend`)에도 없다 → "가성비", "로지텍 말고", "레이저로", "오래 쓸 거라"가 결과에 반영되지 않는다.

원인은 화면 연결(10-14 10:29, `e63acfd`)이 서버 필드 추가(같은 날 12:26, `fe8f986`)보다 먼저 들어간 것이다.

**서버 변경:** 추천 요청 `PeripheralsRecommendIn`에 `hand_size`(`small`·`medium`·`large`)를 더했다. 나머지 셋은 이미 받는다.

**요청:**

```ts
// 해석 결과 타입·변환에 더한다
emphasis: Record<string, string[]>; brandLike: Record<string, string[]>; brandAvoid: Record<string, string[]>; handSize: 'small'|'medium'|'large'|null
// 추천 body
{ ..., emphasis, brand_like, brand_avoid, hand_size }
```

## 3. 채팅 답장을 "이번 문장" 기준으로 (PQA-013)

**지금:** `interpretReply`가 이어 말하기로 **합친 해석 전체**에서 문구를 만든다. 그래서 질문("스피커는 어떤 조건으로 나눌 수 있어?")이나 못 읽은 문장에도 매번 "말씀한 조건을 반영했어요: 무선 · 가벼운 무게"라고 답한다(종합#16 스크린샷, 종합#33).

**요청(지금 할 수 있는 것):** 보내기 전 해석과 받은 해석의 조건 이름을 비교해 **새로 생긴 것만** 말한다.

| 경우 | 답장 |
|---|---|
| 새로 반영한 것이 있음 | 이번에 반영했어요: {새 조건들} |
| 새로 반영한 것이 없고 `unrecognized`가 있음 | 이 부분은 아직 반영하지 못했어요: {…} |
| 둘 다 없음 | 이번 문장에서는 새로 반영한 조건이 없어요. 예: "조용한 무선 마우스 5만원 이하" |

13번(질문 답변)이 들어오면 답장 문장을 서버가 만들어 보낸다. 그때는 화면이 받은 문장을 그대로 보여 주면 된다.

## 4. 유의사항(`notices`)을 채팅에 (PQA-001·012)

**서버 변경:** PC 견적 없이 모니터를 고르면 이제 **해상도·주사율로 거르지 않는다**(4K 포함 33종 모두 후보, 종합#52). 대신 추천 응답 최상위에 `notices`를 싣는다.

```json
"notices": [
  {"kind": "monitor", "code": "pc_unknown", "text": "PC 사양을 모르는 상태로 골랐어요. 쓰시는 PC나 PC 견적을 알려 주시면 해상도·단자가 맞는지 확인해 드릴게요."},
  {"kind": "monitor", "code": "gpu_4k", "text": "4K 모니터로 게임을 하려면 높은 그래픽카드 성능이 필요해요. …"}
]
```

`code`: `pc_unknown` · `gpu_4k` · `gpu_high_res` · `low_refresh`. 요구사양 행 `resolution_assumed`의 이름도 "해상도 조건(PC 사양 모름)"으로 바뀌었다.

**요청:** 결과를 받은 뒤 채팅에 `notices[].text`를 한 줄씩 보여 준다(품목 이름을 앞에 붙여도 좋다). 문구는 서버 것을 그대로 쓴다. 같은 내용을 결과 카드 아래 `ignored_inputs` 처럼 보여도 되지만, 채팅에는 반드시 나와야 한다.

## 5. 상충 조건을 채팅에 (PQA-006)

**서버 변경:** 함께 있을 수 없는 조건(지금은 키보드 텐키리스·컴팩트 ↔ 풀배열)이 둘 다 풀리면 서버가 정리하고 `resolved[kind].conflicts`로 알린다.

```json
"conflicts": [{"conditions": ["compact", "full_size"], "labels": ["텐키리스·컴팩트", "풀배열"], "kept": "compact"}]
```

**요청:**

- `kept`가 있으면: "{labels 중 kept 쪽}을 우선했어요(함께 고를 수 없는 조건이에요)."
- `kept`가 `null`이면 둘 다 뺀 것이다: "{A}와 {B}는 함께 고를 수 없어요. 어느 쪽으로 할까요?" — 두 조건을 칩으로 내면 좋다(누르면 그 조건 이름을 문장으로 보냄).

## 6. 빠른 선택 칩을 품목에 맞게 (PQA-015)

**지금:** `QUICK = ['FHD 144Hz', 'QHD 165Hz', '4K', '잘 모르겠어요']`가 품목과 관계없이 항상 나온다(종합#31). 누르면 글자를 문장으로 보내는데, 예전에는 서버가 이 낱말을 못 읽어 아무 일도 없었다(종합#52).

**서버 변경:** "4K"·"UHD"(고해상도), "QHD"·"1440p"(QHD 해상도), "유선"(마우스), "노래"(음악 감상)를 읽는다. "묵직한 키보드"·"타건감이 가벼운"처럼 어순이 달라도 키압으로 읽는다.

**요청:** 고른 품목마다 아래 칩을 보여 준다. 모두 서버에서 읽히는 것을 확인한 문장이다(모니터를 고르지 않았으면 해상도 칩은 숨긴다). 칩을 누를 때 그 품목을 `kinds`로 함께 보낸다.

| 품목 | 칩 문장 | 서버가 읽는 조건 |
|---|---|---|
| 모니터 | 4K · QHD 165Hz · 게임용 · 문서·코딩용 · 맥북 연결 | 높은 해상도 / QHD+높은 주사율 / 게임 / 문서·코딩 / 노트북 연결 |
| 키보드 | 조용한 키보드 · 텐키리스 · 묵직한 키압 · 래피드 트리거 | 조용한 곳 / 컴팩트 / 묵직한 키압 / 래피드 트리거 |
| 마우스 | 가벼운 무선 · 손목 편한 · 유선 · fps용 | 무선+가벼운 무게 / 손목 / 유선 / 경쟁 게임 |
| 스피커 | 작은 스피커 · 음악 감상 · 블루투스 · 영화·게임용 | 작은 크기 / 음악 / 블루투스 / 영화·게임 |

결과를 받은 뒤에는 지금처럼 서버의 `adjust_chips`를 쓴다.

## 7. 다른 선택지 리뷰 문장을 한글로 (PQA-020)

**지금:** `aspectsFromWire`가 `members[0].observation_text`를 보여 준다. 이 값은 리뷰를 분석한 **영어 요약**이다(3,676건 중 347건만 한글, 종합#18).

**요청:** `members[0].evidence_sentences[0]`(리뷰 원문 문장, 한글)을 보여 준다. 비어 있을 때만 `observation_text`로 물러난다.

## 8. 결과 화면에 머물기 (PQA-022)

**지금:** 결과 화면에서 칩 카드를 누르거나(종합#41) 채팅으로 조건을 바꾸면 첫 화면(조건 대화)으로 돌아간다.

**요청:** 결과 화면에서 조건이 바뀌면 결과 영역만 다시 불러온다(불러오는 동안 기존 결과를 흐리게 두는 정도면 충분).

## 13. (예고) 채팅 질문 답변 (PQA-014)
