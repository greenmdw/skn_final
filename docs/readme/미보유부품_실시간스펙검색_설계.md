# DB 미보유 부품 실시간 스펙 검색 — 동작 설명

카탈로그(DB)에 없는 PC 부품의 스펙을 **웹 검색 → LLM 검증**으로 찾아 **임시 부품 저장소**에 두고, 받은 견적 점검과 추천의 호환 검사에 보탠다. 이 문서는 현재 코드가 어떻게 동작하는지 설명한다.

| 구성 | 위치 |
|---|---|
| 검색·검증·저장 서비스 | `src/services/live_spec_lookup.py` |
| 저장소 읽기·쓰기 | `src/repo/live_spec_lookup_repo.py` |
| 저장 테이블 | `catalog.live_spec_lookup_cache` (`db/migrations/0009`, `0010`) |
| 웹 검색·LLM 호출 | `src/clients/llm_client.py` — `call_web_search`(OpenAI Responses API `web_search` 도구), `call_llm`(구조화 출력) |
| 검증 프롬프트 | `src/engine/prompts.py` — `live_spec_lookup_system()`, `live_reference_price_rules()` |
| API | `POST /pc/review-drafts/{draft_id}/items/{item_id}/live-lookup`, `POST /pc/review-drafts/{draft_id}/live-lookup-batch` |
| 화면 | `web/src/pages/check/PartsPage.tsx` — "정보 찾아보기", "확인하지 못한 제품 N개 한꺼번에 찾기" |
| 사람 검토 도구 | `db/review_live_lookup.py` |

## 1. 켜는 조건

`available()`이 참일 때만 검색한다. 아니면 버튼·대화 모두 "지금은 실시간 검색을 쓸 수 없어요"로 끝난다.

- `LIVE_PART_LOOKUP=1` (기본 0, 배포 견본 `deploy/aws.env.example`은 1)
- `MOCK_MODE=0`, `LLM_PROVIDER=openai`, `OPENAI_API_KEY` 있음

## 2. 언제 검색하나 — 사용자가 요청할 때만

비용이 드는 검색은 **사용자가 명시적으로 요청한 경우에만** 일어난다. 추천 계산이나 점검 분석이 자동으로 검색을 부르지 않는다.

| 진입점 | 조건 | 결과 |
|---|---|---|
| 받은 견적 점검 — 항목의 "정보 찾아보기" 버튼 | 항목 상태가 `unmatched`·`inferred`·`candidate`(카탈로그에서 확실히 찾지 못함) | 항목 하나 검색 |
| 받은 견적 점검 — "확인하지 못한 제품 N개 한꺼번에 찾기" | 위 상태의 항목, 한 번에 최대 `LIVE_LOOKUP_BATCH_MAX`(6)개 | 항목별 찾음 / 못 찾음 / 실패 / 건너뜀 |
| 조건 대화 에이전트 (`conditions_agent`) | 사용자가 말한 제품이 카탈로그에 없고, 에이전트가 "외부 검색을 할까요?"라고 물은 뒤 사용자가 동의 | 찾은 값을 "추가 조건"으로 기록(카탈로그 정식 값 아님 표시) |
| 결과 대화 에이전트 (`result_agent`) | 위와 같은 동의 절차 | 찾은 값을 참고로 안내 |
| 견적 점검 대화 (`quote_chat_service`) | "이 부품 정보 찾아줘" → 비용이 든다고 먼저 묻고(`pending_search`), 다음 턴에 동의하면 검색 | 찾은 값을 참고로 안내 |

카탈로그에 이름만 조금 다르게 있는 제품(예: "엔비디아 5070")이면 에이전트는 검색을 묻지 않고 카탈로그 제품을 안내한다.

## 3. 검색 한 번의 흐름 (`lookup_with_meta`)

```text
견적 원문 "[DDR5 32G] 삼성 DDR5-5600 16GB x2 189,000원"
  │ ① 이름 정리: 가격·수량·상품코드·괄호·묶음 용량 표기·"메모리:" 같은 이름표를 걷어 냄
  ▼
이름 "삼성 DDR5-5600 16GB"  →  저장소 키 lookup_key = 소문자 이름
  │ ② 저장소 조회: 쓸 수 있는 행이 있으면 검색 없이 바로 반환 (cached=true)
  │ ③ 없으면 한도 확인: 서비스 전체 분당 6회 · 동시 2개 — 넘으면 "검색이 몰려 있어요"(503)
  ▼
웹 검색 "삼성 DDR5-5600 16GB 정식 스펙"
  │ ④ 모델 번호 확인(코드): 검색 글에 질문한 제품의 모델 번호가 모두 나오는가?
  │      아니면 LLM을 부르지 않고 "못 찾음"으로 저장
  │ ⑤ LLM 검증: 그 제품을 다룬 글인지(relevant), 글에 실제로 적힌 값만 필드에 채움
  │ ⑥ 코드 정리: 부품 종류에 맞는 필드만 남기고 엔진 표기로 맞춤(DDR5, AM5, ATX …)
  ▼
저장소에 저장(못 찾음도 저장) → 결과 반환
```

### ① 이름 정리와 저장소 키

`normalize_lookup_key()`는 같은 제품이면 견적의 가격·수량·상품코드·표기 차이와 관계없이 같은 키가 되게 한다. 용량(16GB)과 모델 낱말(5600 vs 5600X)은 남겨, 다른 제품이 같은 키로 합쳐지지 않게 한다.

### ④ 모델 번호 확인 (`snippet_mentions_the_product`)

질문한 제품 이름에서 숫자가 든 모델 번호(예: `rm850x`, `9800x3d`)를 뽑아, 검색 결과 글에 모두 있는지 본다. DDR 세대·"32G" 같은 용량 표기·짧은 낱말은 모델 번호로 보지 않는다. 일반 소개 페이지만 잡혔을 때 그 글의 일반 값을 이 제품 값으로 옮기는 오탐을 막는다. 모델 번호로 쓸 낱말이 없는 이름(예: "Dark Rock Pro 5")은 이 확인을 건너뛴다.

### ⑤ LLM 검증 규칙 (프롬프트)

- 검색 글이 질문한 바로 그 브랜드·모델이 아니면 `relevant=false`, 모든 필드 null
- 글에 **명시된 값만** 채운다. 일반 지식·추론·같은 제품군의 통상 사양으로 채우지 않는다
- 숫자 필드는 숫자로 적힌 경우만, 단위 변환·어림값 금지
- `source_url`은 검색 결과의 출처를 그대로 옮긴다(http·https 주소만 저장)
- 성능·추천 여부·호환 여부는 판단하지 않는다
- 부품 종류에 맞지 않는 필드는 값이 보여도 null(예: 메인보드의 "최대 지원 메모리"를 `capacity_gb`에 넣지 않음)

출력은 `LiveSpecLookupResult`(`extra="forbid"`)로 검증한다. 스키마 밖 필드를 지어내면 검증에서 걸린다.

### ⑥ 부품 종류별 필드

| 부품 | 저장·사용하는 필드 |
|---|---|
| CPU | `socket`, `mem_type` |
| GPU | `interface` |
| RAM | `mem_type`, `speed_mts`, `capacity_gb`, `module_config`, `height_mm` |
| 메인보드 | `socket`, `mem_type`, `form_factor` |
| 저장장치 | `capacity_gb`, `interface`, `form_factor` |
| 파워 | `wattage_w`, `form_factor`, `module_config` |
| 케이스 | `supports_form_factors` |
| 쿨러 | `cooling_type`, `radiator_mm`, `height_mm`, `socket`(지원 소켓 목록) |

값은 `src/engine/part_values.py`의 정규화 함수로 엔진이 읽는 표기로 맞추고, 하나로 정해지지 않는 값은 버린다. RAM은 "2 x 16GB" 같은 구성 문장을 "16GB × 2"로 바꾸고 총용량을 맞춘다.

## 4. 임시 부품 저장소 (`catalog.live_spec_lookup_cache`)

카탈로그가 아니다. 후보 목록·가격 비교·합계에는 연결되지 않는다.

| 컬럼 | 뜻 |
|---|---|
| `lookup_key` (UNIQUE) | 정리한 이름(소문자) |
| `query_text`, `brand`, `model` | 검색 질의와 참고 정보 |
| `relevant`, `supported_fields`, `source_url` | 검증 결과, 찾은 필드(JSON), 출처 |
| `fetched_at` | 검색한 시각 |
| `status`, `reviewed_at` | 사람 검토 상태: `unreviewed`(기본) · `confirmed` · `rejected` |
| `reference_price`, `reference_price_source_url`, `reference_price_at` | 참고가(기본 꺼짐, 7장) |

**언제까지 쓰나 (`get_fresh`)**

| 행 | 사용 기간 |
|---|---|
| `confirmed` (사람이 확인) | 만료 없음 |
| 찾음 (`relevant`, `rejected` 아님) | `LIVE_SPEC_LOOKUP_FOUND_TTL_DAYS` (기본 90일) |
| 못 찾음 또는 `rejected` | `LIVE_SPEC_LOOKUP_NOTFOUND_TTL_DAYS` (기본 7일) — 출시 뒤 다시 찾을 수 있게 짧게 둔다 |

- 기간이 지나면 다음 요청에서 다시 검색한다. 다시 저장하면 상태는 `unreviewed`로 돌아간다. 단 `confirmed` 행은 덮어쓰지 않는다.
- `rejected` 행은 "못 찾음"으로 취급한다.

**사람 검토** — 원문 출처를 열어 확인한 뒤 상태를 바꾼다.

```bash
DATABASE_URL=... python db/review_live_lookup.py list                 # unreviewed 목록
python db/review_live_lookup.py list --status confirmed
python db/review_live_lookup.py confirm 3f2a9c1b                       # id 앞 8자리 이상
python db/review_live_lookup.py reject 3f2a9c1b
python db/review_live_lookup.py reset 3f2a9c1b                         # unreviewed로 되돌림
```

못 찾은 행(`relevant=false`)은 `confirmed`로 바꿀 수 없다.

## 5. 저장된 값이 쓰이는 곳 — 읽기만 함

아래 경로는 저장소를 **읽기만** 하고 새로 검색하지 않는다.

| 쓰는 곳 | 하는 일 |
|---|---|
| 받은 견적 점검 분석 (`quote_review_service`, `quote_replacement_plan`) | 카탈로그에서 찾지 못한 부품의 스펙을 저장소 값으로 채워 호환 검사에 쓴다(`cached_for_kept_parts` → `owned_parts.merge_live_lookup`). 출처는 `source="live"`로 남는다 |
| 견적 초안 항목 표시 (`quote_draft_service.mark_live_values`) | 저장된 값이 있는 항목에 `live_value=true` 표시 |
| 새 PC 추천 — 보유 부품 | 그대로 쓰는 보유 부품 중 카탈로그에서 확인 못 한 것을 저장소 값으로 보강 |
| 새 PC 추천 — [3-A] 하드 필터 (`catalog_enrichment.make_enricher`) | 스펙이 비어 "보류"된 후보의 빈 값을 저장소 값으로 채운다. 저장소가 다루지 않는 값(성능 등급·가격)은 채우지 않는다 |

채우는 규칙:
- 카탈로그로 확인한 부품(`catalog`)과 가장 비슷한 제품으로 본 부품(`candidate`)의 값은 건드리지 않는다.
- 글에서 일부만 읽은 부품(`text`·`inferred`)은 이미 읽은 값을 지키고 빈 키만 채운다.
- RAM은 검색 값이 "제품 하나" 기준이라 견적에 적힌 수량으로 곱한다.

## 6. 호출 한도와 오류 처리

| 한도 | 기본값 | 범위 |
|---|---|---|
| `LIVE_PART_LOOKUP_LIMIT_PER_MIN` | 5회/분 | IP별, 버튼·일괄 검색 요청 단위(일괄 1번 = 1회) |
| `LIVE_LOOKUP_GLOBAL_LIMIT_PER_MIN` | 6회/분 | 서비스 전체, 저장소에 없어 실제로 검색하는 경우만 |
| `LIVE_LOOKUP_MAX_CONCURRENCY` | 2 | 동시에 도는 검색 수(일괄 검색도 이 수만큼 병렬) |
| `LIVE_LOOKUP_BATCH_MAX` | 6 | 일괄 검색 한 번의 항목 수 |

- 전체 한도는 OpenAI 계정의 분당 토큰 한도 때문이다(웹 검색 1회가 약 1만 7천 토큰, 2026-10-05 측정).
- OpenAI가 한도 초과(429)를 내면 4초 기다렸다 한 번 더 시도하고, 그래도 안 되면 "지금 검색 요청이 몰려 있어요"(503)로 알린다. 대화 에이전트는 대화를 끊지 않고 이 문장을 답으로 낸다.
- 일괄 검색에서 한 항목이 실패해도 나머지는 계속한다.
- 한도는 서버 프로세스마다 따로 센다.

## 7. 참고가 (기본 꺼짐)

`LIVE_REFERENCE_PRICE=1`이면 검색 질의에 "현재 판매 가격"을 붙이고, 판매처와 원화 금액이 같은 문장에 명시된 경우만 `reference_price`로 저장한다(가격대·출시가·중고가·해외 가격·계산한 값은 저장하지 않음). 금액은 코드가 허용 범위를 다시 확인한다. 참고가는 `LIVE_REFERENCE_PRICE_TTL_DAYS`(기본 2일)가 지나면 내지 않는다. 켜도 가격 관측·가격 비교·합계·후보 선정에는 연결되지 않는다.

## 8. 하지 않는 것

- 검색 결과를 카탈로그 정식 제품으로 등록하지 않는다(`confirmed`는 승격 후보 표시일 뿐).
- 성능 등급(tier)은 찾지 않는다. 보유 부품의 업그레이드 하한처럼 성능 등급이 필요한 판단은 이 값으로 메울 수 없다.
- 부품 종류를 모르는 호출(표에 없는 종류)은 필드를 거르지 않고 검증 결과 그대로 저장한다.
