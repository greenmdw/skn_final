# PC 규칙 엔진 설계 (확장 가능 구조 유지)

**상태**: 설계 확정, 구현 전
**범위**: [3-A]~[3-C] 검증, [4] 최적화, [3-B] 랭킹, [5] 설명 생성, 카테고리 정의(YAML), 프론트 결과 화면 렌더링
**방향 전환 (2026-09-16)**: 중간발표 멘토 피드백(화자3·화자4)에서 "PC와 유아용품은 판단 성격 자체가 달라 안 와닿는다", "일정이 촉박하면 PC에 집중하고 다른 도메인은 확장 가능하다는 정도로만 남기라"는 지적을 독립적으로 받음. 이에 따라 **이번 라운드의 실제 작업 대상은 PC 하나로 좁힌다.** 다만 이 문서가 원래 잡았던 "규칙 평가와 도메인 지식을 분리한다"는 설계 자체는 PC 검증 로직의 정확성 문제(§1.2 "가짜 ok" 버그)를 고치는 데 그대로 필요하므로 폐기하지 않는다 — **유아용품 관련 내용은 삭제하지 않고 "나중을 위해 자리는 남겨두되 지금 구현하지 않는 것"으로 표시한다.**
**작성 배경**: 팀의 핵심 컨셉 중 하나인 "어떤 도메인이 추가되더라도 즉각 적용되는 AI 모델"이 실제 코드에는 거의 반영돼 있지 않다는 문제 제기에서 출발. 코드 감사 결과, 조건 대화(채팅) 단계는 이미 설정 기반이지만 실제 추천 엔진(검증·최적화)은 PC와 유아용품이 완전히 분리된 두 개의 하드코딩 파이프라인으로 확인됨. **이 감사 과정에서 PC 자체의 검증 로직도 절반이 가짜값(§1.2)이라는 더 근본적인 문제가 드러났고, 지금은 이걸 고치는 게 확장성보다 우선순위가 높다고 판단.**

## 1. 문제 정의

### 1.1 발견된 것 — 조건 대화는 설정 기반, 엔진은 하드코딩

`src/categories.py`의 `load_category()`가 `config/categories/{category}.yaml`을 읽어 슬롯·질문·라벨을 데이터로 제공하는 구조는 이미 잘 돼 있다(체감 70~80% 설정 기반). 문제는 그 다음이다.

- `src/engine/stage2_requirement.py`, `stage3_0_candidates.py`, `stage4_optimize.py`: `category != "computer"`면 `NotImplementedError`. 유아용품은 `build_baby_requirements`/`get_baby_candidates`/`optimize_baby`라는 **완전히 별도의 함수**로 처리된다.
- `src/engine/stage3c_verify.py`, `stage5_explain.py`: 같은 파일 안에 `run()`(PC)과 `verify_baby_candidate()`/`explain_baby_candidate()`(유아용품)가 로직 공유 없이 병존한다.
- `src/services/recommendation_service.py`: `_execute_baby_recommendation`이 `execute_recommendation`(PC 경로)과 아예 분리된 함수다.
- 프론트 `frontend/js/pages/results.js`의 `TF_RESULT_CATEGORY_CONFIG`: 카테고리별 슬롯 순서·문구가 파이썬 딕셔너리처럼 하드코딩돼 있고, 팀 스스로 주석에 "새 카테고리는 이 표에 한 줄 추가"라고 적어 이를 인지하고 있었다.

시스템 전체로 보면 대략 **30~35% 설정 기반, 65~70% 카테고리별 하드코딩**. `config/categories/baby.yaml` 자체에도 `status: stub`이라고 적혀 있다.

### 1.2 설계 중 추가로 발견한 것 — "가짜 ok" 버그

`stage4_optimize.py`의 `build_computer()`가 반환하는 `link_check` 딕셔너리:
```python
link_check={"socket": socket_status, "power": "ok (근사)", "gpu_len": "ok",
            "cooler_height": "ok", "bios": "ok"},
```
`socket`만 실제 계산되고 나머지 4개(전력·GPU 길이·쿨러 높이·BIOS)는 **실제 스펙 비교 없이 항상 "ok"로 고정된 상수**다. 즉 지금 시스템은 GPU가 케이스보다 길어도, 파워가 부족해도 절대 걸러내지 못한다. `data/parts_list.csv`에 필요한 필드(`length_mm`, `tgp_w`, `max_gpu_len_mm`, `wattage`, `height_mm`)는 설계돼 있지만, 실제로 엔진이 읽는 `data/demo_part_overrides.csv`에는 이 필드들이 없다 — 설계는 됐지만 데이터 수집이 끝나지 않은 상태다.

### 1.3 반대로, 이미 잘 만들어져 있던 것 (참고용 — 이번 범위 아님)

`src/rag/verification.py` + `config/baby_verification_rules.yaml`은 이미 완전한 설정 기반 규칙 레지스트리다. `rule_id`/`scopes`(synthetic_demo·production)/`required_claims`/`pass_when`/`unknown_when`/`fail_when`/`source`(출처 신뢰도 검증까지) 스키마를 갖추고 있다. **PC 집중 방향에서는 이걸 지금 당장 손대거나 새 계약으로 이관할 필요가 없다** — 그대로 잘 동작 중이니 건드리지 않고, "증거클레임 패밀리가 필요해지면 이 파일이 그 실례다"라는 참고 자료로만 남겨둔다.

## 2. 목표와 원칙

**우선순위 1 — PC 검증·최적화를 실제로 정확하게 만든다.** §1.2의 "가짜 ok"를 없애고, 신뢰도 계산이 실제 스펙 비교에 근거하게 만드는 것이 이번 라운드의 진짜 목표다. 확장성은 이 작업의 부산물이지 목적이 아니다.

**우선순위 2 — 그 작업을 하는 방식이 우연히도 확장 가능한 구조가 되게 한다** (비용이 들지 않는 선에서):
1. **결과를 소비하는 쪽(검증 집계·설명 생성·프론트 렌더링)은 규칙이 몇 개로 늘어나든 다시 고치지 않는다.** (도메인이 아니라 "PC 안의 규칙 개수"가 늘어나는 경우에도 적용됨.)
2. **규칙을 늘릴 때 늘어나는 것은 오직 선언적 데이터(YAML)뿐이어야 한다.**
3. **상상으로 설계하지 않는다(YAGNI).** 지금 확정된 범위(PC)에 실제로 필요한 것만 만든다. 유아용품·캠핑 관련 내용은 "나중에 필요해지면 이 구조가 받아줄 수 있다"는 근거로만 남기고, 지금 그것들을 위해 별도 코드를 새로 만들지 않는다.
4. **판단은 코드가, 서술은 LLM이 한다는 기존 원칙을 그대로 유지한다.** 규칙 평가는 결정론적 파이썬 함수로, AI는 규칙 초안 작성·문장화에만 관여한다.

## 3. 전체 아키텍처 한눈에 보기

```
조건 대화 (이미 설정 기반, 안 건드림)
        │
        ▼
config/categories/<domain>.yaml
  ├─ slots, questions        (기존)
  ├─ slot_specs              (신규 — 스펙 필드 스키마)
  ├─ spec_rules               (신규 — equals/fits/budget_sum/member_of)
  ├─ claim_rules_ref          (신규 — baby_verification_rules.yaml류 파일 참조)
  ├─ optimize_strategy        (신규 — slot_assignment | budget_knapsack)
  ├─ verify_aggregation       (신규 — confidence_score | gate)
  └─ rank_weights             (신규)
        │
        ▼
┌─────────────────────────────────────────────┐
│  규칙 평가 엔진 (도메인 무관, 공통 코드)         │
│  스펙비교 패밀리 ─┐                            │
│  증거클레임 패밀리 ┴→ RuleResult(공통 결과 계약)│
└─────────────────────────────────────────────┘
        │
        ▼
stage3b(랭킹) → stage4(최적화, 전략 패턴) → stage3c(검증 집계) → stage5(설명)
        │                                                        │
        └────────────── 전부 RuleResult/BasketResult 공통 계약만 소비 ──┘
        │
        ▼
프론트 결과 화면 (제네릭 렌더링, 카테고리 하드코딩 없음)
```

**핵심 아이디어 하나로 요약하면**: *"규칙을 평가하는 로직"과 "규칙이 무엇인지(도메인 지식)"를 분리하고, 평가 결과는 항상 같은 모양(계약)으로 내보낸다.* 이 계약 하나만 지키면 뒷단(집계·설명·화면)은 규칙이 몇 개든 절대 안 바뀐다.

**지금 실제로 구현하는 범위**: 위 다이어그램에서 `config/categories/computer.yaml` 한 줄만 실제로 채워진다. `claim_rules_ref`, `optimize_strategy: budget_knapsack` 등 baby가 쓰던 자리는 스키마상 존재하되 값이 채워지지 않은 채로 남는다 — 나중에 다른 도메인을 붙일 때 이 문서를 다시 펼치면 되는 정도로만 취급한다.

## 4. A. 규칙(Rule) 시스템

### 4.1 [결정 1] 규칙 패밀리는 통합하지 않고 결과 계약만 통일한다

**검토한 대안**: 스펙비교와 증거클레임을 하나의 `rules:` 리스트, 하나의 `type` enum으로 통합.
**기각한 이유**: PC(스펙 대 스펙 비교)와 유아용품(증거 기반 클레임 검증 — 수치 비교가 아니라 "주장+출처 신뢰도" 구조)은 패러다임 자체가 다르다. 억지로 통합하면 `type: compare`/`type: claim`으로 나뉜 채 내부적으로는 결국 다른 코드를 타게 되어 통합의 실익이 없고, 오히려 이미 잘 검증된 `src/rag/verification.py`를 건드릴 위험만 커진다.

**채택한 방식**: 두 패밀리를 유지하되, 둘 다 같은 모양의 결과를 낸다.

```python
RuleResult = {
    "rule_id": str,
    "slot": str,
    "status": "pass" | "fail" | "unknown",
    "severity": "critical" | "warning" | "info",
    "weight": int,             # confidence_score 집계용 감점 값
    "reason_code": str,        # 기계가 읽는 사유 코드(패밀리마다 자기 어휘 사용 가능)
    "message": str,            # 사람이 읽는 중립 서술
    "evidence": list[dict],    # 근거(RAG 인용·실측값)
    "source": dict | None,     # 출처 신뢰도(baby는 항상, PC는 RAG 연결되면)
}
```

stage3c_verify·stage5_explain·프론트는 이 계약 하나만 알면 되고, 어느 패밀리가 만들었는지 신경 쓰지 않는다.

**대가**: 두 패밀리를 각각 유지보수해야 한다(완전 통합보다 코드량이 약간 더 많음). 그러나 서로 다른 패러다임을 억지로 합칠 때 생기는 복잡도보다는 작다고 판단.

### 4.2 [결정 2] 규칙은 `(슬롯 타입, 필드명)`을 명시적으로 선언하고, 슬롯 타입별 스펙 스키마로 이중 검증한다

**검토한 대안**: "GPU 슬롯은 원래 `length_mm`을 갖는다"는 암묵적 컨벤션.
**기각한 이유**: 오늘 발견한 "가짜 ok" 버그가 정확히 이 암묵적 방식의 실패 사례다 — 필드가 없어도 조용히 넘어가서 설계 실수인지 데이터 누락인지 구분이 안 됐다.

**채택한 방식**:
```yaml
spec_rules:
  - rule_id: socket_match
    type: equals
    operands:
      - {slot: CPU, field: socket}
      - {slot: mainboard, field: socket}

  - rule_id: gpu_length_fit
    type: fits              # left <= right
    left:  {slot: GPU, field: length_mm}
    right: {slot: mainboard, field: max_gpu_len_mm}

  - rule_id: power_budget
    type: budget_sum        # sum(operands) <= limit
    operands:
      - {slot: CPU, field: tdp_w}
      - {slot: GPU, field: tgp_w}
    limit: {slot: PSU, field: wattage}

slot_specs:
  GPU:       {required: [length_mm, tgp_w, vram_gb]}
  mainboard: {required: [socket, form_factor, mem_type, max_gpu_len_mm]}
  PSU:       {required: [wattage]}
```

이중 검증: ① 규칙 작성 시점 — 참조하는 `(slot, field)`가 `slot_specs`에 실제 등록된 필드인지 검증(오타 차단). ② 카탈로그 적재 시점 — 그 슬롯 타입 상품이 `required` 필드를 실제로 갖고 있는지 검증(오늘 겪은 데이터 누락을 로딩 단계에서 잡아냄).

`budget_sum`은 `operands`를 리스트로 받아 슬롯 개수 제약 없이 확장 가능(캠핑의 "인원수만큼 곱해서 합산" 같은 것도 이 구조 위에 자연스럽게 얹힘).

### 4.3 [결정 3] 규칙 실패 처리는 `status(pass/fail/unknown)`+`severity`로 통일하되, 집계 방식은 도메인이 선택한다

**개별 결과 매핑**:

| 기존 PC(감점) | 기존 baby(합불) | 통일된 결과 |
|---|---|---|
| 위반(20점 감점) | `fail_when`(active_recall 등) | `status=fail, severity=critical` |
| 확인 필요(6점, "근사") | `unknown_when` | `status=unknown, severity=warning` |
| 예산 초과(15점) | — | `status=fail, severity=warning` |
| 통과 | `pass_when` | `status=pass` |

**집계는 통일하지 않는다.** PC는 규칙들을 모아 신뢰도 숫자 하나(`confidence_score`)로 내지만, baby는 규칙 하나라도 `fail`이면 후보 자체를 차단하는 게이트(`gate`) 방식이다. 이건 "채점 방식이 여러 개라서 신뢰도를 높이는 것"이 아니라 **"안전 문제(카시트 월령 등)를 숫자로 흐리면 안 되기 때문"**이다. 치명적 안전 이슈 1개와 사소한 문제 여러 개를 평균 내서 "신뢰도 70%"라고 보여주면, 실제로는 사면 안 되는 상품인데 숫자가 심각성을 가리게 된다.

```yaml
# computer.yaml
verify_aggregation: confidence_score
# baby.yaml
verify_aggregation: gate
```

두 집계 전략 모두 같은 개별 `RuleResult` 위에서 동작하므로, 규칙 평가 자체는 여전히 공통 엔진이다.

### 4.4 [결정 4] 필드 결측 시 절대 `pass`로 넘기지 않고 `unknown` + 이유 코드를 낸다

지금 PC의 `_compat_filter()`는 "정보 없는 후보는 통과시킨다"는 정책인데, 이게 1.2절의 가짜 ok 버그의 근본 원인이다. baby는 이미 `unknown_when`으로 "왜 모르는지"(missing_rule_evidence, missing_product_identity 등)까지 구분해서 낸다 — 이 방식을 PC에도 그대로 적용한다.

```python
RuleResult(status="unknown", severity="warning",
           reason_code="spec_field_missing",
           message="GPU 길이 정보가 없어 확인하지 못했습니다.")
```

- **PC(confidence_score)**: `unknown`은 작은 감점을 받고, 기존 "회색축(gray_axes)" 자리에 투명하게 표시된다.
- **baby(gate)**: `unknown`은 자동 선택 대상에서 제외되지만(`eligibility=="pass"`만 자동 선정), 완전히 숨기지 않고 "확인 필요" 상태로 목록엔 남는다.

`reason_code`는 패밀리마다 자기 어휘를 쓴다 — baby는 `missing_rule_evidence` 등 기존 코드를, 스펙비교는 `spec_field_missing`/`spec_field_invalid` 같은 자기 코드를 새로 쓴다. 모양(unknown+reason_code)만 같으면 되고 어휘까지 통일할 필요는 없다.

### 4.5 [검토했으나 기각] 세 번째 규칙 패밀리

시간/일정 비교, 재고/가용성, 지역·법규 준수, 사용자 자격 검증 등을 검토했으나 전부 기존 두 패밀리(스펙비교의 새 타입 추가, 또는 증거클레임)로 흡수된다. 특히 유아용품의 월령 체크(`verify_seat`)는 이미 "증거클레임으로 기준값을 추출 → 스펙비교로 사용자 입력과 비교"하는 **두 패밀리의 합성**으로 동작 중이며, 이는 두 패밀리만으로 복합적인 체크도 커버 가능하다는 증거다. **지금은 세 번째 패밀리를 만들지 않고, 정말 필요해지면 그때 추가한다.**

## 5. B. 카탈로그 스펙 데이터 모델

### 5.1 [결정 5] PC 규칙별 필요 필드 — 확정 및 존재 여부 실사

| 규칙 | 타입 | 필요 필드 | 데이터 존재 |
|---|---|---|---|
| 소켓 일치 | `equals` | CPU.socket ↔ mainboard.socket | ✅ 존재 |
| 메모리 타입 일치 | `equals` | CPU.mem_type ↔ mainboard.mem_type | ✅ 존재 |
| 폼팩터 호환 | `member_of` | mainboard.form_factor ↔ 케이스.supports_form_factors | ✅ 존재 |
| GPU 길이 적합 | `fits` | GPU.length_mm ≤ mainboard.max_gpu_len_mm | ❌ 없음(설계만 됨) |
| 전력 예산 | `budget_sum` | CPU.tdp_w + GPU.tgp_w ≤ PSU.wattage | ❌ 없음 |
| 쿨러 높이 적합 | `fits` | 쿨러.height_mm ≤ 케이스.max_cooler_height_mm | ❌ 없음 |

실사 근거: `data/parts_list.csv`의 `fields_needed` 컬럼엔 이미 이 필드들이 설계돼 있으나, 실제로 엔진이 읽는 `data/demo_part_overrides.csv`(컬럼: `product_key,price,perf_tier,socket,mem_type,form_factor,supports_form_factors`)엔 없다. `data/parts_specs.json`(크롤링 결과)도 socket·form_factor만 실제로 채워져 있다.

baby는 `config/baby_verification_rules.yaml`의 기존 15슬롯 레지스트리를 그대로 재사용 — 이번 스펙 필드 목록과 별개, 추가 조치 불필요.

### 5.2 [결정 6] 필드 네이밍/단위 표준

이미 자연발생적으로 쓰이던 방식을 공식 표준으로 채택:

1. 수치형(물리량) 필드는 반드시 `_단위` 접미사: `length_mm`, `tgp_w`, `capacity_gb`, `weight_kg` 등.
2. 열거형(카테고리) 필드는 접미사 없음: `socket`, `mem_type`, `form_factor`.
3. 무차원 점수도 접미사 없음: `perf_tier`.
4. **단위 변환은 하지 않는다.** 한 필드는 항상 하나의 고정 단위만 쓰고, 단위가 필드명에 못박혀 있어 "mm인지 cm인지 헷갈리는" 버그가 원천 차단된다. 원본 데이터가 다른 단위면 적재(ingest) 단계에서 표준 단위로 변환 후 저장 — 규칙 엔진은 절대 단위 변환을 하지 않는다.

`{value, unit}` 객체 구조 대신 이 방식을 택한 이유: 규칙 평가 코드가 매번 "이 필드의 unit이 뭔지 확인→변환"하는 복잡도와 변환 실수 위험을 원천 제거하기 위함.

### 5.3 [결정 7] 백필(backfill) 실행 계획

| 필드 | 개수 | 방법 |
|---|---|---|
| CPU.tdp_w | 10 | `scripts/build_specs.py` 재실행(이미 이 필드를 추출하도록 설계돼 있음) |
| GPU.length_mm, tdp_w | 5 | 동일 도구 재실행 |
| PSU.wattage | 5 | **자동 파싱 가능** — 상품명에 와트수가 이미 포함(`RM650e`→650W 등) |
| mainboard.max_gpu_len_mm | 10 | 크롤러 미지원 → 수기(공식 스펙 URL은 `parts_list.csv`에 이미 있음) |
| case.max_gpu_len_mm/max_cooler_height_mm | 4 | 수기 |
| cooler.height_mm | 4 | 수기 |

자동(크롤러 재실행+정규식 파싱) 20개 + 수기 18개 — 하루 안에 끝낼 수 있는 규모. **이 작업은 순수 데이터 수정이다**: `data/demo_part_overrides.csv`에 값을 채우고 기존 `db/seed_catalog.py`를 재실행하는 것으로 끝나며, 엔진 코드를 고치지 않는다. DB를 직접 SQL로 고치지 않는 이유: DB는 파일에서 매번 다시 만들어지는 결과물이라, 직접 고치면 다음 재시드 때 조용히 덮어써진다.

## 6. C. 최적화 알고리즘 구조

### 6.1 [결정 8] 단일 알고리즘이 아니라 전략 패턴 (지금은 `slot_assignment` 하나만 실제 구현)

PC(`slot_assignment` — 고정 슬롯에 후보 1개씩 배정+호환성 가지치기)와 baby(`budget_knapsack` — 다중 독립 요구사항의 예산 제약 배분)는 문제 모양이 달라 하나의 함수로 억지로 합치지 않는다는 게 원래 결정이었다. **PC 집중 방향에서는 `budget_knapsack`을 지금 구현하지 않는다** — `optimize_baby()`는 이미 잘 동작하는 별도 함수로 그대로 두고 손대지 않는다. `optimize_strategy`라는 선택 필드 자체는 인터페이스에 남겨두되(6.2절), 실제로 값을 갖는 건 `slot_assignment` 하나뿐이다.

```yaml
computer.yaml: { optimize_strategy: slot_assignment }   # 지금 실제로 쓰는 유일한 값
# baby.yaml의 optimize_strategy: budget_knapsack — 기존 optimize_baby() 그대로 유지, 이관 안 함
```

**캠핑/여행 도메인 메모(참고용, 지금 구현 안 함)**: "하나의 여행 시나리오 → 여러 품목 카테고리(텐트·침낭·버너 등)"라는 구조는 baby와 완전히 동형(isomorphic)이라 나중에 실제로 캠핑을 붙일 때는 `optimize_baby()`를 그대로 재사용하면 된다는 검토 결과가 있었다. 지금은 실행하지 않고, 이 문단만 "다음에 다른 도메인을 붙일 때 참고할 것"으로 남겨둔다.

### 6.2 [결정 9] 전략 확장 계약 — 입출력 형태 통일

지금 PC(`BuildResult`)와 baby(`BasketDecision`)는 반환값 모양이 다르다. A번(결과 계약) 원칙을 stage4에도 적용한다.

```python
BasketResult = {
    "items": list[...],       # 공통 모양: slot/requirement_id, product, qty, price, selected, timing
    "totals": {"selected_price": int, "budget_remaining": int, "over_budget": bool, ...},
    "feasible": bool,
    "missing": list[dict],    # 못 채운 요구사항
    "strategy_meta": dict,    # 전략 고유 정보(PC의 link_check·balance, baby의 alternatives.search 등)
}

def run(candidates, requirements, budget, owned, log) -> BasketResult: ...
```

새 전략 추가 = 이 시그니처를 구현하는 함수 하나 + `OPTIMIZE_STRATEGIES` 레지스트리 등록. stage4 진입점은 `category_def.optimize_strategy` 값으로 레지스트리에서 전략을 찾아 호출하는 디스패처 역할만 하고, 도메인 분기(`if category=="computer"`)는 사라진다.

## 7. D. 검증·신뢰도 스코어링

- **신뢰도 공식**은 `100 - Σweight`로 공통이고, `weight`는 규칙마다 YAML에서 선언(4.2절 예시의 `weight` 필드). 숫자만 도메인/규칙별로 다르다.
- **회색축**은 별도 판정 로직이 필요 없다 — `status: unknown`인 규칙들의 집합이 곧 회색축이다(4.4절과 동일 개념, 자동 도출).

## 8. E. 랭킹(stage3b)

- **리뷰축 가중치**: `_WEIGHTS`(가격/성능/밸런스/리뷰/호환여유)가 PC 전용 축을 포함해 그대로 못 쓴다 → `rank_weights`를 카테고리 YAML로 분리. 리뷰 신호 계산(`_review_axis`, 오늘 만든 `resolve_risk_store()`)은 이미 도메인 무관이라 그대로 재사용.
- **규칙 결과의 랭킹 반영**: A번 규칙 결과를 랭킹 단계의 감점 축으로 추가 추천 — critical fail은 큰 감점, unknown은 작은 감점. 나쁜 후보가 최적화 탐색 전에 미리 후순위로 밀려 가짜 ok가 숨어있던 문제도 랭킹 단계에서 예방된다.

## 9. F. 설명 생성(stage5·LLM)

A번 결과 계약(`RuleResult.message`)이 이미 사람이 읽을 문장이므로, 기존 `explanation_text_with_caveats()` 패턴에 이 메시지 리스트를 그대로 흘려보낸다. **새 프롬프트 작성 불필요** — 기존 `EXPLAIN_SYSTEM` 재사용.

## 11. H. Agent(Strands) 통합

- **규칙 평가(실행)**: 일반 파이썬 함수 유지. 대량 후보를 매번 LLM 경유로 평가하면 느리고 비결정적이라 부적합.
- **규칙 작성 지원(신규 도메인 온보딩)**: Agent화 추천. 스키마(두 패밀리)와 기존 예시(PC 5규칙, baby clothing/recall 규칙)를 few-shot으로 주고, 자연어 체크리스트를 넣으면 "이 항목은 이 패밀리, 초안 규칙은 이거"를 뽑아내는 tool. **새 패밀리를 아예 새로 만드는 것도 AI가 초안(스키마+평가 함수+테스트)까지 작성 가능하지만, 사람 검토·테스트 통과 없이 자동 배포하지 않는다** — 미지의 영역에서 AI 생성 코드는 그럴듯해 보이지만 엣지케이스가 틀릴 위험이 크기 때문. "판단은 코드/사람, 서술·초안은 AI"라는 프로젝트 철학과 일치.

## 12. I. 프론트엔드 렌더링 (우선순위 낮음 — PC 집중 기간에는 보류)

- `TF_RESULT_CATEGORY_CONFIG`(하드코딩 표) 대신, 백엔드가 `{slot_label, product, checks:[{status,severity,message}]}` 형태로 내려주는 걸 그대로 렌더링하는 범용 컴포넌트로 교체하는 안은 유효하지만, **카테고리가 사실상 PC 하나뿐인 지금 시급성이 낮다.** 이 표에 카테고리가 하나만 있어도 하드코딩 자체가 문제를 일으키지 않으므로, 백엔드(A~F) 작업이 끝난 뒤 여유가 있을 때 진행한다.
- "구매 시점" 같은 작은 도메인별 UI 차이는 완전 규칙화하지 않고 `has_timing: true/false` 플래그로 표현(과설계 방지) — 이건 그대로 유효.

## 13. J. 마이그레이션·회귀 검증

**이관 순서 (PC 집중 버전 — baby 어댑터 단계 제거)**:
1. PC 소켓/멤타입/폼팩터 3개 규칙(데이터 이미 있음)을 새 엔진으로 이관 → 골든테스트(`tests/test_domain_refactor_golden.py`) 통과 확인
2. PC 나머지 3개 규칙(7번 백필 완료 후)
3. **"외부 견적 검증" 기능(유튜브 링크/부품 리스트를 가져와 사용자 조건과 맞는지 확인)을 이 엔진 위에 연결.** 이건 새 최적화가 아니라, 사용자가 입력한 부품 리스트를 곧바로 `BuildResult` 입력으로 삼아 기존 stage3c(검증)·stage5(설명)를 그대로 태우는 것이라 이 문서의 규칙 엔진이 정확히 필요한 지점이다 — PC 전용 확장이지만 이 설계의 첫 실사용처가 된다.
4. 프론트 제네릭 렌더링 전환 (§12, 우선순위 낮음)

baby claim_rules 어댑터는 **지금 진행하지 않는다** — `optimize_baby()`/`verify_baby_candidate()`는 그대로 두고 건드리지 않는다.

**완료 기준**: 각 단계마다 이관 전/후 골든테스트 100% 동일 통과.

**과거 데이터**: `engine.recommendation_run`의 과거 `link_check`/`checks` 값은 마이그레이션하지 않고 읽기 전용 기록으로 둔다. 새 스키마는 새로 생성되는 run부터 적용 — 억지 변환은 과거 기록 왜곡 위험이 있고 실익도 적다.

## 14. K. 운영/거버넌스 (우선순위 낮음)

H번의 "규칙 초안 Agent"가 비개발자의 규칙 작성 문턱을 낮춘다는 아이디어 자체는 유효하지만, **지금은 도메인이 PC 하나뿐이라 "새 도메인 온보딩"이라는 문제 자체가 당장 없다.** YAML 스키마 검증기(존재하지 않는 필드 참조, 네이밍 규칙 위반을 잡는 린터)는 PC 규칙 수가 늘어나면서 필요해지면 그때 만든다.

## 16. 다음 단계

이 문서는 설계 확정 상태이며 구현은 아직 시작하지 않았다. 실제 구현에 들어갈 때는 §13(이관 순서)을 따르며, 각 단계마다 골든테스트로 행동 동일성을 검증한다.

**이번 라운드 실행 범위(PC 집중)는 다음 셋뿐이다**:
