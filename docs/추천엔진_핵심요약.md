- 기준: 2026-09-27 작업 트리. 미커밋 구현을 포함하며 배포 완료를 뜻하지 않는다.

- 수치 예제는 설명용 가상 상품이다. 실제 판매 견적이나 성능 측정 결과가 아니다.

## 1. 어떤 문제를 푸는 엔진인가

Truefit은 사용자의 용도·예산·우선순위를 받아 **PC 부품 구성을 선택하고, 선택 이유와 구매 전 확인할 사항을 제공하는 엔진**이다.

신규 조립은 CPU·GPU·RAM·메인보드·저장장치·파워·케이스·쿨러의 8종을 대상으로 한다. 코드에서 각 종류를 **슬롯**이라고 부른다. 업그레이드는 이 중 교체할 슬롯만 구매 대상으로 삼는다. 모니터·키보드·마우스·스피커는 별도의 주변기기 하위 엔진이 담당하지만 API에는 아직 연결되지 않았다.

중요한 문제는 “좋은 부품 8개를 찾는 것”만이 아니다. CPU와 메인보드의 소켓이 다르거나 GPU가 케이스보다 길면 함께 쓸 수 없다. 따라서 **개별 상품의 선호도와 전체 조합의 예산·호환 조건을 함께 고려**해야 한다.

현재 구조는 다음과 같다.

> 규칙 기반 요구사양 생성 + 후보 점수화 + 제약을 고려한 조합 탐색 + 검증 쟁점 집계 + 설명 문장 생성

추천 본체는 구매 이력으로 선호를 학습하는 모델이 아니다. 요구 기준과 가중치는 YAML 설정 파일로 관리한다. LLM(대규모 언어 모델)은 추천 본체의 상품 선택·수치 계산을 대신하지 않고, 주로 결과를 문장으로 설명한다. 피드백 이벤트 기록은 있지만 가중치를 자동 학습하는 단계는 아직 없다.

먼저 다음 세 숫자를 구분하자.

| 숫자 | 용도 | 뜻하지 않는 것 |
|---|---|---|
| 후보 점수 | 같은 슬롯의 상품 순위와 조합 점수 합 계산 | 실제 성능, 고장 확률 |
| 신뢰도 | 검증 쟁점 감점을 합산한 재탐색 종료 기준 | 조립 성공 확률, 구매 승인 |
| 기여도 | 선택된 부품의 일부 가중 점수를 가격·성능·호환성으로 묶어 100%로 표시 | 성능 향상률, 모든 선택 원인의 비율 |

## 2. 한 요청은 어떤 단계를 거치는가

예를 들어 사용자가 “150만원, QHD 게임용, 가성비 우선”을 요청했다고 하자.

```text
[1] 조건 수집 → [2] 요구사양 생성 → [3-0] 상품 후보 로드
 → [3-A] 후보 필터 → [3-B] 점수·순위 → [4] 부품 조합 탐색
 → [3-C] 세트 검증 → 기준 미달이면 후보 하나 제외 후 [4]부터 재실행
 → [5] 선택 이유·확인 사항 설명
```

번호는 기획 단계의 이름이다. **PC 실행 순서는 [4] 다음 [3-C]**다. 검증할 세트를 먼저 만들어야 하기 때문이다.

| 단계 | 실제 하는 일 | 예 / 결과 |
|---|---|---|
| [1] 조건 수집 | 대화·선택값을 구조화 | `budget_max=1500000`, `purpose=game`, `priority=value` |
| [2] 요구사양 | 조건을 슬롯별 비교 기준으로 변환 | QHD: GPU 등급 ≥ 7, GPU 전용 메모리(VRAM) ≥ 12GB, CPU 등급 ≥ 5 |
| [3-0] 후보 로드 | 상품·스펙·가격을 공통 형태로 읽기 | `Candidate`: 상품 키, 가격, 스펙, 출처 |
| [3-A] 하드 필터 | 각 상품 자체가 최소 기준을 충족하는지 검사 | Pass / Fail / Pending과 이유 |
| [3-B] 점수·순위 | 가격·성능 등 여러 축을 가중합 | CPU·GPU 상위 5개, 나머지 상위 3개 |
| [4] 조합 탐색 | 예산·확인된 호환 조건을 고려해 슬롯별 하나 선택 | 선택 부품, 총액, 호환 상태 |
| [3-C] 검증 | 호환·예산 상태를 쟁점과 감점으로 집계 | 내부 신뢰도와 확인할 문제 |
| [5] 설명 | 계산된 선택과 쟁점을 문장으로 전달 | 요약, 부품별 이유, 주의 사항 |

실제 API의 기본 조건 추출은 정규식 규칙이다. 선택적인 LLM 조건 대화 기능은 있지만, 그 기능과 추천 본체의 규칙 계산은 별개다.

공통 필수 입력은 신규/업그레이드 모드, 용도, 최대 예산, 우선순위다. 업그레이드는 교체 부품과 조건부 추가 답변도 필요하다. 누락된 필수값이 있으면 추천을 시작하지 않는다. 생략한 일부 선택 조건은 기본값으로 채우며, 예를 들어 기본 해상도는 FHD다. 생략과 명시적인 빈 값은 항상 같은 처리가 아니므로 재현할 때 입력을 그대로 기록한다.

개발자가 보는 데이터 흐름은 `Slots` → `RequirementSpec` → `Candidate`·`RankResult` → `BuildResult` → `VerificationResult` → `Explanation`이다. 이 이름들은 각 단계가 주고받는 데이터 상자이지, 그대로 DB 테이블이나 API 응답을 뜻하지 않는다.

## 3. 성능 등급과 데이터는 어디서 오는가

### 3.1 CPU·GPU 등급은 독립적인 성능 평가가 아니다

실경로는 수집 파일의 **‘제품 라인업’ → DB의 `lineup` → 설정표의 `perf_tier`** 순서로 등급을 만든다. 예를 들어 GPU는 `Mainstream → 6`, `Mid-Range → 7`, `High-End → 8`로 변환한다.

이것은 **수집된 분류를 내부 숫자로 바꾼 임시 대용 지표**다. 현재 코드가 벤치마크·게임 FPS·코어 수·동작 속도를 종합해 새로운 성능 등급을 계산하는 것은 아니다. 같은 라인업의 서로 다른 세대·모델이 같은 등급을 받을 수 있으며, 등급 8이 4보다 두 배 빠르다는 뜻도 아니다.

원문·코드 주석의 “제조사 등급”은 이 문서에서는 “수집된 제품 라인업”으로 표현한다. 수집 컬럼을 사용한다는 사실만으로 **제조사가 공식 공인한 성능 등급이라고 단정하지 않는다.** 매핑은 [PC 정책 설정](../config/computer_verification_rules.yaml), 원천 컬럼 연결은 [PC 데이터 적재 코드](../db/seed_pc_parts_specs.py)에서 확인할 수 있다.

등급을 **부여하는 방법**과 **사용하는 규칙**은 다르다.

- 상품의 등급 부여: 제품 라인업을 숫자표로 변환한다.
- 요구사양: “QHD 게임이면 GPU 등급 7 이상”처럼 최소값을 정한다.
- 순위: 성능 축은 `등급 / 10`, 밸런스 축은 목표 등급과의 거리로 계산한다.

설정값 `QHD_165`에서 QHD는 2560×1440 해상도, 165는 목표 모니터 주사율인 165Hz를 뜻한다. Hz는 화면이 갱신되는 빈도이고 FPS는 컴퓨터가 초당 만드는 프레임 수다. **실제 게임에서 165 FPS를 보장하지 않는다.** 게임 제목별 요구 등급도 현재 잠정 정책값이다. 표에 없는 게임은 미해결 항목으로 남기며, 지원한다고 단정하지 않는다.

### 3.2 실경로 데이터도 실시간 수집 데이터는 아니다

PC 상품·스펙·가격은 미리 적재된 DB 카탈로그에서 읽는다. 가격이 확인되지 않는 상품은 후보에서 제외한다. 한 요청을 처리할 때 인터넷에서 가격이나 재고를 새로 수집하지 않는다.

따라서 “DB의 실제 상품을 사용했다”와 “지금 그 가격으로 구매 가능하다”는 다른 주장이다. 가격 관측 ID는 어떤 가격 기록을 사용했는지 추적하는 장치다. 옵션별 판매 가격과 선택 스펙의 정합성도 별도 확인 대상이다.

리뷰는 평균 별점만 사용하는 것이 아니라, 리뷰 몰림 같은 **상품 단위 관측 신호**를 비교 집단과 대조해 순위에 반영한다. 개별 리뷰가 가짜인지 판정하거나 삭제하는 기능은 아니다. 리뷰 산출물·상품 키 매핑이 없으면 “관측 없음”으로 처리하며, 이때 리뷰 점수가 고정되어 추천 결과가 달라질 수 있다.

## 4. 왜 단품 1위가 최종 견적에서 빠지는가

### 4.1 먼저 후보의 자격과 선호도를 구분한다

하드 필터는 상품 자체의 최소 조건을 본다. 예를 들어 GPU 등급 7·VRAM 12GB가 요구된다면:

- 등급 8, VRAM 12GB → **Pass**: 알려진 요구를 충족한다.
- 등급 6, VRAM 12GB → **Fail**: 등급이 부족하다.
- 등급 8, VRAM 정보 없음 → **Pending**: 정보가 없어 판정을 보류한다.

여러 조건 중 하나라도 확정 실패면 Fail이다. Pass가 슬롯당 3개 이상이면 Pending은 제외하고, 부족하면 Pending도 후보에 남기되 점수에서 0.20을 뺀다. GPU의 Pass는 GPU 자체 요구를 통과했다는 뜻이지, 어느 케이스에도 들어간다는 뜻이 아니다.

**반드시 알아둘 예외:** Pass와 Pending이 모두 없는 슬롯에서는 Fail 후보를 다시 남긴다. 이 예외는 데모뿐 아니라 API에도 적용된다. 이후 검증이 원래 요구사양을 모두 재검사하지도 않으므로, 현재 엔진이 최소 요구를 항상 보장한다고 말하면 안 된다.

남은 후보에는 가격·성능·밸런스·리뷰·호환여유 점수를 매긴다. 소음 축은 해당 가중치가 있을 때 전력·쿨러 유형을 대용값으로 사용한다. 소음 실측값이 아니다.

```text
최종 후보 점수 = 각 축의 (가중치 × 점수) 합
                − Pending 감점 − 일부 필수 검사 스펙의 결손 감점
```

가중치는 팀이 정한 정책값이다. 가성비 우선은 가격 비중 50%, 성능 우선은 성능 비중 55%인 식으로 바뀐다. 현재 사용자 만족도 실험으로 최적값을 입증한 값은 아니다. DB에서 CPU·GPU 외 슬롯은 성능 등급이 없어 성능·밸런스 축이 사실상 상수이며, 다른 축과 결손 감점이 순위를 구분한다.

### 4.2 150만원 견적을 손으로 계산해 보기

이하 A·B·C·D는 가상 상품이다. 신규 조립·QHD 게임·가성비 우선이며 게임 제목은 지정하지 않았다고 가정한다.

GPU 가격 점수의 기준은 전체 예산의 40%, 즉 **60만원**이다. 이는 순위 계산 기준액이지 GPU 가격의 강제 상한이 아니다. 실제 예산 제약은 전체 부품 합계에 적용한다.

| GPU | 가격 | 등급 / VRAM | 전력 | 길이 |
|---|---:|---|---:|---:|
| A | 42만원 | 7 / 12GB | 210W | 330mm |
| B | 48만원 | 8 / 12GB | 237W | 250mm |

두 후보 모두 Pass이고, 리뷰 관측은 없으며 다른 결손 감점도 없다고 가정한다. 가성비 가중치는 가격 0.50, 성능 0.15, 밸런스 0.10, 리뷰 0.20, 호환여유 0.05다.

| 점수 축 | A | B |
|---|---:|---:|
| 가격: `1 − 가격/60만원` | 0.30 | 0.20 |
| 성능: `등급/10` | 0.70 | 0.80 |
| 밸런스: `1 − 목표 등급 7.5와의 차이/4` | 0.875 | 0.875 |
| 리뷰: 관측 없음 | 0.50 | 0.50 |
| 호환여유: `1 − 전력/300W` | 0.30 | 0.21 |
| 가중합, 소수 셋째 자리 반올림 | **0.458** | **0.418** |

예를 들어 A는 `0.50×0.30 + 0.15×0.70 + 0.10×0.875 + 0.20×0.50 + 0.05×0.30 = 0.4575`다. B의 등급이 높아도 이번 요청에서는 A의 가격·전력 점수가 더 유리하다.

이제 케이스를 함께 고른다. C는 6만원·GPU 길이 한도 300mm·점수 0.600, D는 12만원·350mm·점수 0.400이라고 가정한다. 케이스 점수는 조합 원리를 보여 주기 위한 가정값이다. 나머지 6종은 95만원으로 고정하고, GPU 길이 외 호환 조건은 모두 충족한다고 가정한다.

| 조합 | 전체 금액 | GPU + 케이스 점수 합 | 판단 |
|---|---:|---:|---|
| A + C | 143만원 | 1.058 | GPU 330mm가 한도 300mm를 넘으므로 제외 |
| A + D | 149만원 | 0.858 | 선택 가능 |
| B + C | 149만원 | **1.018** | **선택 가능한 조합 중 최고점** |
| B + D | 155만원 | 0.818 | 예산 초과 |

나머지 부품의 점수는 모든 조합에 똑같이 더해지므로 비교에서 생략했다. 최종 선택은 **GPU 단품 2위 B + 케이스 C**다. 엔진은 개별 1위를 무조건 모으는 것이 아니라, 가능한 조합의 점수 합을 비교한다.

### 4.3 탐색이 보장하는 범위

처음에는 CPU·GPU 각 5개, 나머지 각 3개의 상위 후보만 조합한다. 후보가 모두 차면 조합 수는 `5² × 3⁶ = 18,225`개다. 모든 슬롯에 100개씩 두는 `100⁸`개보다 작다.

**분기한정 탐색**은 부품을 하나씩 선택하다가 예산 초과·확정 비호환이 드러나거나, 남은 슬롯 최고 점수를 모두 더해도 현재 최선보다 낮으면 그 가지를 중단한다. 한 가지를 다 본 뒤에는 선택을 되돌려 다음 조합을 검사한다.

1. 상위 후보 안에서 예산·확인된 호환 조건을 만족하는 최대 점수 조합을 찾는다.
2. 못 찾으면 필터 이후의 전체 후보 풀로 넓힌다. 확장 탐색에는 최대 150,000 노드 상한이 있다.
3. 그래도 못 찾으면 예산을 넘더라도 호환되는 저가 구성, 또는 비호환이 적은 대체 구성을 반환하는 경로가 있다. 필요한 확장 풀이 없으면 일부 단계를 건너뛴다.

예산 초과는 `budget=fail`, 비호환·슬롯 누락은 `set=fail`로 구분한다. **결과가 나왔다는 것 자체가 조건 충족을 뜻하지 않는다.**

처음의 상위 후보에서 답을 찾으면 전체 풀은 보지 않는다. 따라서 최적이라는 말은 우선 **탐색한 제한 후보 안의 점수 합**에 관한 말이다. 전체 카탈로그의 최적해나 실측 성능 최고를 보장하지 않으며, 탐색 상한 때문에 해를 놓칠 수도 있다.

## 5. 검증 신뢰도와 재탐색은 무엇인가

### 5.1 모르는 것과 비호환을 구분한다

세트 호환 검사는 소켓·RAM 규격·GPU 길이·쿨러 높이·전원 등을 비교한다. 값이 없다는 이유만으로 비호환이라고 단정하지 않는다. 일부 미확인 상태는 내부적으로 `ok (근사)`라고 표시하지만 뜻은 **“확인하지 못함”**이지 안전 확인이 아니다.

실경로의 신뢰도는 다음 정책 계산이다.

```text
신뢰도 = max(0, 100 − 쟁점 감점 합계)
내부 통과 = 신뢰도 80 이상

확정 비호환: 20 감점 / 확인 필요: 6 감점
예산 초과: 20 감점 / 예산 110% 초과 사용: 추가 15 감점
```

| 다른 쟁점은 없다고 가정 | 신뢰도 | 해석 |
|---|---:|---|
| 확인 필요 3건 | 82 | 내부 통과지만 미확인은 남음 |
| 확인 필요 4건 | 76 | 제외할 후보가 있으면 재탐색 |
| 예산 105% 사용 | 80 | 내부 통과지만 예산 위반. 확정 API는 별도로 거절 |
| 예산 115% 사용 | 65 | 기준 미달. 예산만 문제라면 후보 제외 방식의 재탐색 대상은 아님 |

**80은 성공 확률 80%가 아니다.** 감점과 문턱은 정책값이며 통계적 확률로 보정되지 않았다. 모든 누락 스펙이 쟁점에 집계되는 것도 아니므로 100도 완전 검증을 뜻하지 않는다.

검증은 [4]의 호환 결과를 다시 집계하는 구조다. 별도 모델이나 독립적인 실험으로 교차 검증했다고 설명해서는 안 된다.

### 5.2 부족하면 무엇을 다시 실행하는가

실경로는 주로 **스펙 미확인 문제를 줄일 수 있는 다른 후보**를 찾아본다. 확인 필요 쟁점과 누락 스펙을 보고 현재 선택 후보 하나를 제외한 뒤 [4] 조합 탐색 → [3-C] 검증만 다시 실행한다. 요구사양·필터·순위를 전부 다시 계산하거나 상품을 새로 수집하지 않는다.

- 최대 3라운드다. **첫 구성 1회 + 재구성 최대 2회**다.
- 통과하거나 제외할 후보가 없으면 더 일찍 끝난다.
- 실제 제외 전략은 예산·확정 위반을 대상으로 삼지 않고, CPU·GPU와 유지 부품도 직접 제외하지 않는다.
- 시도한 결과 중 신뢰도가 가장 높은 것을 채택한다. 동점이면 먼저 나온 결과를 유지한다.

가령 신뢰도가 76 → 70 → 76이면 첫 결과, 76 → 88이면 두 번째 결과를 채택한다. **신뢰도가 첫 결과보다 나빠지지 않는다는 보장이지, 가격·성능이 항상 좋아진다는 보장은 아니다.** CPU·GPU도 다른 부품과의 조합이 바뀌면 간접적으로 달라질 수 있다.

사용자가 결과 화면에서 직접 부품을 교체하거나 수량을 바꾼 경우에는 호환·예산을 재검증하되, 자동 재탐색으로 사용자의 선택을 다시 바꾸지는 않는다.

## 6. 데모와 실경로를 혼동하지 말자

같은 요구사양·필터·순위·조합 탐색 함수와 재탐색 루프를 공유한다. 다만 입력, 검증 함수, 결과 저장 방식이 다르다.

| 구분 | 데모: `main.py` → `pipeline.py` | 실경로: API → `recommendation_service.py` |
|---|---|---|
| 조건 | 시나리오 JSON의 준비된 값 | 사용자 대화·선택으로 모아 DB에 저장한 값 |
| PC 후보 | DB 우선, 실패·빈 카탈로그면 합성 데이터. 합성 모드 직접 지정 가능 | DB 카탈로그. 필요한 슬롯의 후보가 없으면 오류 |
| 검증 | `verify_set`: 시나리오의 신뢰도·쟁점 주입 | `verify_build`: 실제 호환·예산 결과의 감점 집계 |
| 재탐색 제외 | 시나리오의 문제 슬롯 기준 | 쟁점·누락 스펙에 따른 규칙 |
| 출력 | 콘솔·메모리 결과 | DB 저장 후 API 조회 |

예를 들어 `computer_research`의 신뢰도 **72 → 86은 시나리오에 적힌 값**이다. [4]에서 조합 계산은 실행하지만, 뒤의 신뢰도는 그 계산으로부터 나온 값이 아니다. 이것은 재탐색 흐름의 연결을 시연하지, 실제 품질 개선 효과를 측정한 실험이 아니다.

환경 변수도 분리해서 이해한다.

- `MOCK_MODE=1`: 이 추천 흐름의 LLM·사용 가이드 임베딩을 모의 처리한다. API의 DB 조회나 규칙 계산을 끄는 스위치가 아니다.
- `CATALOG_SOURCE=mock`: 데모·재현 도구가 합성 카탈로그를 쓰게 한다. API의 DB 카탈로그를 합성 데이터로 바꾸지 않는다.
- 데모에서 `MOCK_MODE=0`으로 바꾸어도 시나리오 신뢰도가 실제 검증으로 바뀌지는 않는다.

즉 **실경로도 모의 LLM으로 실행할 수 있고, 데모도 실제 DB 상품을 사용할 수 있다.** 실경로라는 이름은 API 실행 경로를 뜻하며 운영 배포 실적을 뜻하지 않는다.

## 7. LLM·리뷰 설명·RAG는 어디에 쓰이는가

### 7.1 LLM은 계산 뒤의 문장화를 돕는다

기본 추천 경로에서 LLM은 [3-C]의 일부 쟁점 문장과 [5]의 요약·부품별 이유를 작성한다. 상품 선택·가격 합산·판정·감점은 코드가 정한다. 호출 실패나 일부 금지 표현이 있으면 재시도 또는 규칙 템플릿을 사용한다. LLM 문장 실패 때문에 신뢰도가 바뀌지는 않는다.

다만 금지어·슬롯 혼입 검사가 모든 잘못된 수치나 주장을 잡는 것은 아니다. 필터가 Fail 후보를 복구한 경우 정형 설명의 “조건 충족” 같은 문구도 그대로 믿으면 안 된다. **문장보다 판정값·쟁점·예산을 먼저 확인한다.**

기여도는 가격·성능·호환성에 해당하는 일부 가중 점수를 묶어 100%로 정규화한다. 리뷰·소음·감점 전체를 설명하는 비율이 아니다. 신뢰도 숫자는 사용자 설명 문장에 넣지 않지만, 내부 값과 API의 `verification.confidence` 필드에는 남아 있다.

리뷰 관측의 “개별 리뷰 진위를 뜻하지 않는다”는 주의 문구는 문턱 초과 신호가 있을 때 붙는다. “관측 없음”에는 원본 데이터 부재뿐 아니라 전달 누락도 영향을 준다. 현재 [5]의 리뷰 플래그 조회는 상위 후보 `ranked`만 보므로, 확장 탐색에서 전체 `pool`의 후보가 선택되면 플래그가 있어도 설명에서 누락될 수 있다.

### 7.2 RAG가 호환성을 독립적으로 증명하는 것은 아니다

RAG는 관련 문서를 검색해 답변에 활용하는 방식이다. 이 추천 흐름에서는 다음을 구분한다.

| 경로 | 현재 역할 | 하지 않는 것 |
|---|---|---|
| 데모 근거 검색 | 준비된 시나리오 문장에서 분야·축에 맞는 근거 선택 | 실제 웹 검색·호환 입증 |
| 실경로 검증 근거 | 비교한 스펙값에 카탈로그 출처 URL·확인일 연결 | 매뉴얼을 찾아 새로운 호환 사실 판정 |
| 실경로 구매 전 안내 검색 | 선택 후 부품별 사용 안내 문서를 검색해 보충 | 추천 점수·호환 판정 변경 |

사용 안내 검색은 부품 종류로 문서를 좁히고, 텍스트를 숫자 벡터로 바꾸어 유사도를 비교한다. 모의 모드의 벡터는 실제 의미 검색 품질을 입증하지 않는다. **매뉴얼 검색을 통한 독립 호환 검증은 현재 추천 API에 연결되어 있지 않다.**

## 8. 업그레이드와 주변기기는 어디까지 되는가

### 8.1 업그레이드: 실제 API에 연결됨

`upgrade_parts`로 고른 슬롯만 구매 총액에 넣고, 나머지 유지 부품은 `owned` 정보로 호환 검사에 사용한다. GPU만 교체하면 GPU에 구매 예산을 배분하고 기존 파워·케이스와 맞는지 확인하는 식이다.

현재 CPU·GPU의 등급을 추론할 수 있으면 그보다 낮은 등급을 피하도록 하한을 올리고, 같은 상품도 다시 고르지 않도록 제외한다. 다만 등급 자체가 거친 대용값이고 하드 필터 예외도 있으므로 **실측 성능 향상을 보장하지 않는다.**

필요한 현재 사양이 입력되어 있지 않으면 다음 답변이 추가로 필요하다.

| 교체 대상으로 고른 부품 | 추가로 묻는 값 |
|---|---|
| CPU·메인보드·쿨러 중 하나 | 플랫폼/소켓: `owned_platform` |
| RAM·메인보드 중 하나 | RAM 종류: `owned_ram_type` |
| GPU | 파워 용량: `owned_psu_w` |

여러 행에 해당하면 모두 필요하다. 질문에 `"unknown"`으로 답하면 추천은 진행하되 미확인으로 남긴다. **답을 생략하는 것은 “모르겠다”는 답변과 달라 추천을 막을 수 있다.** 현재 사양에 관련 값이 있으면 질문을 생략하지만, 글이 있다는 것과 정확한 스펙 추론이 성공했다는 것은 별개다.

### 8.2 주변기기: 계산 구현과 서비스 연결은 다름

모니터·키보드·마우스·스피커의 조건 생성, 필터, 순위, 예산별 선택, 품목별 검증은 구현되어 있다. 모니터는 PC 목표 해상도·주사율 조건과 GPU 연결 가능성을 추가로 검사한다.

| 영역 | 현재 상태 |
|---|---|
| 계산 본체 | `peripheral_select.run_peripherals` 구현 |
| 데모 호출 연결 | 조건에 `peripherals`가 있으면 PC 구성 뒤 실행 |
| 기본 데모 시나리오 | 그 조건이 없어 그대로 실행하면 주변기기 계산은 건너뜀 |
| 실제 API | 조건 수집·추천 실행 연결·결과 저장·응답 노출 미연결 |

주변기기는 PC 8슬롯에 끼워 넣지 않고 **별도 결과와 예산**으로 다룬다. 현재 가격은 판매처·관측일이 확인되지 않은 참고가여서 PC 총액에 합산하지 않는다. API 적용에는 조건 입력, 저장 위치, 응답·화면 계약을 정해야 한다.

또한 GPU 출력 단자 정보가 현재 DB 로더에 없어 모니터 연결 검사가 “확인 필요”로 남는다. 원하는 모니터가 없을 때 조건을 조용히 완화하지 않는다. 일부 종류만 골라도 전체 상태가 `ready`일 수 있으므로 종류별 누락 결과를 확인해야 한다.

## 9. API에서는 결과가 어떻게 전달되는가

사용자는 조건을 채운 뒤 `POST /session/{list_id}/recommend`를 호출한다. HTTP 202는 접수 완료이지 추천 완료가 아니다. 백그라운드에서 계산하고, 화면은 `GET /session/{list_id}/result`를 반복 조회한다. 이를 폴링이라고 한다.

저장은 두 묶음으로 나뉜다. **트랜잭션**은 DB 변경을 함께 반영하거나 취소하는 단위다.

1. 부품 구성·가격·검증을 계산해 저장하고 먼저 확정한다. 이때부터 부품표를 조회할 수 있다.
2. 설명 문장과 구매 전 안내를 별도로 만들고 저장한다. 이 단계가 실패해도 먼저 저장한 부품표는 남는다.

따라서 추천 상태가 `done`이어도 설명은 `pending` 또는 `failed`일 수 있다. 또한 [3-C]의 일부 LLM 문장화는 첫 트랜잭션 안에 있으므로 모든 LLM 대기가 없어진 구조는 아니다. API 프로세스 안의 백그라운드 작업이므로 프로세스 종료 후 자동 복구도 보장하지 않는다.

`list_id`는 견적 목록, `revision_id`는 그 목록의 조건 버전, `run_id`는 추천 실행 1회의 식별자다. 주요 저장소는 상품의 `catalog`, 조건의 `planning`, 추천 결과의 `engine` 스키마다.

조회 API는 추천 탐색을 다시 실행하지 않지만, 현재 선택과 카탈로그로 호환 상세를 재계산한다. 내부 탐색 통계·전체 라운드 기록·기여도·근거 목록이 모두 API로 공개되는 것은 아니다. **계산되어 있음, 저장되어 있음, 화면에서 보임을 구분**해야 한다.

## 10. 평가 앞에서 무엇을 설명하고 증명할 것인가

### 10.1 발표의 줄거리

다음 여섯 문장을 연결하면 짧은 발표의 뼈대가 된다.

1. “PC는 부품 하나의 선호도뿐 아니라 조합의 예산과 호환성을 함께 봐야 합니다.”
2. “명시된 사용자 조건을 정책 기준으로 변환하고, 후보를 필터링·점수화합니다.”
3. “제한된 후보 안에서 가능한 조합의 점수 합을 비교합니다. 예제에서는 단품 1위 A 대신 B+C를 고릅니다.”
4. “미확인 정보와 확정 위반을 구분해 집계하고, 가능한 경우 후보를 바꿔 최대 세 라운드까지 확인합니다.”
5. “LLM은 계산 결과의 설명을 돕습니다. 문서 출처 연결과 사용 안내 검색은 있지만 매뉴얼 기반 독립 호환 검증은 미연결입니다.”
6. “현재 성능 지표는 라인업 대용값이며, 필터 예외와 탐색 범위 한계가 있습니다. 주변기기도 계산 구현과 API 연결 상태를 구분해 보고합니다.”

### 10.2 과장하기 쉬운 주장과 정확한 답

| 질문 | 정확한 답변 |
|---|---|
| 가장 좋은 PC를 보장하나? | 제한된 후보와 정책 점수 기준이다. 전체 상품·실측 성능 최고는 보장하지 않는다. |
| 신뢰도 80이면 80% 믿어도 되나? | 아니다. 규칙 감점으로 만든 내부 문턱이다. 예산 위반이 있어도 80이 될 수 있다. |
| 최소 사양은 반드시 충족하나? | 현재는 아니다. 모든 후보가 Fail인 슬롯에서 후보를 복구하는 예외가 있다. |
| 성능 등급은 객관적 벤치마크인가? | 아니다. 수집된 라인업을 내부 표로 변환하며 모델별 실측 평가 체계는 아직 없다. |
| 재탐색하면 무조건 좋아지나? | 채택 신뢰도는 낮아지지 않지만 가격·성능까지 좋아진다는 보장은 없다. |
| 주변기기도 서비스에서 추천하나? | 계산과 조건부 데모 연결은 구현했지만 실제 API 연결은 아직이다. |
| 테스트 통과가 추천 품질을 증명하나? | 준비한 사례의 계산·계약 동작을 확인한다. 실제 조립 성공·만족도·실시간 가격은 별도 검증이다. |

### 10.3 검증할 때 남길 증거

“잘 나온 견적 하나” 대신 게임·사무·창작, 신규·업그레이드, 충분한·부족한 예산, 알려진·누락된 스펙의 고정 요청 묶음을 사용한다.

- 조건 하나를 바꾸고 요구사양·가중치·구성이 어떻게 바뀌는지 비교한다.
- 작은 후보 풀은 모든 조합을 계산해 탐색 결과와 비교한다.
- 재탐색 전후의 쟁점 수뿐 아니라 가격·성능 등급 변화도 기록한다.
- 코드·정책·카탈로그·리뷰 데이터 버전, 입력, 모의 모드 여부, 성공·실패 건수를 함께 남긴다. 동점 후보는 입력 순서의 영향도 받는다.
- 속도·정확도·개선율을 측정하지 않았다면 “미측정”이라고 답한다. 모의 LLM 결과를 실호출 문장 품질의 증거로 쓰지 않는다.

DB 테스트는 일회용 `truefit_test_<UUID>` DB를 사용한다. 개발 DB `truefit`에 테스트하지 않고, 완료 확인에는 `TRUEFIT_REQUIRE_TEST_DB=1`을 설정한다. 마커가 누락된 DB 테스트도 있으므로 “DB 없는 테스트”는 확인된 파일·테스트 함수를 명시한다. 상세 명령은 원문 §14를 따른다.

### 10.4 읽기를 마치기 전 확인할 다섯 질문

아래에 자기 말로 답할 수 있으면 이 문서의 핵심을 이해한 것이다.

1. GPU A가 단품 점수 1위인데 왜 B+C가 선택되는가? → **조합 전체의 예산·길이 조건과 점수 합 때문이다.**
2. 데이터가 없으면 왜 바로 Fail이 아닌가? → **정보 부족과 확정 미달을 구별하기 위해서다. 다만 미확인은 통과 보장이 아니다.**
3. 확인 필요 4건이면 무엇을 다시 실행하는가? → **신뢰도 76이며, 제외 가능한 후보가 있으면 [4]→[3-C]를 다시 실행한다.**
4. 데모의 72→86은 어떤 증거인가? → **시나리오로 재탐색 흐름을 시연한 것이지 실제 품질 개선 측정이 아니다.**
5. 성능 등급·주변기기·RAG의 공통 주의점은? → **정책·함수의 존재와 실측 검증·API 연결 완료를 혼동하지 않는다.**
