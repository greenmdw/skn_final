# Temporary Review Observation Pilot Contract

Purpose: evaluate extraction on a small sample of actual-source Korean reviews before catalog mapping and database registration are complete. This is an offline experiment, not production ingestion or a benchmark of full-corpus accuracy.

## 1. Precedence and explicit exceptions

Read `docs/리뷰속성_관측_에이전트_지시서.md` as the base extraction contract. This pilot document overrides ONLY these prerequisites:

| Base prerequisite | Pilot replacement |
|---|---|
| Registered document UUID | Coordinator-generated temporary UUID with a source-record mapping |
| Confirmed catalog product UUID | Temporary UUID identifying the source product label; not a catalog identity |
| Registered, approved rules | Coordinator-defined, frozen experimental rules derived from the base aspect table |
| Production mode | `mode: "test"` |
| Registered product as evaluation target | Source-labeled product as the provisional text-analysis target |
| Database ingestion | Prohibited; omit all ingestion commands and import-ready artifacts |

Empty review/rule tables and unconfirmed exact SKU mappings MUST NOT block this pilot. Do not query the database to satisfy those prerequisites. Never change `is_synthetic` to true merely because this is a test: actual-source records remain false. Actual-source metadata is not independent verification of authenticity.

All other base rules remain effective, including exact Korean evidence, exclusion of other-component statements, no inferred contexts/noise sources, no invented scores, and reporting unresolved observations. Test UUIDs and experimental rules are not evidence of production approval.

## 2. Sample and provenance

- Analyze no more than 24 actual-source PC-component reviews, ideally up to three per supported component type.
- Prefer the existing `selected_source_snapshot.json` under `outputs/review_aspect_luna_pilot/20261001T084703Z/`. Validate its bodies against the processed source before reuse.
- Otherwise select from `data/reviews/computer_review_processed.jsonl`. The raw JSON is provenance, not an additional review corpus.
- Exclude synthetic records, unsupported peripheral types, unreadable bodies, and records without an identifiable source record or component type. Report every exclusion.
- Do not invent reviews to fill categories. Do not process the whole corpus for extraction.
- Missing exact SKU mapping is a recorded limitation, not a text-extraction blocker. If the source label and body conflict, exclude the conflicting target evidence; do not guess a catalog match.
- Inspect the small sample for clear evaluations, expectations, unknown contexts/noise sources, other-component evaluations, and conflicting contexts. Report uncovered categories honestly.

## 3. Temporary identities and execution artifacts

Create a NEW directory `outputs/review_aspect_luna_pilot/<unique_run_id>/`. Do not overwrite the blocked run.

Create a random UUID namespace for this run and derive UUIDv5 identifiers from:
- Document: authoritative source path + stable source review ID (or source record location).
- Product: source product key. Reviews with the same source product key share a temporary product UUID.
- Rule: pilot analysis version + part_type + aspect_code + context_code.

Save the namespace and all mappings in `manifest.json`. Each mapping records `identity_scope: "pilot_only"`, source location, source label, and `catalog_mapping_status: "unconfirmed"` unless separately evidenced. Never present temporary IDs as registered records.

Set the analysis version to `pilot-luna-v1-<run_id>`. Freeze source bodies, the complete base contract, this pilot contract, and experimental rules with checksums. Keep metadata in the manifest, not as extra fields in the base input/output JSON contract.

## 4. Prepare experimental rules before dispatch

The coordinator is explicitly authorized to create local experimental rules for this pilot. No additional approval or database registration is required. Workers MUST NOT invent or edit rules.

Use the base contract's allowed aspect codes for the sampled component types. For each supplied rule, include:
- Temporary id, pilot analysis_version, part_type, aspect_code, context_code.
- definition.label, positive, negative, context, and match_policy.
- Explicit inclusion/exclusion criteria and distinctions needed by the sample.

Define rules as reusable criteria, not as expected labels for individual reviews. Do not attach source answers to worker inputs. Freeze all rules before any worker starts.

Context requirements:
- For noise/thermal/performance aspects, distinguish explicitly stated low load, gaming load, other named workloads, and unspecified workload when applicable.
- Unknown workload can have an explicit unknown-context rule. Unknown noise source MUST NOT become a fan/coil/pump rule.
- Keep gaming and non-gaming CPU performance contexts distinct.
- Distinguish initial detection/operation, explicitly stated extended use, and duration unspecified for stability aspects. Do not invent a long-term duration threshold.
- Preserve firmware, XMP/EXPO/manual settings, resolution, frame generation, cooling setup, transfer counterpart, and installation constraints when stated. Define separate contexts where needed to prevent opposing experiences being merged.
- If one context matches multiple rules, resolve the definitions before dispatch. If a distinction cannot be defined reliably, allow `unmapped_rule` or `ambiguous_rule`; do not force classification.

Document experimental assumptions in `rules_notes.md`. Missing production rules are no longer a blocker. Genuinely unresolved experimental definitions remain a reportable limitation.

## 5. Worker delegation

Use extraction sub-agents with explicit model `gpt-6-luna` and reasoning effort `medium` where supported. Record the actual tool configuration. If model selection is unavailable, stop and report that limitation; do not claim Luna execution or substitute silently.

Assign at most six reviews per batch, respecting context limits and available concurrency. Each review belongs to exactly one batch. Queue excess batches. Do not split or truncate reviews.

Each worker receives the full base contract, this override document, its frozen input JSON, and one exclusive output path. Explicitly tell the worker that temporary IDs and experimental rules are valid for this offline pilot and database registration is unnecessary.

Workers analyze only their batch, write only their assigned output, do not access the database or network, and do not delegate further. Return the base contract JSON with no added schema fields. Preserve Korean evidence verbatim; other text may be English.

## 6. Validation and review

Validate all outputs mechanically: field contracts, coverage/order, IDs, rule membership, versions, component types, uniqueness, valid directions/diagnostics, and exact nonempty evidence substrings.

Preserve first-pass outputs. Retry malformed outputs at most twice with concrete errors, saving each attempt separately. Never relax rules or alter source text to obtain a pass. Semantic corrections MUST NOT replace first-pass results silently.

Before viewing worker outputs, the coordinator records an independent provisional assessment of each sampled review against the frozen rules in `reference_review.json`. This is a reviewer judgment, not authoritative ground truth. Do not send it to workers.

After extraction, review EVERY sampled review, including empty and ok results. Check wrong target/aspect/context/direction, unsupported inference, missed observations, evidence sufficiency, expectations, and mixed handling. Classify each as accepted, correction_needed, or unresolved; distinguish worker errors from rule/input ambiguity. Give concise evidence-based reasons, not internal reasoning traces. Record proposed corrections separately.

If rule changes are needed after dispatch, preserve the original evaluation. Any revised-rule rerun uses a new analysis version and separate artifacts. Do not combine results from different rule versions into one purported evaluation.

## 7. Required deliverables

- `manifest.json`: provenance, temporary ID mappings, exclusions, requested/actual worker settings, batch assignments, checksums, and `database_import_allowed: false`.
- `rules.json` and `rules_notes.md`: frozen experimental rules and assumptions.
- `inputs/<batch_id>.json`: base-contract input, mode=test.
- `outputs/<batch_id>.json`: original worker output.
- `retries/<batch_id>/<attempt>.json`: retry outputs if any.
- `combined_input.json` and `combined_output.json`: aligned results from one frozen rule version; record which attempts were used.
- `reference_review.json`: independent provisional assessments.
- `validation_report.json`: mechanical checks, missing results, retries, and errors.
- `review_report.md`: per-review assessments, error examples, counts, limitations, and next steps.
- `PILOT_ONLY_DO_NOT_IMPORT.txt`: explicitly states that identities/rules are experimental and these files must not be passed to the DB importer.

Account for every selected record. Distinguish excluded inputs, unresolved results, worker failures, and completed observations. A failed batch must remain an explicit missing-output entry in the validation report; never fabricate successful empty results. Do not label a partial combined output as complete.

End with a Korean summary of worker model, sample size, completed/accepted/correction-needed/unresolved counts, first-pass versus retry outcomes, and whether a larger pilot is warranted. Do not generalize accuracy from this small diagnostic sample.

## 8. Prohibited operations

No DB reads or writes, catalog registration, source-file modifications, operational-rule changes, embeddings, aggregate/score calculations, importer calls (including dry-run), or Git commits. Only the new pilot output directory may be written during execution. Production ingestion requires a separate workflow with verified catalog mappings and registered rules/documents.
