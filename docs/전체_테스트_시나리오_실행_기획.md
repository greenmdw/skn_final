# 전체 테스트 시나리오 실행 기획

- 상태: **계획 초안 — 실행 전** (1·2번은 팀원 RAG/리뷰근거 작업 중이라 **계획까지만** 작성, 실행은 보류 — §0 참고)
- 배경: 2026-10-01 LLM_MODEL을 gpt-6-luna로 전환하면서 에이전트별 동작을 수동으로 하나씩 확인했는데, 범위가 넓어지면서 "무엇을 테스트할지"뿐 아니라 "어떻게(수동/자동화, 어떤 환경으로, 몇 번) 실행할지"를 먼저 정리할 필요가 생겼다.
- 이 문서가 다루는 것: §0 제외 범위, §1 실행 환경 매트릭스, §2 실행 순서, §2.5 반복 횟수 정책, §3~§12 카테고리별 전체 시나리오(1번·2번 포함, 전부 실행 방법·통과 기준·반복 횟수까지), §13 결과 기록 방식, §14 미결정 사항.
- 지난 버전과 차이: 1번(RAG)·2번(ML 연동)이 빠져 있던 걸 채웠고, 이전엔 "이전 합의 내용, 변경 없음"으로 참조만 해두었던 3~6번도 전부 이 문서 안에 표로 직접 옮겼다 — 이 문서 하나만 보면 전체를 알 수 있게.

## 1. 실행 환경 매트릭스

카테고리마다 "진짜 LLM을 부를지", "어떤 DB를 쓸지", "수동/자동화 중 뭘로 할지", "몇 번 반복할지"가 다르다. 섞으면 결과가 오염된다(예: MOCK_MODE 테스트에 실제 LLM 결과를 기대하면 전부 실패).

| 구분 | 진행 가능 여부 | MOCK_MODE | DB | 실행 방식 | 반복 |
|---|---|---|---|---|---|
| 1번(RAG 품질 점검) | ⏸ 보류 | 0(실호출)/1 혼합 | 불필요 | pytest 확장(`test_care_guide_slot_filter.py`) | §2.5 |
| 2번(ML 연동 확인) | 🟡 부분(§4 참고) | **0(실호출 필수)** | 테스트 DB 일부 | 스크립트 + pytest 혼합 | §2.5 |
| 3번(E2E) | ✅ (리뷰 줄 제외) | **0(실호출)** | dev DB(`truefit`) | 브라우저 수동(Claude Browser) | §2.5 |
| 4번(예외 — 폴백 경로) | ✅ (리뷰부족 제외) | 0 일부 / 1 일부 | 테스트 DB(`TRUEFIT_REQUIRE_TEST_DB=1`) | pytest 자동화 우선 | §2.5 |
| 5번(적대적) | ✅ | **0(실호출 필수)** | 테스트 DB 또는 dev DB(수동) | 수동 + 일부 스크립트 | §2.5 |
| 6번(사양 추출) | ✅ | **0(실호출 필수)** | 불필요(DB 안 거침) | 스크립트(scratchpad) — 이미 쓰던 방식 | §2.5 |
| 7번(성능/부하) | ✅ | 0 | dev DB | 스크립트(동시 요청) + 브라우저 관찰 | §2.5 |
| 8번(보안/권한) | ✅ | 0 또는 1 무관 | dev DB | pytest 자동화(API 직접 호출) | §2.5 |
| 9번(동시성/정합성) | ✅ | 1(LLM 무관한 DB 레이어 문제라 mock으로 충분) | 테스트 DB | pytest 자동화 | §2.5 |
| 10번(회귀) | ✅ | 1 | 테스트 DB | 기존 `pytest -q` 그대로 | §2.5 |

실호출(MOCK_MODE=0) 구간은 전부 **실제 OpenAI 비용이 발생**한다 — 2·3·5·6·7번은 실행 전에 대략적인 호출 횟수를 추산해 알려드리고 진행한다(§14).

## 2. 실행 순서

```
10 (기준선 확보: 지금 pytest 통과 상태 기록)
 └─▶ 4 (예외/폴백 — 다른 모든 테스트의 전제조건, 리뷰부족 제외)
      └─▶ 6 (사양 추출 — 독립적, 회귀 고정)
           └─▶ 5 (적대적 — 4·6에서 확인한 폴백/가드 위에서 공격)
                └─▶ 3 (E2E — 리뷰 줄 제외, 나머지 전부 정상 동작 확인)
                     └─▶ 9 (동시성/정합성)
                          └─▶ 8 (보안/권한 — 아무 때나 끼워도 무방)
                               └─▶ 7 (성능/부하 — 다른 모든 게 정상 동작할 때라야 "느리다"는 판단이 의미 있음)
                                    └─▶ 2 (ML 연동 — 리뷰·임베딩 아닌 부분만, §4 참고)
                                         └─▶ (팀원 작업 완료 후) 1 (RAG) + 2 나머지(임베딩) + 4의 리뷰부족 + 3의 리뷰 줄
```

8번은 의존성이 없어서 실제로는 4번과 동시에 진행해도 무방하다 — 순서는 "느린 것부터 하면 나중 결과가 묻힌다"는 이유로 뒤로 뺀 것뿐. 2번을 뒤에 둔 이유는 리뷰·임베딩과 겹치지 않는 조각만 먼저 떼어내는 판단을 다른 카테고리 결과를 보고 하는 게 안전해서다.

## 2.5 반복 횟수 정책 — "1번씩만 하면 되는지"

**아니다. 카테고리 성격에 따라 다르다** — 결과가 결정론적인지(같은 입력엔 항상 같은 출력) 아닌지가 기준이다.

| 카테고리 | 반복 필요? | 권장 횟수 | 이유 |
|---|---|---|---|
| 1번 RAG | 보류 중 미정 | — | 팀원 작업 완료 후 재설계 시 같이 정함 |
| 2번 ML(도구 호출 성공 여부) | **예** | 최소 3회 | LLM 도구 호출은 비결정적 — 한 번 성공했다고 항상 성공한다는 보장 없음(이번 세션에 result_agent 테스트도 1회만 함 — 재확인 필요) |
| 3번 E2E | **예** | 최소 2~3회(조건 문구를 바꿔서) | 플로우 버그는 1회로 드러나지만, 설명 생성 품질·도구 호출 안정성은 1회로 판단 불가 |
| 4번 예외(검증·스키마·폴백) | 아니오 | 1회 | 인위적으로 에러를 주입하는 결정론적 코드 경로 — 몇 번을 돌려도 같은 결과 |
| 4번 중 "API/LLM오류" | 아니오 | 1회(모킹으로 강제 발생) | 네트워크 예외를 코드로 강제 발생시키는 것이라 LLM 비결정성과 무관 |
| 5번 적대적 | **예** | **최소 3회, 입력 문구도 바꿔가며** | 가드가 가끔 뚫릴 수 있다 — 1회 방어 성공이 "안전하다"를 보장하지 않는다. 이번 세션의 환각 테스트도 이미지 1장당 1회씩만 해서 재현성 확인이 약했다 |
| 6번 사양 추출 | **예** | 동일 이미지 **최소 2회** | temperature=0이어도 100% 결정론은 아니고, gpt-6-luna는 애초에 temperature 지정 자체가 안 먹는다(코드가 자동으로 빼고 재시도하는 모델) — 재현성 자체가 측정 대상 |
| 7번 성능/부하 | **예** | 5~10회 | 1회 측정은 노이즈(캐시 워밍업, OS 스케줄링 등)에 취약 — 평균·최대·분산을 봐야 함 |
| 8번 보안/권한 | 아니오 | 1회 | 토큰 검증·권한 체크는 결정론적 로직 |
| 9번 동시성 | **예** | 최소 3~5회 | 레이스 컨디션은 타이밍에 따라 1회에선 안 터질 수 있다 — 안 터졌다고 버그가 없다는 뜻이 아니다 |
| 10번 회귀 | 아니오(기본) | 1회, flaky 의심 시 재실행 | pytest는 결정론적 설계가 원칙 |

## 13. 결과 기록 방식

- 각 카테고리 실행 후 이 문서에 **§15 실행 결과**를 추가해 나간다(`사용자_선호비선호_기록_설계.md`의 "10. 구현 결과" 절과 같은 패턴).
- 실패/이상 발견 시 재현 절차를 scratchpad가 아니라 **이 문서에 직접 인용**해 남긴다(scratchpad는 세션 종료 시 사라짐).
- LLM 실호출 결과(사양 추출 비교 등)는 JSON으로 저장 후 요약만 문서에 남긴다.
- 반복 실행한 시나리오는 **매 회차 결과를 다 기록**한다(예: 3/3 성공, 2/3 성공 등) — "됐다/안 됐다"만 남기면 §2.5의 반복 정책이 무의미해진다.

## 14. 미결정 사항

- 8번에서 확정된 발견 사항(`/lists` 페이지네이션 미구현, pc_check rate limit 없음)을 이 세션에서 바로 고칠지 별도 건으로 분리할지
