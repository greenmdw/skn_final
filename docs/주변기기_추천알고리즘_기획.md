# 주변기기 추천 알고리즘 기획

작성일: 2026-10-02 · 상태: 기획 초안(구현 전) · 대상 기능: 기획서 5.4절 PER-03~PER-11

모니터·키보드·마우스·스피커를 **사용자가 말로 적은 용도와 원하는 느낌**에 맞춰 추천하는 방법을 정한다. 근거 자료는 [주변기기_시장조사.md](주변기기_시장조사.md), 리뷰 계산의 바탕은 [추천엔진_리뷰적합도_계산알고리즘.md](추천엔진_리뷰적합도_계산알고리즘.md)이다.

이 문서의 숫자(가중치, 가격대 경계, 중요도)는 **모두 잠정값**이다. 9장의 검증을 거쳐 고정한다.

## 0. 확정된 결정 (2026-10-02)

| 결정 | 내용 |
|---|---|
| 사용 사례 | 품목 1개 이상을 고르고, PC 견적 맥락은 있으면 쓰는 선택 입력이다 |
| 품목 | 모니터·키보드·마우스·스피커. 헤드셋은 범위 밖 |
| 구조 | 계산 뼈대는 하나, 정책(질문·조건·가중치)은 품목별 |
| 점수 축 | 스펙을 품목별 기준으로 나누고, 리뷰·가격·브랜드 선호·무상 AS를 더한다 |
| 가중치 | 품목별 기본값에서 시작해 사용자가 강조한 것에 따라 바꾼다 |
| 리뷰 비중 | PC 본체(0.20)보다 높게 둔다 |
| 느낌 조건 | 리뷰를 품질 차원과 성향 차원으로 나눠 읽는다. "묵직한 타건감"처럼 사람마다 원하는 쪽이 다른 느낌을 사용자 목표에 맞춰 점수로 만든다 |
| 리뷰 없는 상품 | 없는 대로 둔다. 리뷰를 만들어 채우지 않는다 |
| 데이터 보강 | 무상 AS 기간만 새로 모은다(스펙에 컬럼 하나). 그 밖의 보강은 지금 하지 않는다 |
| 파이널 프로젝트 | 실제 리뷰(A) + 생성 리뷰(B)를 함께 쓴다 |
| 해커톤 제출 | 실제 리뷰(A)를 빼고 생성 리뷰(B)만 쓴다. 화면에 "생성" 표기는 하지 않는다 |
| 가격 입력 | 품목별 예산 금액을 적으면 그 금액으로, 아니면 가격대를 골라서 진행한다 |

## 1. 전체 흐름과 현재 상태

```text
[사전] 리뷰 번들 적재 → 속성 관측 → 상품·속성별 집계 Q

[요청]
품목 선택 + 자유 문장 (+ 있으면 PC 견적 맥락)
  → 조건 변환(AI): 용도 · 가격 · 스펙 조건 · 체감 태그 · 브랜드 · 강조점
  → 빠진 필수 조건은 칩으로 되묻기
  → 품목마다:
       후보 수집 → 하드 필터 → 축별 값 계산 → 가중합 점수 → 1위와 대안 선정
  → 모니터만: PC 맥락이 있으면 교차 검사
  → 추천 이유(스펙 근거 + 리뷰 근거) 생성
```

기획서 원칙 P1을 따른다. AI는 **말을 조건으로 바꾸는 일**, **리뷰 문장에서 속성을 뽑는 일**, **결과를 문장으로 옮기는 일**만 한다. 후보 점수와 순위는 코드가 계산한다.

### 1.1 이미 구현된 것

| 항목 | 상태 |
|---|---|
| 단독 진입 | `/peripherals` 화면 → `POST /session/{id}/peripherals/recommend`. PC 견적과 묶을 때만 `pc_list_id`를 넘긴다 |
| 리뷰 속성 규칙 | 품목마다 5개가 등록돼 있다(4.1절) |
| 리뷰 적재 | 시드 번들(`data/review_seed`)을 `setup_all.py`가 적재하고 집계를 만든다 |
| 주변기기 리뷰 적합도 R | 후보마다 계산해 근거와 함께 응답에 싣는다. **가중치는 0이라 순위에는 쓰지 않는다.** 응답에 "순위에 반영되지 않았습니다"라는 문구가 붙는다 |
| 속성 중요도 α | 주변기기는 다섯 속성이 모두 같은 비중(0.2)이다. "조용한 키보드"라고 해도 타건 소음의 중요도가 올라가지 않는다 |

### 1.2 본체 추천엔진은 어떻게 했나

이 기획은 본체 쪽 구조에 맞춘다.

- 리뷰 축의 입력을 작성 패턴 신호(0.5 / 0.75 / 0.25)에서 **리뷰 적합도 R**로 바꿨다. 축 가중치 표는 그대로다(리뷰 0.20).
- 가중치는 `priority`(성능·가성비·저소음)에 따라 정해진 행을 고르고, `noise_sensitive`면 소음 축을 올린다. 자유 문장이 가중치를 직접 바꾸지는 않는다.
- α는 등록된 속성마다 1에서 시작하고, 저소음 요청이면 정숙성 속성(팬·코일·펌프)을 3으로 올려 정규화한다.
- 사용 조건은 정책으로 고른다. 사용자가 게임 용도를 **직접 말했을 때만** 게임 부하 조건을 쓰고, 가정한 값이면 "부하 미상"을 쓴다. 조건에 맞는 리뷰가 없으면 다른 조건으로 채우지 않고 0.5로 둔다.
- DB 경로에서는 모든 후보에 리뷰 상세가 있어야 순위를 매긴다. 실행마다 적용한 프로필을 `engine.review_requirement_profile`에 저장한다.
- 추천 이유는 점수에 쓴 관측과 근거 문장으로 만든다.

**본체와 같은 점과 다른 점**

| | 본체 | 주변기기 |
|---|---|---|
| 점수 구조 | 축별 가중합 − 감점 | 같다 |
| 리뷰 계산 | 집계 테이블의 Q, 속성 중요도 α, R | 같은 테이블과 식을 쓴다 |
| 리뷰를 읽는 단위 | 평가 속성(좋다/나쁘다) | 평가 속성을 세분한 **품질 차원 + 성향 차원** |
| 리뷰 비중 | 0.20 고정 | 품목별 0.22~0.35, 사용자가 강조하면 더 올라간다 |
| 가중치를 바꾸는 방법 | `priority` 행 선택 | 사용자가 강조한 축에 배수 |
| 선택 방식 | 부품끼리 맞는 조합을 탐색 | 품목마다 독립으로 고른다 |
| 사용자 몸에 맞추기 | 없다 | 마우스 손 맞춤 |
| 원칙(P1~P10) | | 같다 |

### 1.3 이 기획이 더하는 것

| 항목 | 지금 | 이 기획 |
|---|---|---|
| 받는 조건 | 품목, 예산 합계 하나, 용도, 우선순위, 소음 민감, 해상도 | 품목별 예산·가격대, 품목별 스펙 조건, 체감 태그, 브랜드, 강조점 |
| 문장 해석 | 화면의 정규식 | 조건 에이전트. 실패하면 칩 |
| 점수 축 | 가격(중앙값 기준) + 선호적합 + 데이터충실, 리뷰 0 | 3장 |
| 주변기기 α | 균등 | 용도·사용자 표현에 따라 달라진다(4.6절) |
| 세부 느낌 | 다루지 못한다 | 품질 차원과 성향 차원(4장) |

## 2. 입력 조건

### 2.1 조건 목록

| 필드 | 값 | 필수 | 얻는 방법 |
|---|---|---|---|
| `kinds` | 네 품목 중 1개 이상 | 필수 | 화면에서 선택 |
| `purpose` | 게임 / 사무 / 창작 / 학습·코딩 / 기타 | 필수 | 문장 또는 칩 |
| `environment` | 집 / 사무실·공용 공간 / 야간 사용 | 선택 | 문장 |
| `budget[kind]` | 품목별 상한 금액 | 둘 중 하나 | 문장("마우스 5만 원 이하") |
| `price_tier[kind]` | 가성비 / 중간 / 프리미엄 | 둘 중 하나 | 칩 |
| `spec[kind]` | 품목별 스펙 조건(5장) | 품목별 | 문장 또는 칩 |
| `feel_tags[kind]` | 품목별 체감 태그(4장) | 선택 | 문장 |
| `brand_like[kind]` / `brand_avoid[kind]` | 선호·기피 브랜드 | 선택 | 문장 |
| `emphasis[kind]` | 강조하는 축(3.3절) | 선택 | 문장 |
| `pc_list_id` | 묶을 PC 견적 | 선택 | PC 견적 뒤에 넘어올 때 |

가격은 품목마다 `budget`이 있으면 그것을 쓰고, 없으면 `price_tier`를 칩으로 되묻는다. "상관없음"을 고르면 가격 필터 없이 진행한다.

### 2.2 문장을 조건으로 바꾸는 방법

- AI는 **등록된 필드와 허용값 안에서만** 값을 낸다. 체감 표현과 강조점은 닫힌 목록에서 고른다. 목록에 없는 표현은 `extra`로 남기고 점수에 쓰지 않는다.
- AI는 숫자(가중치, 중요도)를 내지 않는다. 태그만 내고, 태그를 숫자로 바꾸는 표는 코드와 설정이 가진다.
- 금액은 사용자가 말한 그대로 받아 코드가 숫자로 바꾼다.
- AI가 꺼져 있거나 실패하면 칩 질문만으로 같은 조건을 채운다(P5).
- 들어간 조건은 칩으로 보여 주고 사용자가 고칠 수 있다.

예: "타건감이 묵직한 키보드를 10만 원 안에서 찾고 있어요"

```json
{
  "kinds": ["keyboard"],
  "budget": {"keyboard": 100000},
  "feel_tags": {"keyboard": ["heavy_feel"]},
  "emphasis": {"keyboard": ["review"]}
}
```

## 3. 점수 계산

### 3.1 점수식

```text
품목 내 후보 점수 S = Σ (축 가중치 × 축 값) − Pending 감점 − 스펙 결손 감점
```

| 축 | 뜻 | 값 |
|---|---|---|
| 스펙 기준 (품목마다 3~4개) | 조건이 스펙에 맞는 정도 | 0~1, 조건이 없으면 0.5 |
| 리뷰 | 사용자가 중요하게 보는 속성의 리뷰 평가 | 0~1, 근거가 없으면 0.5 |
| 가격 | 사용자 가격 범위 안에서의 위치 | 0~1 |
| 브랜드 선호 | 사용자가 말한 선호 브랜드인가 | 선호 1, 그 외 0.5 |
| 무상 AS | 무상 보증 기간 | 0~1, 정보가 없으면 0.5 |

지금 구현(`peripheral_select.py`)에서 바뀌는 점:

- **스펙 축을 품목별 기준으로 나눈다.** "손에 맞는가"와 "연결 방식이 맞는가"에 다른 비중을 줄 수 있고, 추천 이유에서 어느 기준이 점수를 올렸는지 보여 줄 수 있다.
- **리뷰 가중치를 0에서 올린다.** R은 이미 계산돼 있다. 설정 로더(`peripheral_rules.py`)가 리뷰 가중치 0을 강제하는 검사를 풀어야 한다.
- **브랜드 선호와 무상 AS 축을 추가한다.**
- **데이터충실 축을 없애고 감점으로 옮긴다.** 지금은 스펙이 많이 채워졌다는 이유만으로 0.25~0.30을 준다.
- **가격 값을 중앙값 기준에서 사용자 가격 범위 기준으로 바꾼다.** 중앙값의 2배에서 0점이 되는 식은 양극화된 시장에서 프리미엄 제품을 구조적으로 떨어뜨린다.

사용자가 아무것도 강조하지 않았을 때의 값이다. 각 열의 합은 1이다.

|---|---:|---|---:|---|---:|---|---:|

| 연결 | 0.08 | 기능 | 0.08 | 화질 사양 | 0.10 | 연결·전원 | 0.10 |
| 리뷰 | 0.35 | 리뷰 | 0.35 | 연결 | 0.05 | 리뷰 | 0.25 |
| 가격 | 0.27 | 가격 | 0.27 | 리뷰 | 0.22 | 가격 | 0.32 |
| 브랜드 | 0.04 | 브랜드 | 0.04 | 가격 | 0.23 | 브랜드 | 0.04 |
| 무상 AS | 0.04 | 무상 AS | 0.04 | 브랜드 | 0.04 | 무상 AS | 0.04 |

|---|---|---|
| 키보드 | 스위치·소음 / 배열·크기 / 연결 | 스위치 방식·클릭형·자석축·래피드 트리거 / 배열(크기에서 추정)·무게 / 유선·무선·블루투스 |
| 마우스 | 손 맞춤 / 연결 / 기능 | 크기·무게·폼팩터 / 유선·무선·블루투스 / 버튼 수·클릭 방식·폴링레이트 |
| 모니터 | 화면 / 움직임 / 화질 사양 / 연결 | 크기·해상도·곡률 / 주사율·응답 속도 / 패널·밝기 / USB-C·단자 구성 |
| 스피커 | 형태·크기 / 출력·채널 / 연결·전원 | 형태·크기 / 출력·채널 / 유선·블루투스·전원 방식 |

### 3.3 사용자 요청에 따라 가중치를 바꾼다

기본 가중치는 출발점이다. 사용자가 무엇을 강조했는지에 따라 축 가중치가 달라지고, 리뷰 축 안에서는 어떤 속성을 볼지가 달라진다.

**축 가중치(바깥):** 강조된 축에 1.5를 곱하고 전체를 다시 합 1로 맞춘다.

| 사용자 표현 | 강조되는 축 |
|---|---|
| 체감 태그를 말함("묵직한", "조용한", "손에 잘 맞는") | 리뷰 |
| "가성비", "저렴하게", "예산이 빠듯해" | 가격 |
| "비싸도 좋은 걸로", "오래 쓸 거라" | 리뷰 |
| 브랜드를 지정함 | 브랜드 |
| "AS가 중요해", "고장 나면 곤란해" | 무상 AS |
| 특정 스펙을 강조함("화면 크기가 제일 중요") | 해당 스펙 기준 |

**리뷰 축 안의 차원 중요도:** 4.6절.

**스펙 기준:** 사용자가 조건을 말한 기준만 후보를 가른다. 조건이 없는 기준은 모든 후보가 0.5다.

AI는 강조 태그만 고르고 숫자는 코드가 정한다. 같은 문장이면 같은 가중치가 나온다. 적용한 가중치와 그 이유는 응답에 실어 화면에서 볼 수 있게 한다.

### 3.4 스펙 기준의 값

```text
조건 하나: 충족 1 / 미충족 0 / 정보 없음 0.5
기준 값 = 가중 평균 (사용자가 직접 말한 조건은 가중 2, 용도에서 유도한 조건은 가중 1)
조건이 하나도 없는 기준 = 0.5
```

### 3.5 리뷰 값

본체와 같은 계산이다.

```text
속성 점수   Q = (P + k × 0.5) / (P + N + k)
리뷰 적합도 R = Σ (속성 중요도 α × Q)        Σ α = 1
```

- 리뷰 근거가 없는 속성은 Q = 0.5다.
- **리뷰가 없는 상품은 R = 0.5다.** 평가가 좋은 상품보다는 뒤에, 평가가 나쁜 상품보다는 앞에 선다.
- 리뷰가 적은 상품은 k 보정으로 0.5 근처에 모인다.

### 3.6 가격 값

```text
가격 값 = clamp(1 − (가격 − lo) / (hi − lo), 0, 1)
```

| 입력 | lo | hi | 하드 필터 |
|---|---|---|---|
| 예산 금액 B | 0 | B | 가격 ≤ B |
| 가격대 | 구간 하한 | 구간 상한(프리미엄은 그 품목 카탈로그 최고가) | 구간 안 |
| 상관없음 | — | — | 없음. 가격 값은 기존 중앙값 식을 쓴다 |

예산 안에 후보가 없으면 가장 싼 후보를 "예산 초과"로 표시해 보여 준다.

가격대 경계(잠정, 원):

| 품목 | 가성비 | 중간 | 프리미엄 |
|---|---|---|---|
| 마우스 | 3만 이하 | 3만~10만 | 10만 초과 |
| 키보드 | 7만 이하 | 7만~15만 | 15만 초과 |
| 모니터 | 30만 이하 | 30만~70만 | 70만 초과 |
| 스피커 | 3만 이하 | 3만~10만 | 10만 초과 |

### 3.7 브랜드 선호와 무상 AS

**브랜드**

- 선호 브랜드를 말하면 그 브랜드 후보는 1, 나머지는 0.5다. 아무 말도 없으면 모두 0.5다.
- 기피 브랜드는 **후보에서 뺀다.** "빼 달라"는 명시 요청이므로 조건으로 다룬다.
- 판매량이 많은 브랜드라는 이유로 점수를 주지 않는다.

**무상 AS**

- 스펙에 무상 보증 기간(개월) 컬럼을 하나 추가해 모을 예정이다.
- 값은 같은 품목 후보의 보증 기간 최솟값~최댓값 사이 상대 위치다. 정보가 없으면 0.5다.
- 데이터가 모이기 전에는 모든 후보가 0.5라 순위에 영향이 없다. 코드는 미리 넣어 둘 수 있다.

### 3.8 감점

- **Pending 감점:** 하드 조건을 판정할 스펙이 없으면 0.20을 뺀다(지금과 같다).
- **스펙 결손 감점:** 품목별 검사 키가 비어 있으면 키당 0.05, 최대 0.15를 뺀다. 같은 품목의 다른 후보 중 그 키를 가진 것이 있을 때만 적용한다.

## 4. 리뷰를 읽는 방법 — 품질 차원과 성향 차원

### 4.1 등록된 다섯 속성만으로는 부족하다

리뷰 적재 작업에서 품목마다 5개 속성이 등록돼 있다(조건 `actual_use`, k = 4).

| 품목 | 등록 속성 |
|---|---|
| 키보드 | 타건감, 타건 소음, 연결 안정성, 단축키·설정 편의, 배열·자세 |
| 마우스 | 추적·클릭 정확성, 그립·편안함, 연결 안정성, 버튼·휠·설정 편의, 배터리 |
| 모니터 | 화질, 움직임, 연결·절전 복귀 안정성, 메뉴·스탠드 조절, 고장·불량 없음 |
| 스피커 | 음질, 음량, 잡음 없음, 연결·조작 편의, 고장 없음 |

이 속성들은 "좋았다/아쉬웠다"만 센다. 실제 리뷰로 재 보면 두 가지가 부족하다.

- **상품이 갈리지 않는다.** 리뷰는 대부분 칭찬이다. 키보드 타건감은 긍정 506건 대 부정 44건이고, 40종 중 33종이 Q 0.70 이상이다.
- **사람마다 원하는 쪽을 모른다.** "타건감" 안에는 키압, 반발감, 매끄러움, 소리 성격 같은 세부 느낌이 있다. 묵직한 키압을 좋아하는 사람이 있고 가벼운 키압을 좋아하는 사람이 있다. "가벼워서 좋다"는 리뷰는 두 사람에게 정반대 신호인데, 지금은 둘 다 "타건감 긍정 1건"이다.

그래서 리뷰를 **차원** 단위로 읽는다. 속성 하나(타건감)를 여러 차원(키압, 반발감, 매끄러움 …)으로 나누고, 차원마다 종류를 정한다.

### 4.2 두 종류의 차원

| 종류 | 뜻 | 예 |
|---|---|---|
| **품질 차원** | 누구에게나 한쪽이 낫다 | 통울림·스프링 잡음 없음, 키 흔들림 없음, 빛샘 없음, 잔상 없음, 연결 끊김 없음 |
| **성향 차원** | 양 끝이 있고, 어느 쪽이 좋은지는 사람마다 다르다 | 키압(가벼움 ↔ 묵직), 색감(자연스러움 ↔ 선명·쨍함), 사운드(저음 강조 ↔ 고음·보컬 선명) |

품질 차원은 지금처럼 "좋다/나쁘다"로 센다. 성향 차원은 "어느 쪽으로 묘사됐나"를 세고, **사용자가 원하는 쪽과 맞는지**로 점수를 낸다.

### 4.3 품질 차원 계산

본체와 같다.

```text
Q = (P + k × 0.5) / (P + N + k)        P: 좋다는 관측, N: 나쁘다는 관측
```

### 4.4 성향 차원 계산

차원의 한쪽 끝을 A, 반대쪽 끝을 B라 하자. 키압이라면 A = 묵직, B = 가벼움이다.

```text
a: 그 상품을 A쪽으로 묘사한 관측 수      ("묵직하다", "키압이 높다")
b: 그 상품을 B쪽으로 묘사한 관측 수      ("가볍다", "살짝만 눌러도 입력된다")

사용자가 A를 원하면   M = (a + k × 0.5) / (a + b + k)
사용자가 B를 원하면   M = (b + k × 0.5) / (a + b + k)
```

**같은 리뷰가 사용자에 따라 +도 되고 −도 된다.** "묵직하다"는 관측은 묵직한 걸 찾는 사람에게는 P, 가벼운 걸 찾는 사람에게는 N이다. 식은 품질 차원과 같고, 무엇을 P로 셀지만 사용자 목표에 따라 바뀐다.

| 상품 | 묵직 / 가벼움 관측 | 묵직을 원하는 사용자 | 가벼움을 원하는 사용자 |
|---|---|---:|---:|
| A | 6 / 1 | 0.727 | 0.273 |
| B | 0 / 7 | 0.182 | 0.818 |
| C | 0 / 0 | 0.5 | 0.5 |

- 묘사가 없는 상품은 누구에게나 0.5다. "모름"과 "안 맞음"을 구분한다.
- 관측이 적으면 k 보정으로 0.5 쪽에 머문다.
- 사용자가 그 차원에 대해 아무 말도 하지 않으면 그 차원은 계산에 넣지 않는다.

"적당한 키압"처럼 가운데를 원하는 경우도 다룰 수 있다. 일반식은 다음과 같다.

```text
s = a / (a + b)                    상품이 A쪽으로 묘사된 비율
t = 사용자 목표 (A = 1, 가운데 = 0.5, B = 0)
c = (a + b) / (a + b + k)          근거량에 따른 확신
M = 0.5 + c × ((1 − |s − t|) − 0.5)
```

t가 1이나 0이면 이 식은 위의 두 식과 정확히 같다. 처음에는 양 끝(A·B)만 받고, 가운데 목표는 검증 후 연다.

### 4.6 속성 중요도 α

리뷰 축 안에서 어떤 차원을 얼마나 볼지 정한다.

```text
원점수 b = 품질 차원 기본값(각 1)
         + 용도 보정
         + 사용자 표현 보정
α = b / Σ b
```

| 보정 | 규칙 |
|---|---|
| 용도 | 사무·야간이면 소리 관련 품질 차원 +2, 게임이면 움직임·클릭 정확성 +2 |
| 품질 표현("잔상 없는", "손목이 편한") | 그 품질 차원 +3 |
| 성향 표현("묵직한", "가벼운", "쨍한 색감") | 그 성향 차원을 목표와 함께 4로 넣는다. 그 표현이 속한 상위 속성(예: 타건감)의 품질 차원은 +2 |
| 무선을 명시 | 연결 안정성 +1 |

성향 차원은 사용자가 말했을 때만 들어간다. 지금 코드의 α 생성(`build_review_requirement_profile`)은 저소음 여부만 보므로, 용도와 사용자 표현을 받도록 넓혀야 한다.

### 4.7 계산 예시

2.2절의 요청("타건감이 묵직한 키보드, 10만 원 이하")이다. 상품과 수치는 설명용 가상 데이터다.

**축 가중치:** 느낌 표현이 있으므로 리뷰 축을 강조한다(3.3절).

```text
기본   스위치 0.12  배열 0.10  연결 0.08  리뷰 0.35   가격 0.27  브랜드 0.04  AS 0.04
×1.5                                      리뷰 0.525                            (합 1.175)
정규화 스위치 0.102 배열 0.085 연결 0.068 리뷰 0.447  가격 0.230 브랜드 0.034 AS 0.034
```

**α:** 키압(목표 = 묵직) 4, 매끄러움 3(기본 1 + 관련 2), 나머지 품질 차원은 각 1. 설명을 줄이려고 나머지 품질 차원 넷만 두면 α = 0.364, 0.273, 각 0.091이다.

| 후보 | 가격 | 묵직 / 가벼움 관측 | 매끄러움 좋다 / 나쁘다 |
|---|---:|---|---|
| A | 95,000원 | 6 / 1 | 14 / 1 |
| B | 62,000원 | 0 / 7 | 16 / 1 |

스펙 조건, 브랜드, AS는 조건이 없어 두 후보 모두 0.5다. 나머지 품질 차원도 0.5로 둔다.

```text
A: 키압 M = (6+2)/(7+4) = 0.727   매끄러움 Q = (14+2)/(15+4) = 0.842
   R = 0.364×0.727 + 0.273×0.842 + 0.364×0.5 = 0.677
B: 키압 M = (0+2)/(7+4) = 0.182   매끄러움 Q = (16+2)/(17+4) = 0.857
   R = 0.364×0.182 + 0.273×0.857 + 0.364×0.5 = 0.482

공통(스펙·브랜드·AS 0.5) = 0.162
S_A = 0.162 + 0.447×0.677 + 0.230×0.05 = 0.476
S_B = 0.162 + 0.447×0.482 + 0.230×0.38 = 0.465
```

A가 앞선다. 같은 두 상품을 **가벼운 키압을 원하는 사용자**로 계산하면 키압 M이 A 0.273, B 0.818로 뒤집히고 B가 0.569 대 0.402로 크게 앞선다. 성향 차원 없이 "타건감 좋음"만 쓰면 두 사용자에게 똑같이 3만 원 싼 B를 추천한다.

### 4.8 한계

- **상품 하나당 관측이 적다.** 묵직 표현은 키보드 실제 리뷰의 5%다. 40종으로 나누면 상품당 1~2건인 경우가 많아, 상당수 상품은 0.5로 남는다. 리뷰 없는 상품처럼 "근거 부족"으로 안내한다.
- **생성 리뷰는 표현이 치우쳐 있다.** 모니터 생성 리뷰의 48%가 "선명·쨍함"을 말한다(실제 리뷰 14%). 생성 리뷰만 쓰는 해커톤 구성에서는 색감 차원이 대부분 "선명" 쪽으로 쏠려 변별력이 떨어진다.
- **스피커는 리뷰로 음색을 판단하기 어렵다.** 저음 언급 5%, 고음 1%, 좌우 1%다. 스펙이 주로 판단하고(5.4절), 해커톤 구성에는 스피커 리뷰가 없다.
- 언급률은 낱말 검색 값이라 실제 관측 건수와 다를 수 있다. 차원 규칙으로 추출한 뒤 다시 센다.

### 4.9 만드는 방법

차원마다 규칙을 기존 속성 규칙과 같은 형식으로 등록한다. 성향 차원은 규칙 하나에 "A쪽 묘사"와 "B쪽 묘사"를 정의하고, 관측의 방향 값을 A·B로 저장한다. 집계 테이블의 P·N 칸에 a·b를 담으면 테이블 구조를 바꾸지 않아도 된다. 사용자 목표에 따라 어느 칸을 P로 읽을지는 점수 계산 코드가 정한다.

리뷰를 다시 분석해야 하고, 리뷰 적재 경로는 다른 담당 범위라 협의가 필요하다(10장).

## 5. 품목별 판단 방법

스펙과 리뷰가 어떻게 나눠 맡는지를 품목마다 정리한다. 스펙으로 판단할 수 있으면 스펙이 먼저이고, 스펙에 없는 체감은 리뷰가 맡는다. 둘 다 없으면 "확인하지 못함"으로 안내하고 추측하지 않는다(P3).

### 5.1 모니터 — 화질이 선명한가, 게임에 맞는가

**화질이 선명한가**

| 판단 재료 | 쓰는 방법 |
|---|---|
| 스펙: 패널 | OLED → IPS → VA 순으로 색 표현 선호에 가산(선명함을 원할 때) |
| 스펙: 밝기(nit) | 밝을수록 가산 |
| 리뷰: 색감(성향) | "선명·쨍함"을 원하면 그쪽 묘사가 많은 상품, "자연스러움·정확"을 원하면 그쪽 |
| 리뷰: 블랙·명암, 밝기, 빛샘(품질) | 화질을 중요하게 보면 비중을 올린다 |

색역(DCI-P3 등), HDR 등급, 명암비는 카탈로그에 컬럼이 없다. 일부가 참고사항 글에 섞여 있지만 구조화되지 않아 쓰지 않는다.

같은 "화질 좋은 모니터"라도 게임·영상을 보는 사람은 쨍한 쪽을, 사진·디자인 작업을 하는 사람은 정확한 쪽을 원한다. 용도가 창작이면 "자연스러움·정확"을 기본 목표로 둔다.

**게임에 맞는가**

| 판단 재료 | 쓰는 방법 |
|---|---|
| 스펙: 최대 주사율 | 목표 주사율 이상을 하드 조건으로 |
| 스펙: 응답 속도(GtG) | 빠를수록 가산 |
| PC 맥락 | 있으면 그래픽카드 성능 목표와 해상도·주사율을 교차 검사 |
| 리뷰: 움직임 부드러움, 잔상 없음(품질) | 게임 용도면 비중을 올린다 |

가변 주사율(G-Sync·FreeSync)과 입력 지연은 컬럼이 없어 판단하지 않는다.

**먼저 묻는 것:** 용도, 화면 크기. 해상도·주사율은 PC 맥락이 있으면 이어받고, 없으면 용도에서 유도하거나 묻는다.

### 5.2 키보드 — 키압, 디자인, 소리

**키압**

카탈로그의 스위치 정보로는 일부만 판단할 수 있다.

- "35g", "40g"처럼 키압이 적힌 상품은 몇 개뿐이다.
- 상당수가 "Red / Brown / Blue 등"처럼 **고를 수 있는 스위치를 함께** 적고 있다. 어떤 스위치로 사느냐에 따라 키압이 달라서 상품 단위로 하나를 정할 수 없다.
- 자석축 계열은 키압보다 입력 지점을 조절하는 방식이라 키압과 직접 연결되지 않는다.

그래서 키압은 **리뷰의 성향 차원이 주로 맡는다.** 키압이 적힌 상품은 스펙 값을 함께 쓴다. 스위치 계열(적축·갈축·흑축 …)을 표준 키압으로 바꾸는 참고표를 두면 판단 범위가 넓어지지만, 이는 데이터 보강에 해당해 지금은 넣지 않았다.

**디자인**

리뷰의 27%가 외관을 말한다. 하지만 "예쁘다"는 취향이라, 그 말만으로는 이 사용자에게 맞는지 알 수 없다. 리뷰 추출 규칙도 디자인 취향은 근거로 인정하지 않는다.

| 디자인 요소 | 다루는 방법 |
|---|---|
| 색상, 조명(RGB) | 사용자가 말하면 스펙 조건으로 거른다. **카탈로그에 컬럼이 없다** |
| 배열 | 스펙 조건(크기에서 추정) |
| 마감·키캡 질감 | 리뷰 품질 차원 |
| "예쁘다" | 점수에 넣지 않는다. 결과 화면에서 이미지로 비교하게 한다 |

**소리**

| 판단 재료 | 쓰는 방법 |
|---|---|
| 스펙: 스위치 방식 | 클릭형이면 큰 소리, 저소음 스위치면 조용 쪽 |
| 리뷰: 소리 크기, 소리 성격(성향) | "도각거리는", "조용한" 등 사용자 목표에 맞춰 |
| 리뷰: 잡음(품질) | 통울림·스프링 소리 |

**먼저 묻는 것:** 용도, 소음 민감 여부, 배열, 연결. 느낌 표현(키압, 소리)이 있으면 리뷰 축을 강조한다.

### 5.3 마우스 — 손에 맞는가

**스펙으로 계산한다.** 카탈로그의 크기(폭 × 길이 × 높이 mm)와 무게는 84종 모두 값이 있다.

1. **사용자 손 크기를 받는다.** 세 가지 중 편한 것으로 받는다.
   - 칩: 작음 / 보통 / 큼 (한국 평균 손 길이 남 18.3cm, 여 17cm를 기준으로 구간을 나눈다)
   - 손 길이 직접 입력
   - **지금 쓰는 마우스 이름과 그 크기가 어떤지**("G304 쓰는데 조금 작아요"). 카탈로그에 있는 모델이면 그 크기를 기준으로 삼는다. "지금 쓰는 마우스와 비슷한 형태를 고르면 실패가 적다"는 구매 가이드의 조언과 같다
2. **적정 길이를 정한다.** 마우스 길이가 손 길이의 65~75%이면 적정으로 본다(구매 가이드 기준, 잠정).
3. **그립을 반영한다.** 손바닥 전체로 잡으면(팜) 범위의 긴 쪽·높은 마우스, 손가락 끝으로 잡으면(핑거) 짧은 쪽·낮은 마우스.
4. **손 맞춤 값 = 범위 안이면 1, 범위를 벗어나면 벗어난 만큼 깎는다**(5mm마다 0.2, 잠정).

**리뷰는 보조한다.**

| 차원 | 쓰는 방법 |
|---|---|
| 무게 체감(성향) | "가벼운 마우스"를 원하면 가볍다는 묘사가 많은 상품 |
| 그립 안정감, 손목 편함(품질) | 손목 통증을 말하면 비중을 올린다 |
| 크기 체감 | 리뷰어의 손 크기를 알아야 의미가 있는데 언급이 드물다(5%). 1차에는 쓰지 않는다 |

**먼저 묻는 것:** 용도, 손 크기, 연결, 손목 통증 여부. 그립은 선택 질문이다.

### 5.4 스피커 — 저음, 고음, 좌우 분리

스피커 리뷰는 음색을 거의 말하지 않는다(저음 5%, 고음 1%, 좌우 1%). 해커톤 구성에는 스피커 리뷰가 없다. **스펙이 주로 판단하고, 판단할 수 없는 것은 그렇다고 말한다.**

| 사용자 요청 | 판단 재료 | 판단할 수 있는가 |
|---|---|---|
| 묵직한 저음 | 2.1채널·서브우퍼 구성, 저음반사형 인클로저, 출력(W). 리뷰의 저음 묘사 | 일부. 구성 컬럼이 절반 이상 공란이다 |
| 선명한 고음·보컬 | 주파수 대역, 트위터 유무가 데이터에 없다. 리뷰 언급 1% | **판단할 수 없다.** "확인하지 못함"으로 안내 |
| 좌우 분리감 | 형태: 좌우가 떨어진 북셸프·새틀라이트가 일체형 사운드바보다 유리 | 형태로 근사 |
| 충분한 음량 | 출력(W), 리뷰의 음량 묘사 | 가능 |
| 잡음 없음 | 리뷰의 잡음 묘사 | 리뷰가 있는 상품만 |

**먼저 묻는 것:** 책상 공간·원하는 형태, 용도. 형태를 정하면 좌우 분리와 저음 가능성이 상당 부분 정해진다.

### 5.5 공통 하드 조건과 유도 선호

| 품목 | 하드 조건(사용자가 명시했을 때) | 용도에서 유도하는 선호 |
|---|---|---|
| 모니터 | 크기 범위, 해상도 등급, 주사율 하한 | 사무: 27인치·IPS / FPS 게임: 24~27인치·144Hz 이상 / 창작: 27~32인치·IPS 또는 OLED·색감 정확 |
| 키보드 | 배열, 연결 방식 | 사무·야간: 클릭형 아님 / 게임: 자석축·래피드 트리거, 텐키리스 / 사무: 풀배열 |
| 마우스 | 연결 방식, 폼팩터 | 게임: 80g 이하 / 사무: 무소음 클릭 / 손목 통증: 버티컬 |
| 스피커 | 형태 | 음악: 북셸프·출력 여유 / 좁은 책상: 사운드바·새틀라이트 / 사무: USB 전원 |

지금 규칙 중 "사무·학습 마우스는 무선 선호"와 "게임 스피커는 2채널 이상"은 뺀다. 앞의 것은 근거가 없고(게이밍 상위권도 대부분 무선), 뒤의 것은 카탈로그 전부가 2채널 이상이라 가르는 힘이 없다.

## 6. 선택과 결과

- 품목은 서로 관계가 없으므로 **품목마다 독립으로 1위**를 고른다. 동점이면 더 싼 쪽, 그래도 같으면 상품 키 순이다.
- 품목마다 **대안 상위 3개**를 함께 보관한다.
- 품목별 예산 없이 합계 예산 하나만 있으면 지금 구현의 조합 탐색을 그대로 쓴다.
- 하드 필터 뒤 후보가 없으면 어느 조건 때문에 비었는지 알려 준다.

추천 이유는 품목마다 다음을 붙인다(PER-06, PER-11).

- 조건과 연결된 스펙 근거. 어느 축이 점수를 올렸는지
- 리뷰 근거: "리뷰 N건 중 M건이 '묵직하다'고 언급"과 대표 문장. 집계에 포함된 관측에서만 가져온다
- 리뷰가 없으면 "리뷰가 없어 스펙과 가격으로 골랐다", 적으면 건수와 함께 "리뷰가 적어 판단 근거가 약함"
- 적용한 가중치와 그 이유("느낌 조건을 말씀하셔서 리뷰 비중을 높였어요")

## 7. 제출처별 리뷰 구성

### 7.1 두 묶음

| 묶음 | 내용 | 파이널 프로젝트 | 해커톤 제출 |
|---|---|:---:|:---:|
| A | 크롤링으로 모은 실제 리뷰 | 사용 | **제외** |
| B | A를 바탕으로 증강해 만든 생성 리뷰 | 사용 | 사용 |

코드와 점수식은 두 제출처에서 같다. 적재하는 리뷰만 다르다.

### 7.2 B를 해커톤에 쓸 수 있는가

B가 A의 문장을 고쳐 쓴 것이라면 A를 빼도 크롤링에서 나온 표현이 남는다. 그래서 B의 각 문장을 같은 모델의 실제 리뷰와 비교해 겹침을 쟀다.

| 품목 | 비교한 생성 리뷰 | 5글자 조각 겹침(중앙값) | 30% 이상 겹침 | 15자 이상 공통 구절 | 25자 이상 공통 구절 |
|---|---:|---:|---:|---:|---:|
| 키보드 | 1,350 | 3% | 6건 | 11건 | 0건 |
| 모니터 | 896 | 3% | 3건 | 46건 | 0건 |
| 마우스 | 2,350 | 0% | 2건 | 1건 | 0건 |

B는 A의 문장을 옮기거나 고쳐 쓴 것이 아니다. 문장 수준의 겹침이 거의 없고, 모니터 생성 리뷰 420건은 같은 모델의 실제 리뷰가 아예 없는 상품에 대한 것이다. **B를 해커톤에 쓰는 것이 가능하다고 본다.** 스펙만으로 새로 만드는 묶음은 만들지 않는다.

조건은 세 가지다.

1. **겹침이 큰 소수는 뺀다.** 15자 이상 공통 구절이 있거나 5글자 조각이 30% 이상 겹치는 생성 리뷰(약 60건)는 해커톤 번들에서 제외한다.
2. **해커톤 규정을 확인한다.** 이 측정은 문장이 얼마나 비슷한지를 잰 것이지 법률 판단이 아니다. 개발 과정에서 쓴 데이터까지 권리를 요구하는 규정이라면 B도 문제가 될 수 있다.
3. **데이터 출처를 질문받으면 사실대로 답한다.** 제출물에 A가 없는 것과, B가 어떻게 만들어졌는지를 숨기는 것은 다른 일이다.

### 7.3 번들 단위로 나눈다 — 기존 도구를 그대로 쓴다

리뷰 적재는 이미 **시드 번들** 방식으로 돼 있다. "번들"은 DB에 넣을 리뷰 데이터를 미리 만들어 한 폴더에 묶어 둔 것이다. `data/review_seed` 폴더에 네 파일이 있다.

| 파일 | 내용 |
|---|---|
| `documents.json` | 리뷰 원문 5,653건 |
| `rules.json` | 속성 규칙 102개 |
| `consolidated_observation_drafts.json` | 리뷰에서 뽑아 검수한 관측 3,676건 |
| `bundle_manifest.json` | 건수와 파일별 해시 |

`setup_all.py`가 이 폴더를 읽어 DB에 넣고 집계를 만든다. 파일이 없거나 해시가 다르면 적재가 실패한다. Git에는 올리지 않고 팀 내부 채널로 주고받는다.

따로 적재 가드를 만들 필요가 없다. **번들을 묶음별로 만들고 어느 번들을 넣을지만 고르면 된다.**

| 번들 | 내용 | 상태 |
|---|---|---|
| A 번들 | 실제 리뷰 5,653건, 관측 3,676건 | 있음(`data/review_seed`) |
| B 번들 | 생성 리뷰와 그 관측 | **없음** |

| 제출처 | 적재하는 번들 |
|---|---|
| 파이널 | A + B |
| 해커톤 | B |

**새로 필요한 일은 B 번들 하나다.** 지금 B는 속성 추출을 거치지 않았고, 기존 적재 코드는 생성 리뷰를 제외한다. 그래서 지금 상태에서 A를 빼면 DB에 리뷰가 하나도 남지 않는다. B 번들은 파이널(A + B)에도 필요하므로 두 제출처가 같은 작업을 공유한다.

B 번들을 만들려면:

- 번들 빌더(`build_review_seed_bundle.py`)가 `is_synthetic`을 `false`로 고정하고 있다. 생성 리뷰를 담을 수 있게 넓힌다.
- B를 A와 같은 규칙·추출·검수 경로에 태워 관측을 만든다.
- 적재 스크립트가 번들 폴더를 고를 수 있게 한다(지금은 `data/review_seed` 고정).
- 차원 규칙(4장)을 넣는다면 A와 B 모두 같은 규칙 버전으로 다시 분석한다.

B의 범위는 상품마다 다르다. 생성 리뷰가 있는 상품은 키보드 40종, 모니터 25종, 마우스 67종이고 **스피커는 0종**이다. 해커톤 구성에서 스피커는 리뷰 축이 전부 0.5로 계산된다. 리뷰 없는 상품은 없는 대로 둔다.

### 7.4 해커톤 제출 구성

- 제출은 **별도 저장소**로 낸다. A 데이터, A 번들, 수집 스크립트는 가져가지 않는다.
- 해커톤 DB는 빈 DB에 B 번들만 적재해 만든다. 파이널 DB에서 행을 지워 만들지 않는다. 지우는 방식은 관측·집계·임베딩에 A에서 나온 것이 남을 수 있다.

제출 전 점검:

1. `evidence.review_document`에 A 묶음의 `source_code`가 없는지 확인한다.
2. 제출 저장소와 배포 이미지에 A 파일과 A 번들이 없는지 확인한다. 도커 이미지는 `data/`를 통째로 복사하므로 빌드 폴더에 B 번들만 있어야 한다.
3. 화면의 대표 리뷰 문장, 리포트, 발표 자료 캡처가 B에서 나온 것인지 확인한다.
4. B 번들만 적재한 상태로 주변기기 전 여정을 한 번 돌린다.

같은 요청이라도 적재한 리뷰가 달라 두 제출처의 순위가 다를 수 있다. 정상이다.

- **AI 끔 검증:** 조건 에이전트를 꺼도 칩만으로 같은 추천이 나오는지 확인한다.

## 12. 자체 리뷰로의 확장

TrueFit의 최종 방향은 플랫폼 안에서 제품별 리뷰를 직접 받고, 그 리뷰로 추천하는 것이다. 지금 기획이 그 방향을 막지 않는지 점검한다.

### 12.1 그대로 쓸 수 있는 것

| 항목 | 이유 |
|---|---|
| 점수 계산(Q, α, R, 축 가중합) | 리뷰가 어디서 왔는지 모른다. 집계만 읽는다. 자체 리뷰가 들어와도 식이 바뀌지 않는다 |
| 리뷰 없는 상품 0.5, k 보정 | 자체 리뷰는 0건에서 시작한다. 리뷰가 몇 건뿐인 상품이 1위가 되지 않게 막는 장치가 이미 있다 |
| 묶음 구분 | 자체 리뷰는 세 번째 묶음이다. 권리가 분명하므로 쌓이면 A·B를 줄여 갈 수 있다 |
| 리뷰 작성 구조 | `community.review`(작성자, 상태: 초안·게시·숨김·삭제)와 작성·게시 API가 이미 있다 |

### 12.2 그대로는 안 되는 것

점수 계산이 아니라 **리뷰를 넣고 갱신하는 쪽**이다. 지금은 한 번 모은 리뷰를 사람이 검수해 통째로 적재하는 방식이라, 리뷰가 계속 들어오는 상황과 맞지 않는다.

| 지금 | 자체 리뷰에 필요한 것 |
|---|---|
| 회원 리뷰(`community.review`)와 추천에 쓰는 리뷰(`evidence.review_document`)가 이어져 있지 않다 | 게시된 회원 리뷰를 추천용 문서로 넘기는 통로 |
| 속성 관측은 담당자가 한 건씩 검수해 승인한다 | 자동 검증(근거 문장이 원문에 실제로 있는지, 등록된 차원인지)과 표본 검수 |
| 집계는 전체를 다시 만든다. 갱신 절차가 서비스 중단을 전제로 한다 | 리뷰가 게시·수정·삭제될 때 그 상품만 다시 집계 |
| 추천용 문서에 작성자·별점이 없다 | 별점과 작성자 연결 |

지금 고칠 필요는 없다. 해커톤과 파이널은 지금의 리뷰 적재 방식(7.3절)으로 충분하다.

### 12.3 지금 정해 두는 것

자체 리뷰는 **별점(5점 만점)과 자유 글**로 받는다. 질문형 양식은 두지 않는다.

**1. 자체 리뷰도 외부 리뷰와 같은 방식으로 읽는다.**

자유 글에서 차원별 관측을 뽑는 AI 추출이 자체 리뷰에도 그대로 쓰인다. 4장의 차원 정의가 곧 추출 기준이므로, 지금 정의를 세밀하게 잡아 두면 자체 리뷰가 들어와도 바꿀 것이 없다. 사람들이 자유 글에 쓰는 표현("살짝 묵직한데 반발이 탱탱해요")은 "좋았다/아쉬웠다" 선택지보다 정보가 많다. 성향 차원은 그 정보를 살리기 위한 것이다.

**2. 별점은 따로 저장한다.**

별점은 상품 전체에 대한 만족도라 특정 차원과 연결되지 않는다. 그래서 차원 점수(Q, M)에 섞지 않는다. 쓸지 여부는 13장에서 정한다.

**3. 추천 코드는 집계만 읽는다.**

추천 경로가 리뷰 파일이나 특정 묶음을 직접 알지 못하게 한다. 리뷰가 파일로 적재되든 회원이 써서 들어오든 집계 테이블에 반영되면 추천은 똑같이 동작한다. 지금 구현이 이미 이렇게 돼 있고, 이 기획도 그 경계를 넘지 않는다.

### 12.4 나중에 정할 것

- **누가 쓸 수 있는가.** TrueFit은 구매를 대행하지 않아 구매 확인을 할 수 없다. 견적을 확정한 사용자에게만 리뷰를 받는 식의 기준이 필요하다.
- **작성자 조건.** 자유 글에 "손이 작은 편인데", "게임용으로"처럼 작성자 조건이 적혀 있으면 추출 때 함께 뽑아 사용 조건(context)으로 남길 수 있다. "손이 작은 사람들의 평가"처럼 조건별로 집계하면 외부 리뷰로는 못 하던 추천이 된다. 규칙에 사용 조건 자리가 이미 있어 구조를 바꾸지 않고 넣을 수 있다.
- **묶음별 비중.** 지금 집계는 묶음을 구분하지 않고 건수를 합친다. 자체 리뷰를 외부 리뷰보다 무겁게 세려면 집계 구조를 바꿔야 한다.
- **어뷰징.** 한 상품에 한 사람이 한 건, 작성 빈도 제한, 신고와 숨김.
- **동의와 삭제.** 리뷰를 추천에 쓴다는 동의, 작성자가 지우면 관측과 집계에서도 빠지는 절차.
