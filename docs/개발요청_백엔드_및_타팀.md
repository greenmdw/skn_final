## 5. 응답 속도

프론트에서 HTTP로 잰 값이다(2026-09-30, 개발 PC·로컬 DB, 브라우저 → vite 프록시 → API, 테스트 계정의 8개 부품 견적).

| API | 이전 체감 | 지금 |
|---|---|---|
| `POST /session/{id}/items/{item_id}/swap` | 수 초 | 약 0.9~1.6초 |
| `PATCH /session/{id}/items/{item_id}` (수량·구매 시점) | 수 초 | 약 1.0~1.2초 (처음 한 번은 2.2초) |
| `POST /session/{id}/recommend` → `GET .../result` | 약 15~20초 | 다시 재지 않음 |

- 백엔드가 `swap_item`/`patch_item`을 직접 호출해서 잰 값은 50~70ms였는데, HTTP로는 그보다 15배쯤 걸린다. 함수 밖 — 응답을 만드는 부분(결과 재조회·직렬화·가격 감시 등), 커넥션·미들웨어 — 에서 시간이 쓰이는 것으로 보인다. 함수 안쪽이 아니라 **요청 전체 구간**을 재서 나눠 봐 달라.
- `recommend` → `result`의 15~20초(설명 문장 생성 LLM 호출)는 그대로다. 먼저 구성을 보여 주고 문장은 `pending`으로 나중에 채우는 방식(결과 화면 계약 `explanation.status`)을 검토해 달라.

## 6. 주변기기 추천 API (프론트 담당: Charlie)

> **처리됨(2026-10-01, `pc-catalog-engine`)**: `POST /session/{id}/category`로는 안 열었다(주변기기는 독립 카테고리가 아니라는 기존 설계 결정, `config/peripherals.yaml` 머리말 참고). 대신 **`POST /session/{id}/peripherals/recommend`**를 새로 열었다(C안). PC 견적 대화 없이 바로 호출할 수 있고(ChoosePage "/peripherals" 입구), `pc_list_id`를 같이 주면 그 PC 견적의 해상도를 묶어 모니터↔GPU 교차검사를 추가로 켠다("PC 견적 이후 주변기기도 같이 보기").
>
> **요청**:
> ```json
> {"kinds": ["monitor", "keyboard"], "budget_max": 500000,
>  "purpose": "game", "priority": "quiet", "noise_sensitive": true,
>  "resolution": "QHD_165", "pc_list_id": "4f2b1a9e-..."}
> ```
> `kinds`만 필수(1개 이상, `monitor`|`keyboard`|`mouse`|`speaker`). `purpose`/`priority`/`noise_sensitive`/`resolution`은 PC 대화에서 쓰는 것과 **같은 조건 어휘**(새 필드를 안 만들었다). `pc_list_id`는 principal 소유가 아니거나 못 찾으면 조용히 무시(독립 추천으로 진행, 에러 안 냄). `resolution`을 안 주면 `pc_list_id`가 준 해상도를 모니터 요구사양에도 그대로 쓴다(명시하면 그게 우선).
>
> **응답**: `src/engine/peripheral_payload.py`가 이미 내던 모양(`status`/`items[]`/`empty[]`/`totals`) 그대로. LLM·네트워크 호출이 없어 **PC 추천과 달리 요청 한 번으로 끝난다**(`run_id` 폴링 없음).
>
> **한계**: 모니터↔GPU 포트(HDMI/DP 버전·포트 수) 교차검사는 `catalog.gpu_spec`에 그 컬럼이 아예 없어 항상 "확인 필요"(unknown)로 남는다 — 해상도 일치 검사(`monitor_resolution`)만 실제로 ok/fail이 난다. 리뷰 관측은 4번이 끝나야 채워진다(기존과 동일).
> - 테스트: `tests/test_peripherals_recommend_http.py`.

## 7. RAM: DDR5 16GB 듀얼채널 SKU가 카탈로그에 없음

추천 엔진이 듀얼채널 키트를 우대하도록 고쳤다(`stage3b_rank.py`, `ram_dual_channel_bonus`). 다만 게임 목적(기본 규격 DDR5)에는 **DDR5 16GB 듀얼채널(8GB×2) SKU가 이 카탈로그에 아예 없어서**(DDR5 16GB는 전부 단일 모듈) 가장 흔한 "게임용" 견적은 여전히 단일 모듈 16GB 한 개가 나온다. DDR4를 허용하는 용도(사무·학습 등)에서는 듀얼채널이 선택된다.
요청: 카탈로그(`data/parts_list_modify.xlsx` → `seed_pc_parts_specs.py`)에 DDR5 16GB 듀얼 SKU를 추가할지 결정해 달라. 추가하지 않기로 하면 이 항목은 닫아도 된다(프론트는 서버가 준 수량·구성을 그대로 표시한다).

## 10. 견적서(revision) 하나만 삭제·이름 바꾸기

> **처리됨(2026-10-01, `pc-catalog-engine`)**: `DELETE /lists/{id}/reports/{revision_no}`·`PATCH /lists/{id}/reports/{revision_no}`(`{"name": ...}`)를 추가했다. `planning.plan_revision`에 `deleted_at`을 더하는 마이그레이션(`0006_report_soft_delete.sql`)이 필요해서 **개발 DB에 `python db/migrate.py up`을 한 번 돌려야 한다**(실행 안 해도 테스트는 일회용 DB를 매번 새로 만들어 통과하니, 멀쩍이 보일 수 있다 — 실제 개발 서버 기동 전에 꼭 돌려 달라).
> - 지우는 견적서가 지금 작업 중인(current) 견적서면: 남은 확정 견적서가 있으면 그걸로 current를 옮기고, 하나도 안 남으면 지우는 견적서의 조건·부품 구성을 그대로 들고 **초안으로 되돌린다**(8번 `clone_revision`과 같은 메커니즘 — "새 견적서 시작"을 자동으로 누른 것과 같음, 재추천 없이 바로 그 구성을 갖고 있다).
> - 지운 견적서는 `GET /lists`의 `reports[]`와 `GET /lists/{id}/report`(그 번호)에서 모두 404/사라짐 — soft delete라 데이터는 남지만 눈에는 안 보인다.
> - 테스트: `tests/test_report_delete_rename_http.py`.

좌측 패널에서 대화(목록)는 이름 바꾸기(`PATCH /lists/{id}`)와 삭제(`DELETE /lists/{id}`)를 이미 쓴다. 하지만 **한 대화 안의 견적서 하나**만 지우거나 이름을 바꾸는 API는 없다.
- `DELETE /lists/{id}`는 대화와 그 안의 견적서 전체를 지운다(soft delete). 견적서 하나만 지우려면 예: `DELETE /lists/{id}/reports/{revision_no}`가 필요하다. 마지막 남은 견적서를 지울 때의 동작(대화는 유지, 상태는 초안으로 되돌림 등)도 정해 달라.
- 견적서 이름은 확정 때 정한 `name_snapshot`이라 `PATCH /lists/{id}`(대화 이름)로는 바뀌지 않는다. 예: `PATCH /lists/{id}/reports/{revision_no}`로 `name`을 받아 달라.
- 프론트는 이 둘이 생기면 패널의 견적서 행에 우클릭(터치는 길게 누르기) 메뉴(이름 바꾸기·삭제)를 붙인다. 대화 행에는 이미 있다.

## 11. 견적서마다 주변기기 개수·합계 (저장한 견적 필터용)

좌측 패널의 "저장한 견적"은 모든 견적서를 시간 순으로 나열하고, **PC 본체 / PC 주변기기 종류 필터**와 "부품 8 · 주변기기 3" 표시를 넣도록 설계했다. 그런데 `GET /lists`의 `reports[]`와 `GET /lists/{id}/report`는 본체 부품 수(`item_count`)만 주고 주변기기 정보가 없다. 값이 없으면 프론트는 종류 필터와 주변기기 표시를 **숨긴다**(코드는 준비돼 있어 값이 오면 자동으로 나타난다).

요청: `reports[]` 각 항목에 아래를 추가해 달라.
- `peripheral_count`: 그 견적서에 담긴 주변기기(모니터·키보드·마우스·스피커) 수. 없으면 0.
- `item_count`는 **본체 부품 수만**으로 정의를 확정해 달라(주변기기를 합치지 않는다). 본체만 있는 견적서는 `peripheral_count: 0`, 주변기기만 있는 견적서는 `item_count: 0`이 되도록.
- `total`은 **본체 + 주변기기 합계**인지 알려 달라(프론트는 서버가 준 합계를 그대로 견적서 금액으로 보여 준다).
- 주변기기 견적을 저장할 수 있게 되는 시점(6번)에 맞춰 같이 정해 주면 된다.

## 12. 개발 환경: 로그인이 403 (`허용되지 않은 출처`)으로 막힘

프론트를 `npm run dev`(5173)로 띄우고 `http://localhost:5173`으로 접속해 로그인하면 `POST /auth/login`이 `403 origin_not_allowed`로 거절된다. `.env.example`의 `ALLOWED_ORIGINS=http://127.0.0.1:5173`가 **주석 처리돼 있어서**, 브라우저가 보내는 `Origin`이 서버 자신의 origin과 달라 막히기 때문이다. 처음 프론트를 띄우는 팀원마다 한 번씩 부딪힐 수 있다.

요청: `APP_ENV=development`일 때는 `http://localhost:5173`과 `http://127.0.0.1:5173`을 기본 허용 origin으로 넣어 달라(운영에서는 지금처럼 `ALLOWED_ORIGINS`가 비면 자기 origin만 허용). 어렵다면 `.env.example`의 해당 줄 주석을 풀고 "`localhost`가 아니라 `127.0.0.1:5173`으로 접속" 안내를 `README`에 적어 달라.
