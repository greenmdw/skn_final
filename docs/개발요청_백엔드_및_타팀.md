## 5. 응답 속도

사용자가 화면에서 누르는 **세 가지 동작**이 기다리게 만든다.
- **부품 교체**: 결과 화면에서 부품 카드를 열어 다른 제품을 골랐을 때(`swap`).
- **수량 변경·부품 빼기**: 부품의 수량을 바꾸거나 부품을 뺐을 때(`PATCH`). 화면에서 "구매 시점" 선택은 없앴다(서버의 `timing` 값은 그대로 두면 된다).
- **추천 받기**: 조건을 다 정하고 "추천 받기"를 눌렀을 때(`recommend` → `result`).

프론트에서 HTTP로 잰 값이다(2026-09-30, 개발 PC·로컬 DB, 브라우저 → vite 프록시 → API, 테스트 계정의 8개 부품 견적).

| API | 이전 체감 | 지금 |
|---|---|---|
| `POST /session/{id}/items/{item_id}/swap` | 수 초 | 약 0.9~1.6초 |
| `PATCH /session/{id}/items/{item_id}` (수량 변경·부품 빼기) | 수 초 | 약 1.0~1.2초 (처음 한 번은 2.2초) |
| `POST /session/{id}/recommend` 접수 | — | 약 0.02초 (즉시 202) |
| 〃 → `GET .../result`에서 **부품·가격이 나올 때까지** | 약 15~20초로 알고 있었음 | 약 0.8~1.4초 (2회 측정) |
| 〃 → **설명 문장**(`explanation`)이 `pending`에서 `ready`가 될 때까지 | 〃 | 약 14~18초 (14.4초·18.3초) |

- 백엔드가 `swap_item`/`patch_item`을 직접 호출해서 잰 값은 50~70ms였는데, HTTP로는 그보다 15배쯤 걸린다. 함수 밖 — 응답을 만드는 부분(결과 재조회·직렬화·가격 감시 등), 커넥션·미들웨어 — 에서 시간이 쓰이는 것으로 보인다. 함수 안쪽이 아니라 **요청 전체 구간**을 재서 나눠 봐 달라.
- **추천 받기가 느린 것은 서버가 부품을 못 찾아서가 아니다.** 부품·가격은 약 1초 안에 `status: done`으로 나온다. 느린 것은 그 뒤 **설명 문장을 만드는 AI 호출** 하나(14~18초)다. 서버는 이미 "부품 먼저, 문장은 `pending`으로 나중에" 구조다.
- 지금 프론트(`plans.ts`의 `waitForResult`)는 그 문장이 `ready`가 될 때까지 최대 20초 기다렸다가 결과 화면을 보여 준다. 즉 사용자가 느끼는 15~20초는 **프론트가 문장을 기다리는 설계** 때문이기도 하다. 이건 **프론트에서 고친다**(부품이 나오면 바로 결과 화면을 보여 주고 설명 문장은 나중에 채우기). 백엔드는 따로 바꿀 필요가 없다.
- 백엔드에 바라는 것(선택): 설명 문장 생성이 14~18초 걸리는 이유(모델 크기, 프롬프트 길이, 여러 번 호출 여부)를 확인해 줄일 수 있으면 줄여 달라. 프론트가 문장을 나중에 채우게 해도, 문장이 빨리 오면 더 낫다.

## 7. RAM: DDR5 16GB 듀얼채널 SKU가 카탈로그에 없음

**무슨 문제인가:** 게임용으로 PC를 맞추면 램이 **16GB짜리 한 개**(단일 모듈)로 추천된다. 램은 같은 16GB라도 8GB 두 개를 꽂는 **듀얼채널**이 더 빠르다. 추천 엔진은 듀얼채널을 우대하도록 이미 고쳤다(`stage3b_rank.py`, `ram_dual_channel_bonus`). 그런데 게임용은 기본 규격이 DDR5인데, 카탈로그의 DDR5 16GB 제품은 **전부 한 개짜리**이고 8GB×2 키트가 **아예 없어서** 우대할 후보가 없다.

- DDR4 데이터가 없는 것이 **아니다**. DDR4를 허용하는 용도(사무·학습 등)에서는 듀얼채널 키트가 이미 선택된다.
- 부족한 것은 **DDR5 16GB(8GB×2) 키트 제품 1종 이상**이다. 다른 용량(32GB 등)의 DDR5 듀얼 키트는 있어도, 16GB 예산대에서는 비싼 32GB가 선택될 위험이 있어 우대 대상에서 뺐다.

요청: 카탈로그(`data/parts_list_modify.xlsx` → `seed_pc_parts_specs.py`)에 DDR5 16GB(8GB×2) 키트를 추가할지 결정해 달라. 추가하지 않기로 하면 이 항목은 닫아도 된다(프론트는 서버가 준 수량·구성을 그대로 표시한다).

## 11. 견적서마다 주변기기 개수·합계 (저장한 견적 필터용)

좌측 패널의 "저장한 견적"은 모든 견적서를 시간 순으로 나열하고, **PC 본체 / PC 주변기기 종류 필터**와 "부품 8 · 주변기기 3" 표시를 넣도록 설계했다. 그런데 `GET /lists`의 `reports[]`와 `GET /lists/{id}/report`는 본체 부품 수(`item_count`)만 주고 주변기기 정보가 없다. 값이 없으면 프론트는 종류 필터와 주변기기 표시를 **숨긴다**(코드는 준비돼 있어 값이 오면 자동으로 나타난다).

요청: `reports[]` 각 항목에 아래를 추가해 달라.
- `peripheral_count`: 그 견적서에 담긴 주변기기(모니터·키보드·마우스·스피커) 수. 없으면 0.
- `item_count`는 **본체 부품 수만**으로 정의를 확정해 달라(주변기기를 합치지 않는다). 본체만 있는 견적서는 `peripheral_count: 0`, 주변기기만 있는 견적서는 `item_count: 0`이 되도록.
- `total`은 **본체 + 주변기기 합계**인지 알려 달라(프론트는 서버가 준 합계를 그대로 견적서 금액으로 보여 준다).
- 주변기기 견적을 저장할 수 있게 되는 시점(6번)에 맞춰 같이 정해 주면 된다.

## 12. 개발 환경: 로그인이 403 (`허용되지 않은 출처`)으로 막힘

**무슨 일인가:** 로그인·저장 같은 "바꾸는 요청"(POST·PATCH·DELETE)에는 브라우저가 `Origin`(지금 보고 있는 페이지가 어느 주소에서 열렸는지)을 붙여 보낸다. 서버(`src/auth/origin.py`)는 다른 사이트가 사용자의 로그인 쿠키를 몰래 쓰는 공격(CSRF)을 막으려고 **이 `Origin`이 서버 자신의 주소와 같을 때만** 받고, 다르면 `403 허용되지 않은 출처`로 돌려보낸다. 예외로 허용할 주소는 `.env`의 `ALLOWED_ORIGINS`에 적는다.

개발할 때는 화면(`npm run dev`, 5173 포트)과 서버(8000 포트)가 **서로 다른 주소**라서 이 검사에 걸린다. `.env.example`의 `ALLOWED_ORIGINS=http://127.0.0.1:5173` 줄이 주석(`#`) 처리돼 있어, 줄을 풀지 않으면 `http://localhost:5173`으로 접속해 로그인할 때 `POST /auth/login`이 403으로 막힌다. (프론트 담당이 로컬 `.env`에서 이 줄을 풀어 둔 상태에서는 `http://127.0.0.1:5173`으로 접속하면 로그인된다.) 서버 코드 버그가 아니라 **개발 환경 설정 문제**다.

요청(우선순위 낮음): `APP_ENV=development`일 때만 `http://localhost:5173`과 `http://127.0.0.1:5173`을 기본으로 허용해 달라(운영에서는 지금처럼 `ALLOWED_ORIGINS`가 비면 자기 주소만 허용하므로 보안은 그대로다). 어렵다면 `.env.example`의 해당 줄 주석을 풀고 "`127.0.0.1:5173`으로 접속" 안내를 README에 적어 달라.

## 13. 부품별 구매 시점(`timing`) 값 삭제

**배경:** 결과 화면의 부품 카드에서 "구매 시점"(지금 / 곧 / 나중에) 선택을 **프론트에서 없앴다**. 이 값은 유아용품 장바구니 시절의 기능(품목마다 지금·곧·나중에 살지 정함)이라 PC 견적에는 쓰임이 불분명하다. 프론트는 이제 `timing`을 보내지도, 화면에 보이지도 않는다.

**삭제하면 안 되는 것 (구분 주의):**
- `PATCH /session/{id}/items/{item_id}` **엔드포인트 자체는 남긴다.** 수량(`qty`)과 부품 빼기·다시 넣기(`selected`)가 같은 엔드포인트를 쓰고, 프론트가 계속 쓴다.
- **견적서 전체의 "구매 예정일"(`planned_purchase_at`)은 별개라서 그대로 둔다.** 확정(`POST /lists/{id}/confirm`) 때 사용자가 정하는 값이고, 리포트에 "구매 예정"으로 보인다. 부품별 `timing`과 관계없다.

**삭제해 달라는 것 — 부품별 `timing` 값만:**
- 요청: `schemas.py`의 `ItemPatchIn.timing`(538행 부근). 응답의 `timing` 필드: 결과 항목(`schemas.py` 508행 부근)과 리포트 항목(754행 부근), `dto.py:136`.
- 저장: `engine.recommendation_candidate.timing` 컬럼 — 지우려면 마이그레이션이 필요하다. 어렵다면 컬럼은 두고 API에서만 빼도 된다. 연관 코드: `engine_repo.update_candidate_state`, `plan_repo`(견적서 복사 시 컬럼 복사), `list_service.py`(확정 스냅샷 286·321행).
- 결과 화면 채팅: `result_agent.py`의 `set_timing` 도구와 `set_item(..., timing=...)`, 안내 문구의 "(나중에)/(곧)" 표시(`recommendation_service.py:489`), 결과 목록의 "시점" 표기(`result_agent.py:274`). 사용자가 채팅으로 "이건 나중에 살게"라고 하면 지금은 이 도구가 동작한다 — 없애면 그 말은 일반 대화로 처리돼야 한다.
- 프론트는 서버가 `timing`을 빼는 때에 맞춰 `wire.ts`의 `timing` 필드 선언을 지운다(지금은 응답에 있어도 읽지 않는다). 급하지 않아서 우선순위는 낮다.

## 14. 예전 견적서에서도 "견적 수정하기" — 원본 번호를 지정해 새 초안 만들기

**문제:** 한 대화에 견적서가 여러 개일 때(예: 1~4번), 리포트 화면의 **견적 수정하기**가 **가장 최근 견적서(4번)에서만** 된다. 1~3번을 열면 버튼이 없다. `POST /lists/{id}/revisions`(`list_service.new_revision`)가 **항상 "현재(current) 견적서"를 복사**하고 어느 견적서를 고칠지 고를 방법이 없어서, 프론트가 예전 견적서에는 버튼을 숨겼다(누르면 최신 견적서의 구성이 열려 버리기 때문).

**요청:**
- `POST /lists/{id}/revisions`가 **복사할 견적서 번호**를 받게 해 달라. 예: 본문 `{"from_revision_no": 2}`. 안 주면 지금처럼 최근 확정본을 복사한다. 지정한 견적서의 조건·부품 구성(8번에서 만든 `clone_revision`)을 새 초안으로 복사하면 된다.
- **이미 작성 중인 초안이 있을 때:** 지금은 "있으면 그대로 돌려준다"(두 번 눌러도 초안 하나)인데, 다른 번호를 지정하면 그 초안은 엉뚱한 구성이다. 지정 번호가 있으면 기존 초안을 버리고 새로 복사할지(권장), 에러로 거절할지 정해 달라. 거절하면 프론트가 "작성 중인 견적이 있어요. 버리고 시작할까요?"를 묻는다.

**프론트가 이미 처리한 것 (참고):** "견적 수정하기"로 들어오면 장바구니에서 **원본 덮어쓰기 / 새 견적서로 저장**을 사용자에게 고르게 한다. 덮어쓰기는 서버에 API가 없어 **새 견적서로 확정한 뒤 원본을 `DELETE /lists/{id}/reports/{revision_no}`로 지우는 두 단계**로 한다. 중간에 실패하면 새 견적서만 남고(원본은 안 지워짐) 안내를 띄운다. 원자적으로 하고 싶다면 선택 사항으로 `POST /lists/{id}/confirm`에 `replaces_revision_no`(그 견적서를 새 내용으로 교체)를 받아 달라. 급하지 않다.
