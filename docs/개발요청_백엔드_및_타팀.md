# 개발 요청 — 백엔드 및 타 팀 (프론트 작업에서 나온 항목)

작성: 프론트(front 브랜치) · 2026-09-29
프론트는 `web/`(React)에서 화면을 백엔드 API에 연결하는 중이다. 아래는 **프론트가 할 수 없거나 백엔드가 맞춰야 화면이 완성되는 일**이다.
표의 "프론트 상태"는 프론트가 이미 처리했거나 임시로 막아 둔 부분이다.

## 1. 리포트의 "조립 가이드" 제거 (백엔드 삭제 요청) — 우선순위 높음

팀 결정으로 조립 가이드는 하지 않기로 했다. 프론트는 화면과 관련 코드를 모두 지웠다(`careGuide`, `guideStepsFromWire`, `GuideStep` 타입, 프로토타입 화면의 조립 가이드 구역).

백엔드에서 지울 것:

| 위치 | 내용 |
|---|---|
| `src/schemas.py` `ReportOut.care_guide` | 리포트 응답 필드 삭제 |
| `src/services/list_service.py` (`build_guide`, `care_guide` 조립부, 응답 dict) | 확정 시 조립 가이드를 만드는 코드 삭제 |
| `src/agent/assembly_guide_agent.py` | 조립 가이드 에이전트 삭제 |
| 관련 테스트 | 위 코드를 검사하는 테스트 삭제·수정 |

주의:
- **"구매 전 확인"(부품 카드의 `checks`)은 조립 가이드가 아니다.** `src/rag/care_guides.py`·`data/pc_care_guides.json`은 그쪽에서도 쓰므로, 조립 가이드만 지우고 구매 전 확인 기능이 남는지 확인해 달라. (구매 전 확인도 없애는 결정이라면 알려 달라.)
- `ReportOut.data_notice`("상품·가격·리뷰는 합성 데이터입니다.")는 그대로 둬도 된다. 프론트는 아직 쓰지 않는다.

## 2. 리포트 "견적 리스트 히스토리" 요약 API (신규) — 우선순위 높음

리포트 페이지의 조립 가이드 자리에 **"견적 리스트 히스토리"** 구역을 만들었다. 사용자가 사이트에서 채팅으로 이것저것 묻고, 본인이 마음에 든 것(favorite)을 골라 최종 리스트를 만든 **여정을 요약**해 보여 주는 곳이다.
프론트는 자리와 표시 코드(`web/src/components/ListHistory.tsx`)만 만들었고, **요약 문장은 서버가 만들어 줘야 한다.** 지금은 "요약은 준비 중이에요"라고만 나온다(값을 지어내지 않는다).

요청:
- 새 API 제안: `GET /lists/{list_id}/history` (또는 리포트 응답에 `history` 필드 추가). 응답 예:
  ```json
  { "summary": { "status": "ready", "text": "게임용 150만 원 조용한 PC를 찾다가 GPU를 RX 7600에서 RTX 3050으로 바꾸고…" },
    "events": [ { "at": "2026-09-29T08:01:00Z", "kind": "question|swap|qty|favorite", "text": "…" } ] }
  ```
  `summary`는 `{status, text}` 형식(다른 서버 텍스트와 동일)이면 프론트가 바로 붙일 수 있다.
- 재료: 조건 대화 메시지, 결과 대화 메시지, 부품 교체·수량·구매 시점 변경 기록(이미 `feedback_service.emit_replaced` 등이 있음), 그리고 favorite.
- 원칙은 기존과 같게: **숫자와 사실은 코드가, 문장은 LLM이.** 기록에 없는 것은 쓰지 않는다.
- **favorite 개념이 서버에 없다.** "마음에 든 것"을 어떻게 표시하고 저장할지(찜 API, 대안 비교에서 하트 등) 정의가 필요하다. 정해지면 프론트가 버튼을 붙인다. 결정 전까지는 교체·수량 변경 기록으로 대신해도 된다.
- 로그인한 사용자의 확정된 목록에 대해서만 제공하면 된다.

## 3. 대안 목록(`GET /session/{id}/items/{item_id}/alternatives`) 품질

부품 교체 화면이 이 API를 쓴다. 지금은 그 자리의 **전체 카탈로그**를 돌려줘서 쓰기 어렵다(GPU 기준 40개 이상).

- 워크스테이션·전문가용 제품(RTX 6000 Ada, Radeon PRO W7900 등)과 수백~수천만 원대 제품까지 섞여 나온다.
- 같은 제품이 이름만 다르게 중복된다. 예: `GeForce RTX 3050 (6GB)` / `GeForce RTX 3050 6GB`, `RTX 3060 (12GB)` / `RTX 3060 12GB`, `RX 6800 XT` / `RX 6800 16GB`.
- **현재 고른 제품이 목록에 없다**(`current: true` 항목이 오지 않는다). 프론트는 `current`가 있으면 "지금 고른 제품"으로 표시하도록 만들어 뒀다.
- 리뷰 관측이 전부 없다(`review: null`).

요청: 성능 등급이 비슷한 후보 위주로 거르기(예: 원래 화면 설계는 "비슷한 성능 3개"), 중복 제거, 현재 제품 포함. 프론트는 임시로 "현재 제품과 가격이 가까운 순 6개 + 더 보기"로 보여 준다.

## 4. 카탈로그 데이터

- **`spec_summary`가 비어 있는 제품이 많다.** 결과 화면 "주요 스펙" 칸이 `GPU · AMD`처럼 브랜드만 나온다. `db/seed_pc_parts_specs.py`가 `spec_summary`를 채우도록 보강 필요(예: GPU는 VRAM·인터페이스, CPU는 코어·소켓, RAM은 규격·용량).
- 추천 결과 8개 부품 모두 **리뷰 관측이 없다**(`review: null`). 리뷰 요약 시드는 51개 부품뿐이라서다. 리뷰 데이터 담당 팀원이 아래 5번 작업을 하면 해결될 것으로 본다.

## 5. 리뷰 데이터 적재 (리뷰 담당 팀원)

- 원본: `data/reviews/*.jsonl` 5개(팀 내 파일 공유, Git 제외). 설명은 `data/reviews/README.md`.
- 읽어서 DB(`evidence.*`)와 추천에 반영하는 코드는 아직 없다. 제품 연결 키는 `manufacturer` + `model`이다.
- 프론트는 `review.total_count`·`rating_refined`·`signals`가 오면 그대로 보여 준다. 값이 없으면 "리뷰 관측이 아직 없어요"로 나온다.

## 6. 응답 속도

프론트 확인 중 아래가 눈에 띄게 느렸다(개발 PC, 로컬 DB 기준).

| API | 체감 |
|---|---|
| `POST /session/{id}/items/{item_id}/swap` | 수 초 (교체 후 호환 재검증) |
| `PATCH /session/{id}/items/{item_id}` (수량·구매 시점) | 수 초 |
| `GET /lists/{id}/report` | 건당 수 초 |
| `POST /session/{id}/recommend` → `GET .../result` | 약 15~20초 (설명 문장 생성 대기 포함) |

특히 **저장한 견적 목록**이 문제다. `GET /lists`에는 합계 금액·구매 예정일·부품 수가 없어서 프론트가 확정된 목록마다 `GET /lists/{id}/report`를 따로 불러야 한다(N+1). 목록 개수만큼 느려진다.
요청: `GET /lists` 응답에 `total`, `planned_purchase_at`, `item_count`(확정된 것만이라도)를 넣어 주면 프론트는 목록에서 리포트를 미리 읽지 않아도 된다.

## 7. 에러 응답 (확정)

- 예산을 넘는 구성을 확정하면 `422` + `"선택한 구성이 예산을 초과합니다."`가 온다. 프론트는 확정 전에 미리 안내하고 버튼을 막지만, **`error.code`가 없어서**(메시지 문자열로만 구분해야 함) 다른 검증 오류와 구분하기 어렵다. `code`(예: `over_budget`)를 넣어 달라.
- 그 외 확정 시 조건이 바뀐 추천 거절(`stale_recommendation`) 등은 기존 코드 그대로 쓴다.

## 8. 주변기기 추천 API (프론트 4번 작업의 선행 확인)

주변기기(모니터·키보드·마우스·스피커) 조건 대화와 추천 화면을 React로 옮길 예정이다. 서버에 카탈로그와 규칙(`config/peripherals.yaml`, `src/engine/peripheral_*`)은 있으나, **세션 API로 주변기기를 추천받는 경로가 열려 있는지** 확인이 필요하다.
- `POST /session/{id}/category`에서 주변기기 카테고리를 받는가? (코드 주석상 일반 카테고리 목록에서는 빠져 있음)
- 열려 있지 않다면 노출 방식(엔드포인트·요청·응답 형식)을 정해 달라.
- 리뷰 관측은 5번이 끝나야 채워진다.

## 9. 그 밖의 참고

- **"교체 뒤 재검증 없음"이라는 옛 문서 내용은 사실과 다르다.** 코드상 `swap_item`이 `reverify_set`을 호출한다. 남아 있는 문서가 있으면 고쳐 달라.
- 추천 결과에서 RAM이 항상 1개(16GB)로 온다. 듀얼 채널용 2개 구성을 의도한다면 추천 엔진이 `qty=2`를 주도록 판단이 필요하다. 프론트는 서버가 준 수량을 그대로 표시한다.
- 테스트 계정(`test@test.com`)으로 프론트에서 확정·삭제를 시험한다. 개발 DB에 확정 목록이 몇 건 남아 있다.
