## 4. 리뷰 데이터 적재

- 담당: 회종님이 개발 중이다. 주변기기 추천 API(`POST /session/{id}/peripherals/recommend`)는 열려 있고, **주변기기 리뷰는 이 4번이 끝나야 채워진다.**
- 원본: `data/reviews/*.jsonl` 5개(팀 내 파일 공유, Git 제외). 설명은 `data/reviews/README.md`. 제품 연결 키는 `manufacturer` + `model`.
- 추천 결과 8개 부품 모두 지금은 `review: null`이다(리뷰 요약 시드가 51개 부품뿐). 부품 교체 후보의 리뷰도 마찬가지다.

## 5. 응답 속도

사용자가 화면에서 누르는 **세 가지 동작**이 기다리게 만든다.
- **부품 교체**: 결과 화면에서 부품 카드를 열어 다른 제품을 골랐을 때(`swap`).
- **수량 변경·부품 빼기**: 부품의 수량을 바꾸거나 부품을 뺐을 때(`PATCH`). 화면에서 "구매 시점" 선택은 없앴다(서버의 `timing` 값은 그대로 두면 된다).
- **추천 받기**: 조건을 다 정하고 "추천 받기"를 눌렀을 때(`recommend` → `result`).

프론트에서 HTTP로 잰 값이다(2026-09-30, 개발 PC·로컬 DB, 브라우저 → vite 프록시 → API, 테스트 계정의 8개 부품 견적).

| API | 이전 체감 | 지금 |
|---|---|---|
| `POST /session/{id}/items/{item_id}/swap` | 수 초 | 약 0.9~1.6초 |
| `PATCH /session/{id}/items/{item_id}` (수량 변경·부품 빼기) | 수 초 | 약 1.0~1.2초 (처음 한 번은 2.2초) |
| `POST /session/{id}/recommend` 접수 | — | 약 0.02초 (즉시 202) |
| 〃 → `GET .../result`에서 **부품·가격이 나올 때까지** | 약 15~20초로 알고 있었음 | 약 0.8~1.4초 (2회 측정) |
| 〃 → **설명 문장**(`explanation`)이 `pending`에서 `ready`가 될 때까지 | 〃 | 약 14~18초 (14.4초·18.3초) |

- 백엔드가 `swap_item`/`patch_item`을 직접 호출해서 잰 값은 50~70ms였는데, HTTP로는 그보다 15배쯤 걸린다. 함수 밖 — 응답을 만드는 부분(결과 재조회·직렬화·가격 감시 등), 커넥션·미들웨어 — 에서 시간이 쓰이는 것으로 보인다. 함수 안쪽이 아니라 **요청 전체 구간**을 재서 나눠 봐 달라.
- **추천 받기가 느린 것은 서버가 부품을 못 찾아서가 아니다.** 부품·가격은 약 1초 안에 `status: done`으로 나온다. 느린 것은 그 뒤 **설명 문장을 만드는 AI 호출** 하나(14~18초)다. 서버는 이미 "부품 먼저, 문장은 `pending`으로 나중에" 구조다.
- 지금 프론트(`plans.ts`의 `waitForResult`)는 그 문장이 `ready`가 될 때까지 최대 20초 기다렸다가 결과 화면을 보여 준다. 즉 사용자가 느끼는 15~20초는 **프론트가 문장을 기다리는 설계** 때문이기도 하다. 이건 **프론트에서 고친다**(부품이 나오면 바로 결과 화면을 보여 주고 설명 문장은 나중에 채우기). 백엔드는 따로 바꿀 필요가 없다.
- 백엔드에 바라는 것(선택): 설명 문장 생성이 14~18초 걸리는 이유(모델 크기, 프롬프트 길이, 여러 번 호출 여부)를 확인해 줄일 수 있으면 줄여 달라. 프론트가 문장을 나중에 채우게 해도, 문장이 빨리 오면 더 낫다.

## 7. RAM: DDR5 16GB 듀얼채널 SKU가 카탈로그에 없음

**무슨 문제인가:** 게임용으로 PC를 맞추면 램이 **16GB짜리 한 개**(단일 모듈)로 추천된다. 램은 같은 16GB라도 8GB 두 개를 꽂는 **듀얼채널**이 더 빠르다. 추천 엔진은 듀얼채널을 우대하도록 이미 고쳤다(`stage3b_rank.py`, `ram_dual_channel_bonus`). 그런데 게임용은 기본 규격이 DDR5인데, 카탈로그의 DDR5 16GB 제품은 **전부 한 개짜리**이고 8GB×2 키트가 **아예 없어서** 우대할 후보가 없다.

- DDR4 데이터가 없는 것이 **아니다**. DDR4를 허용하는 용도(사무·학습 등)에서는 듀얼채널 키트가 이미 선택된다.
- 부족한 것은 **DDR5 16GB(8GB×2) 키트 제품 1종 이상**이다. 다른 용량(32GB 등)의 DDR5 듀얼 키트는 있어도, 16GB 예산대에서는 비싼 32GB가 선택될 위험이 있어 우대 대상에서 뺐다.

요청: 카탈로그(`data/parts_list_modify.xlsx` → `seed_pc_parts_specs.py`)에 DDR5 16GB(8GB×2) 키트를 추가할지 결정해 달라. 추가하지 않기로 하면 이 항목은 닫아도 된다(프론트는 서버가 준 수량·구성을 그대로 표시한다).

## 12. 주변기기 추천: 예산 초과 여부가 응답에 없음

**무슨 문제인가:** `POST /session/{id}/peripherals/recommend`에 `budget_max`를 줘도, 그 예산 안에 드는 조합이 없으면 엔진이 **가장 싼 조합을 조용히 돌려준다**. 실측(2026-10-02): `kinds` 4종 전부, `budget_max=300000`, `resolution=QHD_165` → 합계 376,120원. 엔진 안(`run_peripherals(...).budget`)에는 `{'max': 300000, 'total': 376120, 'over_budget': True}`가 있는데, `peripheral_payload`가 이 값을 응답에 싣지 않는다(`peripheral_payload.py` 머리말 "budget을 최상위에 안 넣는 이유"). 그래서 프론트는 "예산 안에서 고른 것"인지 "예산을 넘겼지만 가장 싼 조합"인지 서버 응답만으로 알 수 없다.

요청: 응답의 `totals`에 아래 필드를 추가해 달라(`PeripheralTotalsOut`, `src/schemas.py`).
- `budget_max: int | null` — 요청한 예산(없으면 null)
- `over_budget: bool` — 예산 안에 드는 조합이 없어 가장 싼 조합을 돌려줬는지

프론트는 값이 오면 "예산 30만 원을 넘어요(합계 376,120원)" 안내를 서버 값으로 띄운다. 그 전까지는 프론트가 예산과 `reference_price`를 직접 비교해 임시로 같은 안내를 한다(`PeripheralsPage.tsx`).
