# 개발 요청 — 백엔드 및 타 팀 (프론트 작업에서 나온 항목)

작성: 프론트(front 브랜치) · 2026-09-29 · 정리: 2026-09-30
프론트는 `web/`(React)에서 화면을 백엔드 API에 연결하는 중이다. 아래는 **아직 남아 있는 요청**만 적는다.
완료된 항목(리포트 히스토리 API, `GET /lists` 목록 필드, `over_budget` 에러 코드, 좌측 패널의 대화 내역·견적서 N개)은 지웠다.

## 1. 리포트의 "조립 가이드" 제거 (백엔드 삭제 요청) — 우선순위 높음

> **처리됨(2026-09-30, `fix/confirm-qty-timing`)**: 아래 표의 네 곳을 지웠다. `care_guides.py`·`data/pc_care_guides.json`은 "구매 전 확인"이 계속 쓰므로 남겼다(설치 문서 `kind=install`은 이제 읽는 곳이 없다). 리포트 응답이 건당 약 3초 → 수 ms로 줄었다 — 5번 참고.

팀 결정으로 조립 가이드는 하지 않기로 했다. 프론트는 화면과 관련 코드를 모두 지웠다(`careGuide`, `guideStepsFromWire`, `GuideStep` 타입, 프로토타입 화면의 조립 가이드 구역).

백엔드에서 지울 것:

| 위치 | 내용 |
|---|---|
| `src/schemas.py` `ReportOut.care_guide` | 리포트 응답 필드 삭제 |
| `src/services/list_service.py` (`build_guide`, `care_guide` 조립부, 응답 dict) | 확정 시 조립 가이드를 만드는 코드 삭제 |
| `src/agent/assembly_guide_agent.py` | 조립 가이드 에이전트 삭제 |
| 관련 테스트 | 위 코드를 검사하는 테스트 삭제·수정 |

주의:
- **"구매 전 확인"(부품 카드의 `checks`)은 조립 가이드가 아니다.** `src/rag/care_guides.py`·`data/pc_care_guides.json`은 그쪽에서도 쓰므로, 조립 가이드만 지우고 구매 전 확인 기능이 남는지 확인해 달라. (구매 전 확인도 없애는 결정이라면 알려 달라.)
- `ReportOut.data_notice`("상품·가격·리뷰는 합성 데이터입니다.")는 그대로 둬도 된다. 프론트는 아직 쓰지 않는다.

## 2. 대안 목록(`GET /session/{id}/items/{item_id}/alternatives`) 품질

> **처리됨(2026-09-30, `pc-catalog-engine`)**: 성능 등급이 가까운 후보 3개로 추리고(등급 없는 슬롯은 기존대로 전체), 표기만 다른 중복 제품은 더 싼 쪽만 남기고, 현재 고른 제품을 `current: true`로 목록 맨 앞에 포함한다. 리뷰(`review: null`)는 4번 범위라 그대로 뒀다.

부품 교체 화면이 이 API를 쓴다. 지금은 그 자리의 **전체 카탈로그**를 돌려줘서 쓰기 어렵다(GPU 기준 40개 이상).

- 워크스테이션·전문가용 제품(RTX 6000 Ada, Radeon PRO W7900 등)과 수백~수천만 원대 제품까지 섞여 나온다.
- 같은 제품이 이름만 다르게 중복된다. 예: `GeForce RTX 3050 (6GB)` / `GeForce RTX 3050 6GB`, `RTX 3060 (12GB)` / `RTX 3060 12GB`, `RX 6800 XT` / `RX 6800 16GB`.
- **현재 고른 제품이 목록에 없다**(`current: true` 항목이 오지 않는다). 프론트는 `current`가 있으면 "지금 고른 제품"으로 표시하도록 만들어 뒀다.
- 리뷰 관측이 전부 없다(`review: null`).

요청: 성능 등급이 비슷한 후보 위주로 거르기(예: 원래 화면 설계는 "비슷한 성능 3개"), 중복 제거, 현재 제품 포함. 프론트는 임시로 "현재 제품과 가격이 가까운 순 6개 + 더 보기"로 보여 준다.

## 3. `spec_summary` 채우기

결과 화면 "주요 스펙" 칸이 `GPU · AMD`처럼 브랜드만 나오거나 비어 있다.

- 원인: 부품별 스펙 테이블(`catalog.cpu_spec`·`gpu_spec`·`ram_spec` 등)에는 값이 이미 있다(예: `gpu_spec.vram_gb`·`pcie_interface`·`power_w`). 그런데 `spec_summary`는 DB 컬럼이 아니라 `src/services/recommendation_service.py`(추천 결과·대안 응답 조립부)가 만드는 문자열이고, 지금은 `성능 티어 N` 한 가지만 만든다.
- 요청: `db/seed_pc_parts_specs.py`가 아니라 **`recommendation_service.py`에서 슬롯별로 스펙 테이블을 읽어 문자열을 만들도록** 보강. 예: GPU는 VRAM·인터페이스, CPU는 코어·소켓, RAM은 규격·용량.
- 부수: `spec_summary`에 "성능 티어"가 들어 있는 것을 `result_agent.py`가 파싱해 쓴다(100~102행). 문자열 형식을 바꾸면 그 파싱이 깨지지 않게 티어를 별도 필드로 빼거나 형식을 유지해 달라.

- 본체(PC 부품) 리뷰: 회종님 개발 중. 주변기기(모니터·키보드·마우스·스피커) 리뷰: 프론트 담당(Charlie)이 곧 개발 예정.
- 원본: `data/reviews/*.jsonl` 5개(팀 내 파일 공유, Git 제외). 설명은 `data/reviews/README.md`. 제품 연결 키는 `manufacturer` + `model`.
- 추천 결과 8개 부품 모두 지금은 `review: null`이다(리뷰 요약 시드가 51개 부품뿐).
- 프론트는 `review.total_count`·`rating_refined`·`signals`가 오면 그대로 보여 준다. 값이 없으면 "리뷰 관측이 아직 없어요"로 나온다.

## 5. 응답 속도 (측정 필요)

프론트 확인 중 아래가 눈에 띄게 느렸다(개발 PC, 로컬 DB 기준). **원인은 아직 측정하지 않았다** — 아래 원인은 코드를 읽고 짐작한 것이다.

| API | 체감 | 짐작하는 원인 |
|---|---|---|
| `POST /session/{id}/items/{item_id}/swap` | 수 초 | 교체 뒤 구성 전체 재검증(`reverify_set`) |
| `PATCH /session/{id}/items/{item_id}` (수량·구매 시점) | 수 초 | 위와 같은 재검증으로 추정 |
| `GET /lists/{id}/report` | 건당 수 초 | **측정·해결(2026-09-30)**: 조립 가이드 폴백이 부품마다 RAG 검색(임베딩 호출) 2번 ≈ 2.9초, 그동안 DB 연결(풀 최대 10)을 붙잡아 저장 목록이 많으면 채팅 API까지 대기(동시 12개일 때 4ms → 2.7초). 1번 삭제로 3.1초 → 1ms |
| `POST /session/{id}/recommend` → `GET .../result` | 약 15~20초 | 설명 문장 생성 대기 |

요청: 위 API의 구간별 시간을 먼저 재고, 재검증 범위를 바뀐 부품 관련으로 줄이거나 설명 문장을 나중에 채우는 방식(먼저 구성을 보여 주고 문장은 `pending`)을 검토해 달라. (저장한 견적 목록의 N+1 문제는 `GET /lists`에 값이 들어가 해결됐다.)

## 6. 주변기기 추천 API (프론트 담당: Charlie)

주변기기(모니터·키보드·마우스·스피커) 조건 대화와 추천 화면은 프론트에서 직접 옮긴다. 서버에 카탈로그와 규칙(`config/peripherals.yaml`, `src/engine/peripheral_*`)은 있으나, **세션 API로 주변기기를 추천받는 경로가 열려 있는지** 확인이 필요하다.
- `POST /session/{id}/category`에서 주변기기 카테고리를 받는가? (코드 주석상 일반 카테고리 목록에서는 빠져 있음)
- 열려 있지 않다면 노출 방식(엔드포인트·요청·응답 형식)을 정해 달라.
- 리뷰 관측은 4번이 끝나야 채워진다.

## 7. 그 밖의 참고

- 추천 결과에서 RAM이 항상 1개(16GB)로 온다. 듀얼 채널용 2개 구성을 의도한다면 추천 엔진이 `qty=2`를 주도록 판단이 필요하다. 의도가 아니면 이 항목은 닫아도 된다(프론트는 서버가 준 수량을 그대로 표시한다).

## 8. "견적 수정하기": 확정본의 부품 구성을 새 견적서로 복사 (우선순위 높음)

> **처리됨(2026-09-30, `pc-catalog-engine`)**: `PlanRepo.clone_revision`이 요구사항 노드·`recommendation_run`·후보(선택·수량·시점·교체된 variant·가격 기준)·검증 결과를 새 draft로 복사한다. 가격은 확정 당시 값을 그대로 유지한다(재추천·재검증 전까지 갱신 안 함). `SHOW_REVISE`를 켜도 된다.

리포트 화면에 **견적 수정하기** 버튼을 두려고 한다. 누르면 그 견적서를 **저장하기 전 상태로 되돌려**, 추천 결과 화면(2번 단계)에서 이전 채팅 내역과 함께 부품을 바꾸고 다시 확정하는 흐름이다. 다시 확정하면 새 견적서(다음 번호)로 저장된다. 조건으로 추천을 새로 받는 것이 아니다 — 견적서에 있던 제품 리스트가 **그대로** 보여야 한다.

지금 서버로는 안 된다.
- `POST /lists/{id}/revisions`(`list_service.new_revision` → `plan_repo.clone_revision`)가 **조건만 복사**하고 부품 구성은 복사하지 않는다(`clone_revision` 주석: "부품 노드·요구사양은 추천할 때 revision 마다 새로 만들어지므로 복사하지 않는다").
- 그래서 새 견적서에는 `engine.recommendation_run`도 후보도 없고, 프론트는 추천을 다시 받는 수밖에 없다. 그러면 결과가 달라질 수 있고, 사용자가 직접 교체·수량·구매 시점을 바꿔 둔 것도 사라진다.
- 확정된 견적서는 읽기 전용 스냅샷이라, 프론트가 화면에만 부품을 그려도 교체·수량 변경·재확정 요청이 실패한다.

요청: `new_revision`이 확정본의 **추천 결과까지 복사**해 새 초안(draft)이 그 결과를 바로 가지게 해 달라.
- 복사 대상: 실행 결과(`recommendation_run`)와 후보(선택 여부, 수량, 구매 시점, 교체된 variant, 가격 기준 `offer_observation`), 요구사항 노드, 검증 결과, 설명 문장.
- 복사한 뒤에는 `GET /session/{id}/result`가 새 초안 기준으로 그 구성을 돌려주고, 교체·수량·확정이 기존처럼 동작해야 한다.
- 가격이 그사이 바뀌었으면 어떻게 할지 정해 달라(확정 당시 가격 유지 vs 현재 가격 갱신). 프론트는 서버가 준 값을 그대로 보여 준다.
- 이 요청이 반영되기 전까지 프론트는 버튼을 숨겨 둔다(`ReportPage.tsx`의 `SHOW_REVISE`). 반영되면 그 값만 켜고 `reviseSetup`이 추천 재실행 대신 저장된 구성을 열도록 바꾼다.

## 9. 대화 목록의 `conditions_summary`가 너무 길다

`GET /lists`의 `conditions_summary`(`recommendation_service._conditions_summary`)가 대화 제목 아래 한 줄에 쓰인다. 새 PC 대화는 `새 컴퓨터 · 게임 · 1,500,000원 · 성능 우선`처럼 괜찮지만, **업그레이드 대화**는 `CPU: AMD Ryzen 7 7800X3D · GPU: RTX 4070 SUPER · RAM: DDR5 32GB · 메인보드: B650M WiFi · 저장장치: Samsung 990 PRO 1TB · GPU · RAM · 모름 · 게임 · 1,000,000원 · 저소음`처럼 부품명이 줄줄이 붙어 매우 길다.

요청: 목록용 요약은 **핵심 값 3~4개**(모드, 용도, 예산, 우선순위)만 주도록 줄이거나, 짧은 필드(예: `conditions_brief`)를 따로 추가해 달라. 프론트는 지금 두 줄까지만 보여 주고 나머지는 자른다.

## 10. 견적서(revision) 하나만 삭제·이름 바꾸기

좌측 패널에서 대화(목록)는 이름 바꾸기(`PATCH /lists/{id}`)와 삭제(`DELETE /lists/{id}`)를 이미 쓴다. 하지만 **한 대화 안의 견적서 하나**만 지우거나 이름을 바꾸는 API는 없다.
- `DELETE /lists/{id}`는 대화와 그 안의 견적서 전체를 지운다(soft delete). 견적서 하나만 지우려면 예: `DELETE /lists/{id}/reports/{revision_no}`가 필요하다. 마지막 남은 견적서를 지울 때의 동작(대화는 유지, 상태는 초안으로 되돌림 등)도 정해 달라.
- 견적서 이름은 확정 때 정한 `name_snapshot`이라 `PATCH /lists/{id}`(대화 이름)로는 바뀌지 않는다. 예: `PATCH /lists/{id}/reports/{revision_no}`로 `name`을 받아 달라.
- 프론트는 이 둘이 생기면 패널의 견적서 항목에 ⋯ 메뉴(이름 바꾸기·삭제)를 붙인다.
