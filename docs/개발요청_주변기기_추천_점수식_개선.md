- 작성: 2026-10-06 · 상태: **제안 — 검토 요청** (코드 변경 없음, 담당자 확인 후 구현 시작)
- 관련 문서: [주변기기_추천알고리즘_기획.md](local/주변기기_추천알고리즘_기획.md) — 3.1(점수식), 3.3(조건 스펙 가중), 3.8(근거 부족 감점), 9장(검증)

## 1. 한 줄 요약

기획서의 점수식을 구현하고, 시뮬레이션에서 효과가 확인된 두 규칙(조건 스펙 가중 ×2, 근거 부족 감점)을 같이 넣는다. 결과 화면에는 "왜 이 상품인가", "근거가 약한가", "비슷한 점수의 대안"을 보여준다.

## 3. 요청 내용

### 3.1 순서 제안

| 단계 | 내용 | 다른 담당과 겹치는가 |
|---|---|---|
| **A. 요청 계약 확장** | 품목별 예산·가격대, 스펙 조건(직접/유도 구분), 강조점, 브랜드 선호·기피를 받는다 | API 계약, 조건 해석 담당 |
| **B. 점수식 교체** | 축·가중치·가격 값 교체, 데이터충실 축 제거, **조건 스펙 가중 ×2**, **근거 부족 감점** | 엔진 담당 |
| **C. 결과 계약·화면** | 축별 값·가중치·감점·리뷰 건수·대안(최대 2개)·접전 표시 (3.4절) | API 계약, 프론트 |
| D. 후속(이번 범위 밖) | 성향 차원(키압 등), 무상 AS 데이터, B 번들 | 리뷰 데이터·카탈로그 담당 |

A 없이 B만 하면 시뮬레이션과 같은 입력이 없어서 가격 값과 조건 스펙 가중을 계산할 수 없다. **A와 B는 같이 가야 한다.**

### 3.3 점수식과 두 규칙 (요약)

자세한 식은 기획서를 따른다. 구현에서 지켜야 할 핵심만 적는다.

```text
점수 S = Σ(축 가중치 × 축 값) − Pending 감점 − 스펙 결손 감점 − 근거 부족 감점
```

- **가중치 순서:** ① 품목별 기본 가중치 → ② 강조한 축 ×1.5 → ③ **직접 말한 조건이 있는 스펙 기준 ×2** → ④ 합 1로 정규화. 스펙을 강조하면서 그 조건도 말했다면 ×3이 된다(기획 3.3).
- **근거 부족 감점:** `0.10 × max(0, 1 − n/5)`. n = 점수에 쓰는 등록 속성의 긍정 + 부정 관측 수의 합(혼합 제외). 상품을 후보에서 빼지 않는다(기획 3.8).
- 하드 조건·예산 필터는 항상 먼저 적용되고, 가중은 소프트 조건에만 영향을 준다.
- AI는 조건과 강조 태그만 고른다. 가중치 숫자와 점수는 코드가 정한다(기획 P1).

### 3.4 화면에 필요한 응답 필드 (화면 기획 반영, 2026-10-06)

주변기기 결과 화면(결과 먼저 + 접전 비교 + 근거 표시)이 쓰는 값이다. 지금 `PeripheralsOut` 응답과 비교했다. **서버에 없는 값은 화면에서 숨기고, 0이나 추정값으로 채우지 않는다.**

| 화면 요소 | 필요한 값 | 지금 응답 |
|---|---|---|
| 리뷰 근거 배지 ("근거 N건") | 후보별 리뷰 근거 건수 = 관측 수(`p + n` 합) | `review.contributions`로 계산 가능. 정식 필드(`evidence_count`)로 받는 것을 권한다 |
| 근거 부족 안내 | 근거 부족 감점이 붙었는지(`evidence_penalty`) | 없음 |
| 접전 배너 | 서버가 판단한 접전 여부(`close_call: bool`). **한 응답에서 최대 2개 품목에만 true** | 없음 |
| 대안 | 접전일 때 대안 **최대 2개**, 대안마다 이름·가격·근거 건수·주요 스펙 | 이름·가격·차액만 있음 |
| 주요 스펙 칩 | 상품별 주요 스펙 요약 목록(`spec_summary: string[]`, 3~5개) | 없음 (`requirement`는 요구사양이다) |
| "어떻게 골랐나요?" | 축별 비중(`weights`)과 적용 이유 한 줄(`weights_reason`) | 없음 |
| "이렇게 이해했어요" 칩 | 서버가 해석한 조건 목록(`understood_conditions: string[]`) | 없음 (지금은 화면의 정규식) |
| 예산 초과 경고 | 예산 초과 여부와 초과 금액 | 없음 (개발요청 12번: 지금은 프론트가 직접 비교) |
| 대안이 2위인 이유 | 대안마다 `why_not_first` 한 줄(예: "더 저렴하지만 근거가 5건뿐이라 점수를 조금 낮췄어요") | 없음 |
| 리뷰 근거 인용 | `evidence_quote`: 속성 표현("쫀득하다"), 언급 건수 m, 전체 근거 건수 n, 대표 문장 1개. 사용자가 느낌 조건을 말했을 때만 | 없음 |
| 이유 문장 작성 상태 | `reason.status` (`pending`/`ready`/`failed`) | 있음. 결과 먼저 보이고 이유는 나중에 채우는 화면이 이 상태를 쓴다 |
| 대화 패널의 조건 해석 | CHAT-05(주변기기 대화) 연동 | 지금은 화면 정규식과 고정 응답. 임시로 정규식을 유지한다 |

화면 기획에서 정한 사항:
- **접전 판단은 서버가 한다.** 점수 차 기준은 서버가 정하고 `close_call`로 내려준다. 화면은 임계값을 알지 못한다. (참고: 시뮬레이션에서 점수 차 0.02 미만이 전체의 약 56%라, 기준이 넓으면 배너가 너무 흔해진다.)
- **대안은 접전일 때 최대 2개**만 보여준다. 접전이 아니면 대안은 화면에 나오지 않는다.
- **리뷰 근거 건수는 관측 수**이고, 화면에는 "근거 N건"으로 표시한다(리뷰 문서 수가 아니다).
- **결과 먼저, 이유는 나중에:** 후보 선정(1위·대안·점수)은 바로 응답하고, 이유 문장은 `reason.status`로 뒤에 채운다. 화면은 이유가 `pending`인 동안 스켈레톤을 보이고, `failed`면 이유 줄만 숨긴다. (25초 지연에 대한 멘토 피드백 대응)
- **대화 패널은 유지한다.** 한 문장 입력과 결과 뒤 보정(더 조용하게 등)은 대화 패널에서 한다. 서버 연동(CHAT-05)이 되기 전에는 화면 정규식으로 처리한다.
- **리뷰 근거 인용의 대표 문장은 해커톤 구성에서 생성 리뷰(B 번들)에서 나와야 한다**(기획 7.4 제출 전 점검).
- **후보 풀 전체에 리뷰가 없는 품목**(해커톤 구성의 스피커)은 `weights`에서 리뷰 항목을 빼고 내려준다. 화면은 값이 없는 막대를 숨기고, 리뷰 비중을 지어내지 않는다.
- **예산을 말하지 않은 요청**은 예산 관련 필드(예산, 남은 금액, 초과 여부)를 생략한다. 화면은 해당 줄을 숨긴다.
- **접전 배너는 한 화면에 최대 2개로 정했다.** 서버는 접전인 품목이 3개 이상이어도 점수 차가 작은 순으로 최대 2개 품목에만 `close_call=true`를 준다. 화면은 `close_call=true`인 품목에만 배너를 그린다(임계값과 순서를 화면이 알 필요가 없다). 실제 접전 비율이 요청의 약 32%라 평균 1~2개이고, 3개 이상이면 소란스럽다.
- 화면 명세와 목업은 `docs/local/주변기기_화면기획.md`, `주변기기_화면_목업.html`에 있다(로컬 문서).

## 4. 수용 기준 (검증)

**단위 테스트**
- 가중치 합 1, 조건 없는 기준은 ×2가 안 붙는다, 스펙 강조와 겹치면 ×3, 유도한 조건만 있는 기준에는 곱하지 않는다
- 근거 부족 감점: 0건 0.10 / 1건 0.08 / 5건 이상 0, 후보 풀이 바뀌어도 같은 값, 다른 감점과 합산, 리뷰 없는 상품이 후보에서 빠지지 않는다
- 리뷰 가중치 0이 아니어도 로더가 통과한다. 예산과 하드 조건을 어긴 후보는 리뷰를 올려도 뽑히지 않는다
- 해커톤 구성(스피커 리뷰 0종)에서 스피커의 모든 후보에 같은 감점이 붙어 순위가 안 바뀐다
- 기존 계약 테스트(`test_peripheral_payload.py`, `test_peripherals_recommend_http.py`, `test_peripheral_rules.py`, `test_peripherals_engine.py`, `test_peripheral_review_scoring.py`)를 새 축 구조에 맞게 고친다

**시뮬레이션 대조 (구현이 기획서와 같은지)**
`scripts/peripheral_sensitivity.py`는 기획서 식을 따로 구현한 기준 구현이다. 구현이 끝나면 같은 요청 1,000개(품목당 250개, 시드 고정)를 엔진에 넣어서 **1위가 기준 구현과 일치하는지**를 본다. 일치하지 않는 요청은 원인(스펙 판정 규칙의 차이 등)을 확인한다. 이 스크립트는 지금 저장소에 올라가 있지 않다 — **올릴지 말지**를 정해 주셔야 한다(5장).

## 5. 시뮬레이션 근거 (요약)

| 확인한 것 | 결과 |
|---|---|
| 가중치가 잠정값이어도 결과가 안정적인가 | 가중치를 ±20% 흔들어도 1위가 평균 92%, ±50%에서 80% 유지 |
| 리뷰를 켜면 순위가 달라지는가 | 요청의 약 50%에서 1위가 바뀐다 |
| 접전의 원인 | 요청의 32%가 1·2위 점수 차 0.01 미만이고, 그중 92%가 리뷰 ↔ 가격 상쇄 → 1위만 내지 말고 대안을 함께 보여준다 |
| 리뷰 없는 상품을 일괄 제외하면 | 모니터·스피커에서 추천 불가 요청이 20% 넘게 생긴다 → 제외하지 않고 감점 |
| 1위 쏠림 (스피커 46%, 모니터 49%) | 조건 스펙 가중 ×2 + 근거 부족 감점을 함께 쓰면 스피커 21%, 마우스 28%로 줄고, 리뷰 근거 3건 미만 1위가 모니터 30% → 4%, 마우스 13% → 1% |
| 부작용 | 1위가 더 비싼 쪽으로 이동한다(1위의 가격 위치: 모니터 0.35 → 0.53, 스피커 0.24 → 0.40). 리뷰를 켰을 때 1위가 바뀌는 요청이 50% → 40% |
| 모니터 | ×2는 쏠림 감소가 작고(49% → 44%) 접전이 늘어난다. 감점만이 접전이 가장 낮다 → **모니터에 ×2를 쓸지는 별도 결정** |

한계: 요청 1,000개는 자동 생성한 가정이고, 실제 사용자 요청 분포가 아니다. 실제 리뷰(A 묶음) 기준이며 해커톤 구성(B만)은 측정하지 못했다. 성향 차원·브랜드·무상 AS는 측정에 넣지 못했다.

| 엔진 담당 | 이 순서(A·B·C)로 갈지, 요청 계약 확장(A)을 먼저 따로 할지. 현재 `budget_max`(합계) 입력을 품목별 예산과 어떻게 같이 둘지 |
| 조건 해석(LLM) 담당 | 문장 → 품목별 예산·스펙 조건·강조 태그 변환(기획 2.2). 직접 말한 조건과 용도에서 유도한 조건을 구분해서 넘겨 줄 수 있는지 |
| API 계약 / 프론트 | 3.2절의 응답 필드 추가. 접전일 때 대안을 보여주는 방식 |
| 팀 전체 | **`scripts/peripheral_sensitivity.py` 등 시뮬레이션 스크립트를 저장소에 올릴지**. 올리면 위 대조 검증을 팀이 재현할 수 있다 |
| 모니터 | 조건 스펙 가중 ×2를 모니터에도 쓸지 (쏠림 vs 접전) |

## 7. 범위 밖

- **성향 차원**(키압·색감·사운드 밸런스): 리뷰 재분석이 필요하고 리뷰 데이터 담당 범위다. 기획 4장은 유지하고 후속으로 둔다
- **무상 AS 데이터 수집**: 카탈로그 컬럼 추가가 필요하다. 코드는 미리 넣어 둘 수 있고, 데이터가 없는 동안 모든 후보가 0.5라 순위에 영향이 없다
- **해커톤용 B 번들(생성 리뷰) 구축**: 기획 7장, 별도 작업
- **PC 본체 추천 알고리즘**: 건드리지 않는다
