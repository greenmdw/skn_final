# 계정·저장(5.8절) 완성 기획

2026-09-27. 코드 조사만 하고 구현은 하지 않았다. CHAT-08(채팅 내역 저장)은 설계가 명확해 바로 구현 가능하고,
ACC-02(목표가 알림)는 **과거 팀 결정과 최신 기획서가 서로 다른 말을 하고 있어** 착수 전 확인이 필요하다.

## CHAT-08 — 채팅 내역 저장 · 복원

### 지금 상태 (조사 결과)

- **조건 대화(S1~S2, 추천 전)는 이미 저장된다.** `session_service`의 `handle_message`·`handle_answer`가
  매 턴마다 `ConversationRepo.add_message(conversation_id, "user"/"assistant", ...)`를 부른다
  (`identity.message` 테이블). `GET /session/{id}`가 이 메시지를 이미 `messages` 필드로 돌려준다
  (`_state()` → `_messages_out(message_rows)`) — **복원 API는 이미 있다.**
- **결과 화면 대화(추천 후 "왜 이거야?", "바꿔줘")는 저장되지 않는다.** `result_agent._HISTORY`가
  프로세스 메모리 딕셔너리(`run_id` → 최근 8턴)일 뿐이고, `recommendation_service.handle_result_message`
  (에이전트 경로·규칙 경로 둘 다) 어디에도 `ConversationRepo` 호출이 없다(`grep` 결과 0건). 서버 재시작·
  다른 워커가 요청을 받으면 그 대화는 사라진다. 기획서 4.1.1의 7번째 단계("저장한 견적 다시 열기 → 이전
  채팅 내역 복원 + 이전 맥락으로 답변")가 이 부분이다.

### 설계 — 새 테이블·컬럼 없이 가능

같은 `identity.conversation`(계획 하나에 대화 하나)에 결과 화면 대화도 같이 쌓는다. 조건 대화와 결과 대화가
시간순으로 같은 `identity.message`에 쌓이므로, `GET /session/{id}`가 이미 하는 일(그 conversation의 메시지를
시간순으로 반환)이 그대로 복원 역할을 한다 — **새 엔드포인트가 필요 없다.**

1. **`recommendation_service.handle_result_message`에 저장 추가**(에이전트 경로·규칙 경로 둘 다):
   ```python
   conversation_id = PlanRepo(conn).get_revision(revision_id)["conversation_id"]  # 이미 조회에 포함됨
   ConversationRepo(conn).add_message(conversation_id, "user", text)
   ConversationRepo(conn).add_message(conversation_id, "assistant", reply)
   ```
   실패(교체 등 부분 실패) 시에도 사용자 발화와 최종 답변은 남겨야 한다 — `quote_chat_service.chat()`이
   이미 이 순서(도구 실행 → 저장은 항상 마지막에 한 번)로 짜여 있으니 그대로 따른다.

2. **에이전트가 "이전 맥락을 기억"하게 하려면 `_HISTORY`(프로세스 메모리)를 DB 조회로 바꾸거나 보강한다.**
   지금은 `_history_messages(run_id)`가 `_HISTORY` 딕셔너리만 본다 — 서버가 재시작되면 DB에는 있어도
   에이전트는 못 본다. `quote_chat_service._pairs()`(이번 세션에서 견적 점검 채팅에 이미 구현한 것과 같은
   패턴: `ConversationRepo.messages(conversation_id)`를 user/assistant 쌍으로 묶어 최근 N턴만 취함)를
   `result_agent`에도 적용한다. 프로세스 메모리 `_HISTORY`는 지워도 되고, 캐시로 남겨 DB 조회를 줄이는
   선택지도 있다(선택).

3. **조건 대화와 결과 대화를 화면에서 구분해야 한다면**(예: "조건을 물어보던 채팅"과 "결과 화면 채팅"을
   별 영역에 보여주고 싶다면) 두 가지 방법이 있다:
   - **구분 안 함(권장, 스키마 변경 없음)**: 시간순으로 이어 붙여 하나의 대화로 보여준다 — 실제로도
     사용자 입장에선 한 대화의 연장이다("조건 다 됐고 → 추천 나왔고 → 이거 왜 골랐어?").
   - **구분함**: `identity.message`에 컬럼을 추가해야 해서 마이그레이션 기준선(4파일 고정) 원칙과
     부딪힌다. 꼭 필요하면 팀 논의 후 진행.
   특별한 요청이 없으면 첫 번째(구분 안 함)로 진행할 계획이다.

4. **"이전 채팅 내역을 화면에 복원"**은 프론트가 이미 있는 `GET /session/{id}`의 `messages`를 그대로
   렌더링하면 된다 — 백엔드 작업만으로 충분하고 프론트 변경은 "저장 목록에서 다시 열 때 이 필드를 표시"
   정도로 작다.

### 견적 점검 되묻기 채팅과의 관계

이번 세션에서 만든 `quote_chat_service`(CHAT-04)가 정확히 이 패턴(같은 conversation에 `identity.message`로
저장, `GET /pc/reviews/{id}/messages`로 복원)을 이미 구현해 뒀다. `result_agent` 쪽에 그대로 옮기면 된다 —
새로 설계할 게 없고 옮겨 적용하는 작업에 가깝다.

### 예상 작업량

- `src/services/recommendation_service.py`의 `handle_result_message` 수정(저장 추가) — 작음
- `src/agent/result_agent.py`의 `_history_messages`를 DB 조회로 바꿈 — 작음
- 테스트: 재시작을 흉내 내려면(`_HISTORY` 딕셔너리를 비우고도 맥락을 기억하는지) 기존
  `tests/test_result_agent.py` 패턴에 몇 건 추가 — 중간

## ACC-02 — 목표가 알림

### 발견한 모순 (착수 전에 팀 확인이 필요한 이유)

- **2026-09-12 팀 확인 문서**(`docs/db/db_schema_reduction_proposal_2026-09-12.md` 116~120행)에
  `notification` 스키마(`price_watch`·`price_watch_evaluation`·`notification_event`) 자체를
  **"RDB에서 완전히 제거"**하기로 팀 확인 완료라고 적혀 있다. 회의록 인용까지 있다: "가격 알림 기능은
  이번 개발 범위에서 완전히 제외하기로 팀 확인 완료." (멘토: "저희는 후반이 없어요")
- **그런데 지금 스키마에는 `notification.price_watch` 테이블이 그대로 있고**, `POST /lists/{id}/alert`
  엔드포인트가 실제로 동작한다(`NotificationRepo.get_for_revision`·`upsert_active`·`pause`는 스텁이
  아니라 구현돼 있다). 이 셋 말고 나머지 7개 메서드(`create_watch`·`list_active_watches`·`add_evaluation`·
  `create_event`·`pending_events`·`mark_sent`·`mark_failed`)와 `notification_service.create_watch`/
  `get_watch_status`, 워커 둘(`price_poll_worker`·`notification_worker`)만 `NotImplementedError` 스텁이다.
  `price_poll_worker.py`의 주석은 "목표가 알림은 P0 v3에서 범위 밖으로 완전히 제거됐다"고 적어 뒀다 —
  **9/12 결정을 그대로 반영한 주석**이다.
- **2026-09-30 기획서(가장 최신)**는 ACC-02를 "목표가 알림 ✅"로 표시하며 존재하는 기능처럼 다룬다.
  실제로는 on/off 저장(토글)만 되고 판정·발송은 없다 — 표기가 실제보다 앞서 있다는 지적을 이전에 드린 바 있다.

정리하면 **"완전히 제거하기로 했다"는 과거 결정**과 **"이미 되어 있다고 전제하는 최신 기획"**이 부딪힌다.
어느 쪽을 따를지에 따라 할 일이 완전히 달라진다.

### 선택지

**A안 — 9/12 결정대로 기능을 걷어낸다**
- `POST /lists/{id}/alert`와 관련 스키마·프론트 UI(알림 on/off 토글)를 제거한다.
- 이미 저장된 `price_watch` 데이터가 있다면 삭제 여부를 정한다.
- 장점: 팀이 이미 논의하고 결정한 방향과 일치, 작업량 없음(오히려 제거라 코드가 줄어듦).
- 단점: 9/30 기획서를 다시 고쳐야 하고, 이미 만들어 둔 on/off 저장 기능(3개 메서드)을 버리게 된다.

**B안 — 9/30 기획서대로 완성한다**
남은 7개 저장소 메서드 + 서비스 2개 + 워커 2개를 구현한다. 순서:
1. `NotificationRepo`: `create_watch`(중복 방지 위해 `get_for_revision` 재사용해 기존 활성 watch가
   있으면 그걸 반환), `list_active_watches(due_before=...)`, `add_evaluation`, `create_event`
   (`dedupe_key` UNIQUE로 같은 판정에 대해 중복 이벤트 방지), `pending_events`, `mark_sent`, `mark_failed`.
   전부 이미 있는 `notification.*` 테이블(스키마 변경 없음)에 대한 CRUD라 위험이 낮다.
2. `notification_service.create_watch`/`get_watch_status`: 리포지토리를 감싸는 얇은 서비스. `set_alert`
   라우터가 이미 쓰는 패턴(`upsert_active`)과 합쳐도 되고, 이번에 새로 만드는 이력형 메서드로 옮겨도 된다
   — 지금 `POST /lists/{id}/alert`의 계약(`PriceWatchOut`)을 안 깨는 선에서 결정.
3. `price_poll_worker.run()`: **제휴 커머스 API 실연동이 필요하다** — 이게 가장 큰 미지수다. 지금
   카탈로그 가격은 `catalog.offer_observation`에 이미 있는 관측값을 쓰는 건지, 아니면 실시간 재조회가
   필요한 건지부터 정해야 한다. 실시간 조회 API가 없으면(현재 프로젝트에 그런 연동이 안 보인다) 이
   워커는 **"이미 있는 최신 offer_observation을 보고 판정만 한다"**로 범위를 줄이는 게 현실적이다 —
   가격을 새로 수집하는 게 아니라, 이미 수집된 값 중 최신 것과 목표가를 비교하는 정도.
4. `notification_worker.run()`: "데모는 SES 샌드박스 + 콘솔 로그"라고 주석에 이미 적혀 있다 — 실제
   이메일 발송(SES) 대신 **콘솔 로그로 경계를 좁히면** 외부 연동 없이 완성할 수 있다. 이 정도가
   해커톤 데모 범위에 맞다.
5. 배치 실행 방식: 이 프로젝트에 스케줄러(cron)가 안 보인다 — FastAPI 안에서 주기 실행할지, 별도
   프로세스로 돌릴지 결정 필요. 데모 규모면 API 시작 시 `asyncio` 백그라운드 루프로 충분해 보인다.

- 장점: 최신 기획서와 맞음, 이미 반쯤 만들어진(토글) 기능을 완성.
- 단점: 9/12 팀 결정을 뒤집는 것이므로 팀(특히 그 결정에 참여한 분들)에게 먼저 알려야 한다. 제휴
  커머스 API 실연동 여부에 따라 작업량이 크게 달라진다.

**C안 — 절충: 지금 있는 토글만 유지, 판정·발송은 "보류"로 명확히 표기**
- 코드는 그대로 두고(토글 3개 메서드만 동작), `NotImplementedError` 스텁은 그대로 둔다.
- 기획서 ACC-02 표기를 "🟡 설정만 저장, 판정·발송 보류"로 고쳐서 실제 상태와 맞춘다.
- 장점: 아무것도 안 바꿔도 됨, 표기만 정직하게.
- 단점: 기능이 안 끝난 채로 남음(원래 문제 그대로).

### 추천

**C안(표기만 정직하게 고치기)을 우선 제안**한다. 이유: 9/12 결정을 이 대화에서 제가 뒤집을 근거가
없고(멘토가 참여한 팀 논의였다), 9/30 기획서가 이 결정을 알고도 뒤집은 것인지 단순히 놓친 것인지도
모른다. **이 모순 자체를 팀(특히 리뷰·알림 담당)에게 먼저 보여드리고, B안으로 갈지 A안으로 갈지 정한
뒤에 실제 작업에 들어가는 게 순서**라고 판단한다.
